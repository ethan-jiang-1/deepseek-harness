**状态**：计划已就绪，**尚未执行**。快照时间 2026-10-19；环境 macOS、Node v22.23.1、pnpm 11.28.5。

**读者**：负责执行升级的另一个 Agent，或直接操作的人。动手前必须读完本文件与 [执行手册](./01-runbook.md)；验收按 [验收清单](./02-acceptance.md)；判断依据在 [证据附录](./03-evidence.md)。

## 这个目录是什么

一份"照着敲就能完成"的升级执行包，把 2026-10-19 的调研结论固化下来：升什么、什么顺序、每一步怎么验证、失败怎么退。它不是设计文档，执行时不需要再读仓库源码。

## 两条铁律（先记这两条，其它都可以慢慢看）

### 1. 升级只走"老方法"：npm 全局安装 + `dsh plugin`

DSH 是命令行全局安装的，**升级也只用命令行那一套**：

- 升级本体：`npm i -g @deepseek-ai/dsh@next`
- 升级插件：`dsh plugin --profile web add <包>@<版本>`

**不得**借助本仓库（`/Users/bowhead/deepseek-harness`）完成升级：

- 不跑 `pnpm dsh ...`（那是源码路径，不是安装路径）
- 不跑 `pnpm install` / `pnpm build` / `pnpm dev:web`
- 不用 `dsh plugin ... add link:<repo>/...` 或任何指向仓库的路径安装
- 不用 `--patch` 指向仓库里的文件
- 不把仓库当成"已经有 0.2.1-rc.2，所以可以直接用"的来源（仓库恰好是这个版本，但它是开发源码，不是安装产物）

本目录里的 Markdown 只是文档；仓库代码只用于调研时理解行为，升级过程一律不读不跑。

### 2. 执行者不能是"正在被升级的那个进程"

当前的 Web GUI（`http://127.0.0.1:3080`）就跑在全局安装的 `dsh web` 上，同一个包目录就是 `npm i -g` 要替换的那个目录。因此：

- **不要在当前这个 Web 会话里执行升级**：停 `dsh web` 会终止会话，替换全局包会让正在运行的进程与磁盘文件不一致。
- 正确做法：在一个**独立终端**里操作（先停 `dsh web`，再升级，再启动，最后回浏览器刷新）。
- 如果要让另一个 Agent 执行：让它跑在一个**不依赖 `dsh web`** 的进程里，并且把"停 web / 起 web"这两步交给终端或人工，而不是交给正在被停掉的那个会话。

## 三条硬约束（执行时先确认）

1. **顺序不能反**：先升 DSH 本体，再升插件。新版插件（`skill-explorer@0.4.7`、`auto-approval@0.0.43`、`better-sidebar@0.28`）都要求 DSH ≥ 0.2.1，先装会被判不兼容。
2. **先备份再动手**：`~/.dsh/profiles/web/cordis.patch.yml`（13,632 字节，sha256 `9ae14672…`，全文见验收清单）是唯一存着 7 个 provider 配置的文件，启动失败时宿主可能把它改名成 `.bak-<时间戳>` 再写空壳。
3. **失败就停，不要"顺手再试一下"**：每个阶段都有停止条件，命中就停下、按回滚章节退回，把日志留下来。

## 已知的两个"看起来像报错、其实是预期"的现象

- 升级完本体、还没换插件时先启动一次：`dsh-better-sidebar` 会报 `pending (waiting for service: webRuntime)`。这是预期的，换到 0.28.0 后消失。
- 第一次启动时如果出现 `Plugins waiting for services` 且列表里有 `webRuntime`，同上，属预期；除它以外出现任何 pending 都要当失败处理。
