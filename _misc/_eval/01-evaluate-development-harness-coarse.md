# 开发 Harness 评估 · 粗粒度（先过一遍）

**这份文档是什么。** 开发 Harness 评估的**粗粒度**一半：先用较小成本过一遍十七维，判断"值不值得投入、哪几维最痛"，回答一个问题：*一个不熟悉这个项目的 coding agent（或新人），进入这个仓库之后，能不能读懂、改对、验证、交付？* 评估对象是**仓库本身**——它的文件、命令、检查、惯例、协作面——不是团队里某个人的水平，也不是产品的架构。

**谁用。** 仓库维护者自查；新人或外部评审做尽职调查；coding agent 按本协议对目标仓库跑一遍。三种用法都指向同一份产物：一张评分卡 + 一张缺口清单 + 一份切片走查记录。

**前置知识。** 无。本文不假设你读过任何其它材料，术语在本页定义。文中出现的 DeepSeek Harness（DSH）只是**例证**：钉版在 commit `46a7f68b0922371ce7144b668b90e377d8e799f4`，用来指认"这件事在成熟仓库里长什么样"。全文只有 §1 一条带链接的原文引文，其余例证是不带链接的"可选核对"段落——**不打开任何链接也能完成评估**。

**编号约定。** 维度用两字母前缀（知识归位 `KN` / 变更路径 `CP` / 证据与交付 `EV` / 状态与上下文 `ST` / 维护与发布 `MT`），探针用 `PB`，证据级 `EL`，信息缺口 `IG`，成熟度档 `MG`；完整对照见 [README 的标识符约定](./README.md#标识符约定token)。

**两份粒度。** 本文（`01`）是粗粒度：定义、两轴、十七维粗判、产出模板与验收。**细粒度**（[`02`](./02-evaluate-development-harness-fine.md)）才有每维的探针、锚点与封顶规则——只在粗判为红、或要动的维度上翻它。**粗粒度定下来后基本不动，细粒度会持续增补。**

**配套文档。** [运行时评估粗粒度](./11-evaluate-runtime-harness.md)（仅当这个仓库本身是 agent 产品时适用）· [细粒度](./02-evaluate-development-harness-fine.md) · [从缺口到计划](./20-from-gaps-to-plan.md)

## 0 · 怎么用

### 两种模式

| | 快诊 | 全量 |
|---|---|---|
| 时间 | 30–60 分钟（6 维 × 5 个探针 + 一次切片） | 1–2 天（85 个探针 + 第三层反证 + 一次切片 + 填 4 张表；不含整理时间） |
| 做哪些维 | 六维：KN1 入口链、KN2 归属、CP2 正确路径、EV1 反馈分层、EV3 闭环完整性、ST1 静与动 | 全部十七维 |
| 做几层 | 第一层 + 第二层（另加一步 EV2 抽检） | 三层全做 |
| 产出 | 六行评分卡 + 缺口清单 | 四张表齐全 |
| 什么时候够 | 只想判断"值不值得投入" | 要拿这张清单排施工顺序 |

快诊的六维是十七维里**信息量最高的六个**：它们红了（**红 = 该维的覆盖面或约束力 ≤ 1**），其余十一维基本不可能绿。快诊不能替代全量——它只告诉你"要不要往下做"。

**粗粒度的两处已知偏差。** 六个维度里有 EV1（有没有检查）却没有 EV2（检查算不算数），而 EV2 是唯一检验其它维度真假的维度（见 [02 的 EV2 卡](./02-evaluate-development-harness-fine.md#ev2-负例控制--negative-control)）。所以快诊至少要补一步 EV2 抽检：任选一个现有检查，问"它最近一次为红是什么回归"；答不出，就把**成熟度档**下调一档——这个仓库的绿灯可能不可信。

### 铁律

**只有当场做过的才算证据。** 一个维度给 2 分以上（覆盖面或约束力任一），必须能说出"我做了什么、看到了什么"。凡是只能说出"我们文档里写了"、"我记得有"、"应该是有的"，两个轴都按 `1` 档封顶——不记 2 分以上。

这条铁律不是形式主义。它针对的是评估最常见的失效模式：**评估者和被评估者是同一批人，他们读自己的文档会觉得哪哪都对**。

### 人做 vs agent 做

| | 人可以做的 | agent 做不了的 |
|---|---|---|
| 证据来源 | 仓库 + **提问**（"这条规则上次改是什么时候？""这个检查拦住过东西吗？"） | 只有仓库。问不到人，问不到历史决策，问不到"我们当初为什么没做" |
| 补偿方式 | — | 把"提问"改成"找痕迹"：`git log`、CI 历史、被 revert 的提交、注释里的 TODO/FIXME、README 的 Known Limitations |

**agent 做评估时，有两维会系统性低估**：KN3 决策记录（理由可能真的只存在于会议里，仓库里看不到）与 EV2 负例控制（检查为红的历史可能在 CI 里而不在仓库里）。agent 在这两维上给出低分时，应标注"证据受限"，而不是断言缺失。

### 产出

四张表，在[第 6 节](#6--四张产出表空白模板)有空白模板：

1. **评分卡**：十七行 × 两轴（覆盖面 / 约束力）
2. **缺口清单**：每条挂在一个**具体症状**上，不是抽象评价
3. **切片走查记录**：一笔真实变更的六步走查
4. **三张清单**：打不开的链接 / 靠猜的 owner / 无证据的声称

## 1 · 什么是"仓库的开发 Harness"

> **Development harness（开发 Harness）**：一个仓库为了让参与者理解它、修改它、验证自己没改错而提供的全部机制的总和——规则文件、目录约定、决策记录、任务流程、检查命令、CI、以及这些之间的链接关系。

一个仓库的**产品**是它交付给用户的东西；它的**开发 Harness** 是它交付给自己的东西。两者可以差距极大：一个产品极其精良的仓库，可能完全靠三个老员工脑子里的默契运转。

### 公理层：fresh agent 缺的七类信息

一个第一次进入这个仓库的编码代理，缺少的是七类**信息**（不是七种能力）：

| 缺口 | 它缺的那句话 | 缺了之后的症状 |
|---|---|---|
| **IG1 必须遵守什么** | 这里有哪些铁律？哪些事绝对不能做？ | 违反约定、绕过安全边界、破坏不变量 |
| **IG2 系统由什么组成** | 这个库有哪些部分，谁依赖谁，东西放哪？ | 抓不住主线，读散、读偏，文件放错地方 |
| **IG3 为什么这样设计** | 当初为什么选这条路？什么方案被否了？ | 重走已否定的路；把历史实现细节误当当前接口 |
| **IG4 改动落在哪里** | 这个需求应该改哪个机制？ | 在错误的地方插代码；自己发明一套新接法 |
| **IG5 这类任务按什么流程做** | 这类任务该按什么步骤？什么时候停？ | 从多份规则里重新拼流程，漏步骤 |
| **IG6 怎么算做对** | 什么证据能证明我没做错？ | 交付了没法验证的半成品；"全绿"但没人信 |
| **IG7 交付怎样算完整** | 实现、文档、证据要一起交吗？缺口如实说吗？ | 代码先合并、文档后补；声称的行为没有证据 |

**"糊涂"来自 IG1–IG3，"乱发挥"来自 IG4–IG5，"交付不可信"来自 IG6–IG7。** 三者性质不同：前两者是"知不知道"，后两者是"会不会做错、做错了有没有人拦"。

### 一个关键反转

最容易犯的归因错误是：*DSH 之所以好，是因为给它干活的 agent 聪明。* 事实相反。DSH 自己的记录写的是：

> This codebase is developed primarily by coding agents. Agents follow enforced gates far more reliably than prose conventions.
>
> — DSH [`quality-gates` Agent Note](https://github.com/deepseek-ai/deepseek-harness/blob/46a7f68b0922371ce7144b668b90e377d8e799f4/.agents/notes/implemented/process/2026-06-11-quality-gates.md)

因果是反的：**因为干活的主力天然缺背景、会忘、会走捷径，仓库才被迫把成本结构整个反过来**——让"读对、改对"成为阻力最小的路径，让"读错、改错"在离错误源头最近的地方被机器拒绝。

所以评估的落点不是"我们的 agent 够不够聪明"，而是"**我们的仓库把正确路径修得比错误路径更省力了吗**"。

### 三条立场（十七维背后的同一个东西）

1. **参与者是一等公民。** 知识必须外置成可搜索、可检查的文件，而不是留在资深成员脑子里。
2. **规则要能被机器执行。** 写在贡献指南里靠自觉的规则，和接在检查里会拦人的规则，是两种东西。
3. **每类事实有唯一的 owner。** 一处一个权威，其余地方只放链接。一处事实两个家，早晚分叉。

十七维是这三条立场在具体机制上的展开。评估时如果某一维得分低，先问：它坏的是哪一条立场。

## 2 · 为什么不能自评：证据四级

同一个"我们有 X"，可以是四个完全不同的档位：

| 档 | 名称 | 判据 | 例子 |
|---|---|---|---|
| **EL0** | 只存在于人和口传 | 你问五个人，得到五种说法；或者根本没有 | "提交前记得跑一下那个脚本" |
| **EL1** | 写在 prose 里 | 有文件写了，但没有东西会因为你违反它而失败 | CONTRIBUTING.md 里的"请为所有新函数写测试" |
| **EL2** | 可核对 | 有一条命令或一个流程，跑/走一遍能得到确定的结论 | `make lint`；一份能照着走的 review checklist |
| **EL3** | 机器强制 + 负例控制 | 违规必然红，**并且证明过它会红** | 一个 gate；有人记得"这个检查上次为红是因为 XX 回归" |

**EL2 和 EL3 的差别是整份文档里最值钱的一条。** 一个从不失败的检查和一个不存在的检查，在"通过率"上完全一样，在保护效果上差别是全部。区分方法见 [02 的 EV2 负例控制](./02-evaluate-development-harness-fine.md#ev2-负例控制--negative-control)。

### 三级追问法

对任何一个"我们有"的说法，连问三次：

1. **在哪个文件？** → 说不出 = EL0
2. **跑哪条命令能验证？** → 说不出 = EL1
3. **它最近一次为红是什么时候、因为什么？** → 说不出 = EL2（不能记 EL3）

第三问是分水岭。它同时筛掉两种东西：从没被触发过的检查，和只在理论上存在的检查。

### 自评偏置的三种表现

- **文档即事实**：把"写了"当成"做到了"。文档描述的是意图，不是当前行为。
- **作者视角**：评估者知道东西在哪，所以觉得"很好找"。检验法是换一个不知道的人（或换一个没有上下文的 agent 会话）再走一遍。
- **例外隐身**：记得的是规程，忘的是"上次赶工期就没走"。切片走查（第 3 节第二层）专治这一条——它不看规程，看**最近这笔变更实际怎么做的**。

### 第一层 · 静态清点

按第 4 节的十七维逐维走探针，每一维记两轴的档位，并记下**一个最痛的真实案例**。

记录格式：`KN2 归属：覆盖面 2 / 约束力 1。案例：上周有人改了 CI 超时，改了 .github 里那份，但 CONTRIBUTING 里那份没动，两边差了两周没人发现。`

**案例是扣分的佐证，不是扣分的前置条件。** 说不出具体案例时，仍按探针证据给分，并把这维的证据状态标为"证据受限"；不要把"没听到事故"当成"机制存在"。
**细粒度（第二层切片六步、第三层反证四动作）见 [02 §3](./02-evaluate-development-harness-fine.md#3--第二层与第三层切片与反证)。** 粗粒度只需要知道三层的分工与先后：清点 → 切片 → 反证。

## 4 · 十七维粗判

### 两轴怎么打

每一维打**两个**分，因为"有"和"硬"是两件正交的事。

**轴一 · 覆盖面（Coverage）** —— 这一维有没有家

| 档 | 判据 |
|---|---|
| 0 | 没有。没有任何文件、目录、命令或惯例承载它 |
| 1 | 有但不完整。零散存在，没有纪律，覆盖不到常见情况 |
| 2 | 有且成体系。常见情况都能被它覆盖，新参与者能找到它 |
| 3 | 有且被主动维护。有明确的 owner、有更新触发条件、有维护记录 |

**轴二 · 约束力（Enforcement）** —— 这一维靠什么成立

| 档 | 判据 |
|---|---|
| 0 | 只靠人和口传 |
| 1 | 写在 prose 里（指南、贡献文档、README），违反了不会发生任何事 |
| 2 | 可核对：有一条命令或一个流程，跑/走一遍能得到确定结论 |
| 3 | 机器强制，且有负例控制：违规必红，且能说出它最近一次为红是什么回归 |

**读法。** `覆盖面 2 / 约束力 1` 是最常见的形态，也是最危险的形态——看起来什么都有，实际上全靠自觉。**约束力 3 才是"像回事"**。

### 总分与成熟度档

十七维不求和（不同维量纲不同），看**分布**：

| 档 | 判据 | 一句话 |
|---|---|---|
| **MG0 依赖个人** | 多数维度覆盖面 ≤ 1 | 这个仓库靠少数人的记忆运转 |
| **MG1 有文档** | 多数覆盖面 = 2，多数约束力 ≤ 1 | 写下来了，但没人拦得住违反 |
| **MG2 可核对** | 六维快诊集合中**适用**的至少四个（适用不足四个时全部）约束力 ≥ 2 | 走一遍能得出确定结论 |
| **MG3 可自证** | 至少三个维度的约束力 = 3，且 MT1 防漂移的**约束力** ≥ 2（检查接进了提交流程） | 机制会自己报告失效 |

达标线：**至少 MG2，且你最痛的三维达到约束力 3。** 这是"能不能用"的下限；判断一轮打磨**能不能收工**用[20 的收工线](./20-from-gaps-to-plan.md#7--一轮打磨的循环与停止条件)——它更严（裁剪后的每一维都要到覆盖面 2）。

**档位怎么记。** 四个档的判据可以同时满足：**记最高的那个**。档位与达标线相互独立——MG3 的仓库也可能未达标（最痛的三维没到约束力 3），MG2 的仓库可能已经达标。

**"多数"与计数的口径。** 本节所有"多数"指该档适用维度里的**超过一半**；"至少四个""至少三个"这类计数也只在适用维度里数；标了 N/A 的维度不计入分母（见[第 5 节](#5--适用性裁剪)）。

### 十七维粗判一览

**怎么用**：对每一维看"粗判信号"那一列——只要命中，就把它记进缺口清单并标红；要定死档位再翻 02 的对应卡片。

| 维 | 它管什么 | 粗判信号（一眼看什么） | 通常 N/A |
|---|---|---|---|
| `KN1` 入口链 | 新会话先读到的最小规则集与它的路由 | 根入口是不是"一堵墙"（只有规则、指不出去）；有没有混着教程与历史 | — |
| `KN2` 归属 | 每类事实只有一个家 | 同一个东西会不会在两处各写一版；术语有没有两个名字指同一件事 | — |
| `KN3` 决策记录 | 为什么这么选、什么被否了 | 被否的方案半年后会不会被重提；旧理由有没有假装成现行 | — |
| `KN4` 分类学 | 东西放哪、谁维护、能不能手改 | 新文件该放哪要不要问人；生成物有没有被手改 | — |
| `CP1` 意图入口 | 任务怎么变成可开工的描述 | 最近 5 个工作项写不写得出"怎么观察结果" | — |
| `CP2` 正确路径 | 常见改动有没有首选入口与范本 | 有没有人绕过既有封装自己发明一套接法 | — |
| `CP3` 流程固化 | 反复出现的任务有没有成文流程 | 同类任务第三次出现时还在现场发明步骤 | — |
| `CP4` 执行与授权链 | 自动化动作走同一管线，授权独立于可见性 | 加一条权限规则要改几个文件；有没有"部分成功"流下去 | 仓库里没有自动化代理时 |
| `EV1` 反馈分层 | 检查分层，每层知道证明不了什么 | 有没有"一层绿当成全绿"；失败信息说不说得出去哪修 | — |
| `EV2` 负例控制 | 检查被证明过会失败 | 随便挑一个检查，说得出它最近一次为红是什么回归吗 | — |
| `EV3` 闭环完整性 | 实现+文档+证据同批交付 | 最近 5 笔有没有"先合并后补文档" | — |
| `EV4` 评审与批准 | 批准条件与风险挂钩，作者凑不满放行线 | 最近 10 笔评审是不是清一色"LGTM" | 单人项目（标 N/A 并写理由） |
| `ST1` 静与动 | 状态分层：规则 / 配置 / 事实源 / 派生 | 同一个数据能不能两处写；出事后能不能回放 | 没有跨轮存活的东西时 |
| `ST2` 披露与隔离 | 按需加载、超预算回收、子任务不带父上下文 | 规则文档是不是越塞越多；子任务是不是继承全部上下文 | 没有上下文预算压力的小仓库 |
| `ST3` 运行时查询 | 一条命令问出"实际生效的是什么" | 是不是只能读源码猜；有没有手工维护的接口清单 | 单层配置的小仓库 |
| `MT1` 防漂移 | 知识与现实不漂移 | 文档写的时候对、三个月后处处对不上 | — |
| `MT2` 发布与版本纪律 | 发布序列、兼容承诺、回退路径 | 版本号规则说不说得清哪些接口真稳定；坏版本退不退得回去 | 不对外发布产物时 |

## 5 · 适用性裁剪

不是每种仓库都要评全部十七维。**不适用的维度记 `N/A`，不记 0 分**——把"不适用"打成 0 会让评分卡失真，让你去修一个根本不存在的问题。

### 按仓库形态裁剪

| 形态 | 必评 | 通常 N/A | 特别注意 |
|---|---|---|---|
| **库 / SDK**（被别人引用） | 知识归位全组、CP1 CP2 CP3、证据与交付全组、ST1、MT1 MT2 | CP4、ST2 ST3 | MT2 兼容承诺是核心；KN2 归属要覆盖公开 API 与文档的一致 |
| **服务 / 后端** | 知识归位全组、变更路径全组、证据与交付全组、状态与上下文全组、MT1 | MT2（若内部服务，版本纪律可能极轻） | ST1 静与动、ST3 运行时查询权重高；CP4 授权链必看 |
| **Monorepo** | 全部 | — | KN4 分类学权重最高；MT1 防漂移是成败关键；KN2 要跨包查重 |
| **插件平台 / 框架** | 全部 | — | CP2 正确路径是核心（"改哪里"必须有表可查）；CP3 流程固化权重高 |
| **数据 / ML 仓库** | 知识归位全组、CP2 CP3、证据与交付全组、ST1、MT1 MT2 | CP4、ST2 ST3 | ST1 的"事实源 vs 派生"要覆盖数据集与特征；MT2 要覆盖数据 schema 版本 |
| **文档站 / 知识库** | 知识归位全组、CP1 CP3、EV1 EV2 EV3、MT1 | CP2 CP4、状态与上下文全组、MT2 | KN1 入口链、KN2 归属、MT1 防漂移是**重点**（其余按"必评"列照做）；证据与交付组查"链接与锚点是否有检查" |
| **单文件脚本 / 小工具** | KN1 KN2、EV1 EV2、MT1 | 其余 | 上列五维已足够（EV2 与 MT1 对脚本最便宜也最有用）；不要为了评分卡去造机制 |
| **agent 产品 / 自带 agent 运行时** | 本文全部 | — | **另加**：[运行时 Harness 粗粒度](./11-evaluate-runtime-harness.md) |

### 三条裁剪纪律

1. **标 N/A 要写理由**，一行即可（"本仓库不发布产物，MT2 不适用"）。
2. **N/A 的维度不参与成熟度档判定**，分母按实际评估的维度数算。
3. **不确定是否适用时，先按适用处理**，评估过程中发现没有对应压力，再改标 N/A 并记录。

### 与运行时评估的形态口径不同

本表的"仓库形态"决定十七维里哪些要评；[02 的形态裁剪](./11-evaluate-runtime-harness.md#4--形态裁剪)那套（内部 / 产品 / 平台 / 单机实验 / 多入口）决定十一维里哪些要评。两者正交：一个仓库的形态是"agent 产品"时，两套各判一次。

## 7 · 评估者自己的验收

评估做完，先用这五条检验**评估本身**：

1. **每个扣分点都能指到具体证据。** 说不出"我在哪个文件、哪次提交、哪条命令上看到的"，这一条就不算扣分——回去补证据，或者撤销这条。
2. **换一个人复测，档位稳定。** 同一维度由另一个人（或另开一个无上下文的 agent 会话）走一遍，档位差不应超过 1。差 2 以上，说明探针写得不够客观。
3. **缺口清单里的每一条都能归到某一维。** 归不进去的，要么是新维度（记下来），要么根本不是开发 Harness 的问题（删掉）。
4. **表 4 不是空的。** 一次评估如果三张清单全是空的，八成是没认真找——除非这个仓库真的处于极高水平。
5. **每一次命中封顶，都说得出观察它的探针。** 封顶规则是按锚点阶梯逐条展开的（见 [02 的附录 A](./02-evaluate-development-harness-fine.md#附录-a--封顶规则速查)），每条都由某一维的某个探针观察。说不出是哪条探针，说明这条封顶在本次评估里用不出来——把它当方法缺陷记下来，不要照记分。

### agent 做评估的三条额外纪律

- **区分"看不见"和"没有"。** 只有仓库可查时，很多事实看不到。看不到就标"证据受限"，不要断言缺失。
- **不要用仓库自己的文档当证据。** 文档是**被评估对象**的一部分，不是评估依据。文档说"我们有严格的测试要求"，这句话本身只能证明"文档里写了这句话"。
- **不允许跳过第三层的第 4 个动作**（故意制造一个违规，看检查红不红，然后还原）。它是唯一能区分 EL2 与 EL3 的手段，而且 agent 做这件事比人快得多。

## 8 · 短例

> **说明**：这是一个**构造的示意**，不是对任何真实仓库的评估。目的是让你看到"填成什么样算合格"。

### 背景

- 仓库：一个运行了三年的后端服务，Go 主体 + TypeScript 前端，约 6 万行，15 人团队。
- 已有：`README.md`（400 行，包含架构、部署、编码规范、常见问题）、`docs/` 目录（12 篇，最后更新日期跨度两年）、`Makefile`、GitHub Actions 跑 `go test ./...` 与前端构建。
- 模式：快诊（六维）+ 一次切片。

### 表 1 · 评分卡（节选）

| 维 | 覆盖面 | 约束力 | 最痛的真实案例 |
|---|---|---|---|
| KN1 入口链 | 1 | 1 | `README.md` 400 行里混着架构说明、编码规范和历史遗留的部署步骤；没有给 agent 的入口文件；新人第一个问题是"该读哪一段"，答案靠问人 |
| KN2 归属 | 1 | 1 | 超时配置有两个家：`config/timeouts.go` 与 `README.md` 的"关键参数"一节；上周改代码里那份，README 那份滞后两周无人发现 |
| CP2 正确路径 | 1 | 1 | 三个月前有人为了加一个后端接口，在 handler 里直接开了 goroutine 写库，绕过了既有的 task queue 封装；评审时才发现 |
| EV1 反馈分层 | 2 | 2 | 有单测与 CI，但只有"局部行为"一层；没有契约测试、没有端到端；配置错误只能在启动时炸 |
| EV3 闭环完整性 | 1 | 1 | 最近 5 笔变更里 3 笔只改代码；`docs/` 里 12 篇有 7 篇描述的接口已经变了 |
| ST1 静与动 | 1 | 0 | 有一个内存缓存层，与数据库同时可写；没人说得清哪个是权威。任务状态只存在 Redis 里，出事后无法回放 |

```
成熟度档：MG0 依赖个人（快诊六维里五维的覆盖面停在 1）
最痛的三维：ST1 静与动、KN2 归属、EV3 闭环完整性
```

### 表 2 · 缺口清单（节选）

| # | 维 | 症状 | 后果 | 缺口 | 严重度 |
|---|---|---|---|---|---|
| 1 | ST1 | 缓存与 DB 同时可写；任务状态只在 Redis | 缓存与 DB 不一致时无人知道哪边对；线上问题无法回放 | IG2 | 高 |
| 2 | KN2 | 超时配置在代码与 README 各有一份 | 新人按 README 改配置，改完不生效；上周已发生一次 | IG1 IG3 | 高 |
| 3 | EV3 | 12 篇文档里 7 篇接口描述已过期 | agent 会照过期文档写出调用不存在接口的代码 | IG7 | 高 |
| 4 | CP2 | 没有"目标→机制"表；新接口绕过 task queue | 每次新功能都可能重新发明一套接法，评审才发现 | IG4 | 中 |
| 5 | KN1 | 400 行 README 无路由结构；无 agent 入口 | 每次新会话先花 10 分钟找该读哪里，且常常读错 | IG1 IG2 | 中 |

### 表 3 · 切片走查记录

```
被走查的变更：commit a3f9c21「订单超时时间改为可配置」
为什么选它：最近完成、改动小、不涉及核心架构
```

| 步 | 观察到的 | 证据状态 |
|---|---|---|
| 1 核对现场 | 从 `develop` 分支切出；base 没有记录在提交信息里，但从时间推断得出 | 只有口头说法 |
| 2 判定窄 diff | 窄 diff 是 3 个文件：`config/timeouts.go`、`order/service.go`、一个测试；同一事实的另一份 `README.md` 未改 | 能指出文件 |
| 3 改 owner 面 | 改了代码侧配置；**没有**改 README 里那份同名配置清单 | 能指出文件 |
| 4 最小匹配证据 | 有测试 `TestOrderTimeoutConfig`。红灯对照：注释掉配置读取改回硬编码 → 测试**仍然通过** | 能指出文件，但证据不成立 |
| 5 沉淀 | 无决策记录（这笔变更确实没有持久取舍，✓ 合理） | — |
| 6 只报告跑过的 | PR 描述写"已测试"，CI 确实跑了 `go test ./...` | 能指出文件 |

```
⑤ 「靠猜」的条目：README 里那份超时配置是不是权威（靠问人才知道是代码侧权威）
   「没证据」的条目：TestOrderTimeoutConfig 看起来在测配置，实际没有钉住配置读取路径
```

### 一句话结论

这个仓库的问题不是"没有文档"——它有 400 行 README 和 12 篇 docs——而是**文档与代码是两个可以各自漂移的家，且没有任何检查会发现它们漂了**。切片走查给出了确凿证据：一笔本该同时改两处的变更只改了一处，而那个看起来在保护的测试实际上什么都没保护。

## 附录 A · 术语表

| 词 | 含义 |
|---|---|
| **development harness** | 仓库为了让参与者理解、修改、验证自己而提供的全部机制的总和 |
| **fresh agent** | 第一次进入这个仓库、没有任何项目背景的编码代理 |
| **知识外置** | 把原本留在个人经验里的知识，变成可搜索、可检查或可执行的仓库内容 |
| **owner / 归属** | 某类事实的唯一权威所在的位置；其它地方只放链接 |
| **paved road / 正确路径** | 仓库为常见变更提供的首选入口、生产范本和升级条件 |
| **procedural memory / 流程固化** | 面向特定任务、带适用条件和验证步骤的工作方法，被写成可复用文档 |
| **inspectability / 可查询性** | 查询实际配置、注册项和运行状态的能力 |
| **负例控制** | 故意制造一个该被抓住的回归，确认检查确实会失败，然后还原 |
| **红灯对照** | 回滚实现、保留检查，跑一次看它红不红；不红说明这个检查没在测它以为在测的东西 |
| **窄 diff** | 这次改动真正触达的行为面，不含顺带的重构与格式化 |
| **覆盖面** | 这一维有没有家：0 没有 / 1 零散 / 2 成体系 / 3 有 owner 与更新触发条件（见第 4 节） |
| **约束力** | 一条规则靠什么成立：口传 / prose / 可核对 / 机器强制且有负例控制 |
| **EL0–EL3** | 上述四档证据级（证据级与维度编号是两套前缀，不再同字母） |
| **漂移** | 外置知识与它所描述的现实之间产生的、无人发现的偏差 |
| **freshness 门禁** | 检查派生内容跟不跟得上源头：源头变了、派生没跟着变就红 |
| **第一 / 第二 / 第三层** | 三个评估层：静态清点、垂直切片、反证（层与维度是两回事，别混读） |

## 附录 B · 常见伪证清单

评估时最常听到的十句话，以及每一句为什么不能作为加分依据。

| 说法 | 为什么不算 |
|---|---|
| "我们有 `AGENTS.md`" | 有文件不等于有路由。看它有没有指出去的链接 |
| "我们的文档很全" | 全不等于有家。两份都全，就是两个家 |
| "我们遵循语义化版本" | 版本号规则不说明**哪些接口真的承诺稳定** |
| "源码就是文档" | 源码说的是可能是什么，回答不了现在是什么 |
| "我们 CI 全绿" | 全绿只覆盖检查碰巧碰到的地方，与"声称的行为都有证据"无关 |
| "我们的检查很全" | 检查全绿但没人信，是这类系统最贵的走形。用 EV2 抽检 |
| "我们有严格的双人评审" | 数最近 10 笔的评论条数与内容，比制度描述准 |
| "我们要求每个 PR 带测试" | 要求是一回事，最近 5 笔里带了几笔是另一回事 |
| "我们的工具自己会检查权限" | 那是策略散在 N 处，改一次要动 N 个文件 |
| "我们的文档更新很及时" | 及时靠人，防漂移靠机器。两者不能互相替代 |
