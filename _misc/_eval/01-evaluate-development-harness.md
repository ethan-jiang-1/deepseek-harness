# 评估任何仓库的开发 Harness

**这份文档是什么。** 一套可以当场做完的评估方法，回答一个问题：*一个不熟悉这个项目的 coding agent（或新人），进入这个仓库之后，能不能读懂、改对、验证、交付？* 评估对象是**仓库本身**——它的文件、命令、检查、惯例、协作面——不是团队里某个人的水平，也不是产品的架构。

**谁用。** 仓库维护者自查；新人或外部评审做尽职调查；coding agent 按本协议对目标仓库跑一遍。三种用法都指向同一份产物：一张评分卡 + 一张缺口清单 + 一份切片走查记录。

**前置知识。** 无。本文不假设你读过任何其它材料，术语在本页定义。文中出现的 DeepSeek Harness（DSH）只是**例证**：钉版在 commit `46a7f68b0922371ce7144b668b90e377d8e799f4`，用来指认"这件事在成熟仓库里长什么样"。全文只有 §1 一条带链接的原文引文，其余例证是不带链接的"可选核对"段落——**不打开任何链接也能完成评估**。

**配套文档。** [运行时 Harness 评估](./02-evaluate-runtime-harness.md)（仅当这个仓库本身是 agent 产品时适用）与 [缺口到计划](./03-from-gaps-to-plan.md)（用本文的缺口清单决定下一步做什么）。本文可单独使用。

## 0 · 怎么用

### 两种模式

| | 快诊 | 全量 |
|---|---|---|
| 时间 | 30–60 分钟（6 维 × 5 个探针 + 一次切片） | 1–2 天（85 个探针 + 第三层反证 + 一次切片 + 填 4 张表；不含整理时间） |
| 做哪些维 | 六维：A1 入口链、A2 归属、B2 正确路径、C1 反馈分层、C3 闭环完整性、D1 静与动 | 全部十七维 |
| 做几层 | 第一层 + 第二层（另加一步 C2 抽检） | 三层全做 |
| 产出 | 六行评分卡 + 缺口清单 | 四张表齐全 |
| 什么时候够 | 只想判断"值不值得投入" | 要拿这张清单排施工顺序 |

快诊的六维是十七维里**信息量最高的六个**：它们红了（**红 = 该维的覆盖面或约束力 ≤ 1**），其余十一维基本不可能绿。快诊不能替代全量——它只告诉你"要不要往下做"。

**快诊的一处已知高估。** 六个维度里有 C1（有没有检查）却没有 C2（检查算不算数），而 C2 是唯一检验其它维度真假的维度（见 [C2 负例控制](#c2-负例控制--negative-control)）。所以快诊至少要补一步 C2 抽检：任选一个现有检查，问"它最近一次为红是什么回归"；答不出，就把**成熟度档**下调一档——这个仓库的绿灯可能不可信。

### 铁律

**只有当场做过的才算证据。** 一个维度给 2 分以上（覆盖面或约束力任一），必须能说出"我做了什么、看到了什么"。凡是只能说出"我们文档里写了"、"我记得有"、"应该是有的"，两个轴都按 `1` 档封顶——不记 2 分以上。

这条铁律不是形式主义。它针对的是评估最常见的失效模式：**评估者和被评估者是同一批人，他们读自己的文档会觉得哪哪都对**。

### 人做 vs agent 做

| | 人可以做的 | agent 做不了的 |
|---|---|---|
| 证据来源 | 仓库 + **提问**（"这条规则上次改是什么时候？""这个检查拦住过东西吗？"） | 只有仓库。问不到人，问不到历史决策，问不到"我们当初为什么没做" |
| 补偿方式 | — | 把"提问"改成"找痕迹"：`git log`、CI 历史、被 revert 的提交、注释里的 TODO/FIXME、README 的 Known Limitations |

**agent 做评估时，有两维会系统性低估**：A3 决策记录（理由可能真的只存在于会议里，仓库里看不到）与 C2 负例控制（检查为红的历史可能在 CI 里而不在仓库里）。agent 在这两维上给出低分时，应标注"证据受限"，而不是断言缺失。

### 产出

四张表，在[第 6 节](#6--四张产出表空白模板)有空白模板：

1. **评分卡**：十七行 × 两轴（覆盖面 / 约束力）
2. **缺口清单**：每条挂在一个**具体症状**上，不是抽象评价
3. **切片走查记录**：一笔真实变更的六步走查
4. **三张清单**：打不开的链接 / 靠猜的 owner / 无证据的声称

## 1 · 什么是"仓库的开发 Harness"

> **Development harness（开发 Harness）**：一个仓库为了让参与者理解它、修改它、验证自己没改错而提供的全部机制的总和——规则文件、目录约定、决策记录、任务流程、检查命令、CI、以及这些之间的链接关系。

一个仓库的**产品**是它交付给用户的东西；它的**开发 Harness** 是它交付给自己的东西。两者可以差距极大：一个产品极其精良的仓库，可能完全靠三个老员工脑子里的默契运转。

### 公理层：fresh agent 缺的七类信息

一个第一次进入这个仓库的编码代理，缺少的是七类**信息**（不是七种能力）：

| 缺口 | 它缺的那句话 | 缺了之后的症状 |
|---|---|---|
| **G1 必须遵守什么** | 这里有哪些铁律？哪些事绝对不能做？ | 违反约定、绕过安全边界、破坏不变量 |
| **G2 系统由什么组成** | 这个库有哪些部分，谁依赖谁，东西放哪？ | 抓不住主线，读散、读偏，文件放错地方 |
| **G3 为什么这样设计** | 当初为什么选这条路？什么方案被否了？ | 重走已否定的路；把历史实现细节误当当前接口 |
| **G4 改动落在哪里** | 这个需求应该改哪个机制？ | 在错误的地方插代码；自己发明一套新接法 |
| **G5 这类任务按什么流程做** | 这类任务该按什么步骤？什么时候停？ | 从多份规则里重新拼流程，漏步骤 |
| **G6 怎么算做对** | 什么证据能证明我没做错？ | 交付了没法验证的半成品；"全绿"但没人信 |
| **G7 交付怎样算完整** | 实现、文档、证据要一起交吗？缺口如实说吗？ | 代码先合并、文档后补；声称的行为没有证据 |

**"糊涂"来自 G1–G3，"乱发挥"来自 G4–G5，"交付不可信"来自 G6–G7。** 三者性质不同：前两者是"知不知道"，后两者是"会不会做错、做错了有没有人拦"。

### 一个关键反转

最容易犯的归因错误是：*DSH 之所以好，是因为给它干活的 agent 聪明。* 事实相反。DSH 自己的记录写的是：

> This codebase is developed primarily by coding agents. Agents follow enforced gates far more reliably than prose conventions.
>
> — DSH [`quality-gates` Agent Note](https://github.com/deepseek-ai/deepseek-harness/blob/46a7f68b0922371ce7144b668b90e377d8e799f4/.agents/notes/implemented/process/2026-06-11-quality-gates.md)

因果是反的：**因为干活的主力天然缺背景、会忘、会走捷径，仓库才被迫把成本结构整个反过来**——让"读对、改对"成为阻力最小的路径，让"读错、改错"在离错误源头最近的地方被机器拒绝。

所以评估的落点不是"我们的 agent 够不够聪明"，而是"**我们的仓库把正确路径修得比错误路径更省力了吗**"。

### 三条立场（十七维背后的同一个东西）

1. **参与者是一等公民。** 知识必须外置成可搜索、可检查的文件，而不是留在资深成员脑子里。
2. **规则要能被机器执行。** 写在贡献指南里靠自觉的规则，和接在检查里会拦人的规则，是两种东西。
3. **每类事实有唯一的 owner。** 一处一个权威，其余地方只放链接。一处事实两个家，早晚分叉。

十七维是这三条立场在具体机制上的展开。评估时如果某一维得分低，先问：它坏的是哪一条立场。

## 2 · 为什么不能自评：证据四级

同一个"我们有 X"，可以是四个完全不同的档位：

| 档 | 名称 | 判据 | 例子 |
|---|---|---|---|
| **E0** | 只存在于人和口传 | 你问五个人，得到五种说法；或者根本没有 | "提交前记得跑一下那个脚本" |
| **E1** | 写在 prose 里 | 有文件写了，但没有东西会因为你违反它而失败 | CONTRIBUTING.md 里的"请为所有新函数写测试" |
| **E2** | 可核对 | 有一条命令或一个流程，跑/走一遍能得到确定的结论 | `make lint`；一份能照着走的 review checklist |
| **E3** | 机器强制 + 负例控制 | 违规必然红，**并且证明过它会红** | 一个 gate；有人记得"这个检查上次为红是因为 XX 回归" |

**E2 和 E3 的差别是整份文档里最值钱的一条。** 一个从不失败的检查和一个不存在的检查，在"通过率"上完全一样，在保护效果上差别是全部。区分方法见 [C2 负例控制](#c2-负例控制--negative-control)。

### 三级追问法

对任何一个"我们有"的说法，连问三次：

1. **在哪个文件？** → 说不出 = E0
2. **跑哪条命令能验证？** → 说不出 = E1
3. **它最近一次为红是什么时候、因为什么？** → 说不出 = E2（不能记 E3）

第三问是分水岭。它同时筛掉两种东西：从没被触发过的检查，和只在理论上存在的检查。

### 自评偏置的三种表现

- **文档即事实**：把"写了"当成"做到了"。文档描述的是意图，不是当前行为。
- **作者视角**：评估者知道东西在哪，所以觉得"很好找"。检验法是换一个不知道的人（或换一个没有上下文的 agent 会话）再走一遍。
- **例外隐身**：记得的是规程，忘的是"上次赶工期就没走"。切片走查（第 3 节第二层）专治这一条——它不看规程，看**最近这笔变更实际怎么做的**。

## 3 · 评估分三层

三层缺一不可。只做第一层是自报，只做第二层没有结构，只做第三层没有依据。

### 第一层 · 静态清点

按第 4 节的十七维逐维走探针，每一维记两轴的档位，并记下**一个最痛的真实案例**。

记录格式：`A2 归属：覆盖面 2 / 约束力 1。案例：上周有人改了 CI 超时，改了 .github 里那份，但 CONTRIBUTING 里那份没动，两边差了两周没人发现。`

**案例是扣分的佐证，不是扣分的前置条件。** 说不出具体案例时，仍按探针证据给分，并把这维的证据状态标为"证据受限"；不要把"没听到事故"当成"机制存在"。

### 第二层 · 垂直切片

挑**最近完成的一笔真实变更**（修 bug 或小功能，不动核心架构），按六步走一遍。每一步只问一件事：**它留下了什么可以事后核对的痕迹？**

| 步 | 走查问题 | 痕迹在哪 |
|---|---|---|
| 1 **核对现场** | 这笔变更基于哪个 revision？谁能确认？ | 提交/PR 的 base；分支从哪来 |
| 2 **判定窄 diff** | 这次真正触达的行为面是什么？范围是怎么定出来的？ | diff 本身；commit message；PR 描述 |
| 3 **改 owner 面** | 改的是源头还是派生？有没有同一事实的另一份拷贝也该改？ | diff 里有没有生成物被手改、有没有双份文件只改一边 |
| 4 **最小匹配证据** | 哪条检查会**因为这次回归而失败**？ | 测试/检查文件；回滚实现保留测试跑一次（红灯对照） |
| 5 **沉淀** | 这笔变更产生的新判断去哪了？ | 决策记录 / gate / 什么都没有（什么都没有也可能是对的） |
| 6 **只报告跑过的** | 交付说明里声称的验证，和实际跑过的对得上吗？ | PR 描述 vs CI 记录 |

第 4 步的**红灯对照**是切片的灵魂：把实现回滚、保留新增的测试或检查，跑一次，看它红不红。

- 红了 → 这个证据是真的。
- 绿着 → 这个测试没在测它以为在测的东西。这是本轮评估里价值最高的一次发现。

第 3 步的**五问走查**（对应 G1–G5）：

1. 这笔变更的用户可观察结果是什么？写得出两行"外部结果 + 如何观察"吗？
2. 从任务描述出发，能不能一路找到改动位置的 owner（不靠当时作者带路）？
3. 交付里有没有携带持久取舍？有的话它记在哪里？没有的话，理由说得出吗？
4. 哪项证据会在旧行为上失败？（就是上面那次红灯对照）
5. 每一步标注证据状态：**能指出文件的 / 只有口头说法的 / 完全没有的**。

### 第三层 · 反证

第三层检验的是**前面两层自己的可信度**。四个动作：

1. **抽检一个检查**：随便挑一个现有的检查，说得出它最近一次为红是因为什么回归吗？说不出，按 E2 记；这维的约束力按第 4 节的封顶规则处理（C2 那条会把它压得更低）。
2. **抽检一条规则**：随便挑一条写在文档里的规则，找一条最近违反过它的提交。找得到 → 规则在裸奔（E1）。
3. **抽检一个链接**：从根入口文件随机点 5 个链接。打不开的记进第 4 张表。
4. **抽检一次"应该失败"**：故意制造一个小违规（加一个错别字进被检查的文件、破坏一个链接），跑检查，看它红不红，然后还原。**不允许跳过这一步**——它是你判断"这个仓库的检查是真的吗"的唯一手段。

### 三层怎么合起来用

```
第一层 → 结构在哪缺（哪一维低）
第二层 → 实际怎么跑（缺口造成什么后果）
第三层 → 已有的机制可信吗（低分是"没有"还是"有但假的"）
```

第一层的缺口清单和第二层的走查记录会合流成一张**施工顺序表**（这张表由[缺口到计划](./03-from-gaps-to-plan.md)的[排序原则](./03-from-gaps-to-plan.md#1--排序原则)与[循环](./03-from-gaps-to-plan.md#7--一轮打磨的循环与停止条件)产出，本文不提供模板）：每一个"靠猜"和"没证据"都能归到十七维里的某一维，**哪一维的案例最多最痛，就先去那份文档里找那一维的处置卡**。

## 4 · 十七维评分卡

### 两轴怎么打

每一维打**两个**分，因为"有"和"硬"是两件正交的事。

**轴一 · 覆盖面（Coverage）** —— 这一维有没有家

| 档 | 判据 |
|---|---|
| 0 | 没有。没有任何文件、目录、命令或惯例承载它 |
| 1 | 有但不完整。零散存在，没有纪律，覆盖不到常见情况 |
| 2 | 有且成体系。常见情况都能被它覆盖，新参与者能找到它 |
| 3 | 有且被主动维护。有明确的 owner、有更新触发条件、有维护记录 |

**轴二 · 约束力（Enforcement）** —— 这一维靠什么成立

| 档 | 判据 |
|---|---|
| 0 | 只靠人和口传 |
| 1 | 写在 prose 里（指南、贡献文档、README），违反了不会发生任何事 |
| 2 | 可核对：有一条命令或一个流程，跑/走一遍能得到确定结论 |
| 3 | 机器强制，且有负例控制：违规必红，且能说出它最近一次为红是什么回归 |

**读法。** `覆盖面 2 / 约束力 1` 是最常见的形态，也是最危险的形态——看起来什么都有，实际上全靠自觉。**约束力 3 才是"像回事"**。

### 总分与成熟度档

十七维不求和（不同维量纲不同），看**分布**：

| 档 | 判据 | 一句话 |
|---|---|---|
| **L0 依赖个人** | 多数维度覆盖面 ≤ 1 | 这个仓库靠少数人的记忆运转 |
| **L1 有文档** | 多数覆盖面 = 2，多数约束力 ≤ 1 | 写下来了，但没人拦得住违反 |
| **L2 可核对** | 六维快诊集合中**适用**的至少四个（适用不足四个时全部）约束力 ≥ 2 | 走一遍能得出确定结论 |
| **L3 可自证** | 至少三个维度的约束力 = 3，且 E1 防漂移的**约束力** ≥ 2（检查接进了提交流程） | 机制会自己报告失效 |

达标线：**至少 L2，且你最痛的三维达到约束力 3。** 这是"能不能用"的下限；判断一轮打磨**能不能收工**用[缺口到计划的收工线](./03-from-gaps-to-plan.md#7--一轮打磨的循环与停止条件)——它更严（裁剪后的每一维都要到覆盖面 2）。

**档位怎么记。** 四个档的判据可以同时满足：**记最高的那个**。档位与达标线相互独立——L3 的仓库也可能未达标（最痛的三维没到约束力 3），L2 的仓库可能已经达标。

**"多数"与计数的口径。** 本节所有"多数"指该档适用维度里的**超过一半**；"至少四个""至少三个"这类计数也只在适用维度里数；标了 N/A 的维度不计入分母（见[第 5 节](#5--适用性裁剪)）。

### A 组 · 知识归位

#### A1 入口链 · Entry chain

**填的缺口**：G1 必须遵守什么 / G2 系统由什么组成

**一句话**：新会话开始时被稳定读到的那份最小规则集，以及它指向其余知识的路由。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | `ls -a` 根目录与主要子树，找出所有面向 agent 的入口文件（`AGENTS.md` / `CLAUDE.md` / `.cursorrules` / `CONTRIBUTING.md` / `.github/copilot-instructions.md`） | 有几个？分别服务谁？有没有重复 |
| P2 | 若同一目录同时存在两个入口文件名：`ls -la` | 是不是符号链接。不是 → 两份事实，迟早分叉 |
| P3 | 数根入口文件的行数与词数 | 是不是"大而全总览"。含教程、历史故事、完整流程 → 超预算；有没有成文的字数预算与维护触发条件，以及执行它的字数上限门禁（它红过吗） |
| P4 | 从根入口里抽 5 条规则，逐条找它的详细 home | 每条能不能点到唯一一个更详细的位置 |
| P5 | 数列子树入口文件的数量与理由 | 是不是"为放而放"。绝大多数目录只该有 README |

**覆盖面**：0 没有入口 / 1 有但混着教程与历史 / 2 短入口 + 布局 + 命令，其余链接出去 / 3 且有明确的字数预算与维护触发条件

**约束力**：0 靠口传 / 1 写在 prose 里 / 2 有链接检查（断链会红）/ 3 且有字数上限门禁

**封顶规则**
- 同一目录存在两个**非符号链接**的入口文件 → 覆盖面封顶 1（已经有两份事实了）
- 根入口文件包含教程或历史叙述 → 覆盖面封顶 1
- 根入口里的链接有打不开的 → 约束力封顶 1（路由断了，等于没有）
- 根入口没有指向更详细 home 的链接（一堵墙）→ 覆盖面封顶 1
- 根入口超出行/词预算（大而全总览，即使不含教程与历史）→ 覆盖面封顶 1
- 根入口没有成文的字数预算或维护触发条件 → 覆盖面封顶 2
- 根入口没有字数上限门禁 → 约束力封顶 2

**常见伪证**："我们有 `AGENTS.md`" —— 有文件不等于有路由。文件里如果没有指出去的链接，它不是入口链，是一堵墙。

**走形症状**：把根入口写成一份完整手册；或者到处放子树入口，让每个目录都要重新学一套。

**例证**（可选核对）：DSH 的根 `AGENTS.md` 只放常驻规则、布局与命令，每条规则 1–3 行并立刻给出链接；`CLAUDE.md` 是 `AGENTS.md` 的符号链接，四个目录各一处；根文件有字数上限（≤1,950 词），由 `verify-doc-budgets` 执行。

#### A2 归属 · One home per fact

**填的缺口**：G1 G2 G3

**一句话**：每类事实住在**负责它的那一层**，其它地方只放链接、不复制。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 随便挑 5 条规则，掐表找它的唯一 home | 能不能在 10 秒内指出来；home 里有没有写清"不该从这里取得什么"（禁放什么） |
| P2 | 对每条规则，全局搜它的关键句 | 是不是在第二个地方又写了一遍 |
| P3 | 找一个"改了 A 必须同时改 B"的例子，并看派生内容 | 这种耦合是否存在；有没有机制保证两边同步；派生内容有没有 freshness 门禁（源头变了、派生没跟上会红吗） |
| P4 | 检查当前事实与决策理由是否分家 | 现状文档里有没有夹着大段"为什么当初…"；决策记录里有没有被当成当前接口说明 |
| P5 | 找负知识：有没有记录"我们为什么不走某条路" | 被否决的方案，新参与者还会不会再提一遍 |

**覆盖面**：0 没有归属概念 / 1 部分事实有家 / 2 每类事实有明确 owner 且写了"不该从这里取得什么" / 3 且有维护触发条件与同步门禁

**约束力**：0 靠口传 / 1 写在 prose 里 / 2 有链接/一致性检查（复制件不一致会红）/ 3 且有生成物 freshness 门禁（源头变了派生没跟上就红）

**封顶规则**
- 任何一条规则指不出唯一 home → 覆盖面封顶 1
- 存在同一事实的两份**可写**拷贝（非生成物） → 覆盖面封顶 1
- 有事实类别没写出"不该从这里取得什么" → 覆盖面封顶 1
- 找不到任何负知识记录（被否的方案、已知限制）→ 覆盖面封顶 2
- 存在"改了 A 必须同时改 B"的耦合却没有同步机制 → 覆盖面封顶 2、约束力封顶 1
- 派生内容没有 freshness 门禁（源头变了派生不跟着变也不会红）→ 约束力封顶 2

**常见伪证**："我们的文档很全" —— 全不等于有家。两份都全，就是两个家。

**走形症状**：owner 表写了，正文却在每一处全文复制。补救方向是**把 home 补全**，不是允许复制。

**例证**（可选核对）：DSH 的文档分层表每行同时写"放什么"和"禁放什么"，例如常驻规则的 home 明确标注"不含详细教程、历史故事"；决策理由单独进 `.agents/notes/`，README 只写 now。

#### A3 决策记录 · Decision records

**填的缺口**：G3 为什么这样设计

**一句话**：存"为什么"而不是"是什么"、存取舍而不是实现，并且能跟着决定一起演进的知识载体。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找 3 个"当初有明显别的选择"的地方，看有没有记录 | 记了 / 没记 / 记了但只有结论没有备选；再数最近 10 条记录里有几条对应机械性改动（无真实备选） |
| P2 | 打开一条记录读一遍，并看一次反转 | 能不能回答"为什么这样决定、什么方案输了、后果是什么"；反转时旧记录的独有内容（理由、备选、后果、验证缺口）有没有先被吸收进新记录 |
| P3 | 状态怎么区分；过时记录最后被放到哪 | 现行 / 已否决 / 已过时三种状态是否一眼可分；有没有成文的归档规则与归档位置（还是过时记录留在原地、无处可去） |
| P4 | 有没有"过时的理由冒充现行" | 被取代的记录是否还挂在权威位置 |
| P5 | 被否决的方案还会不会被重提 | 问一个不了解历史的人（或新开一个 agent 会话）会不会想到那条路 |

**覆盖面**：0 没有 / 1 零散存在，没有判据 / 2 有明确判据（存在真实备选与持久取舍才写）与状态区分 / 3 且有取代纪律与归档规则

**约束力**：0 靠口传 / 1 只靠自觉 / 2 有模板/结构检查 / 3 且有取代前的完整性检查（旧记录独有内容必须先被吸收）

**封顶规则**
- 记录里没有"备选与为什么不行" → 覆盖面封顶 1（那不是决策记录，是变更说明）
- 存在被取代的记录仍被当作现行权威引用 → 覆盖面封顶 1
- 为机械性改动批量建档（最近 10 条记录里过半没有真实备选）→ 覆盖面封顶 1（记录通胀会让真记录一起被无视）
- 现行 / 已否决 / 已过时三种状态不可分 → 覆盖面封顶 1
- 没有任何归档规则（过时记录仍留在权威位置之外无处可去）→ 覆盖面封顶 2
- 取代时没有先吸收旧记录的独有内容（没有取代前的完整性检查）→ 约束力封顶 2

**常见伪证**：数量。**一段"为什么不"的记忆，只在它仍能阻止一个可信的错误时才有价值。** 记录数不是指标。

**走形症状**：两个方向都会坏——没有备选的修补硬写记录（机械建档，很快没人再读），以及有真实取舍的变更不写（知识随人走）。

**例证**（可选核对）：DSH 的决策记录强制四节（问题 / 决定 / 备选 / 后果），验证与遗留是可选节；备选必须真实存在过、不得编造；生命周期由目录承载（`proposed` / `implemented` / `rejected` / 归档目录），归档件保留 `Status: implemented` 并加一行 `Archived:`，归档后不再是当前权威。

#### A4 分类学 · Repository taxonomy

**填的缺口**：G2 系统由什么组成

**一句话**：任何一个"这东西该放哪、谁维护它、能不能手改"的问题，都有命名的 owner 或机器门禁。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 列顶层目录，为每个写一句"它拥有什么" | 写得出来吗？有两个目录职责重叠吗 |
| P2 | 对每个顶层区域，指出它的规则 owner | 有没有一个文件说清这个区域的规矩 |
| P3 | 找生成物（catalog、类型桩、快照、投影站点） | 能不能手改；有没有 freshness 检查；有没有人真的手改过（`git log` 看这些路径） |
| P4 | 找测试期望输出的存放规则 | 是"跟被证明的对象住一起"还是"全堆在一个大目录" |
| P5 | 找第三方/vendored 代码 | 有没有本地修改日志；上游版本钉在哪 |

**覆盖面**：0 没有分类概念 / 1 有一些约定但不成文 / 2 每个区域有 owner、有"能不能手改"的说明 / 3 且按内容维护形态分类（手写 / 生成 / 录制 / 投影），每类有机器边界

**约束力**：0 靠口传 / 1 写在 prose 里 / 2 有生成物 freshness 门禁或结构检查 / 3 且有"手改生成物被拒绝"的直接拦截

**封顶规则**
- 两个顶层目录的职责说不清边界 → 覆盖面封顶 1
- 存在生成物被手改而没有任何检查发现 → 覆盖面封顶 2、约束力封顶 1
- 测试期望输出没有存放规则（各人放各处）→ 覆盖面封顶 2
- 有顶层区域指不出规则 owner → 覆盖面封顶 1
- 存在生成物却没有任何 freshness 门禁或结构检查 → 约束力封顶 1

**常见伪证**："我们的目录结构很清晰" —— 清晰是给作者的。检验法是让一个外部 agent 判断"新增一个 X 该放哪"，看它会不会猜错。

**走形症状**：大型仓库最常见的漂移不是代码错误，是**东西放错了地方**——同一事实的第二份手写清单、被手改的生成物、期望输出堆错目录。

**例证**（可选核对）：DSH 的根入口按顶层区域列出每个区域拥有什么；文档分层表每行同时写"放什么"和"不放什么"两列；生成类内容由源码再生成并有 freshness 门禁，手改生成物被拒绝。

### B 组 · 变更路径

#### B1 意图入口 · Work intake

**填的缺口**：G7 交付怎样算完整

**一句话**：一个任务从"有人说要做点什么"变成"一份写得清验收条件的可开工描述"的路径。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找最近 5 个工作项的原始描述 | 能不能从中读出"外部可观察结果 + 如何观察" |
| P2 | 找一个描述最差的工作项，看它后来怎么开工的 | 靠提问补齐 / 靠猜 / 靠口头约定；"验收条件缺失"的工作项有没有被系统明确拦下 |
| P3 | 看工作项与提交的关联 | 提交或 PR 能不能回溯到它服务的意图 |
| P4 | 看小改动走什么路径 | 是否所有事都必须走完整仪式（过度流程 = 会被绕过） |
| P5 | 看"不做"的决定记在哪 | 被否的需求会不会被反复重提 |

**覆盖面**：0 没有入口，任务靠口头分派 / 1 有模板但没人按它写 / 2 每项有可观察的验收条件，且与提交可关联 / 3 且区分大小改动，小改动有轻量路径

**约束力**：0 靠口传 / 1 模板只是模板 / 2 有检查（缺少关联会红） / 3 且"验收条件缺失"会被明确拦下

**封顶规则**
- 最近 5 个工作项里有任何一项写不出"如何观察" → 覆盖面封顶 1
- 所有改动都必须走完整仪式，没有轻量路径 → 覆盖面封顶 2（流程会被绕过，绕过就全失效）
- 提交无法回溯到意图 → 覆盖面封顶 1
- "验收条件缺失"的工作项不会被拦下 → 约束力封顶 2

**常见伪证**："我们有 issue 模板" —— 模板存在不等于被使用，更不等于验收条件是可观察的。

**走形症状**：两个方向——意图完全不落盘（做完没人知道为什么做），以及所有改动都被同一个重仪式压住（小的绕过去，大的靠人情）。

#### B2 正确路径 · Paved road

**填的缺口**：G4 改动落在哪里

**一句话**：仓库为常见变更提供首选入口、生产范本和升级条件，让"做对"成为阻力最小的路径。

*适用性：仓库存在代码或配置变更路径时适用；纯文档站（没有代码变更路径）标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找一张"目标 → 机制"的归属表 | 有没有；右列是不是**能直接执行的动作**（改哪个文件、调哪个注册点） |
| P2 | 拿一个真实需求，只看这张表 | 能不能答出"改哪里"，不翻代码 |
| P3 | 找一个"本可用配置解决、却改了核心"的例子 | 有没有升级条件在拦 |
| P4 | 找常见任务的操作范本（cookbook / 示例） | 有没有；是不是可复制可运行的 |
| P5 | 看有没有人自己发明过新接法 | `git log` 找旁路式实现；有没有检查拦它 |

**覆盖面**：0 没有 / 1 有架构文档但只说"找相关模块" / 2 有归属表 + 范本 + 升级条件 / 3 且按参与半径分层（配置 → 扩展点 → 完整能力 → 核心），每层有升级判据

**约束力**：0 靠口传 / 1 文档只是文档 / 2 有检查（绕过入口会被结构检查发现） / 3 且有"必须走入口"的强制机制（例如只允许通过注册 API 接入）

**封顶规则**
- 归属表右列是"参考架构文档"这类二级指引 → 覆盖面封顶 1
- 属于常见变更类型却没有任何范本 → 覆盖面封顶 1
- 存在"能配置却改了核心"的近期实例且无人拦下 → 约束力封顶 1
- 归属表没有升级条件（什么情况该从配置升级到改核心没有判据）→ 覆盖面封顶 1

**常见伪证**："我们有架构文档" —— 架构文档解释系统**是什么**，不回答**我该改哪里**。这是两件事。

**走形症状**：归属表变成审批流程（申请→批准→实施），偏离了"降低判断成本"的本意；或者参与分层变成等级制（"高级的改核心"）。

#### B3 流程固化 · Procedural memory

**填的缺口**：G5 这类任务按什么流程做

**一句话**：反复出现、需要上下文判断的任务流程，被固化成带触发条件、步骤、停止条件和验证方式的短文档。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找出同一类任务第三次出现时发生了什么 | 是固化成了流程，还是每次现场发明 |
| P2 | 打开一份流程文档 | 触发条件写清楚了吗；每一步有可执行命令或可打开的文件吗；判断标准是规则还是形容词 |
| P3 | 看它有没有越界 | 是否把可机械判断的部分也写成了 prose（那部分应该在检查里） |
| P4 | 看它有没有自我声明边界 | 是否说明"这是指导，不是清单" |
| P5 | 看发现机制 | 模型/人能不能在**不读完**的情况下判断该不该读它（有没有摘要层） |

**覆盖面**：0 没有 / 1 有一些 wiki 页但没人用 / 2 有按任务组织的流程文档，带触发条件与步骤 / 3 且有摘要层（只看标题+适用条件决定读不读）与维护触发条件

**约束力**：0 靠口传 / 1 流程只是建议且无人遵守 / 2 且流程里指到的命令真实存在、可跑 / 3 且可机械化的部分已经下沉到检查，流程本身只管判断

**封顶规则**
- 流程文档里出现"做好验证"这类没有可执行内容的句子 → 覆盖面封顶 1
- 流程文档写成"必须依次执行 N 步"且没有判断标准 → 覆盖面封顶 2（清单病：环境一变就卡死在错的步骤上）
- 没有摘要层，只能整篇读 → 覆盖面封顶 2
- 流程文档没有写触发条件（不知道什么情况该读它）→ 覆盖面封顶 1
- 流程文档里指到的命令不存在或跑不通 → 约束力封顶 1
- 可机械判断的部分仍留在流程 prose 里、没有下沉到检查 → 约束力封顶 2

**常见伪证**："我们有详细的文档" —— 详细到把判断收走，就是清单病；详细到全是散文，就等于没写。

**走形症状**：散文病（"推送前做好本地验证"——执行者还得自己猜步骤）与清单病（把判断固化成仪式）。正确形态是**步骤 + 每步的判断标准**，判断留给执行者。

---

#### B4 执行与授权链 · Execution and authorization

**填的缺口**：G1 必须遵守什么（安全与权限铁律）

**一句话**：一个自动化动作从发起到落定，走的是同一条管线；策略判在动作之前，结果只有一条出口。

*适用性：仓库里只要有自动化代理在跑（CI 机器人、代码生成器、任何让 agent 直接改仓库的流程），这一维就适用。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找"谁允许这个动作发生"的判定点 | 有几处？加一条新规则要改几个文件？ |
| P2 | 看动作有没有在执行前被记录 | 失败的调用在不在记录里 |
| P3 | 看结果怎么回到模型/人 | 有没有统一归一化；会不会出现"部分成功""未知状态" |
| P4 | 找权限边界与"看得见"的边界 | 这两者是不是被混为一谈 |
| P5 | 看危险动作有没有独立的授权步骤 | 还是靠"模型不会那么做" |

**覆盖面**：0 没有 / 1 检查散在每个工具/脚本自己身上 / 2 有统一的执行前判定层 + 单一结果出口 / 3 且有独立授权步骤与审计记录

**约束力**：0 靠自觉 / 1 写在 prose 里 / 2 权限判定在代码里强制 / 3 且越权必然失败并有记录

**封顶规则**
- 加一条策略规则需要改多个文件（策略散在各处）→ 覆盖面封顶 1、约束力封顶 1
- 存在"部分成功""未知状态"被直接喂给模型或人 → 覆盖面封顶 1、约束力封顶 1
- 把"可查询/可试验"当成"已授权" → 约束力封顶 1
- 危险动作没有独立的授权步骤（靠"模型不会那么做"）→ 覆盖面封顶 2
- 动作没有执行前的审计记录（失败的调用查不到）→ 覆盖面封顶 2

**常见伪证**："我们的工具自己会检查权限" —— 那是策略散在 N 处，改一次要动 N 个文件，而且总有一个忘了改。

**走形症状**：在工具体内部做权限检查（绕过统一判定层）；把未归一化的中间态直接塞回上下文。

**例证**（可选核对）：DSH 的工具执行管线把策略全部放在工具体之外（`pre-execute` 判定权限、审批走独立服务、结果在注册表外层归一化，异常一律变成 `isError`），并且多处明确标注边界——例如核心作用域原语写明"不是沙箱或权限边界"、包加载检查写明"不是防范恶意包代码的沙箱"。

---

### C 组 · 证据与交付

#### C1 反馈分层 · Feedback layers

**填的缺口**：G6 怎么算做对

**一句话**：不同类型的问题由不同层的检查负责，且每一层只拥有它能观察到的性质。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 列出仓库所有的检查，按"它最早能在什么时候发现问题"排序 | 编译/加载期、局部行为、组装行为、运行时关系、语义判断，各有没有 |
| P2 | 对每一层，找它**不能**证明什么 | 仓库里有没有说清层与层的边界 |
| P3 | 看本地反馈延迟 | 改一行到拿到相关结论要多久；要等全套吗 |
| P4 | 看本地与远端的分工 | hooks 跑什么、CI 跑什么；hooks 是不是"小号 CI" |
| P5 | 看错误信息的质量 | 失败时说得出「失败对象 + 违反规则 + 修正入口」吗 |

**覆盖面**：0 只有"跑得起来" / 1 有测试但只有一层 / 2 至少四层齐备且各有分工说明 / 3 且每层有明确的"不能单独证明"清单

**约束力**：0 靠自觉 / 1 有检查但可在本地跳过且常被跳过 / 2 检查在流水线里强制 / 3 且本地按改动范围选检查（不全跑）同时远端跑穷举

**封顶规则**
- 绿色的一层被当作其它层也绿（例如用覆盖率证明产品可用）→ 覆盖面封顶 2
- 本地反馈需要等全套跑完 → 约束力封顶 2
- 失败信息只说"失败"，说不出违反哪条规则、去哪修 → 约束力封顶 2
- 检查层不足四层（编译/加载期、局部行为、组装行为、运行时关系、语义判断有缺）→ 覆盖面封顶 1

**常见伪证**："我们 CI 全绿" —— 全绿只覆盖检查碰巧碰到的地方，与"声称的行为都有证据"是两件事。

**走形症状**：层与层互相冒充——覆盖率绿了就当产品工作，快照绿了就当接口合理，评审去手工重复机器已经精确拒绝的格式问题。

**例证**（可选核对）：DSH 的测试分层文档逐层写明它**不能单独证明**什么（例如"覆盖率只证明行被执行，不证明功能可用"）；本地按改动面选最小证据，CI 拥有穷举覆盖与平台矩阵；Git 钩子明文不跑测试、快照、构建这类随改动面变化的检查。

---

#### C2 负例控制 · Negative control

**填的缺口**：G6 怎么算做对

**一句话**：每一个检查都被证明过**会失败**。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 随机挑 3 个现有检查 | 说得出它最近一次为红是什么回归吗；那次验证有没有留下记录（文件 / 注释 / CI 记录），还是只靠人口头记得 |
| P2 | 挑一个检查，故意制造它该抓的违规 | 看它红不红，然后还原 |
| P3 | 看仓库有没有"新检查必须验证"的成文要求 | 有要求 vs 有实践 |
| P4 | 看端到端验证是"验证世界"还是"验证自述" | 测试是重新读文件/跑命令/看状态，还是相信执行者的声称 |
| P5 | 看有没有"永远为绿"的检查 | 长期未变更、从未失败过的检查 |

**覆盖面**：0 没有这个概念 / 1 有人偶尔做 / 2 有明确要求（新检查必须做一次负例控制）/ 3 且留了记录，可追溯每次检查的验证

**约束力**：0 靠自觉 / 1 写在 prose 里 / 2 有流程要求且被抽查 / 3 且"没有负例控制的检查"会被明确拒绝合入

**封顶规则**
- 抽检的 3 个检查里，没有一个说得出最近一次为红的原因 → 本维约束力封顶 1
- 存在长期未失败过的检查且无人核查 → 约束力封顶 1
- 负例控制只做了"引入违规看它红"，没有验证"还原后变绿" → 约束力封顶 2
- 没有"新检查必须做一次负例控制"的成文要求 → 覆盖面封顶 1
- 负例控制没有留下可追溯的记录 → 覆盖面封顶 2

**常见伪证**："我们的检查很全" —— 检查全绿但没人信，是这类系统最贵的走形。

**走形症状**：绿灯数目成了 KPI；负例控制没人做过；检查逐渐变成仪式，然后有人开始绕过它。

**这一维为什么单列**：它是整份评分卡里**唯一一个检验"其它维度是不是真的"的维度**。C1 问"有没有检查"，C2 问"检查算不算数"。一个 E2 的检查和一个 E3 的检查，在通过率上完全一样，在保护效果上差别是全部。

---

#### C3 闭环完整性 · Delivery completeness

**填的缺口**：G7 交付怎样算完整

**一句话**：实现、当前文档、回归证据在**同一次交付**里一起走，缺口如实标注。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 拿最近 5 笔变更，看每一笔带了什么；其中最小的那笔是什么性质 | 代码 / 文档 / 测试 / 决策记录，各带了几笔；机械性改动是走轻量路径还是也必须走完整仪式 |
| P2 | 找"代码合并了、文档还没跟上"的情况 | `git log` 看文档滞后代码多久 |
| P3 | 看交付说明与证据是否一一对应 | 声称跑过的检查，CI 里真的有吗 |
| P4 | 看缺口怎么处理 | 没有证据的声称是"如实标注为缺口"还是"用绿灯盖过去" |
| P5 | 看回滚的粒度 | 出错时是整个切片原样退回，还是打补丁式热修 |

**覆盖面**：0 代码合并即完成 / 1 有时带文档和测试 / 2 常见变更都同批交付实现+文档+证据 / 3 且区分大小改动（机械性改动有轻量豁免），例外有明确理由

**约束力**：0 靠自觉 / 1 写在 prose 里 / 2 有检查（缺文档/缺测试会红） / 3 且"声称与证据不符"会被明确拦下

**封顶规则**
- 最近 5 笔变更里出现"先合并后补文档/补测试" → 覆盖面封顶 1
- 交付说明里出现无法对应的验证声称 → 约束力封顶 1
- 没有轻量豁免路径（所有改动一律全套）→ 覆盖面封顶 2
- 交付例外（缺文档/缺测试/缺证据）没有写明理由 → 覆盖面封顶 2

**常见伪证**："我们要求每个 PR 带测试" —— 要求是一回事，最近 5 笔里带了几笔是另一回事。**这一维只能用切片查，不能用文档查。**

**走形症状**：闭环断在两处——"实现 + 文档 + 证据同批交付"退化成"先合并后补"，"缺口如实标注"退化成"绿灯崇拜"。

**自测法**：拿最近一笔变更问——README 或文档声称的行为里，有几条**没有**任何测试钉住？说不出，就是缺口没被管理。

---

#### C4 评审与批准 · Review and approval

**填的缺口**：G6 G7

**一句话**：谁在什么条件下判断"这笔变更可以进"，以及这个判断为什么可信。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 看最近 10 笔变更的批准过程 | 谁批准的？有实质评论还是只点了通过 |
| P2 | 找批准的成文条件 | 有没有明确条件，还是"有人 approve 就行" |
| P3 | 看评审意见的质量 | 有没有指出过真实问题；还是清一色"LGTM" |
| P4 | 看评审与机器的分工 | 评审有没有在手工重复机器已经精确拒绝的问题 |
| P5 | 看谁能批准、需要几个人 | 条件是否与改动风险挂钩 |

**覆盖面**：0 没有评审（直接推主干）/ 1 有评审但无成文条件 / 2 有成文条件且与风险挂钩 / 3 且评审范围（该看什么、不该重复什么）有明确规定

**约束力**：0 靠自觉 / 1 靠人际约定 / 2 平台强制（不能自批/需要 N 人） / 3 且条件（加权、路径归属）被机器计算并强制执行

**封顶规则**
- 最近 10 笔里，评审评论全部是"LGTM"之类的空话 → 覆盖面封顶 1
- 评审在重复机器已经精确拒绝的格式问题 → 覆盖面封顶 2
- 批准条件与改动风险无关（改核心和改错别字走同一套）→ 覆盖面封顶 1
- 有评审但没有成文的批准条件（"有人 approve 就行"）→ 覆盖面封顶 1
- 批准不靠平台强制（可自批、人数不限）→ 约束力封顶 1

**常见伪证**："我们有严格的双人评审" —— 数一数最近 10 笔的评论条数和内容，比任何制度描述都准。

**走形症状**：评审变成橡皮图章（有流程无判断），或者评审变成格式警察（人力被消耗在机器已经管住的事上）。

### D 组 · 状态与上下文

#### D1 静与动 · Static and dynamic

**填的缺口**：G2 系统由什么组成

**一句话**：把仓库里的事实按"变得有多快 / 谁能改 / 丢了多疼"分成层，并且**每层只被上一层或显式操作修改**。

*适用性：只要仓库里跑着会跨轮存活的东西（agent 会话、长任务、缓存、派生索引），这一维就适用。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 列出仓库里所有"会变的事实"，为每一个归类 | 规则（跨版本不变）/ 配置（部署时定）/ 事实源（只追加）/ 派生（每轮重算） |
| P2 | 对每个事实源，问"它丢了大不大" | 丢了不心疼的，它是派生，不是事实源 |
| P3 | 找同一个数据有没有两个**可写**来源 | 有 → 两处存真，早晚分叉 |
| P4 | 试着重放 | 重开进程/新会话，能不能还原"当时到底发生了什么" |
| P5 | 看动态里产生的持久决定去哪了 | 会话里的结论有没有升级回静态层（文档/记录） |

**覆盖面**：0 没有分层概念 / 1 部分数据能说清属于哪层 / 2 四层齐备且各有明确的承载者与修改权限 / 3 且有"模型看到的内容必须可重建"这类不变量

**约束力**：0 靠自觉 / 1 写在 prose 里 / 2 派生物由源头生成（不能手改）/ 3 且有运行时检查断言"可见即可重建"

**封顶规则**
- 存在同一事实的两个可写来源 → 覆盖面封顶 1、约束力封顶 1
- 能进入模型请求的内容无法从记录重建 → 覆盖面封顶 2、约束力封顶 1
- 会话里产生的持久决定没有任何回写路径 → 覆盖面封顶 2
- 有"会变的事实"归不到四层里的任何一层（承载者不明）→ 覆盖面封顶 1

**常见伪证**："我们有数据库，状态当然是持久的" —— 持久不等于**可重建**。能存下来，和能回答"当时它看到了什么"，是两件事。

**走形症状**：把派生当事实源存（缓存成了第二真相）；动态层走私（上下文组装、工具结果绕过记录直接进模型）；不回写（同一个问题下一轮重新发明一遍）。

---

#### D2 披露与隔离 · Progressive disclosure and isolation

**填的缺口**：G2 G5

**一句话**：知识按需加载，而不是一次全塞；超出预算时有回收手段；子任务拿到的是它需要的那部分，不是全部。

*适用性：有内容被注入模型请求、且注入量随规则或文档增长时适用；没有上下文预算压力的小仓库标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 看常驻注入的内容有多大 | 有没有预算上限；超了会发生什么 |
| P2 | 看流程文档/规则怎么被发现 | 是全文注入，还是先给摘要、命中才加载全文 |
| P3 | 看重复内容有没有去重 | 同一份内容会不会被注入两次 |
| P4 | 看长任务超预算时怎么办 | 有回收/压缩吗；压缩时会不会把一个动作的调用和结果拆散 |
| P5 | 看子任务/子代理的输入面 | 是继承全部上下文，还是只给需要的那部分 |

**覆盖面**：0 全量注入，没有预算概念 / 1 有"文档要写短"的纪律但运行时无约束 / 2 有按需加载 + 注入预算 / 3 且有回收与隔离（超预算压缩、子任务不带父上下文）

**约束力**：0 靠自觉 / 1 只靠写作纪律 / 2 有硬预算（超了会被截断并告知）/ 3 且回收过程本身有约束（不拆散调用与结果、压缩后可重建）

**封顶规则**
- 常驻内容没有上限 → 覆盖面封顶 1
- 有预算但超预算时静默丢弃 → 约束力封顶 1（必须能看到"丢了什么"）
- 压缩会拆散一个动作的调用与结果 → 约束力封顶 2
- 规则/流程只能全文注入（没有先摘要、命中才加载全文）→ 覆盖面封顶 1
- 子任务/子代理继承父的全部上下文（没有隔离）→ 覆盖面封顶 2

**常见伪证**："我们的文档写得很短" —— 写短只解决供给，不解决"这一轮该加载哪一份"。那是运行时的事。

**走形症状**：只做一层就当完成（只把文档写短，或只加压缩）；或者有预算但超限时静默丢弃，使用者以为该加载的都加载了。

---

#### D3 运行时查询 · Inspectability

**填的缺口**：G2 系统由什么组成

**一句话**：能用一条命令问出"这台机器/这个进程实际生效的是什么"，而不是读源码猜。

*适用性：存在多层配置叠加、或声明面大到需要用命令查询时适用；单层配置的小仓库标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 问"最终生效的配置是什么" | 有没有一条命令能答；还是要读源码/读多个叠加层自己拼 |
| P2 | 问"仓库声明了哪些接口/注册项" | 有没有生成的清单；还是手工维护（会漂） |
| P3 | 问"当前进程里实际有什么" | 有没有只读查询；还是只能打断点 |
| P4 | 看静态清单会不会过期 | 有没有 freshness 检查 |
| P5 | 看这几者的区别有没有说清、有没有被混用 | "声明了什么" vs "实际跑着什么"，混了吗；文档有没有说清"可查询 ≠ 有授权 ≠ 可回滚"；再找一处只读查询与一处权限判定，看只读是否被当作放行 |

**覆盖面**：0 全靠读源码 / 1 只有一条 dump 命令 / 2 有 dump + 生成的声明面清单 / 3 且有只读的活运行时查询

**约束力**：0 靠自觉 / 1 命令存在但没人知道 / 2 生成清单有 freshness 门禁 / 3 且完整性有守卫（新增的东西不可能静默无文档）

**封顶规则**
- 没有任何一条命令能回答"实际生效的是什么" → 覆盖面封顶 1
- 手工维护的接口清单且无 freshness 检查 → 覆盖面封顶 1、约束力封顶 1
- 把"可查询"当成"有授权"或"可回滚" → 约束力封顶 1
- 没有只读的活运行时查询（只能打断点或读静态清单）→ 覆盖面封顶 2

**常见伪证**："源码就是文档" —— 源码说的是**可能是什么**，回答不了**现在是什么**。多层配置叠加之后尤其如此。

**走形症状**：用"源码就是文档"跳过这一维；或者接口清单手工维护、还把它当权威（清单必然漂）；或者把"可查询"当成"有授权/可回滚"。

### E 组 · 维护与发布

#### E1 防漂移 · Drift prevention

**填的缺口**：全部（元维度）

**一句话**：外置的知识会漂，所以给它配机器检查、配基线、配复核触发条件。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 数一数有多少份外置知识（文档、清单、索引、快照、决策记录） | 每份谁维护？漂了谁发现 |
| P2 | 找结构检查脚本 | 有没有；检查什么（编码、链接、锚点、预算、配对）；它有没有被证明会失败（最近一次为红是什么回归） |
| P3 | 看基线怎么钉 | 文档有没有写"结论以哪个版本为准"；有没有"以当前 checkout 为准"这类会悄悄滑走的表述 |
| P4 | 看数字类事实 | 预算、上限、个数——这类最容易漂的，有没有标注出处 |
| P5 | 看上游更新时的复核路径 | 有没有明确"上游哪些变化要触发重审" |

**覆盖面**：0 没有 / 1 有零散的检查 / 2 有结构性检查脚本 + 明确的复核触发条件 / 3 且有基线钉定、预算表、归档策略，形成一套维护制度

**约束力**：0 靠自觉 / 1 脚本存在但要人记得跑 / 2 检查接进了提交流程 / 3 且检查自己被负例控制过

**封顶规则**
- 存在"手工维护的第二份清单"且无 freshness 检查 → 覆盖面封顶 1
- 文档使用"以当前版本为准"这类相对表述 → 覆盖面封顶 2
- 结构检查脚本从未被证明会失败 → 约束力封顶 1
- 没有明确"上游哪些变化要触发重审"的复核触发条件 → 覆盖面封顶 1
- 预算、上限、个数这类数字事实没有标注出处 → 覆盖面封顶 2

**常见伪证**："我们的文档更新很及时" —— 及时靠人，防漂移靠机器。这两者不能互相替代。

**走形症状**：检查脚本写了一次再没跑过；规则改了引用没跟着改（漏一处漂一处）；文档用"以当前版本为准"这类相对表述，让基线悄悄滑走。

**这一维为什么是元维度**：它不管任何具体知识，管的是**前面十六维能不能长期不失效**。前面做得再好，没有 E1，六个月后会回到原点。

**例证**（可选核对）：DSH 的文档有逐文件字数上限并由门禁执行；生成的目录与源码有 diff 就红；决策记录有冻结归档纪律（归档后不再是当前权威）；历史引用一律用发布标签而不是裸 commit 哈希，并由门禁执行。

---

#### E2 发布与版本纪律 · Release and versioning

**填的缺口**：G7 交付怎样算完整

**一句话**：东西怎么出去、兼容承诺是什么、坏版本怎么退、老用户的数据怎么办。

*适用性：仓库向外部发布产物（包、镜像、服务、数据格式）时适用。不发布任何东西的仓库标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找一次真实发布 | 从"决定发"到"发出去"有几个步骤，有没有成文序列 |
| P2 | 找兼容承诺 | 哪些接口承诺稳定、哪些明确不稳定；有没有写清楚 |
| P3 | 看不可逆的产物（数据格式、已发布记录） | 变更时是就地改还是新增后继代 |
| P4 | 看坏版本怎么退 | 有回退路径吗；回退会不会破坏已发布的数据 |
| P5 | 看版本号与变更的关系 | 破坏性变更有没有被版本号或迁移说明标出 |

**覆盖面**：0 想发就发 / 1 有步骤但不成文 / 2 有成文发布序列 + 兼容承诺分级 / 3 且有不可逆产物的迁移纪律与回退路径

**约束力**：0 靠自觉 / 1 写在 prose 里 / 2 有检查（发布前置条件、格式版本号会红） / 3 且"移动/覆盖已提交世代"这类操作被直接拒绝

**封顶规则**
- 破坏性变更没有版本号或迁移说明 → 覆盖面封顶 2
- 已发布的数据/格式会被就地覆盖 → 覆盖面封顶 2、约束力封顶 1
- 稳定与不稳定的边界没有写明 → 覆盖面封顶 1
- 发布没有成文序列（每次现场拼步骤）→ 覆盖面封顶 1
- 坏版本没有回退路径 → 覆盖面封顶 2

**常见伪证**："我们遵循语义化版本" —— 版本号规则不告诉任何人**哪些接口真的承诺稳定**。那要单独写。

**走形症状**：把仪式当纪律（标签间距、RC 之间的提交数、发布 PR 的文件数），这些不防止任何具体事故；或者破坏性变更就地覆盖已发布的数据。

## 5 · 适用性裁剪

不是每种仓库都要评全部十七维。**不适用的维度记 `N/A`，不记 0 分**——把"不适用"打成 0 会让评分卡失真，让你去修一个根本不存在的问题。

### 按仓库形态裁剪

| 形态 | 必评 | 通常 N/A | 特别注意 |
|---|---|---|---|
| **库 / SDK**（被别人引用） | A 全组、B1 B2 B3、C 全组、D1、E1 E2 | B4、D2 D3 | E2 兼容承诺是核心；A2 归属要覆盖公开 API 与文档的一致 |
| **服务 / 后端** | A 全组、B 全组、C 全组、D 全组、E1 | E2（若内部服务，版本纪律可能极轻） | D1 静与动、D3 运行时查询权重高；B4 授权链必看 |
| **Monorepo** | 全部 | — | A4 分类学权重最高；E1 防漂移是成败关键；A2 要跨包查重 |
| **插件平台 / 框架** | 全部 | — | B2 正确路径是核心（"改哪里"必须有表可查）；B3 流程固化权重高 |
| **数据 / ML 仓库** | A 全组、B2 B3、C 全组、D1、E1 E2 | B4、D2 D3 | D1 的"事实源 vs 派生"要覆盖数据集与特征；E2 要覆盖数据 schema 版本 |
| **文档站 / 知识库** | A 全组、B1 B3、C1 C2 C3、E1 | B2 B4、D 全组、E2 | A1 入口链、A2 归属、E1 防漂移是**重点**（其余按"必评"列照做）；C 组查"链接与锚点是否有检查" |
| **单文件脚本 / 小工具** | A1 A2、C1 C2、E1 | 其余 | 上列五维已足够（C2 与 E1 对脚本最便宜也最有用）；不要为了评分卡去造机制 |
| **agent 产品 / 自带 agent 运行时** | 本文全部 | — | **另加**：[运行时 Harness 评估](./02-evaluate-runtime-harness.md) |

### 三条裁剪纪律

1. **标 N/A 要写理由**，一行即可（"本仓库不发布产物，E2 不适用"）。
2. **N/A 的维度不参与成熟度档判定**，分母按实际评估的维度数算。
3. **不确定是否适用时，先按适用处理**，评估过程中发现没有对应压力，再改标 N/A 并记录。

### 与运行时评估的形态口径不同

本表的"仓库形态"决定十七维里哪些要评；[02 的形态裁剪](./02-evaluate-runtime-harness.md#4--形态裁剪)那套（内部 / 产品 / 平台 / 单机实验 / 多入口）决定十一维里哪些要评。两者正交：一个仓库的形态是"agent 产品"时，两套各判一次。

## 7 · 评估者自己的验收

评估做完，先用这五条检验**评估本身**：

1. **每个扣分点都能指到具体证据。** 说不出"我在哪个文件、哪次提交、哪条命令上看到的"，这一条就不算扣分——回去补证据，或者撤销这条。
2. **换一个人复测，档位稳定。** 同一维度由另一个人（或另开一个无上下文的 agent 会话）走一遍，档位差不应超过 1。差 2 以上，说明探针写得不够客观。
3. **缺口清单里的每一条都能归到某一维。** 归不进去的，要么是新维度（记下来），要么根本不是开发 Harness 的问题（删掉）。
4. **表 4 不是空的。** 一次评估如果三张清单全是空的，八成是没认真找——除非这个仓库真的处于极高水平。
5. **每一次命中封顶，都说得出观察它的探针。** 封顶规则是按锚点阶梯逐条展开的（见[附录 B](#附录-b--封顶规则速查)），每条都由某一维的某个探针观察。说不出是哪条探针，说明这条封顶在本次评估里用不出来——把它当方法缺陷记下来，不要照记分。

### agent 做评估的三条额外纪律

- **区分"看不见"和"没有"。** 只有仓库可查时，很多事实看不到。看不到就标"证据受限"，不要断言缺失。
- **不要用仓库自己的文档当证据。** 文档是**被评估对象**的一部分，不是评估依据。文档说"我们有严格的测试要求"，这句话本身只能证明"文档里写了这句话"。
- **不允许跳过第三层的第 4 个动作**（故意制造一个违规，看检查红不红，然后还原）。它是唯一能区分 E2 与 E3 的手段，而且 agent 做这件事比人快得多。

| 3 改 owner 面 | 改了代码侧配置；**没有**改 README 里那份同名配置清单 | 能指出文件 |
| 4 最小匹配证据 | 有测试 `TestOrderTimeoutConfig`。红灯对照：注释掉配置读取改回硬编码 → 测试**仍然通过** | 能指出文件，但证据不成立 |
| 5 沉淀 | 无决策记录（这笔变更确实没有持久取舍，✓ 合理） | — |
| 6 只报告跑过的 | PR 描述写"已测试"，CI 确实跑了 `go test ./...` | 能指出文件 |

```
⑤ 「靠猜」的条目：README 里那份超时配置是不是权威（靠问人才知道是代码侧权威）
   「没证据」的条目：TestOrderTimeoutConfig 看起来在测配置，实际没有钉住配置读取路径
```

### 一句话结论

这个仓库的问题不是"没有文档"——它有 400 行 README 和 12 篇 docs——而是**文档与代码是两个可以各自漂移的家，且没有任何检查会发现它们漂了**。切片走查给出了确凿证据：一笔本该同时改两处的变更只改了一处，而那个看起来在保护的测试实际上什么都没保护。

→ 下一步去 [缺口到计划](./03-from-gaps-to-plan.md)，按 D1、A2、C3 三张处置卡排顺序。

## 附录 B · 封顶规则速查

封顶规则用于对抗"哪哪都给了高分"的评估通胀。任一条命中，对应轴的上限被压低，**不看其它证据**。

**上限的含义。** 每条规则给出的都是**上限**：它可能比锚点阶梯推导出的更严（这是有意的惩罚），但不会让一个已经违反某档定义的仓库拿到那一档——"命中却仍按更高档记"永远不成立。 封顶规则是按本维锚点阶梯**逐条**展开的：阶梯里凡有明确判据、且探针观察得到的条件，这里都有一条对应的上限；比阶梯更严的惩罚也写在同一份表里。

## 附录 C · 常见伪证清单

评估时最常听到的十句话，以及每一句为什么不能作为加分依据。

| 说法 | 为什么不算 |
|---|---|
| "我们有 `AGENTS.md`" | 有文件不等于有路由。看它有没有指出去的链接 |
| "我们的文档很全" | 全不等于有家。两份都全，就是两个家 |
| "我们遵循语义化版本" | 版本号规则不说明**哪些接口真的承诺稳定** |
| "源码就是文档" | 源码说的是可能是什么，回答不了现在是什么 |
| "我们 CI 全绿" | 全绿只覆盖检查碰巧碰到的地方，与"声称的行为都有证据"无关 |
| "我们的检查很全" | 检查全绿但没人信，是这类系统最贵的走形。用 C2 抽检 |
| "我们有严格的双人评审" | 数最近 10 笔的评论条数与内容，比制度描述准 |
| "我们要求每个 PR 带测试" | 要求是一回事，最近 5 笔里带了几笔是另一回事 |
| "我们的工具自己会检查权限" | 那是策略散在 N 处，改一次要动 N 个文件 |
| "我们的文档更新很及时" | 及时靠人，防漂移靠机器。两者不能互相替代 |
