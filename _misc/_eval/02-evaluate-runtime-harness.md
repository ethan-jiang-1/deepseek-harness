# 评估任何 agent 产品的运行时 Harness

**这份文档是什么。** 一套评估方法，回答一个问题：*这个 agent 系统本身做对了吗——它的会话、循环、工具、扩展点和多入口，是不是一个能被信任、能被扩展、能被模仿的运行时？*

**它和开发 Harness 评估的分工。** [开发 Harness 评估](./01-evaluate-development-harness.md) 问"这个仓库对 agent 友好吗"（任何仓库都能评）；本文问"这个 agent 系统本身做对了吗"（**只有本身是 agent 产品、自带 agent 运行时的仓库才能评**）。两者互不替代：一个普通库可以开发 Harness 满分而本文完全不适用；一个早期的 agent 产品可以本文很好而开发 Harness 很糟。

**前置知识。** 无。术语在本页定义。**本文不举任何外部例子，也不含任何外部链接**——它只给判据。需要"成熟实现长什么样"的例证时，看 [01 的"例证（可选核对）"段落](./01-evaluate-development-harness.md)（钉版在 commit `46a7f68b0922371ce7144b668b90e377d8e799f4`）。

**配套文档。** [缺口到计划](./03-from-gaps-to-plan.md)（用本文的缺口清单排施工顺序）。

## 0 · 先做适用性判定

**在开始评估之前，先回答三个问题。任何一个答"否"，本文就不适用——整份作废，不是打 0 分。**

| # | 问题 | 答"否"意味着 |
|---|---|---|
| **Q1** | 这个仓库里跑着一个 agent 运行时吗？（模型 → 工具调用 → 结果回灌 → 再请求，这个循环由本仓库实现，而不是由外部框架提供） | 它可能是模型应用、插件、或纯提示词工程。本文不适用 |
| **Q2** | 这个运行时是**产品**还是**一次性脚本**？ | 一次性脚本不需要本文的任何一维。等它要被第二个人用、要被扩展、要长期活着时再来 |
| **Q3** | 有第三方或第二个团队要往它上面加东西吗？（插件、自有模型、自有工具、自有入口） | 没有扩展需求时，第 5、6 两维（能力 seam、扩展点）标 N/A——**不要为一个不存在的生态建架构** |

三个都答"是"，继续。只有 Q1 答"是"、Q2 答"部分是"，走[第 4 节](#4--形态裁剪)的"内部 harness"裁剪版。

> **为什么这一步要单独成节。** 运行时 harness 的评估维度里，有一半（格式世代、能力 seam、协议投影）只在系统被长期使用、被多方扩展时才有意义。把它们套到一个一次性脚本上，得到的是"处处不及格"，而正确的结论是"不需要"。

### 铁律（与开发 Harness 评估相同）

**只有当场做过的才算证据。** 一个维度给 2 分以上，必须能说出"我做了什么、看到了什么"。特别地，[第 2 节](#2--评估分三层)的五个活体实验**每一个都必须真的跑过**——运行时 harness 的文档与实际行为之间的差距，比开发 harness 更大，因为它的"实际行为"依赖配置、版本、宿主和时序。

## 1 · 什么是"运行时 Harness"

> **运行时 harness（runtime harness）**：把模型、工具、会话、扩展点和交互组合成一个可运行的 agent 的那套机制。它决定了：模型每一步看到什么、它的动作怎么被执行和授权、发生过的每一件事怎么被记录和重建、别人怎么往它上面加东西、以及同一套内核怎么从多个入口被使用。

它和**开发 harness** 的区别在于被评估的对象：

| | 开发 Harness | 运行时 Harness |
|---|---|---|
| 服务对象 | 在**这个仓库里干活的** coding agent | 运行在**这个产品里的** agent 及其用户 |
| 失败症状 | 读错、改错、交付不可信 | 模型看到的不等于发生过的；动作绕过授权；扩展要改核心；入口各自实现一套循环 |
| 评估方式 | 走一笔真实变更 | 跑一次真实会话 + 五个活体实验 |

### 运行时 harness 的四条核心张力

这四条张力决定了后面十一维为什么长这样：

1. **可靠性 vs 透明度。** 动作要能被执行（可靠），但"执行了什么、模型看到了什么"必须能被事后重建（透明）。**二者冲突时，透明度优先**——不能重建的系统没法排障，也就没法长期可靠。
2. **可扩展 vs 可理解。** 扩展点越多，新能力加得越快；但每个扩展点都是一份需要维护的合同。**只有真的有人要换的东西，才配成为扩展点。**
3. **能力 vs 授权。** "模型能看见这个工具"和"这个动作被允许"是两件独立的事。把它们混成一件，是这类系统最危险的设计错误。
4. **单入口简单 vs 多入口一致。** 只服务一个入口时什么都不用抽象；服务五个入口时，如果每个入口各自实现一遍循环，语义会在第五个入口处开始分叉。

### 一个反转（和开发 harness 那边同源）

运行时 harness 的质量**不来自模型更聪明**，来自两件事：**把"模型看到什么"变成可重建的事实**，以及**把"能不能做"变成独立于可见性的授权判定**。

所以评估时不要问"它的 agent 表现好不好"（那是模型和提示词的事），要问"**它的机制让'表现好'可复现、'表现坏'可诊断吗**"。

## 2 · 评估分三层

### 第一层 · 静态清点

按[第 3 节](#3--十一维评分卡)的十一维逐维走探针，每维记两轴的档位，并记**一个最痛的真实案例**。没有案例的扣分不算数。

### 第二层 · 五个活体实验

这一层是本文的核心工具。**五个实验都要真的跑**，每个实验只问一件事：*系统自己的机制拦住了/接住了吗？*

下文用 **X1–X5** 指代这五个实验。实验编号与维度名（E1 防漂移、E2 发布与版本纪律）、证据档（E0–E3）都无关，不要混读。

| # | 实验 | 怎么做 | 通过的标准 |
|---|---|---|---|
| **X1 回放** | 拿一个**真实发生过**的会话（不是构造的），只读它的持久记录 | 不问系统，直接看记录 | 能逐条重建"模型在第 N 步实际收到的请求"——system prompt 内容、可见工具清单、消息序列。**不是"大致能看出发生了什么"，是能重建出请求本身** |
| **X2 换后端** | 换掉一个可替换的后端（模型提供方、执行沙箱、文件系统、存储），只改配置 | 数一数改了几个文件 | **消费者代码一行不改**；改完功能照常；如果只能通过改代码来换，这一维不及格 |
| **X3 加能力** | 加一个模型可见的新能力（一个新工具），从零到能用 | 数一数改了几个文件、动了哪些层 | 走的是已声明的扩展点，**没有改循环本身**；新能力的 schema 自动进入模型请求；它的可见输入自动留下记录 |
| **X4 坏配置** | 故意把一个引用改错（指向不存在的插件/提供方/文件） | 启动 | **在离错误源头最近的地方大声失败**，并指出缺的是什么。**静默少一个能力 = 不及格** |
| **X5 取消与失败** | 发起一个长动作，中途取消；再制造一次工具内部错误 | 看两个出口 | 取消真的让它停；失败被归一化成**一个明确的错误结果**交给模型，而不是"部分成功"或"未知状态"；取消/失败本身留下记录 |

五个实验里，**X1 和 X3 的失败最贵**：X1 失败意味着这个系统在出问题时无法排障；X3 失败意味着每加一个能力都要动核心，扩展成本会随时间指数上升。

### 第三层 · 反证

四个动作，检验前面两层自己的可信度：

1. **抽一条不变量**：系统声称的某条不变量（"模型看到的一定被记录了""每个注册都会被清理"），**它会在什么时候失败**？找得到那条会触发失败的路径吗？找不到，它可能只是一句注释。
2. **抽一个接口的失败面**：挑一个公开接口，看它在**正常失败**时怎么表现（用户操作非法 vs 基础设施故障）。两者混在一起 = 调用方永远分不清"该重试"还是"该报 bug"。
3. **抽一个"故意不保证"**：成熟的运行时 harness 会**明说自己不保证什么**。找一份这样的清单。找不到，说明它把边界藏起来了——那是把未定义行为留给使用者。
4. **抽一次版本严格性**：拿一份用**更新版本**写的持久数据，喂给当前版本。**必须被拒绝，且提示是"版本过新，请升级"而不是"数据损坏"**。这两句话对用户的意义完全不同。

### 三层怎么合起来用

```
第一层 → 哪些机制缺
第二层 → 机制在实际运行里接得住吗（这一层无法靠读代码替代）
第三层 → 已有的保证是真的边界，还是自我描述
```

## 3 · 十一维评分卡

### 两轴怎么打

**轴一 · 覆盖面（Coverage）** —— 这一维有没有对应的机制

| 档 | 判据 |
|---|---|
| 0 | 没有。这个问题没有对应的机制，靠约定或运气 |
| 1 | 有但不完整。部分场景覆盖，边界情况不成立 |
| 2 | 有且成体系。常见情况都被覆盖，边界有明确处理 |
| 3 | 有且被主动维护。有 owner、有更新触发条件、有测试或检查钉住 |

**轴二 · 约束力（Enforcement）** —— 这一维靠什么成立

| 档 | 判据 |
|---|---|
| 0 | 只靠约定或注释 |
| 1 | 写在文档里，或只在某一条代码路径上成立 |
| 2 | 有测试或检查钉住，违反会红 |
| 3 | 有运行时断言或负例控制：**能被证明会失败**，且失败信息指出违反了什么 |

**读法。** 运行时 harness 最危险的状态是 `覆盖面 2 / 约束力 1`——机制看起来很全（有日志、有扩展点、有配置），但没有任何东西保证它成立。**约束力 3 才是"可以被信任"**。

### 总分与成熟度档

| 档 | 判据 | 一句话 |
|---|---|---|
| **M0 单次可跑** | 多数维度覆盖面 ≤ 1 | 能跑通一次，跑第二次靠运气 |
| **M1 有机制** | 多数覆盖面 = 2，多数约束力 ≤ 1 | 该有的都有了，但没人保证它们成立 |
| **M2 可重建** | 事实源（R2）、模型可见面（R7）、工具执行与授权（R9）三维约束力 ≥ 2 | 出问题能查到为什么 |
| **M3 可扩展可信任** | 至少三维约束力 = 3，且 R5 能力 seam 与 R10 治理 ≥ 2 | 别人能在上面加东西而不改核心 |

达标线：**至少 M2。** 只有要对外开放扩展时才需要 M3。这是"能不能用"的下限；**收工**用[缺口到计划的收工线](./03-from-gaps-to-plan.md#7--一轮打磨的循环与停止条件)（五个活体实验都跑过、对应被评维度的通过）。

**"多数"与计数的口径。** 本节所有"多数"指该档适用维度里的**超过一半**；"至少三个"这类计数也只在适用维度里数；标了 N/A 的维度不计入分母（见[第 4 节](#4--形态裁剪)）。

### R1 组合与启动 · Composition and boot

**一句话**：正在运行的那个系统是**从声明算出来的**，而不是某一份被手改的最终配置。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找"最终生效的配置" | 它是一份文件，还是多层叠加算出来的？有几层？顺序固定吗 |
| P2 | 找一条"dump 出最终配置"的命令 | 有吗；它和真正启动时用的是不是同一套算法 |
| P3 | 看叠加规则 | 同 id 的覆盖是整份替换还是深合并？规则写清楚了吗（没写清楚 = 使用者会踩坑） |
| P4 | 看坏输入 | 引用了不存在的组件、文件语法坏、文件在场但读不了——三种情况分别怎样 |
| P5 | 看启动失败 | 进程起不来时报什么？说得出缺哪个组件吗 |

**覆盖面**：0 一份手改的最终配置 / 1 有分层但规则不成文 / 2 分层 + 顺序 + 明确的叠加规则 + 一条 dump 命令 / 3 且有完整性守卫（引用了不存在的组件必然失败，不静默跳过）

**约束力**：0 靠约定 / 1 文档说明 / 2 有校验（坏配置会红）/ 3 且 dump 与启动共用同一算法，并有测试钉住它

**封顶规则**
- 引用了不存在的组件却静默跳过 → 覆盖面封顶 1、约束力封顶 1
- "文件在场但读不了"被当作"没有这个文件" → 约束力封顶 1
- dump 命令与启动路径是两套代码 → 约束力封顶 2（dump 会撒谎）
- 叠加规则不成文或含糊（使用者分不清深合并还是整份替换）→ 覆盖面封顶 1
- 没有 dump 最终配置的命令 → 覆盖面封顶 1

**常见伪证**："我们有配置文件" —— 配置文件不等于**算出来的**系统。手改的最终配置和叠加算出来的树，在排障时的价值差一个数量级。

**走形症状**：假设深合并而实际是整份替换，导致"我明明加了一个字段，怎么没了"；或者坏配置静默降级，用户以为某个能力开着，实际没装。

### R2 会话事实源 · Session as the single source of truth

**一句话**：发生过的一切有一条**只追加**的记录；模型当时看到什么、做了什么，都能从这条记录重建。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找持久记录 | 是什么形态（只追加日志 / 可变表 / 只有内存） |
| P2 | **做 X1 回放实验** | 只读记录，能重建第 N 步的完整请求吗 |
| P3 | 看派生 | 界面、统计、检索视图是从记录派生的，还是各自另存一份 |
| P4 | 看裁剪 | 上下文超预算时被压缩的内容，是**从记录里删掉**还是只在投影里遮蔽 |
| P5 | 看未知事件 | 读到不认识的事件类型时，默认是跳过还是拒绝重建 |

**覆盖面**：0 没有持久记录 / 1 有日志但模型可见输入不在其中 / 2 只追加记录 + 模型可见的一切都可重建 / 3 且有明确的不变量（新的模型可见输入必须留下记录）

**约束力**：0 靠约定 / 1 文档里写了"应该记录" / 2 有运行时断言检查请求能从记录重建 / 3 且断言会在违反时失败并指出是哪一步

**封顶规则**
- 存在任何进入模型请求但不进记录的内容 → 覆盖面封顶 1、约束力封顶 1
- 压缩会从记录里**删除**内容（而不只是从投影里遮蔽）→ 覆盖面封顶 1（记录不再是只追加的）
- 读到未知事件默认跳过 → 约束力封顶 1（未知事件可能改变其余记录怎么读）
- 记录是可原地改写的表（只追加不成立）→ 覆盖面封顶 1
- 记录重建的断言从不失败、或失败时指不出是哪一步 → 约束力封顶 2

**常见伪证**："我们记录了所有对话" —— 对话不等于请求。模型收到的请求里还有 system prompt、工具清单、动态上下文；这些如果不在记录里，回放出来的是**另一个请求**。

**走形症状**：把会话记录当界面状态存（界面一改，历史就变）；派生视图与记录两处存真，出问题时不知道信哪个。

### R3 格式世代与兼容 · Format generations

**一句话**：持久数据的格式有版本，版本规则是**只向前不向后**：老数据能迁移上来，用新版本写的数据在老版本上被明确拒绝，已提交的世代永不改写。

*适用性：持久数据要跨版本长期存活时评；一次性脚本不做。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找版本号 | 有几个？谁是权威（代码里的常量，还是发布记录，还是文件名） |
| P2 | **做第三层第 4 项** | 用更新版本写的数据喂给当前版本，看提示是什么 |
| P3 | 看迁移 | 老版本数据怎么读上来；迁移会不会**改写**原始文件 |
| P4 | 看未知事件 | 同版本内的未知事件怎么处理？跨版本边呢 |
| P5 | 看触发条件 | 什么情况下才该升版本？（是"任何变化"还是"结构变化"） |

**覆盖面**：0 没有版本概念 / 1 有版本号但没有规则 / 2 单向兼容规则明确（旧可迁、新拒绝）+ 已提交世代不可改写 / 3 且迁移链有独立规格与硬性前置校验

**约束力**：0 靠约定 / 1 文档说明 / 2 有检查（版本不匹配会红）/ 3 且三条路径被明确区分：版本过新、物理损坏、没有可用迁移——三种错误的提示不同

**封顶规则**
- "版本过新"被报成"数据损坏" → 约束力封顶 1（用户会被引向完全错误的处置）
- 迁移会就地改写或删除已提交的世代 → 覆盖面封顶 1、约束力封顶 1
- 版本号有多个来源（代码常量、包版本、文件名各说各话）→ 覆盖面封顶 2
- 更新版本写的数据不被拒绝（被接受或被静默降级）→ 覆盖面封顶 1、约束力封顶 1
- 迁移静默丢字段或跳过读不懂的内容 → 覆盖面封顶 1
- 迁移没有独立规格与前置校验（迁移逻辑散在读路径里）→ 覆盖面封顶 2

**常见伪证**："我们遵循语义化版本" —— 包的版本号和**持久数据的格式版本**是两件不同的事。前者变化频繁，后者只在结构变化时动。

**走形症状**：把"能解析不报错"当成兼容——静默跳过读不懂的内容，会让重建出的历史与真实发生过的历史不一致，这比直接报错危险得多。

### R4 循环与终结边界 · Loop and termination boundaries

**一句话**：一次工作从哪开始、到哪算结束，有**分层的、可判定的**边界；"空闲"不等于"完成"。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找终结层 | 有几层（一次模型请求 / 一个输入被处理完 / 一段连续活动 / 一个长期目标）？各自怎么判定 |
| P2 | 找终结原因 | 结束时记录的原因有几种？是封闭集合吗？**"被取消"和"完成"分得开吗** |
| P3 | **做 X5 取消实验** | 在声明的超时预算内真的停了吗？取消留下记录了吗 |
| P4 | 看恢复 | 进程重启后，正在进行的活动怎么处理？自动续跑还是需要人重新授权 |
| P5 | 看拒绝 | 一个输入在开始处理前就被拒绝，会留下"这次尝试"的痕迹吗 |

**覆盖面**：0 只有"跑完了/没跑完" / 1 有终结事件但原因不完整 / 2 分层边界 + 封闭的终结原因集合 / 3 且有恢复语义（重启后状态怎么重建、是否需要人工确认）

**约束力**：0 靠约定 / 1 文档说明 / 2 有断言（终结原因必须是封闭集合里的值）/ 3 且恢复路径有测试钉住（包括"重启后不自动做危险动作"）

**封顶规则**
- "空闲"被当作"完成" → 覆盖面封顶 1
- 终结原因不是封闭集合（可以随便塞字符串）→ 覆盖面封顶 1
- 重启后自动继续执行危险动作 → 约束力封顶 1
- 取消只是"不再等结果"（动作在后台继续跑）或取消不留记录 → 覆盖面封顶 1
- 重启后没有恢复语义（状态不重建、也不要求人工确认）→ 覆盖面封顶 2

**常见伪证**："我们的 agent 会一直跑到没有工具调用为止" —— 那只是这一次请求序列结束。一个需要多轮推进的任务，在"暂时没有下一步动作"和"已经完成"之间没有区分，用户就无法判断该不该接管。

**走形症状**：把取消做成"不再关心结果"（动作还在后台跑）；或者把重启当成无事发生（危险动作被自动接着做）。

### R5 能力 seam 与可替换性 · Capability seams

**一句话**：一项能力由**定义 + 实现 + 使用方**三个角色构成；换一个实现，使用方一行不改。

*适用性：第二个真实实现出现、或确实要换后端时评；只有一个实现的内部工具标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | **做 X2 换后端实验** | 数改了几个文件。消费者改了吗 |
| P2 | 数一数有哪些"可替换"的能力 | 每个有几个真实实现（不是测试替身）|
| P3 | 看单向依赖 | 使用方依赖的是**定义**还是某个具体实现 |
| P4 | 看"定义"里有什么 | 有没有混进某个使用方的专有名词（某个工具的参数字段名、某个界面的卡片类型）|
| P5 | 找"故意不是可替换点"的地方 | 有没有明确说明"这里不打算做成可替换的"及其理由 |

**覆盖面**：0 没有可替换概念，换实现要改消费者 / 1 有抽象但还没有第二个实现（零个或一个实现） / 2 **至少一项能力有两个真实可互换的实现，且消费者未改** / 3 且有多项能力达到这个状态，并有"故意不可替换"的明确清单

**约束力**：0 靠约定 / 1 文档说明 / 2 有检查（使用方不得直接依赖具体实现）/ 3 且有测试证明"换实现后真实组合仍通过"

**封顶规则**
- 所谓的"可替换点"只有唯一使用方和唯一实现（自产自销）→ 覆盖面封顶 1（**等于还没有市场**）
- 只有定义、没有任何实现 → 覆盖面封顶 1（形状还会被第一个实现改掉）
- 定义里混进了某个使用方的专有名词 → 覆盖面封顶 2
- 换实现需要改消费者代码（X2 实验里消费者被改动）→ 覆盖面封顶 1
- 没有"故意不可替换"的明确清单 → 覆盖面封顶 2

**常见伪证**："我们所有的东西都是插件" —— 插件化说的是**能不能加**，不是**能不能换**。加十个插件不需要 seam；换一个实现才需要。

**走形症状**：为只在一个地方用到的私有逻辑造一个"服务"；或者反过来，为一个真实存在的替换需求拒绝建 seam，导致每次换后端都要改一片代码。

**一个判据**：**一个公开方法只有一个内部调用者，那它其实是私有函数，不该抬成公开合同。**

### R6 扩展点与拦截 · Extension points and interception

**一句话**：加新行为有唯一的、已声明的去处；拦截点在管线里，不在每个实现里各写一份。

*适用性：有第二个人或第二个团队要往上面加东西时评；没有扩展需求时标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | **做 X3 加能力实验** | 数改了哪些文件、动了哪些层。**动核心了吗** |
| P2 | 找一张"新行为挂哪里"的表 | 有吗；右列是具体注册动作还是"参考某文档" |
| P3 | 看拦截点 | 有几类（只观察 / 可改写 / 可短路）？分得清吗 |
| P4 | 看每个拦截点的**边界** | 文档说了它**拦不住什么**吗 |
| P5 | 看注册的生命周期 | 一个注册在卸载时会撤销吗？谁负责 |

**覆盖面**：0 新行为靠改核心 / 1 有扩展点但没有归属表 / 2 有归属表 + 分类型的拦截点 + 明确的"拦不住什么" / 3 且注册的生命周期统一（谁注册谁负责撤销），并有升级条件的说明

**约束力**：0 靠约定 / 1 文档说明 / 2 有检查（绕过扩展点的结构会被发现）/ 3 且有机制强制走扩展点（例如只允许通过注册 API 接入）

**封顶规则**
- 每个实现内部各自做拦截（策略散在 N 处）→ 覆盖面封顶 1、约束力封顶 1
- 归属表右列是"参考某文档"这类二级指引 → 覆盖面封顶 1
- 拦截点没有"拦不住什么"的说明 → 覆盖面封顶 1
- 加一个常见能力需要修改循环本身 → 覆盖面封顶 1
- 拦截点不分类（只观察 / 可改写 / 可短路混在一个事件类型里）→ 覆盖面封顶 1
- 注册在卸载时不撤销（生命周期无人负责）→ 覆盖面封顶 2

**常见伪证**："我们的事件系统很灵活" —— 灵活不等于**分类清楚**。"只观察"、"可以改写结果"、"可以让整个操作短路"是三种完全不同的权限；混在一个事件类型里，扩展作者会误用。

**走形症状**：常见能力被实现成"给核心加一个分支"；或者拦截点太多太细，扩展作者不知道选哪个。

**一个判据**：**你的策略改动要动几个文件？答案应该是"一个"。**

### R7 模型可见面组装 · Model-visible surface assembly

**一句话**：模型这一步看到什么——可见工具、提示词、内容块——是**每一步显式组装**的，并且组装结果**必须留下记录**。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | **做 X1 回放** | 能重建第 N 步的可见工具清单和提示词吗 |
| P2 | 看可见集合怎么算 | 是静态的，还是按作用域每步算的？子任务能不能收窄 |
| P3 | 看提示词的顺序 | 越稳定的内容越靠前吗？（靠后的变化不会让前面缓存失效）|
| P4 | 看"可见但不可用" | "模型看得见这个工具"和"这个动作被允许"是两套判定吗 |
| P5 | 看内容块 | 文件、图片等非文本内容怎么进请求？进来的东西和不进来的东西，规则对称吗 |

**覆盖面**：0 可见集合是写死的 / 1 有动态组装但结果不进记录 / 2 每步显式组装 + 结果进记录 / 3 且有作用域收窄（子任务看到的是子集）与稳定的排序规则

**约束力**：0 靠约定 / 1 文档说明 / 2 有断言（请求必须能从记录重建）/ 3 且断言会在违反时失败并指出哪一步不一致

**封顶规则**
- 有任何进入模型请求的内容不进记录 → 覆盖面封顶 1、约束力封顶 1
- 可见集合影响授权（"看得到就能做"）→ 约束力封顶 1
- 提示词顺序把每台机器/每个用户不同的内容放在最前 → 覆盖面封顶 2（缓存永远命中不了）
- 可见集合不能按作用域收窄（子任务看到的是全集）→ 覆盖面封顶 2
- 请求重建的断言从不失败、或失败时指不出哪一步 → 约束力封顶 2

**常见伪证**："提示词组装很灵活，插件都能加" —— 灵活不是重点，**"加了什么"能不能事后重建**才是。一个不能重建提示词的系统，无法解释自己的行为。

**走形症状**：把"可见性"当成授权边界（危险：以为藏起来就安全）；或者提示词按插件加载顺序拼接，同一个部署两次启动得到不同的前缀。

### R8 入口与协议投影 · Entry surfaces and protocol projection

**一句话**：多个入口（命令行、界面、协议接口）**共用同一套运行时语义**，各自只负责投影，不各自实现一遍循环。

*适用性：两个以上入口时评；只有一个入口时标 N/A（不要提前抽象）。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 数入口，找它们共用什么 | 是不是都通过同一套会话/循环接口驱动 |
| P2 | 看每个入口的**输出通道归属** | 哪个入口的 stdout 是给人看的、哪个是协议帧？（结论决定能不能装日志）|
| P3 | 找"故意不保证"清单 | 每个协议面有没有明说自己不保证什么；这份清单被测试钉住了吗 |
| P4 | 看就绪边界 | 协议入口宣布 ready 之前，等所有异步初始化完成了吗 |
| P5 | 看订阅过滤 | 一个入口收到的事件，是按"是不是它创建的"过滤，还是全量 |

**覆盖面**：0 每个入口一套实现 / 1 共用部分逻辑 / 2 共用运行时语义，入口只做投影 / 3 且每个协议面有明确的能力清单与否决清单

**约束力**：0 靠约定 / 1 文档说明 / 2 有检查（协议帧格式有校验）/ 3 且"故意不保证"是一份被测试钉住的合同

**封顶规则**
- 某个入口自己实现了一套循环 → 覆盖面封顶 1
- 协议入口的 stdout 与人类可读输出混用 → 约束力封顶 1（协议会被日志污染）
- 没有"故意不保证"清单 → 覆盖面封顶 2
- 就绪信号早于异步初始化完成 → 约束力封顶 1
- "故意不保证"清单只是文档、没有测试钉住 → 约束力封顶 2

**常见伪证**："我们的 API 很稳定" —— 稳定是承诺，**不保证什么**才是有用的信息。一个不说自己边界的协议，把未定义行为留给了使用者。

**走形症状**：第五个入口加进来时语义开始分叉；或者协议里混进了内部实现细节，改内部结构就破坏兼容。

### R9 工具执行与授权 · Tool execution and authorization

**一句话**：一个动作从发起到落定走**同一条管线**；参数在进入判定前就被冻结；结果只有一条出口；授权判定**失败时关闭**（fail-closed）。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 画管线 | 从发起到结果回到模型，中间有哪几个环节？每环能做什么、不能做什么 |
| P2 | 看参数 | 判定环节能改写参数吗？参数在判定前是否已冻结 |
| P3 | **做 X5** | 取消、超时、工具内部报错——三种情况各自的结果是什么形态 |
| P4 | 看授权 | 没有审批者时默认是放行还是拒绝？**审计写入失败时会发生什么** |
| P5 | 看记时 | 动作是**先记录再执行**，还是执行完再记录？失败的动作在记录里吗 |

**覆盖面**：0 没有统一管线，各实现自己处理 / 1 有管线但环节不全 / 2 完整管线：先记录 → 判定 → 执行 → 归一化 → 单一出口 / 3 且有独立的审批环节与审计配对（问与答都能对上）

**约束力**：0 靠约定 / 1 文档说明 / 2 权限判定在代码里强制 / 3 且越权必然失败、审计不可静默丢失（写不进去就拒签）

**封顶规则**
- 参数在判定环节可被改写 → 覆盖面封顶 2、约束力封顶 1（判定依据与实际执行的东西不一致）
- 没有审批者时默认放行 → 约束力封顶 1
- 审计写入失败仍返回决策 → 覆盖面封顶 2、约束力封顶 1
- 结果不是单一出口（存在"部分成功""未知状态"）→ 覆盖面封顶 1、约束力封顶 1
- 动作执行完才记录（先执行后记录）→ 覆盖面封顶 1

**常见伪证**："每个工具自己会检查权限" —— 那是策略散在 N 处，而且**判定发生在参数已经进入工具之后**，中间有一段时间窗。

**走形症状**：把"可见性"当授权；审批做成事后通知；取消只是"不再等"。

**两条硬边界**：
- **可见集收窄的是模型的选择空间，不是授权。** 授权必须独立成立。
- **取消不能撤销已经发生的外部效果。** 一个动作如果已经写了远程系统，取消它就等于"不再等结果"，不等于"它没发生"。

---

### R10 可执行治理 · Executable governance

**一句话**：规则被机器拦住，不写在文档里等人自觉；而**拦截机制自己也被证明会失败**。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找检查清单的**聚合点** | 所有检查有一个统一的注册处吗？还是散在几十个脚本里 |
| P2 | 数一数"文档规则"与"机器规则"的比例 | 有多少条写在文档里的规则，其实可以做成检查 |
| P3 | **做第三层第 1 项** | 挑一条声称的不变量，找它会在什么情况下失败 |
| P4 | 看检查的可信度 | 随便挑一个检查，说得出它最近一次为红是什么回归吗 |
| P5 | 看成熟度数字 | 如果有"可替换率""覆盖率"这类数字，能复算吗？复算的坑被列出来了吗 |

**覆盖面**：0 规则都在文档里 / 1 有一些检查但不聚合 / 2 有统一的检查注册处 + 不变量只在有意义时写 / 3 且有负例控制与可复算的成熟度度量

**约束力**：0 靠约定 / 1 检查存在但要人记得跑 / 2 检查接进了提交流程 / 3 且检查自己被负例控制过（证明过会红）

**封顶规则**
- 存在"永远为绿"的检查且无人核查 → 覆盖面封顶 2、约束力封顶 1
- 不变量检查的是"服务在不在""插件元数据对不对"这类存在性 → 覆盖面封顶 1（**那不是不变量**）
- 成熟度数字手工维护且无 freshness 检查 → 覆盖面封顶 2
- 规则只写在文档里，且该规则可机械判断 → 约束力封顶 1
- 检查散在多个脚本里、没有统一注册处 → 覆盖面封顶 1

**常见伪证**："我们有一整套 CI" —— CI 全绿说明检查碰巧碰到的地方没问题。**说得出某个检查最近一次为红的原因**，才说明检查是活的。

**走形症状**：绿灯数目成了 KPI；检查变成仪式，然后开始被绕过；或者相反——不变量写了一大堆，检查的全是"这个服务注册了吗"。

**一个判据**：**不变量只有在"两个独立观察可能分歧"时才值得写。** 检查"某个东西存在"不是不变量；检查"两个独立算出来的结果必须一致"才是。

---

### R11 客户端组装纪律 · Client composition discipline

**仅当这个 harness 带 GUI 客户端时评；没有 GUI 标 N/A。**

**一句话**：界面状态从**权威事实**派生；业务数据不在界面层另存一份；跨模块只走声明的接口。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| P1 | 找一个界面上的数字，往回追 | 它最终来自哪？是权威记录，还是界面层自己攒的 |
| P2 | 看界面层能不能改业务数据、能不能产生输入 | 有没有"界面先改了、再同步回去"的路径；界面发起或产生的模型可见输入（用户消息、附件、卡片动作）进不进会话记录、能不能回放 |
| P3 | 看模块边界 | 一个界面模块能不能直接引用另一个界面模块的实现 |
| P4 | 看订阅 | 组件里有没有各自手写的订阅逻辑（应该有统一机制）|
| P5 | 看未知数据 | 界面遇到不认识的数据形态时，是崩还是回落到通用形态 |

**覆盖面**：0 界面自持业务状态 / 1 部分派生部分自持 / 2 全部从权威事实派生 + 统一订阅机制 / 3 且模块边界有机器检查

**约束力**：0 靠约定 / 1 文档说明 / 2 有检查（越界引用会红）/ 3 且"界面产生的新模型可见输入必须留下记录"被强制

**封顶规则**
- 界面层可以写业务数据 → 覆盖面封顶 1（两处存真）
- 界面产生的新模型可见输入不进记录 → 约束力封顶 1
- 模块之间可以互相引用具体实现 → 覆盖面封顶 2、约束力封顶 1
- 遇到未知数据形态直接崩 → 约束力封顶 2
- 组件各自手写订阅逻辑（没有统一机制）→ 覆盖面封顶 1

**常见伪证**："我们的前端架构很清晰" —— 清晰是给作者的。检验法是问"这个数字改了，界面上几处会跟着变"。

**走形症状**：界面自己攒一份业务状态（两处存真）；模块之间直接引用彼此的实现；遇到不认识的数据形态直接崩；或者界面产生的新模型可见输入没留下记录。

## 4 · 形态裁剪

不是每种 harness 都要评全十一维。**不适用的记 `N/A`，不记 0 分。**

| 形态 | 判据 | 必评 | 通常 N/A | 权重变化 |
|---|---|---|---|---|
| **内部 harness** | 一个团队自用，稳定扩展需求少 | R1 R2 R4 R7 R9 R10 | R3、R5、R8、R11 | R3 格式世代：只有当数据要长期存活时才评。**内部工具最容易在这里过度投入** |
| **产品 harness** | 有外部用户，有自己的界面 | 全部 | — | R2 R7 R9 是核心；R11 若带 GUI 必评 |
| **平台 harness** | 有第三方在它上面开发 | 全部，且 R5 R6 R8 是重点 | — | R5 的判据升级为"**至少两项能力有两个真实可互换的实现**" |
| **单机实验 harness** | 还没决定要不要继续做 | R1 R2 R7 | 其余 | 只评三条：**配置算得出来、请求回放得出来、模型看到什么说得清**。其余等决定继续做再说 |
| **多入口产品**（命令行 + 界面 + 协议 + 桌面）| 两个以上入口 | 全部，R8 为重点 | — | R8 的判据升级为"**新入口加进来时不改运行时**" |

### 三条裁剪纪律

1. **标 N/A 要写理由**，一行即可（"无第三方扩展需求，R5 R6 不评"）。
2. **N/A 的维度不参与成熟度档判定**，分母按实际评估的维度数算。
3. **不确定时先按适用处理**，评估过程中发现没有对应压力，再改标 N/A 并记录。

### 与开发 Harness 评估的形态口径不同

本节的 harness 形态决定十一维里哪些要评；[01 的适用性裁剪](./01-evaluate-development-harness.md#5--适用性裁剪)那套（库 / 服务 / monorepo / 插件平台 / 数据 / 文档站 / 脚本 / agent 产品）决定十七维里哪些要评。同一个仓库按两套各判一次，结论互不替代。

## 5 · 模仿判断：哪些值得抄

评估完，还有第二个问题：**这套做法里，哪些是它的处境逼出来的，哪些是可以学的？** 这两者长得一模一样，但照搬前者会把维护成本搬过来而收益搬不过来。

### 三条判据

**判据一：它解决的是"组合压力"还是"显而易见的缺失"？**

组合压力指这几件事**同时出现**：多个入口、多个可替换后端、会话级隔离、运行时装卸、第三方生态。

- 只出现一两项 → 那些看起来最"高级"的机制（能力 seam、完整扩展点体系、协议投影）**多半不该抄**。它们是为组合压力付的保险费。
- 五项都出现 → 抄形状是划算的，因为你已经在付那份成本了，只是付得没有结构。

**判据二："能换"和"换出差异"是两件事。**

数一数有多少能力真的有两个可互换的实现。**"能换"的比例通常不低；"换出差异"的比例明显更低，而且后者才是产品差异所在。**

一个实用的读法：**多个实现集中的地方，是最该重造的基础设施；只有一个实现的地方，才是产品本身。**

**判据三：分辨"有机制"和"有正确完成标准"。**

一个有机制的系统和一个可信的系统之间差一层：**每一层都有明确的"什么算做完了"**。抄的时候要连这一层一起抄，否则抄来的是空壳。

### 抄与不抄的对照

| 值得抄（几乎零组合压力依赖） | 有压力再抄 | 不要照搬（组合压力的产物） |
|---|---|---|
| **只追加的事实源 + 模型可见即记录** | 格式世代的迁移链 | 完整的能力 seam 体系 |
| **动作先记录再执行；结果单一出口** | 多入口共用运行时（第二个入口出现时做）| 为每个内部函数造一个 service |
| **授权与可见性分离；缺审批者时拒绝** | 上下文预算与回收 | 某些框架独有的调度/注入机制 |
| **规则写成会失败的检查，且检查被负例控制** | 客户端模块边界的机器检查 | 多方审批编排（多数系统用不上）|
| **配置算得出来，且 dump 与启动同一算法** | 协议面的完整能力/否决清单 | 为一次性脚本造的版本机制 |
| **扩展点带"拦不住什么"的说明** | 运行时只读查询 | 把"能自动装"当成"可信" |

### 三条边界（照搬时最容易翻车）

1. **插件化不等于安全。** 能加载第三方代码不等于这些代码受约束。同进程的代码可以直接调用底层能力，绕过任何"扩展点"。**"能自动安装"和"可信"是两件事。**
2. **清理不等于回滚。** 卸载时撤销自己注册的东西，不会补偿已经发生的外部写入（发出的消息、写下的文件、发生的支付）。
3. **记录可见 ≠ 有授权。** 一个能查看运行状态的接口，不代表它有权修改；一个能看见工具的模型，不代表它被允许调用。

## 7 · 评估者自己的验收

1. **五个活体实验都真的跑过。** 任何一个是"看代码推断的"，这一维的结论标"证据受限"。
2. **每个扣分点都能指到具体证据。** 哪次实验、哪一步、看到什么。
3. **区分"没有"和"不适用"。** 一个内部工具没有格式世代机制，是 N/A 不是 0。
4. **区分"它的取舍"和"它的缺口"。** 系统明说自己不保证某件事，且这个取舍有理由 → 不算缺口；系统**没提**这件事，而它确实做不到 → 是缺口。
5. **把"我手动兜住了"记下来。** 评估者经常不自觉地替系统补上缺失的机制（手动重启、手动核对、手动清理）。**每一次你不得不接手，都是一个缺口。**

| 实验 | 结果 | 判断 |
|---|---|---|
| **X1 回放** | 能重建：对话序列、工具调用与结果。<br>重建不出：第 N 步的 system prompt、当时的工具清单、动态注入的上下文。 | **不通过** |

| **X3 加能力** | 加一个"查订单"工具：只改了一个插件文件，未动运行时；schema 自动出现在模型请求里；可见输入留下了记录。 | **通过** |

| **X5 取消与失败** | 取消一个长任务：界面显示已取消，但后台进程继续跑了 40 秒才结束；工具内部异常被包成"返回空结果"交给模型，模型据此继续推理。 | **不通过** |

```

  - 靠我兜住：确认插件真的加载了（每次改配置后要手动 grep 日志）
  - 靠我兜住：判断一次失败是"该重试"还是"该报 bug"（异常被吞成空结果）
```

### 表 3 · 缺口清单

| # | 维 | 症状 | 后果 | 严重度 |
|---|---|---|---|---|
| 1 | R2 | system prompt 与工具清单不进会话记录 | 模型行为异常时无法复盘；改版前后的差异永远说不清 | 高 |
| 2 | R3 | 无格式版本，解析失败一律报"损坏" | 升级后旧会话被误判为数据丢失；用户不敢升级 | 高 |
| 3 | R9 | 工具异常被吞成空结果 | 模型基于错误前提继续推理；问题在上线后很久才暴露 | 高 |
| 4 | R1 | 无 dump 命令；坏配置静默跳过 | 团队以为能力开着实际没装（已发生）| 高 |
| 5 | R5 | 提供方切换靠分支，散在 6 个文件 | 每加一个提供方成本翻倍；无法快速试新模型 | 中 |
| 6 | R7 | 工具顺序随加载顺序变化 | 缓存命中率不稳定；同一个部署两次启动行为不同 | 中 |

### 一句话结论

这个系统的**问题不在模型层，在事实层**：它把"发生过什么"只记了一半（对话记了，模型看到的请求没记），把"现在装了什么"交给一份会静默失败的手改配置，把"动作失败了"归一化成了空结果。三件事的共同后果是——**出了问题查不出来，而且它不会告诉你查不出来。**

→ 下一步去 [缺口到计划](./03-from-gaps-to-plan.md)：最痛的三维对应 R2、R3、R9，按"修尺子先于量东西"的顺序，R2 与 R9 应排在同一轮（它们共同决定"能不能信任系统报告的结果"）。

## 附录 A · 术语表

| 词 | 含义 |
|---|---|
| **运行时 harness** | 把模型、工具、会话、扩展点和交互组合成可运行 agent 的那套机制 |
| **组合内核** | 从声明层算出运行系统的部分；它先于任何插件存在 |
| **事实源** | 只追加的、唯一权威的记录；其它一切从它派生 |
| **模型可见 ⟺ 已记录** | 任何进入模型请求的内容都必须能从持久记录重建 |
| **投影** | 从事实源算出来的视图（界面状态、检索结果、统计）；丢了可以重算 |
| **能力 seam** | 一项能力的三件套：定义 + 实现 + 使用方。三者齐备才算完整 |
| **扩展点** | 新行为被声明可以挂上去的位置；绕过它就意味着绕过该位置的检查 |
| **拦截点** | 管线里可以观察、改写或短路某个环节的位置 |
| **fail-closed** | 判不了的时候按"拒绝"处理，而不是按"放行"处理 |
| **格式世代** | 持久数据格式的一个版本；世代之间的关系是单向的（旧可迁、新被拒）|
| **受管范围** | 一次子进程启动所拥有的、可被观察和终止的进程集合；不假设它等于进程组 |
| **就绪边界** | 系统宣布"可以使用了"的那个时刻；它必须晚于所有异步初始化 |
| **负例控制** | 故意制造一个该被抓住的回归，确认检查确实会失败，然后还原 |
| **组合压力** | 多入口、多可替换后端、会话级隔离、运行时装卸、第三方生态同时出现的处境 |
| **X1–X5** | 五个活体实验：回放（X1）、换后端（X2）、加能力（X3）、坏配置（X4）、取消与失败（X5） |
| **M0–M3** | 运行时 harness 的成熟度档：单次可跑 / 有机制 / 可重建 / 可扩展可信任。与维度编号 R1–R11 无关 |
| **覆盖面** | 这一维有没有对应机制：0 没有 / 1 部分场景 / 2 成体系 / 3 有 owner 与测试钉住（见第 3 节） |
| **约束力** | 这一维靠什么成立：约定 / 文档 / 测试或检查 / 运行时断言与负例控制（见第 3 节） |

## 附录 B · 封顶规则速查

**上限的含义。** 每条规则给出的都是**上限**：它可能比锚点阶梯推导出的更严（这是有意的惩罚），但不会让一个已经违反某档定义的仓库拿到那一档——"命中却仍按更高档记"永远不成立。 封顶规则是按本维锚点阶梯**逐条**展开的：阶梯里凡有明确判据、且探针观察得到的条件，这里都有一条对应的上限；比阶梯更严的惩罚也写在同一份表里。
