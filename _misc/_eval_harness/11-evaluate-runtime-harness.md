# 运行时 Harness 评估 · 粗粒度（coarse-grained；先过一遍）

**这份文档是什么。** 运行时 Harness 评估的**粗粒度（coarse-grained）**一半：先用较小成本过一遍十一维，判断"这套 agent 系统值不值得信、哪几维最痛"，回答一个问题：*这个 agent 系统本身做对了吗——它的会话、循环、工具、扩展点和多入口，是不是一个能被信任、能被扩展、能被模仿的运行时？*

**它和开发 Harness 评估的分工。** [开发 Harness 粗粒度（coarse-grained）](./01-evaluate-development-harness-coarse.md) 问"这个仓库对 agent 友好吗"（任何仓库都能评）；本文问"这个 agent 系统本身做对了吗"（**只有本身是 agent 产品、自带 agent 运行时的仓库才能评**）。两者互不替代：一个普通库可以开发 Harness 满分而本文完全不适用；一个早期的 agent 产品可以本文很好而开发 Harness 很糟。

**谁执行、谁读。** 评估由 agent 执行：它按本协议跑适用性（applicability）判定、五个活体实验（live experiment）与十一维粗判（coarse check），写出一份 Markdown 报告（第 6 节，末尾列出需要人回答的问题）。人读本文是为了理解判据；人读报告是为了复核证据、回答末尾的问题、决定下一步——**人不打分，也不填表**。

**编号约定。** 维度用 `RT`，探针（probe）用 `PB`，五个活体实验（live experiment）用 `LX`，成熟度档（maturity level）用 `MG`（见 [README 的标识符约定](./README.md#标识符约定token)）。

**前置知识。** 无。术语在本页定义。**本文与 12 都不附 DSH 例证（两份里的短例都是构造的），也不含任何外部链接**——它们只给判据。

**两份粒度。** 本文（`11`）是粗粒度（coarse-grained）：适用性（applicability）判定、定义、通用两轴（two axes）、十一维粗判（coarse check）、五个活体实验（live experiment；§2）、形态裁剪（profile tailoring）、模仿判断、报告格式与自检。**细粒度（fine-grained）**（[`12`](./12-evaluate-runtime-harness-fine.md)）有每维的一句话定义、锚点阶梯（anchor ladder）、探针（probe）与封顶规则（cap rules）——只在粗判（coarse check）为红、或要动的维度上翻它。**粗粒度（coarse-grained）定下来后基本不动，细粒度（fine-grained）会持续增补。**

## 0 · 先做适用性（applicability）判定

**在开始评估之前，先回答三个问题。只有 AQ1 答"否"时本文不适用——整份作废，不是打 0 分；AQ2、AQ3 的答案只决定形态与裁剪（tailoring），评估继续。**

| # | 问题 | 答"否"意味着 |
|---|---|---|
| **AQ1** | 这个仓库里跑着一个 agent 运行时吗？（模型 → 工具调用 → 结果回灌 → 再请求，这个循环由本仓库实现，而不是由外部框架提供） | 它可能是模型应用、插件、或纯提示词工程。本文不适用 |
| **AQ2** | 这个运行时要**长期活着**吗（已决定持续维护）？ | 还没决定要不要继续做：按"单机实验"形态只评三维，其余等决定继续做再说 |
| **AQ3** | 有第三方或第二个团队要往它上面加东西吗？（插件、自有模型、自有工具、自有入口） | RT5 能力 seam、RT6 扩展点（Extension points and interception）标 N/A——**不要为一个不存在的生态建架构**。这一条优先于第 4 节形态表（profile table）里的"必评" |

**三问 → 形态**（形态可以叠加；命中多行时按第 4 节的裁剪（tailoring）纪律合并）：

| 条件 | 形态 |
|---|---|
| AQ1 否 | 本文不适用 |
| AQ1 是、AQ2 否 | 单机实验（不与其它形态叠加） |
| AQ2 是，只在组织内部使用 | 内部 |
| AQ2 是，有组织外的用户 | 产品 |
| AQ3 是，且加东西的人不在维护团队里 | 平台（叠加在内部或产品之上） |
| 两个以上入口（命令行、界面、协议、桌面） | 多入口（叠加在内部、产品或平台之上） |

> **为什么这一步要单独成节。** 运行时 harness 的评估维度里，有一半（格式世代、能力 seam、协议投影）只在系统被长期使用、被多方扩展时才有意义。把它们套到一个一次性脚本上，得到的是"处处不及格"，而正确的结论是"不需要"。

### 铁律（与开发 Harness 评估相同）

**只有当场做过的才算证据。** 一个维度给 2 分以上，必须能说出"我做了什么、看到了什么"；说不出，两个轴都按 `1` 档封顶（cap）——不记 2 分以上。特别地，第 2 节的五个活体实验（live experiment）**每一个都必须真的跑过**——运行时 harness 的文档与实际行为之间的差距，比开发 harness 更大，因为它的"实际行为"依赖配置、版本、宿主和时序。

## 1 · 什么是"运行时 Harness"

> **运行时 harness（runtime harness）**：把模型、工具、会话、扩展点和交互组合成一个可运行的 agent 的那套机制。它决定了：模型每一步看到什么、它的动作怎么被执行和授权、发生过的每一件事怎么被记录和重建、别人怎么往它上面加东西、以及同一套内核怎么从多个入口被使用。

它和**开发 harness** 的区别在于被评估的对象：

| | 开发 Harness | 运行时 Harness |
|---|---|---|
| 服务对象 | 在**这个仓库里干活的** coding agent | 运行在**这个产品里的** agent 及其用户 |
| 失败症状 | 读错、改错、交付不可信 | 模型看到的不等于发生过的；动作绕过授权；扩展要改核心；入口各自实现一套循环 |
| 评估方式 | 走一笔真实变更 | 跑一次真实会话 + 五个活体实验（live experiment） |

### 运行时 harness 的四条核心张力

这四条张力决定了后面十一维为什么长这样：

1. **可靠性 vs 透明度。** 动作要能被执行（可靠），但"执行了什么、模型看到了什么"必须能被事后重建（透明）。**二者冲突时，透明度优先**——不能重建的系统没法排障，也就没法长期可靠。
2. **可扩展 vs 可理解。** 扩展点越多，新能力加得越快；但每个扩展点都是一份需要维护的合同。**只有真的有人要换的东西，才配成为扩展点。**
3. **能力 vs 授权。** "模型能看见这个工具"和"这个动作被允许"是两件独立的事。把它们混成一件，是这类系统最危险的设计错误。
4. **单入口简单 vs 多入口一致。** 只服务一个入口时什么都不用抽象；服务五个入口时，如果每个入口各自实现一遍循环，语义会在第五个入口处开始分叉。

### 一个反转（和开发 harness 那边同源）

运行时 harness 的质量**不来自模型更聪明**，来自两件事：**把"模型看到什么"变成可重建的事实**，以及**把"能不能做"变成独立于可见性的授权判定**。

所以评估时不要问"它的 agent 表现好不好"（那是模型和提示词的事），要问"**它的机制让'表现好'可复现、'表现坏'可诊断吗**"。

## 2 · 评估分三层

### 第一层 · 静态清点

按[第 3 节](#3--十一维粗判coarse-check)的十一维逐维粗判（coarse check），每维记两轴（two axes）的粗判档（coarse grade），并记**一个最痛的真实案例**。**案例是扣分的佐证，不是扣分的前置条件**：说不出案例时仍按当场看到的证据给分，并把这维的证据状态标为"证据受限（evidence-limited）"（见表 1）。

### 第二层 · 五个活体实验（live experiment）

这一层是本文的核心工具。**五个实验都要真的跑**，每个实验只问一件事：*系统自己的机制拦住了/接住了吗？*

下文用 **LX1–LX5** 指代这五个实验（`LX` 是活体实验（live experiment）专用前缀）。

| # | 实验 | 怎么做 | 通过的标准 |
|---|---|---|---|
| **LX1 回放** | 拿一个**真实发生过**的会话（不是构造的），只读它的持久记录 | 不问系统，直接看记录 | 能逐条重建"模型在第 N 步实际收到的请求"——system prompt 内容、可见工具清单、消息序列。**不是"大致能看出发生了什么"，是能重建出请求本身** |
| **LX2 换后端** | 换掉一个可替换的后端（模型提供方、执行沙箱、文件系统、存储），只改配置。系统只有一个实现时，改为静态清点"换一个提供方要动哪些文件"，并把 LX2 记 N/A | 数一数改了几个文件 | **消费者代码一行不改**；改完功能照常；如果只能通过改代码来换，这一维不及格 |
| **LX3 加能力** | 加一个模型可见的新能力（一个新工具），从零到能用 | 数一数改了几个文件、动了哪些层 | 走的是已声明的扩展点，**没有改循环本身**；新能力的 schema 自动进入模型请求；它的可见输入自动留下记录 |
| **LX4 坏配置** | 故意把一个引用改错（指向不存在的插件/提供方/文件） | 启动 | **在离错误源头最近的地方大声失败**，并指出缺的是什么。**静默少一个能力 = 不及格** |
| **LX5 取消与失败** | 发起一个长动作，中途取消；再制造一次工具内部错误（给一个工具传一个必然失败的参数，或临时让一个工具抛异常） | 看两个出口 | 取消在**声明的超时预算内**真的停（没有声明预算时，按"取消后动作是否仍在后台继续"判定）；失败被归一化成**一个明确的错误结果**交给模型，而不是"部分成功"或"未知状态"；取消/失败本身留下记录 |

五个实验里，**LX1 和 LX3 的失败最贵**：LX1 失败意味着这个系统在出问题时无法排障；LX3 失败意味着每加一个能力都要动核心，每个新能力的成本都包含一次核心改动和它的回归风险。

### 第三层（细粒度 fine-grained）

第三层的反证（falsification）四动作与每维探针（probe）、封顶规则（cap rules）见 [12](./12-evaluate-runtime-harness-fine.md)。粗粒度（coarse-grained）只到第二层：**清点 → 五个活体实验（live experiment）**。

## 3 · 十一维粗判（coarse check）

### 两轴（two axes）怎么打

**轴一 · 覆盖面（coverage）** —— 这一维有没有对应的机制

| 档 | 判据 |
|---|---|
| 0 | 没有。这个问题没有对应的机制，靠约定或运气 |
| 1 | 有但不完整。部分场景覆盖，边界情况不成立 |
| 2 | 有且成体系。常见情况都被覆盖，边界有明确处理 |
| 3 | 有且被主动维护。有 owner、有更新触发条件（trigger）、有测试或检查钉住 |

**轴二 · 约束力（enforcement）** —— 这一维靠什么成立

| 档 | 判据 |
|---|---|
| 0 | 只靠约定或注释 |
| 1 | 写在文档里，或只在某一条代码路径上成立 |
| 2 | 有测试或检查钉住，违反会红 |
| 3 | 有运行时断言或负例控制（negative control）：**能被证明会失败**，且失败信息指出违反了什么 |

**读法。** 运行时 harness 最危险的状态是 `覆盖面 2 / 约束力 1`——机制看起来很全（有日志、有扩展点、有配置），但没有任何东西保证它成立。**约束力（enforcement） 3 才是"可以被信任"**。

**这两张表与各维锚点（anchor）的关系。** 两张表是所有维度共用的**通用轴**，粗判（coarse check）就用它们记档。每一维在 [12](./12-evaluate-runtime-harness-fine.md) 里另有自己的锚点阶梯（anchor ladder），定档（final grade）时以锚点（anchor）为准；锚点（anchor）的约束力（enforcement） 3 一律包含本表的通用条件"能被证明会失败"。另外，`写在文档里` 必须能指出具体文件或位置；指不出来就是 0 档。

### 总分与成熟度档（maturity level）

档位是**累积**的：每一档都要求先满足上一档。

| 档 | 判据 | 一句话 |
|---|---|---|
| **MG0 单次可跑** | 未达 MG1 | 能跑通一次，跑第二次靠运气 |
| **MG1 有机制** | 多数维度覆盖面（coverage） ≥ 2 | 该有的都有了，但多半没人保证它们成立 |
| **MG2 可重建** | MG1，且事实源（source of truth；RT2）、模型可见面（model-visible surface；RT7）、工具执行与授权（RT9）三维约束力（enforcement） ≥ 2 | 出问题能查到为什么 |
| **MG3 可扩展可信任** | MG2，且至少三维约束力（enforcement） = 3，且 RT5 能力 seam 与 RT10 治理的**覆盖面（coverage）** ≥ 2（换实现有真实样本、检查有统一注册处） | 别人能在上面加东西而不改核心 |

**档位怎么记。** 记满足的最高一档。MG2、MG3 点名的维度是硬条件：点名的维度被裁为 N/A 时，那一档对这个系统不适用——单机实验档（RT9 为 N/A）不追求 MG2，AQ3 答"否"的系统（RT5 为 N/A）不追求 MG3。

达标线（pass line）：**至少 MG2。** 只有要对外开放扩展时才需要 MG3。这是"能不能用"的下限。判断一轮打磨**能不能收工**用 [20 的收工线（stop line）](./20-from-gaps-to-plan.md#7--一轮打磨的循环与停止条件)，它包含达标线（pass line），附加条件在 20 里。

**"多数"与计数的口径。** 本节所有"多数"指适用维度里的**超过一半**；"至少三个"这类计数也只在适用维度里数；标了 N/A 的维度不计入分母（见[第 4 节](#4--形态裁剪profile-tailoring)）。

### 十一维粗判（coarse check）一览

**怎么用**：每一维走三步，得到**粗判档（coarse grade）**。

1. **看粗判（coarse check）信号。** 每条信号后的括号标着它压的轴。命中一条，就把标出的轴粗判（coarse check）记 ≤ 1（标"两轴（two axes）"的两轴（two axes）都记 ≤ 1），并记进缺口清单（gap list）。每条信号都是 12 里一条上限 ≤ 1 的封顶（cap）的一眼版本；活体实验（live experiment）看到的现象同样算命中。
2. **用上面两张通用轴表打两轴（two axes）。** 约束力（enforcement）看"违反时什么会红"：没有东西会红记 0–1，有测试或检查会红记 2，能被证明会失败且指出违反了什么记 3。对应的活体实验（live experiment；见十一维总表）跑过的，以实验结果为准。
3. **判红绿。** **红 = 覆盖面（coverage）或约束力（enforcement） ≤ 1，绿 = 两轴（two axes）都 ≥ 2。** 粗判档（coarse grade）足以判红绿、排优先级。粗判（coarse check）为红、这一轮要动、或要把分数写成最终结论的维度，翻 [12](./12-evaluate-runtime-harness-fine.md) 的对应卡片定档（final grade）；冲突时以定档（final grade）为准（定档（final grade）通常更低）。

| 维 | 它管什么 | 粗判（coarse check）信号（一眼看什么；括号里是命中后记 ≤ 1 的轴） | 通常 N/A |
|---|---|---|---|
| `RT1` 组合与启动（Composition and boot） | 系统从声明算出来，拼错了会大声失败 | 没有 dump 最终配置的命令（覆盖面 coverage）；引用了不存在的组件静默少一个能力（两轴 two axes） | — |
| `RT2` 会话事实源（Session as the single source of truth） | 发生过的一切有一条只追加的记录，模型可见的都能重建 | 进入模型请求的内容（system prompt、工具清单）有不在记录里的（两轴 two axes） | — |
| `RT3` 格式世代与兼容（Format generations） | 持久数据有版本：旧可迁、新被拒、已提交世代不改写 | 更新版本写的数据没被拒绝（两轴 two axes）；"版本过新"被报成"文件损坏"（约束力 enforcement） | 数据不跨版本长期存活时 |
| `RT4` 循环与终结边界（Loop and termination boundaries） | 一次工作从哪开始、到哪算结束 | "空闲"被当成"完成"（覆盖面 coverage）；重启后危险动作自动接着跑（约束力 enforcement） | 无（单机实验档除外） |
| `RT5` 能力 seam 与可替换性（Capability seams） | 换一个实现，使用方一行不改 | 换实现要改使用方代码（覆盖面 coverage）；可替换点只有唯一使用方和唯一实现（覆盖面 coverage） | 只有一个实现的内部工具 |
| `RT6` 扩展点与拦截（Extension points and interception） | 新行为有唯一去处，拦截点分类清楚 | 加常见能力要改循环本身（覆盖面 coverage）；说不清拦截点拦不住什么（覆盖面 coverage） | 没有第二个人要加东西时 |
| `RT7` 模型可见面组装（Model-visible surface assembly） | 模型这一步看到什么、由谁决定、且进了记录 | 进入请求的内容有不在记录里的（两轴 two axes）；可见集合影响授权（约束力 enforcement） | — |
| `RT8` 入口与协议投影（Entry surfaces and protocol projection） | 多个入口共用同一套运行时语义 | 新入口自己实现一遍循环（覆盖面 coverage）；协议 stdout 混进人类可读输出（约束力 enforcement） | 只有一个入口时 |
| `RT9` 工具执行与授权（Tool execution and authorization） | 动作走同一管线，授权独立于可见性 | 参数在判定之后可改写（约束力 enforcement）；没有审批者时默认放行（约束力 enforcement）；"部分成功"、未知状态或被吞掉的异常流回调用方（两轴 two axes） | 单机实验档（无人审批面） |
| `RT10` 可执行治理（Executable governance） | 规则被机器拦住，检查被证明会失败 | 可机械判断的架构规则只写在文档里（约束力 enforcement）；检查散在多个脚本、没有统一注册处（覆盖面 coverage） | 无（单机实验档除外） |
| `RT11` 客户端组装纪律（Client composition discipline） | 界面状态从权威事实派生（derived） | 界面层能直接写业务数据（覆盖面 coverage）；界面产生的模型可见输入不进记录（约束力 enforcement） | 没有 GUI 客户端时 |

## 4 · 形态裁剪（profile tailoring）

不是每种 harness 都要评全十一维。**不适用的记 `N/A`，不记 0 分。**

| 形态 | 判据 | 必评 | 通常 N/A | 权重变化 |
|---|---|---|---|---|
| **内部 harness** | 只在组织内部使用，稳定扩展需求少 | RT1 RT2 RT4 RT7 RT9 RT10 | RT3、RT5、RT6、RT8、RT11 | RT3 格式世代（Format generations）：只有当数据要长期存活时才评；RT6 扩展点（Extension points and interception）：没有第二个人加东西就不建。**内部工具最容易在这里过度投入** |
| **产品 harness** | 有组织外的用户 | 全部（卡片的适用性（applicability）另行判断，见纪律 4） | — | RT2 RT7 RT9 是核心；RT11 若带 GUI 必评 |
| **平台 harness** | 维护团队以外的人在它上面开发（AQ3 是） | 全部，且 RT5 RT6 RT8 是重点 | — | RT5 覆盖面（coverage） 2 的判据升级为"**至少两项能力有两个真实可互换的实现**" |
| **单机实验 harness** | AQ2 答"否"：还没决定要不要继续做（不与其它形态叠加） | RT1 RT2 RT7 | 其余 | 只评三条：**配置算得出来、请求回放得出来、模型看到什么说得清**。其余等决定继续做再说（因此这一档不追求 MG2：RT9 是 N/A，达标线（pass line）留到决定继续做之后再算） |
| **多入口 harness**（命令行 + 界面 + 协议 + 桌面）| 两个以上入口（叠加在内部、产品或平台之上） | 全部，RT8 为重点 | — | RT8 覆盖面（coverage） 2 的判据升级为"**新入口加进来时不改运行时**" |

### 四条裁剪（tailoring）纪律

1. **标 N/A 要写理由**，一行即可（"无第三方扩展需求，RT5 RT6 不评"）。命中多行形态时：必评取并集，通常 N/A 取交集，权重变化全部适用。
2. **N/A 的维度不计入"多数"的分母**，分母按实际评估的维度数算；MG2、MG3 点名的维度为 N/A 时，那一档对这个系统不适用（见第 3 节）。
3. **不确定时先按适用处理**，评估过程中发现没有对应压力，再改标 N/A 并记录。
4. **卡片的适用性（applicability）优先于"必评"。** 12 各卡写的"没有 X 时标 N/A"（没有 GUI、只有一个入口、数据不跨版本存活）是事实判断，优先于形态表（profile table）的"必评"，与 AQ3 同理。

### 与开发 Harness 评估的形态口径不同

本节的 harness 形态决定十一维里哪些要评；[01 的适用性（applicability）裁剪（tailoring）](./01-evaluate-development-harness-coarse.md#5--适用性applicability裁剪tailoring)那套（库 / 服务 / monorepo / 插件平台 / 数据 / 文档站 / 脚本 / agent 产品）决定十七维里哪些要评。同一个仓库按两套各判一次，结论互不替代。

## 5 · 模仿判断：哪些值得抄

评估完，还有第二个问题：**这套做法里，哪些是它的处境逼出来的，哪些是可以学的？** 这两者长得一模一样，但照搬前者会把维护成本（maintenance cost）搬过来而收益搬不过来。

### 三条判据

**判据一：它解决的是"组合压力"还是"显而易见的缺失"？**

组合压力指这几件事**同时出现**：多个入口、多个可替换后端、会话级隔离、运行时装卸、第三方生态。

- 只出现一两项 → 那些看起来最"高级"的机制（能力 seam、完整扩展点体系、协议投影）**多半不该抄**。它们的成本只在组合压力出现后才换得回收益。
- 五项都出现 → 抄形状是划算的，因为你已经在付那份成本了，只是付得没有结构。

**判据二："能换"和"换出差异"是两件事。**

数一数有多少能力真的有两个可互换的实现。**"能换"的比例通常不低；"换出差异"的比例明显更低，而且后者才是产品差异所在。**

一个实用的读法：**多个实现集中的地方，是最该重造的基础设施；只有一个实现的地方，才是产品本身。**

**判据三：分辨"有机制"和"有正确完成标准"。**

一个有机制的系统和一个可信的系统之间差一层：**每一层都有明确的"什么算做完了"**。抄的时候要连这一层一起抄，否则抄来的机制没有完成判据，无法验证它在不在起作用。

### 抄与不抄的对照

| 值得抄（几乎零组合压力依赖） | 有压力再抄 | 不要照搬（组合压力的产物） |
|---|---|---|
| **只追加的事实源（source of truth） + 模型可见即记录** | 格式世代的迁移链 | 完整的能力 seam 体系 |
| **动作先记录再执行；结果单一出口** | 多入口共用运行时（第二个入口出现时做）| 为每个内部函数造一个 service |
| **授权与可见性分离；缺审批者时拒绝** | 上下文预算与回收 | 某些框架独有的调度/注入机制 |
| **规则写成会失败的检查，且检查被负例控制（negative control）** | 客户端模块边界的机器检查 | 多方审批编排（多数系统用不上）|
| **配置算得出来，且 dump 与启动同一算法** | 协议面的完整能力/否决清单 | 为一次性脚本造的版本机制 |
| **扩展点带"拦不住什么"的说明** | 运行时只读查询 | 把"能自动装"当成"可信" |

### 三条边界（照搬时最容易翻车）

1. **插件化不等于安全。** 能加载第三方代码不等于这些代码受约束。同进程的代码可以直接调用底层能力，绕过任何"扩展点"。**"能自动安装"和"可信"是两件事。**
2. **清理不等于回滚。** 卸载时撤销自己注册的东西，不会补偿已经发生的外部写入（发出的消息、写下的文件、发生的支付）。
3. **记录可见 ≠ 有授权。** 一个能查看运行状态的接口，不代表它有权修改；一个能看见工具的模型，不代表它被允许调用。

## 7 · 报告交付前的自检

1. **五个活体实验（live experiment）都真的跑过（被裁为 N/A 的维度，其对应实验记 `N/A`，不算未跑）。** 任何一个是"看代码推断的"，这一维的结论标"证据受限（evidence-limited）"。
2. **每个扣分点都能指到具体证据。** 哪次实验、哪一步、看到什么。
3. **区分"没有"和"不适用"。** 一个内部工具没有格式世代机制，是 N/A 不是 0。
4. **区分"它的取舍"和"它的缺口"。** 系统明说自己不保证某件事，且这个取舍有理由 → 不算缺口；系统**没提**这件事，而它确实做不到 → 是缺口。
5. **把"我手动兜住了"记下来。** 跑实验时，agent 常会顺手替系统补上缺失的机制（手动重启、手动核对、手动清理）。**每一次 agent 不得不接手，都是一个缺口**，写进对应维的案例列。
6. **（若这一轮翻过 12）每一次命中封顶（cap），都说得出观察它的探针（probe）。** 封顶规则（cap rules；见 [12 的附录 A](./12-evaluate-runtime-harness-fine.md#附录-a--封顶规则cap-rules速查)）是写成可观察条件的上限，每条都应由某一维的某个探针（probe）、[12 §3](./12-evaluate-runtime-harness-fine.md#3--第三层反证falsification) 第三层的某个动作，或第 2 节的某个活体实验（live experiment）观察到。说不出是谁观察的，这条封顶（cap）本次不用（按锚点（anchor）定档（final grade）），并把它当方法缺陷记下来。

| **LX3 加能力** | 加一个"查订单"工具：只改了一个插件文件，未动运行时；schema 自动出现在模型请求里；可见输入留下了记录。 | **通过** |
| **LX4 坏配置** | 把一个插件的键名改错：**启动成功**，日志里一行 warning，工具静默消失。 | **不通过** |
| **LX5 取消与失败** | 取消一个长任务：界面显示已取消，但后台进程继续跑了 40 秒才结束；工具内部异常被包成"返回空结果"交给模型，模型据此继续推理。 | **不通过** |

```
「系统自己接住了」与「靠我手动兜住」的分界：
  - 靠我兜住：确认插件真的加载了（每次改配置后要手动 grep 日志）
  - 靠我兜住：判断一次失败是"该重试"还是"该报 bug"（异常被吞成空结果）
```

### 表 3 · 缺口清单（gap list）

| # | 维 | 症状 | 后果 | 严重度 |
|---|---|---|---|---|
| 1 | RT2 | system prompt 与工具清单不进会话记录 | 模型行为异常时无法复盘；改版前后的差异永远说不清 | 高 |
| 2 | RT3 | 无格式版本，解析失败一律报"损坏" | 升级后旧会话被误判为数据丢失；用户不敢升级 | 高 |
| 3 | RT9 | 工具异常被吞成空结果 | 模型基于错误前提继续推理；问题在上线后很久才暴露 | 高 |
| 4 | RT1 | 无 dump 命令；坏配置静默跳过 | 团队以为能力开着实际没装（已发生）| 高 |
| 5 | RT5 | 提供方切换靠分支，散在 6 个文件 | 每加一个提供方成本翻倍；无法快速试新模型 | 中 |
| 6 | RT7 | 工具顺序随加载顺序变化 | 缓存命中率不稳定；同一个部署两次启动行为不同 | 中 |

### 一句话结论

这个系统的**问题不在模型层，在事实层**：它把"发生过什么"只记了一半（对话记了，模型看到的请求没记），把"现在装了什么"交给一份会静默失败的手改配置，把"动作失败了"归一化成了空结果。三件事的共同后果是——**出了问题查不出来，而且它不会告诉你查不出来。**

→ 下一步去 [20 从缺口到计划](./20-from-gaps-to-plan.md)：最痛的三维对应 RT2、RT3、RT9，按"验证手段不可信时先修验证"的顺序，RT2 与 RT9 应排在同一轮（它们共同决定"能不能信任系统报告的结果"）。

## 附录 A · 术语表

| 词 | 含义 |
|---|---|
| **运行时 harness** | 把模型、工具、会话、扩展点和交互组合成可运行 agent 的那套机制 |
| **组合内核** | 从声明层算出运行系统的部分；它先于任何插件存在 |
| **事实源（source of truth）** | 只追加的、唯一权威的记录；其它一切从它派生（derived） |
| **模型可见 ⟺ 已记录** | 任何进入模型请求的内容都必须能从持久记录重建 |
| **投影** | 从事实源（source of truth）算出来的视图（界面状态、检索结果、统计）；丢了可以重算 |
| **能力 seam** | 一项能力的三件套：定义 + 实现 + 使用方。三者齐备才算完整 |
| **扩展点** | 新行为被声明可以挂上去的位置；绕过它就意味着绕过该位置的检查 |
| **拦截点** | 管线里可以观察、改写或短路某个环节的位置 |
| **fail-closed** | 判不了的时候按"拒绝"处理，而不是按"放行"处理 |
| **格式世代** | 持久数据格式的一个版本；世代之间的关系是单向的（旧可迁、新被拒）|
| **受管范围** | 一次子进程启动所拥有的、可被观察和终止的进程集合；不假设它等于进程组 |
| **就绪边界** | 系统宣布"可以使用了"的那个时刻；它必须晚于所有异步初始化 |
| **负例控制（negative control）** | 故意制造一个该被抓住的回归，确认检查确实会失败，然后还原 |
| **组合压力** | 多入口、多可替换后端、会话级隔离、运行时装卸、第三方生态同时出现的处境 |
| **LX1–LX5** | 五个活体实验（live experiment）：回放（LX1）、换后端（LX2）、加能力（LX3）、坏配置（LX4）、取消与失败（LX5） |
| **MG0–MG3** | 运行时 harness 的成熟度档（maturity level）：单次可跑 / 有机制 / 可重建 / 可扩展可信任。与维度编号 RT1–RT11 无关 |
| **覆盖面（coverage）** | 这一维有没有对应机制：0 没有 / 1 部分场景 / 2 成体系 / 3 有 owner 与测试钉住（见第 3 节） |
| **约束力（enforcement）** | 这一维靠什么成立：约定 / 文档 / 测试或检查 / 运行时断言与负例控制（negative control；见第 3 节） |
