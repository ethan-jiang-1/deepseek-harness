# 运行时 Harness 评估 · 细粒度（探针、实验与封顶）

**这份文档是什么。** 运行时 Harness 评估的**细粒度**一半：对粗粒度（[11 粗粒度](./11-evaluate-runtime-harness.md)）里判为红、或这一轮决定要动的维度，用探针与五个活体实验钉死档位，用封顶规则压掉虚高的分。

**什么时候用。** 先跑 11：过适用性三问 → 十一维粗判 → 评分卡与缺口清单。**只在要动的维度上翻到本文对应的小节**；全量细粒度不是必须的。粗粒度的定义、两轴档位表、成熟度档、形态裁剪、产出模板与验收全在 11，本文不重复。

**为什么分两份。** 粗粒度定下来之后基本不动；细粒度会**持续增补**（新探针、新封顶）。分开之后，加一条封顶只改本文。

**编号约定。** 维度用 `RT`，探针用 `PB`，活体实验用 `LX`，成熟度档用 `MG`（见 [README 的标识符约定](./README.md#标识符约定token)）。

**配套文档。** [01 开发粗粒度](./01-evaluate-development-harness-coarse.md) · [02 开发细粒度](./02-evaluate-development-harness-fine.md) · [11 运行时粗粒度](./11-evaluate-runtime-harness.md) · [20 从缺口到计划](./20-from-gaps-to-plan.md)

## 1 · 细粒度怎么用

对每个决定要动的维度，走四步：

1. **走探针。** 用该维的 `PB1`–`PB5` 实际做一遍；需要实验的维度跑对应的 `LX`。
2. **按锚点定档。** 用该维自己的覆盖面/约束力锚点定档（档位含义见本卡的锚点；[11 §3](./11-evaluate-runtime-harness.md#3--十一维粗判) 只是总述）。
3. **命中封顶就压档。** 封顶规则是**上限**：命中哪条，对应轴的上限就被压低，不看其它证据。
4. **出证据。** 每个扣分都要能指到哪次实验、哪一步、看到什么（见 [11 §7](./11-evaluate-runtime-harness.md#7--评估者自己的验收)）。

**探针与判据的分工。** 探针用来收集证据，**改变档位的只有锚点与封顶**。观察到的现象若不在该维的锚点或封顶里（例如 PB5 的补充观察），记进案例列即可，不要据此定档。

**每一次命中封顶，都要说得出是哪个探针、11 第 2 节的哪个活体实验、或第三层的哪个动作观察到的。**

## 2 · 两轴与封顶语义

两轴档位、成熟度档与计数口径在 [11 §3](./11-evaluate-runtime-harness.md#3--十一维粗判)，这里只补两件细粒度才需要的事：

- **每维以自己的锚点为准。** 11 里那两张两轴表是所有维度的概括；冲突时以该维的锚点行为准。
- **封顶是上限，可能比锚点推导出的更严。** 每条规则给出的都是上限：可能更严（有意的惩罚），但不会让一个已经违反某档定义的系统拿到那一档。封顶集中列出**比阶梯更严**的惩罚；未列出的情形按锚点定档。

## 3 · 第三层：反证

### 第三层 · 反证

四个动作，检验前面两层自己的可信度：

1. **抽一条不变量**：系统声称的某条不变量（"模型看到的一定被记录了""每个注册都会被清理"），**它会在什么时候失败**？找得到那条会触发失败的路径吗？找不到，它可能只是一句注释。
2. **抽一个接口的失败面**：挑一个公开接口，看它在**正常失败**时怎么表现（用户操作非法 vs 基础设施故障）。两者混在一起 = 调用方永远分不清"该重试"还是"该报 bug"。结论记进 RT9 的案例列，并进表 3 的缺口清单。
3. **抽一个"故意不保证"**：成熟的运行时 harness 会**明说自己不保证什么**。找一份这样的清单。找不到，说明它把边界藏起来了——那是把未定义行为留给使用者。
4. **抽一次版本严格性**：拿一份用**更新版本**写的持久数据，喂给当前版本。**必须被拒绝，且提示是"版本过新，请升级"而不是"数据损坏"**。这两句话对用户的意义完全不同。

### 三层怎么合起来用

```
第一层 → 哪些机制缺
第二层 → 机制在实际运行里接得住吗（这一层无法靠读代码替代）
第三层 → 已有的保证是真的边界，还是自我描述
```

## 4 · 十一维细粒度卡

> 每张卡给出：一句话定义（一行，与 11 重复）、探针、两轴锚点、封顶规则、常见伪证、走形症状，以及两条硬边界。**改动维度定义或档位时改 11；只加探针或封顶时改这里。**

### RT1 组合与启动 · Composition and boot

**一句话**：正在运行的那个系统是**从声明算出来的**，而不是某一份被手改的最终配置。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找"最终生效的配置" | 它是一份文件，还是多层叠加算出来的？有几层？顺序固定吗 |
| PB2 | 找一条"dump 出最终配置"的命令 | 有吗；它和真正启动时用的是不是同一套算法；这一点有没有测试钉住 |
| PB3 | 看叠加规则 | 同 id 的覆盖是整份替换还是深合并？规则写清楚了吗（没写清楚 = 使用者会踩坑） |
| PB4 | 看坏输入 | 引用了不存在的组件、文件语法坏、文件在场但读不了——三种情况分别怎样 |
| PB5 | 看启动失败 | 进程起不来时报什么？说得出缺哪个组件吗 |

**覆盖面**：0 一份手改的最终配置 / 1 有分层但规则不成文 / 2 分层 + 顺序 + 明确的叠加规则 + 一条 dump 命令 / 3 且有完整性守卫（引用了不存在的组件必然失败，不静默跳过）

**约束力**：0 靠约定 / 1 文档说明 / 2 有校验（坏配置会红）/ 3 且 dump 与启动共用同一算法，并有测试钉住它

**封顶规则**
- 引用了不存在的组件却静默跳过 → 覆盖面封顶 1、约束力封顶 1
- "文件在场但读不了"被当作"没有这个文件" → 约束力封顶 1
- dump 命令与启动路径是两套代码 → 约束力封顶 2（dump 会撒谎）
- dump 与启动共用同一算法这件事没有测试钉住 → 约束力封顶 2
- 叠加规则不成文或含糊（使用者分不清深合并还是整份替换）→ 覆盖面封顶 1
- 没有 dump 最终配置的命令 → 覆盖面封顶 1

**常见伪证**："我们有配置文件" —— 配置文件不等于**算出来的**系统。手改的最终配置和叠加算出来的树，在排障时的价值差一个数量级。

**走形症状**：假设深合并而实际是整份替换，导致"我明明加了一个字段，怎么没了"；或者坏配置静默降级，用户以为某个能力开着，实际没装。

### RT2 会话事实源 · Session as the single source of truth

**一句话**：发生过的一切有一条**只追加**的记录；模型当时看到什么、做了什么，都能从这条记录重建。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找持久记录 | 是什么形态（只追加日志 / 可变表 / 只有内存） |
| PB2 | **做 LX1 回放实验** | 只读记录，能重建第 N 步的完整请求吗 |
| PB3 | 看派生 | 界面、统计、检索视图是从记录派生的，还是各自另存一份 |
| PB4 | 看裁剪 | 上下文超预算时被压缩的内容，是**从记录里删掉**还是只在投影里遮蔽 |
| PB5 | 看未知事件 | 读到不认识的事件类型时，默认是跳过还是拒绝重建 |

**覆盖面**：0 没有持久记录 / 1 有日志但模型可见输入不在其中 / 2 只追加记录 + 模型可见的一切都可重建 + 派生视图全部来自记录（不另存一份） / 3 且有明确的不变量（新的模型可见输入必须留下记录）

**约束力**：0 靠约定 / 1 文档里写了"应该记录" / 2 有运行时断言检查请求能从记录重建 / 3 且断言会在违反时失败并指出是哪一步

**封顶规则**
- 存在任何进入模型请求但不进记录的内容 → 覆盖面封顶 1、约束力封顶 1
- 压缩会从记录里**删除**内容（而不只是从投影里遮蔽）→ 覆盖面封顶 1（记录不再是只追加的）
- 读到未知事件默认跳过 → 约束力封顶 1（未知事件可能改变其余记录怎么读）
- 记录是可原地改写的表（只追加不成立）→ 覆盖面封顶 1
- 界面、统计、检索视图各自另存一份（派生与记录两处存真）→ 覆盖面封顶 1
- 记录重建的断言从不失败、或失败时指不出是哪一步 → 约束力封顶 2

**常见伪证**："我们记录了所有对话" —— 对话不等于请求。模型收到的请求里还有 system prompt、工具清单、动态上下文；这些如果不在记录里，回放出来的是**另一个请求**。

**走形症状**：把会话记录当界面状态存（界面一改，历史就变）；派生视图与记录两处存真，出问题时不知道信哪个。

### RT3 格式世代与兼容 · Format generations

**一句话**：持久数据的格式有版本，版本规则是**只向前不向后**：老数据能迁移上来，用新版本写的数据在老版本上被明确拒绝，已提交的世代永不改写。

*适用性：持久数据要跨版本长期存活时评；一次性脚本不做。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找版本号 | 有几个？谁是权威（代码里的常量，还是发布记录，还是文件名） |
| PB2 | **做第三层第 4 项** | 用更新版本写的数据喂给当前版本，看提示是什么（没有更高版本时，手工把版本号改成更新的值再读） |
| PB3 | 看迁移 | 老版本数据怎么读上来；迁移会不会**改写**原始文件 |
| PB4 | 看未知事件 | 同版本内的未知事件怎么处理？跨版本边呢 |
| PB5 | 看触发条件 | 什么情况下才该升版本？（是"任何变化"还是"结构变化"） |

**覆盖面**：0 没有版本概念 / 1 有版本号但没有规则 / 2 单向兼容规则明确（旧可迁、新拒绝）+ 已提交世代不可改写 / 3 且迁移链有独立规格与硬性前置校验

**约束力**：0 靠约定 / 1 文档说明 / 2 有检查（版本不匹配会红）/ 3 且三条路径被明确区分：版本过新、物理损坏、没有可用迁移——三种错误的提示不同

**封顶规则**
- "版本过新"被报成"数据损坏" → 约束力封顶 1（用户会被引向完全错误的处置）
- 迁移会就地改写或删除已提交的世代 → 覆盖面封顶 1、约束力封顶 1
- 版本号有多个来源（代码常量、包版本、文件名各说各话）→ 覆盖面封顶 2
- 更新版本写的数据不被拒绝（被接受或被静默降级）→ 覆盖面封顶 1、约束力封顶 1
- 迁移静默丢字段或跳过读不懂的内容 → 覆盖面封顶 1
- 迁移没有独立规格与前置校验（迁移逻辑散在读路径里）→ 覆盖面封顶 2

**常见伪证**："我们遵循语义化版本" —— 包的版本号和**持久数据的格式版本**是两件不同的事。前者变化频繁，后者只在结构变化时动。

**走形症状**：把"能解析不报错"当成兼容——静默跳过读不懂的内容，会让重建出的历史与真实发生过的历史不一致，这比直接报错危险得多。

### RT4 循环与终结边界 · Loop and termination boundaries

**一句话**：一次工作从哪开始、到哪算结束，有**分层的、可判定的**边界；"空闲"不等于"完成"。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找终结层 | 有几层（一次模型请求 / 一个输入被处理完 / 一段连续活动 / 一个长期目标）？各自怎么判定 |
| PB2 | 找终结原因 | 结束时记录的原因有几种？是封闭集合吗？**"被取消"和"完成"分得开吗** |
| PB3 | **做 LX5 取消实验** | 在声明的超时预算内真的停了吗？取消留下记录了吗 |
| PB4 | 看恢复 | 进程重启后，正在进行的活动怎么处理？自动续跑还是需要人重新授权；这条恢复路径有没有测试钉住（含"重启后不自动做危险动作"） |
| PB5 | 看拒绝 | 一个输入在开始处理前就被拒绝，会留下"这次尝试"的痕迹吗 |

**覆盖面**：0 只有"跑完了/没跑完" / 1 有终结事件但原因不完整 / 2 分层边界 + 封闭的终结原因集合 / 3 且有恢复语义（重启后状态怎么重建、是否需要人工确认）

**约束力**：0 靠约定 / 1 文档说明 / 2 有断言（终结原因必须是封闭集合里的值）/ 3 且恢复路径有测试钉住（包括"重启后不自动做危险动作"）

**封顶规则**
- "空闲"被当作"完成" → 覆盖面封顶 1
- 终结原因不是封闭集合（可以随便塞字符串）→ 覆盖面封顶 1
- 重启后自动继续执行危险动作 → 约束力封顶 1
- 取消只是"不再等结果"（动作在后台继续跑）或取消不留记录 → 覆盖面封顶 1
- 重启后没有恢复语义（状态不重建、也不要求人工确认）→ 覆盖面封顶 2
- 被拒绝的输入不留任何痕迹（事后无从判断"拒绝过什么"）→ 覆盖面封顶 2
- 恢复路径没有测试钉住 → 约束力封顶 2

**常见伪证**："我们的 agent 会一直跑到没有工具调用为止" —— 那只是这一次请求序列结束。一个需要多轮推进的任务，在"暂时没有下一步动作"和"已经完成"之间没有区分，用户就无法判断该不该接管。

**走形症状**：把取消做成"不再关心结果"（动作还在后台跑）；或者把重启当成无事发生（危险动作被自动接着做）。

### RT5 能力 seam 与可替换性 · Capability seams

**一句话**：一项能力由**定义 + 实现 + 使用方**三个角色构成；换一个实现，使用方一行不改。

*适用性：第二个真实实现出现、或确实要换后端时评；只有一个实现的内部工具标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | **做 LX2 换后端实验** | 数改了几个文件。消费者改了吗 |
| PB2 | 数一数有哪些"可替换"的能力 | 每个有几个真实实现（不是测试替身）、几个真实使用方 |
| PB3 | 看单向依赖 | 使用方依赖的是**定义**还是某个具体实现 |
| PB4 | 看"定义"里有什么 | 有没有混进某个使用方的专有名词（某个工具的参数字段名、某个界面的卡片类型）|
| PB5 | 找"故意不是可替换点"的地方 | 有没有明确说明"这里不打算做成可替换的"及其理由 |

**覆盖面**：0 没有可替换概念，换实现要改消费者 / 1 有抽象但还没有第二个实现（零个或一个实现） / 2 **至少一项能力有两个真实可互换的实现，且消费者未改** / 3 且有多项能力达到这个状态，并有"故意不可替换"的明确清单

**约束力**：0 靠约定 / 1 文档说明 / 2 有检查（使用方不得直接依赖具体实现）/ 3 且有测试证明"换实现后真实组合仍通过"

**封顶规则**
- 所谓的"可替换点"只有唯一使用方和唯一实现（自产自销）→ 覆盖面封顶 1（**等于还没有市场**）
- 只有定义、没有任何实现 → 覆盖面封顶 1（形状还会被第一个实现改掉）
- 定义里混进了某个使用方的专有名词 → 覆盖面封顶 2
- 换实现需要改消费者代码（LX2 实验里消费者被改动）→ 覆盖面封顶 1
- 没有"故意不可替换"的明确清单 → 覆盖面封顶 2
- 可替换点没有任何检查或测试钉住（使用方直接依赖具体实现也没人发现）→ 约束力封顶 1

**常见伪证**："我们所有的东西都是插件" —— 插件化说的是**能不能加**，不是**能不能换**。加十个插件不需要 seam；换一个实现才需要。

**走形症状**：为只在一个地方用到的私有逻辑造一个"服务"；或者反过来，为一个真实存在的替换需求拒绝建 seam，导致每次换后端都要改一片代码。

**一个判据**：**一个公开方法只有一个内部调用者，那它其实是私有函数，不该抬成公开合同。**

### RT6 扩展点与拦截 · Extension points and interception

**一句话**：加新行为有唯一的、已声明的去处；拦截点在管线里，不在每个实现里各写一份。

*适用性：有第二个人或第二个团队要往上面加东西时评；没有扩展需求时标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | **做 LX3 加能力实验** | 数改了哪些文件、动了哪些层。**动核心了吗** |
| PB2 | 找一张"新行为挂哪里"的表 | 有吗；右列是具体注册动作还是"参考某文档"；有没有成文的升级条件（什么时候必须从扩展点升级到核心改动） |
| PB3 | 看拦截点 | 有几类（只观察 / 可改写 / 可短路）？分得清吗 |
| PB4 | 看每个拦截点的**边界** | 文档说了它**拦不住什么**吗 |
| PB5 | 看注册的生命周期 | 一个注册在卸载时会撤销吗？谁负责 |

**覆盖面**：0 新行为靠改核心 / 1 有扩展点但没有归属表 / 2 有归属表 + 分类型的拦截点 + 明确的"拦不住什么" / 3 且注册的生命周期统一（谁注册谁负责撤销），并有升级条件的说明

**约束力**：0 靠约定 / 1 文档说明 / 2 有检查（绕过扩展点的结构会被发现）/ 3 且有机制强制走扩展点（例如只允许通过注册 API 接入）

**封顶规则**
- 每个实现内部各自做拦截（策略散在 N 处）→ 覆盖面封顶 1、约束力封顶 1
- 归属表右列是"参考某文档"这类二级指引 → 覆盖面封顶 1
- 拦截点没有"拦不住什么"的说明 → 覆盖面封顶 1
- 加一个常见能力需要修改循环本身 → 覆盖面封顶 1
- 拦截点不分类（只观察 / 可改写 / 可短路混在一个事件类型里）→ 覆盖面封顶 1
- 注册在卸载时不撤销（生命周期无人负责）→ 覆盖面封顶 2
- 绕过扩展点的结构检查不存在（改了核心也没人发现）→ 约束力封顶 1
- 没有成文的升级条件（何时该从扩展点升级到核心没有判据）→ 覆盖面封顶 2

**常见伪证**："我们的事件系统很灵活" —— 灵活不等于**分类清楚**。"只观察"、"可以改写结果"、"可以让整个操作短路"是三种完全不同的权限；混在一个事件类型里，扩展作者会误用。

**走形症状**：常见能力被实现成"给核心加一个分支"；或者拦截点太多太细，扩展作者不知道选哪个。

**一个判据**：**你的策略改动要动几个文件？答案应该是"一个"。**

### RT7 模型可见面组装 · Model-visible surface assembly

**一句话**：模型这一步看到什么——可见工具、提示词、内容块——是**每一步显式组装**的，并且组装结果**必须留下记录**。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | **做 LX1 回放** | 能重建第 N 步的可见工具清单和提示词吗 |
| PB2 | 看可见集合怎么算 | 是静态的，还是按作用域每步算的？子任务能不能收窄 |
| PB3 | 看提示词的顺序 | 越稳定的内容越靠前吗？（靠后的变化不会让前面缓存失效）|
| PB4 | 看"可见但不可用" | "模型看得见这个工具"和"这个动作被允许"是两套判定吗 |
| PB5 | 看内容块 | 文件、图片等非文本内容怎么进请求？进来的东西和不进来的东西，规则对称吗 |

**覆盖面**：0 可见集合是写死的 / 1 有动态组装但结果不进记录 / 2 每步显式组装 + 结果进记录 / 3 且有作用域收窄（子任务看到的是子集）与稳定的排序规则

**约束力**：0 靠约定 / 1 文档说明 / 2 有断言（请求必须能从记录重建）/ 3 且断言会在违反时失败并指出哪一步不一致

**封顶规则**
- 有任何进入模型请求的内容不进记录 → 覆盖面封顶 1、约束力封顶 1
- 可见集合影响授权（"看得到就能做"）→ 约束力封顶 1
- 提示词顺序把每台机器/每个用户不同的内容放在最前 → 覆盖面封顶 2（缓存永远命中不了）
- 可见集合不能按作用域收窄（子任务看到的是全集）→ 覆盖面封顶 2
- 请求重建的断言从不失败、或失败时指不出哪一步 → 约束力封顶 2

**常见伪证**："提示词组装很灵活，插件都能加" —— 灵活不是重点，**"加了什么"能不能事后重建**才是。一个不能重建提示词的系统，无法解释自己的行为。

**走形症状**：把"可见性"当成授权边界（危险：以为藏起来就安全）；或者提示词按插件加载顺序拼接，同一个部署两次启动得到不同的前缀。

### RT8 入口与协议投影 · Entry surfaces and protocol projection

**一句话**：多个入口（命令行、界面、协议接口）**共用同一套运行时语义**，各自只负责投影，不各自实现一遍循环。

*适用性：两个以上入口时评；只有一个入口时标 N/A（不要提前抽象）。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 数入口，找它们共用什么 | 是不是都通过同一套会话/循环接口驱动 |
| PB2 | 看每个入口的**输出通道归属** | 哪个入口的 stdout 是给人看的、哪个是协议帧？（结论决定能不能装日志）|
| PB3 | 找"故意不保证"清单 | 每个协议面有没有明说自己不保证什么；这份清单被测试钉住了吗 |
| PB4 | 看就绪边界 | 协议入口宣布 ready 之前，等所有异步初始化完成了吗 |
| PB5 | 看订阅过滤 | 一个入口收到的事件，是按"是不是它创建的"过滤，还是全量 |

**覆盖面**：0 每个入口一套实现 / 1 共用部分逻辑 / 2 共用运行时语义，入口只做投影（事件按订阅声明过滤，而不是按"是不是我创建的"） / 3 且每个协议面有明确的能力清单与否决清单

**约束力**：0 靠约定 / 1 文档说明 / 2 有检查（协议帧格式有校验）/ 3 且"故意不保证"是一份被测试钉住的合同

**封顶规则**
- 某个入口自己实现了一套循环 → 覆盖面封顶 1
- 入口按"是不是它创建的"过滤事件（已违反覆盖面 2 的定义）→ 覆盖面封顶 1
- 协议入口的 stdout 与人类可读输出混用 → 约束力封顶 1（协议会被日志污染）
- 没有"故意不保证"清单 → 覆盖面封顶 2
- 就绪信号早于异步初始化完成 → 约束力封顶 1
- "故意不保证"清单只是文档、没有测试钉住 → 约束力封顶 2

**常见伪证**："我们的 API 很稳定" —— 稳定是承诺，**不保证什么**才是有用的信息。一个不说自己边界的协议，把未定义行为留给了使用者。

**走形症状**：第五个入口加进来时语义开始分叉；或者协议里混进了内部实现细节，改内部结构就破坏兼容。

### RT9 工具执行与授权 · Tool execution and authorization

**一句话**：一个动作从发起到落定走**同一条管线**；参数在进入判定前就被冻结；结果只有一条出口；授权判定**失败时关闭**（fail-closed）。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 画管线 | 从发起到结果回到模型，中间有哪几个环节？每环能做什么、不能做什么 |
| PB2 | 看参数 | 判定环节能改写参数吗？参数在判定前是否已冻结 |
| PB3 | **做 LX5** | 取消、超时、工具内部报错——三种情况各自的结果是什么形态 |
| PB4 | 看授权 | 没有审批者时默认是放行还是拒绝？**审计写入失败时会发生什么** |
| PB5 | 看记时 | 动作是**先记录再执行**，还是执行完再记录？失败的动作在记录里吗 |

**覆盖面**：0 没有统一管线，各实现自己处理 / 1 有管线但环节不全 / 2 完整管线：先记录 → 判定 → 执行 → 归一化 → 单一出口 / 3 且有独立的审批环节与审计配对（问与答都能对上）

*适用性：单机实验档（没有审批面）标 N/A（见 [11 §4](./11-evaluate-runtime-harness.md#4--形态裁剪)）。*

**约束力**：0 靠约定 / 1 文档说明 / 2 权限判定在代码里强制 / 3 且越权必然失败、审计不可静默丢失（写不进去就拒签）

**封顶规则**
- 参数在判定环节可被改写 → 覆盖面封顶 2、约束力封顶 1（判定依据与实际执行的东西不一致）
- 没有审批者时默认放行 → 约束力封顶 1
- 审计写入失败仍返回决策 → 覆盖面封顶 2、约束力封顶 1
- 结果不是单一出口（存在"部分成功""未知状态"）→ 覆盖面封顶 1、约束力封顶 1
- 动作执行完才记录（先执行后记录）→ 覆盖面封顶 1
- 授权判定散在每个工具内部、改一条规则要动多处 → 覆盖面封顶 1、约束力封顶 1

**常见伪证**："每个工具自己会检查权限" —— 那是策略散在 N 处，而且**判定发生在参数已经进入工具之后**，中间有一段时间窗。

**走形症状**：把"可见性"当授权；审批做成事后通知；取消只是"不再等"。

**两条硬边界**：
- **可见集收窄的是模型的选择空间，不是授权。** 授权必须独立成立。
- **取消不能撤销已经发生的外部效果。** 一个动作如果已经写了远程系统，取消它就等于"不再等结果"，不等于"它没发生"。

### RT10 可执行治理 · Executable governance

**一句话**：规则被机器拦住，不写在文档里等人自觉；而**拦截机制自己也被证明会失败**。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找检查清单的**聚合点** | 所有检查有一个统一的注册处吗？还是散在几十个脚本里 |
| PB2 | 数一数"文档规则"与"机器规则"的比例 | 有多少条写在文档里的规则，其实可以做成检查 |
| PB3 | **做第三层第 1 项** | 挑一条声称的不变量，找它会在什么情况下失败 |
| PB4 | 看检查的可信度 | 随便挑一个检查，说得出它最近一次为红是什么回归吗 |
| PB5 | 看成熟度数字 | 如果有"可替换率""覆盖率"这类数字，能复算吗？复算的坑被列出来了吗 |

**覆盖面**：0 规则都在文档里 / 1 有一些检查但不聚合 / 2 有统一的检查注册处 + 不变量只在有意义时写 / 3 且有负例控制与可复算的成熟度度量

**约束力**：0 靠约定 / 1 检查存在但要人记得跑 / 2 检查接进了提交流程 / 3 且检查自己被负例控制过（证明过会红）

**封顶规则**
- 存在"永远为绿"的检查且无人核查 → 覆盖面封顶 2、约束力封顶 1
- 不变量检查的是"服务在不在""插件元数据对不对"这类存在性 → 覆盖面封顶 1（**那不是不变量**）
- 成熟度数字手工维护且无 freshness 检查 → 覆盖面封顶 2
- 规则只写在文档里，且该规则可机械判断（连检查都没有）→ 约束力封顶 0
- 检查散在多个脚本里、没有统一注册处 → 覆盖面封顶 1

**常见伪证**："我们有一整套 CI" —— CI 全绿说明检查碰巧碰到的地方没问题。**说得出某个检查最近一次为红的原因**，才说明检查是活的。

**走形症状**：绿灯数目成了 KPI；检查变成仪式，然后开始被绕过；或者相反——不变量写了一大堆，检查的全是"这个服务注册了吗"。

**一个判据**：**不变量只有在"两个独立观察可能分歧"时才值得写。** 检查"某个东西存在"不是不变量；检查"两个独立算出来的结果必须一致"才是。

### RT11 客户端组装纪律 · Client composition discipline

**仅当这个 harness 带 GUI 客户端时评；没有 GUI 标 N/A。**

**一句话**：界面状态从**权威事实**派生；业务数据不在界面层另存一份；跨模块只走声明的接口。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找一个界面上的数字，往回追 | 它最终来自哪？是权威记录，还是界面层自己攒的 |
| PB2 | 看界面层能不能改业务数据、能不能产生输入 | 有没有"界面先改了、再同步回去"的路径；界面发起或产生的模型可见输入（用户消息、附件、卡片动作）进不进会话记录、能不能回放 |
| PB3 | 看模块边界 | 一个界面模块能不能直接引用另一个界面模块的实现 |
| PB4 | 看订阅 | 组件里有没有各自手写的订阅逻辑（应该有统一机制）|
| PB5 | 看未知数据 | 界面遇到不认识的数据形态时，是崩还是回落到通用形态 |

**覆盖面**：0 界面自持业务状态 / 1 部分派生部分自持 / 2 全部从权威事实派生 + 统一订阅机制 / 3 且模块边界有机器检查

**约束力**：0 靠约定 / 1 文档说明 / 2 有检查（越界引用会红）/ 3 且"界面产生的新模型可见输入必须留下记录"被强制

**封顶规则**
- 界面层可以写业务数据 → 覆盖面封顶 1（两处存真）
- 界面产生的新模型可见输入不进记录 → 约束力封顶 1
- 模块之间可以互相引用具体实现 → 覆盖面封顶 2、约束力封顶 1
- 遇到未知数据形态直接崩 → 约束力封顶 2
- 组件各自手写订阅逻辑（没有统一机制）→ 覆盖面封顶 1

**常见伪证**："我们的前端架构很清晰" —— 清晰是给作者的。检验法是问"这个数字改了，界面上几处会跟着变"。

**走形症状**：界面自己攒一份业务状态（两处存真）；模块之间直接引用彼此的实现；遇到不认识的数据形态直接崩；或者界面产生的新模型可见输入没留下记录。


### 表 3 · 缺口清单

| # | 维 | 症状 | 后果 | 严重度 |
|---|---|---|---|---|
| 1 | RT2 | system prompt 与工具清单不进会话记录 | 模型行为异常时无法复盘；改版前后的差异永远说不清 | 高 |
| 2 | RT3 | 无格式版本，解析失败一律报"损坏" | 升级后旧会话被误判为数据丢失；用户不敢升级 | 高 |
| 3 | RT9 | 工具异常被吞成空结果 | 模型基于错误前提继续推理；问题在上线后很久才暴露 | 高 |
| 4 | RT1 | 无 dump 命令；坏配置静默跳过 | 团队以为能力开着实际没装（已发生）| 高 |
| 5 | RT5 | 提供方切换靠分支，散在 6 个文件 | 每加一个提供方成本翻倍；无法快速试新模型 | 中 |
| 6 | RT7 | 工具顺序随加载顺序变化 | 缓存命中率不稳定；同一个部署两次启动行为不同 | 中 |

### 一句话结论

这个系统的**问题不在模型层，在事实层**：它把"发生过什么"只记了一半（对话记了，模型看到的请求没记），把"现在装了什么"交给一份会静默失败的手改配置，把"动作失败了"归一化成了空结果。三件事的共同后果是——**出了问题查不出来，而且它不会告诉你查不出来。**

→ 下一步去 [20 从缺口到计划](./20-from-gaps-to-plan.md)：最痛的三维对应 RT2、RT3、RT9，按"修尺子先于量东西"的顺序，RT2 与 RT9 应排在同一轮（它们共同决定"能不能信任系统报告的结果"）。
