# 开发 Harness 评估 · 细粒度（fine-grained；探针（probe）、锚点（anchor）与封顶（cap））

**这份文档是什么。** 开发 Harness 评估的**细粒度（fine-grained）**一半：对粗粒度（coarse-grained；[01 粗粒度（coarse-grained）](./01-evaluate-development-harness-coarse.md)）里判为红、或这一轮决定要动的维度，用探针（probe）逐条钉死档位，用封顶规则（cap rules）压掉虚高的分。

**什么时候用。** 先跑 01：出评分卡（scorecard；表 1）与缺口清单（gap list；表 2），每维得到一个粗判档（coarse grade）。**快诊（quick check）只在粗判（coarse check）为红、这一轮要动、或要写成最终结论的维度上翻到本文对应的小节**，把粗判档（coarse grade）钉成定档（final grade）；全量模式（full mode）逐维走完本文。维度集合、通用两轴（two axes）、成熟度档（maturity level）、适用性（applicability）裁剪（tailoring）、报告格式与自检在 01；每维的一句话定义、锚点阶梯（anchor ladder）、探针（probe）与封顶（cap）在本文。

**为什么分两份。** 粗粒度（coarse-grained）定下来之后基本不动；细粒度（fine-grained）会**持续增补**（新探针（probe）、新封顶（cap））。分开之后，加一条封顶（cap）只改本文，不会碰到稳定的粗粒度（coarse-grained）。

**编号约定。** 维度用两字母前缀（`KN`/`CP`/`EV`/`ST`/`MT`），探针（probe）用 `PB`，封顶规则（cap rules）见本文附录 A；完整对照见 [README 的标识符约定](./README.md#标识符约定token)。

**本文引用 01 的定义**：信息缺口（information gap） `IG1`–`IG7`（01 §1）、证据级（evidence level） `EL0`–`EL3`（01 §2）、第一 / 第二层（01 §3）、两轴（two axes）档位与成熟度档（maturity level） `MG0`–`MG3`（01 §4），见 [01](./01-evaluate-development-harness-coarse.md)。第三层（反证 falsification）在本文 §3 定义。

## 1 · 细粒度（fine-grained）怎么用

对每个决定要动的维度，走四步：

1. **走探针（probe）。** 用该维的探针（probe；`PB1` 起，最多到 `PB6`）实际做一遍（不是读文档推断），记下"我做了什么、看到了什么"。
2. **按锚点（anchor）定档（final grade）。** 用该维自己的覆盖面（coverage）/约束力（enforcement）锚点（anchor）定档（final grade；[01 §4](./01-evaluate-development-harness-coarse.md#4--十七维粗判coarse-check) 的两轴（two axes）表是通用轴，约束力（enforcement） 3 的通用条件见 [§2](#2--两轴two-axes与封顶cap语义)）。
3. **命中封顶（cap）就压档。** 封顶规则（cap rules）是**上限**：命中哪条，对应轴的上限就被压低，不看其它证据。
4. **出证据。** 每一个扣分都要能指到具体文件、提交或命令；说不出证据的扣分不算数（见 [01 §7](./01-evaluate-development-harness-coarse.md#7--报告交付前的自检)）。

**探针（probe）与判据的分工。** 探针（probe）用来收集证据，**改变档位的只有锚点（anchor）与封顶（cap）**。观察到的现象若不在该维的锚点（anchor）或封顶（cap）里，记进案例列即可，不要据此定档（final grade）。

**每一次命中封顶（cap），都要说得出是哪个探针（probe）或第三层的哪个动作观察到的**；说不出来就把它当方法缺陷记下来，不要照记分。

## 2 · 两轴（two axes）与封顶（cap）语义

两轴（two axes）的通用定义、成熟度档（maturity level）与计数口径在 [01 §4](./01-evaluate-development-harness-coarse.md#4--十七维粗判coarse-check)，这里只补三件细粒度（fine-grained）才需要的事：

- **每维以自己的锚点（anchor）为准。** 01 里那两张两轴（two axes）表是所有维度共用的通用轴；同一档在不同维度上的判据不同，定档（final grade）时以该维的锚点（anchor）行为准。
- **约束力（enforcement） 3 包含通用条件。** 每维锚点（anchor）的约束力（enforcement） 3 只写这一维特有的机制；另外一律要求对应的检查做过负例控制（negative control；引入违规看它红、还原看它绿，见 EV2 卡）。机制在、但没做过负例控制（negative control），约束力（enforcement）停在 2。
- **封顶（cap）是命中即生效的上限。** 多数条目是锚点阶梯（anchor ladder）判据的可观察版本（把"到不了某档"写成探针（probe）看得到的条件），少数比阶梯更严（有意的惩罚）；没有一条比阶梯宽松。命中一条，档位就不高于它写的上限。没有列出的情形，直接按锚点阶梯（anchor ladder）定档（final grade）。

## 3 · 第三层：反证（falsification）

第三层检验的是**前面两层自己的可信度**。四个动作：

1. **抽检一个检查**：随便挑一个现有的检查，说得出它最近一次为红是因为什么回归吗？说不出，这个检查按 EL2 记，它所属维度的约束力（enforcement）到不了 3；如果是在给 EV2 定档（final grade），按 EV2 卡抽满三个再套封顶（cap）。
2. **抽检一条规则**：随便挑一条写在文档里的规则，找一条最近违反过它的提交。找得到 → 规则没有任何东西执行（EL1）。
3. **抽检一个链接**：从根入口文件随机点 5 个链接。打不开的记进表 4。
4. **抽检一次"应该失败"**：故意制造一个小违规（加一个错别字进被检查的文件、破坏一个链接），跑检查，看它红不红，然后还原。**不允许跳过这一步**——判断"这个仓库的检查会不会失败"，只能靠亲手让它失败一次。

### 三层怎么合起来用

第一层（静态清点）与第二层（垂直切片 vertical slice）的定义见 [01 §3](./01-evaluate-development-harness-coarse.md#3--评估分三层)。三层各回答一个问题：

- **第一层** → 结构在哪缺（哪一维低）
- **第二层** → 实际怎么跑（缺口造成什么后果）
- **第三层** → 已有的机制可信吗（低分是"没有"还是"有但假的"）

第一层的缺口清单（gap list）和第二层的走查记录会合流成一张**施工顺序（build order）表**（这张表由[20 从缺口到计划](./20-from-gaps-to-plan.md)的[排序原则（ordering principles）](./20-from-gaps-to-plan.md#1--排序原则ordering-principles)与[循环](./20-from-gaps-to-plan.md#7--一轮打磨的循环与停止条件)产出，本文不提供模板）：每一个"靠猜"和"没证据"都能归到十七维里的某一维，**哪一维的案例最多最痛，就先去那份文档里找那一维的处置卡（remediation card）**。

> 每张卡给出：一句话定义、填的缺口、探针（probe）、两轴（two axes）锚点（anchor）、封顶规则（cap rules）、常见伪证（false evidence）、走形症状（failure symptoms），以及可选的例证。**一句话定义与锚点阶梯（anchor ladder）以本文为准**，01 §4 的一览只给名字与一行概述。增删维度、改通用两轴（two axes）或成熟度档（maturity level）时改 01；改某一维的定义、锚点（anchor）、探针（probe）或封顶（cap）时改这里（改锚点（anchor）时同步检查封顶（cap），见 [README 的维护规则](./README.md#维护规则)）。

### 知识归位 · KN 组

#### KN1 入口链 · Entry chain

**填的缺口**：IG1 必须遵守什么 / IG2 系统由什么组成

**一句话（summary）**：新会话开始时被稳定读到的那份最小规则集，以及它指向其余知识的路由。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | `ls -a` 根目录与主要子树，找出所有面向 agent 的入口文件（`AGENTS.md` / `CLAUDE.md` / `.cursorrules` / `CONTRIBUTING.md` / `.github/copilot-instructions.md`） | 有几个？分别服务谁？有没有重复 |
| PB2 | 若同一目录同时存在两个入口文件名：`ls -la` | 是不是符号链接。不是 → 两份事实，迟早分叉 |
| PB3 | 数根入口文件的行数与词数 | 是不是"大而全总览"。含教程、历史故事、完整流程 → 超预算；有没有成文的字数预算与维护触发条件（trigger），以及执行它的字数上限门禁（gate；它红过吗） |
| PB4 | 从根入口里抽 5 条规则，逐条找它的详细 home | 每条能不能点到唯一一个更详细的位置 |
| PB5 | 数列子树入口文件的数量与理由 | 是不是"为放而放"。绝大多数目录只该有 README |

**覆盖面（coverage）**：0 没有入口 / 1 有但混着教程与历史 / 2 短入口 + 布局 + 命令，其余链接出去 / 3 且有明确的字数预算与维护触发条件（trigger）

**约束力（enforcement）**：0 靠口传 / 1 写在 prose 里 / 2 有链接检查（断链会红）/ 3 且有字数上限门禁（gate）

**封顶规则（cap rules）**
- 同一目录存在两个**非符号链接**的入口文件 → 覆盖面（coverage）封顶（cap） 1（已经有两份事实了）
- 根入口文件包含教程或历史叙述 → 覆盖面（coverage）封顶（cap） 1
- 根入口里的链接有打不开的 → 约束力（enforcement）封顶（cap） 1（路由断了，等于没有）
- 根入口没有指向更详细 home 的链接（所有内容堆在一个文件里）→ 覆盖面（coverage）封顶（cap） 1
- 根入口是大而全总览（超出成文的行/词预算；没有成文预算时，看它是否把流程、架构说明整段写在里面，即使不含教程与历史）→ 覆盖面（coverage）封顶（cap） 1
- 根入口没有成文的字数预算或维护触发条件（trigger） → 覆盖面（coverage）封顶（cap） 2
- 根入口没有字数上限门禁（gate） → 约束力（enforcement）封顶（cap） 2

**常见伪证（false evidence）**："我们有 `AGENTS.md`" —— 有文件不等于有路由。文件里如果没有指出去的链接，它只是一份大文件，不是入口链。

**走形症状（failure symptoms）**：把根入口写成一份完整手册；或者到处放子树入口，让每个目录都要重新学一套。

**例证（exemplar）**（可选核对）：DSH 的根 `AGENTS.md` 只放常驻规则（always-loaded rules）、布局与命令，每条规则 1–3 行并立刻给出链接；`CLAUDE.md` 是 `AGENTS.md` 的符号链接，四个目录各一处；根文件有字数上限（≤1,950 词），由 `verify-doc-budgets` 执行。

#### KN2 归属 · One home per fact

**填的缺口**：IG1 IG2 IG3

**一句话（summary）**：每类事实住在**负责它的那一层**，其它地方只放链接、不复制。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 随便挑 5 条规则，不靠作者带路找它的唯一 home | 不靠作者带路能不能指出来；home 里有没有写清"不该从这里取得什么"（禁放什么） |
| PB2 | 对每条规则，全局搜它的关键句 | 是不是在第二个地方又写了一遍 |
| PB3 | 找一个"改了 A 必须同时改 B"的例子，并看派生（derived）内容 | 这种耦合是否存在；有没有机制保证两边同步；派生（derived）内容有没有 freshness 门禁（gate；源头变了、派生（derived）没跟上会红吗） |
| PB4 | 检查当前事实与决策理由是否分家 | 现状文档里有没有夹着大段"为什么当初…"；决策记录（decision record）里有没有被当成当前接口说明 |
| PB5 | 找负知识：有没有记录"我们为什么不走某条路" | 被否决的方案，新参与者还会不会再提一遍 |
| PB6 | 找同一概念的不同叫法 | 同一个东西有没有两个名字、两个近义词被当成两件事？词表能不能指出每个词的唯一含义 |

**覆盖面（coverage）**：0 没有归属（ownership）概念 / 1 部分事实有家 / 2 每类事实有明确 owner 且写了"不该从这里取得什么"，术语有唯一含义（同一概念一个名字） / 3 且有维护触发条件（trigger）与同步门禁（gate）

**约束力（enforcement）**：0 靠口传 / 1 写在 prose 里 / 2 有链接/一致性检查（复制件不一致会红）/ 3 且有生成物（generated artifact） freshness 门禁（gate；源头变了派生（derived）没跟上就红）

**封顶规则（cap rules）**
- 任何一条规则指不出唯一 home → 覆盖面（coverage）封顶（cap） 1
- 存在同一事实的两份**可写**拷贝（非生成物 generated artifact） → 覆盖面（coverage）封顶（cap） 1
- 有事实类别没写出"不该从这里取得什么" → 覆盖面（coverage）封顶（cap） 1
- 同一概念有两个并行叫法，或一个词被用来指两件事 → 覆盖面（coverage）封顶（cap） 1
- 找不到任何负知识记录（被否的方案、已知限制）→ 覆盖面（coverage）封顶（cap） 2
- 存在"改了 A 必须同时改 B"的耦合却没有同步机制 → 覆盖面（coverage）封顶（cap） 2、约束力（enforcement）封顶（cap） 1
- 派生（derived）内容没有 freshness 门禁（gate；源头变了派生（derived）不跟着变也不会红）→ 约束力（enforcement）封顶（cap） 2

**常见伪证（false evidence）**："我们的文档很全" —— 全不等于有家。两份都全，就是两个家。

**走形症状（failure symptoms）**：owner 表写了，正文却在每一处全文复制。补救方向是**把 home 补全**，不是允许复制。

**例证（exemplar）**（可选核对）：DSH 的文档分层表每行同时写"放什么"和"禁放什么"，例如常驻规则（always-loaded rules）的 home 明确标注"不含详细教程、历史故事"；决策理由单独进 `.agents/notes/`，README 只写 now。

#### KN3 决策记录 · Decision records

**填的缺口**：IG3 为什么这样设计

**一句话（summary）**：存"为什么"而不是"是什么"、存取舍而不是实现，并且能跟着决定一起演进的知识载体。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找 3 个"当初有明显别的选择"的地方，看有没有记录 | 记了 / 没记 / 记了但只有结论没有备选；再数最近 10 条记录里有几条对应机械性改动（无真实备选） |
| PB2 | 打开一条记录读一遍，并看一次反转 | 能不能回答"为什么这样决定、什么方案输了、后果是什么"；反转时旧记录的独有内容（理由、备选、后果、验证缺口）有没有先被吸收进新记录 |
| PB3 | 状态怎么区分；过时记录最后被放到哪 | 现行 / 已否决 / 已过时三种状态是否一眼可分；有没有成文的归档规则与归档位置（还是过时记录留在原地、无处可去） |
| PB4 | 有没有"过时的理由冒充现行" | 被取代的记录是否还挂在权威位置 |
| PB5 | 被否决的方案还会不会被重提 | 新开一个无上下文的 agent 会话，问它会不会想到那条路 |
| PB6 | 挑一件改过几轮的事，只读记录 | 能不能只读一处就说清它现在是什么、中间反转了几次、每次为什么；还是要翻散落的提交与文档才拼得出来 |

**覆盖面（coverage）**：0 没有 / 1 零散存在，没有判据 / 2 有明确判据（存在真实备选与持久取舍才写）与状态区分 / 3 且有取代纪律与归档规则

**约束力（enforcement）**：0 靠口传 / 1 写在 prose 里（有判据说明，没有检查）/ 2 有模板/结构检查 / 3 且有取代前的完整性检查（旧记录独有内容必须先被吸收）

**封顶规则（cap rules）**
- 被当作决策记录（decision record）的记录普遍没有"备选与为什么不行"（抽查的记录里过半）→ 覆盖面（coverage）封顶（cap） 1（那不是决策记录（decision record），是变更说明）
- 存在被取代的记录仍被当作现行权威引用 → 覆盖面（coverage）封顶（cap） 1
- 为机械性改动批量建档（最近 10 条记录里过半没有真实备选）→ 覆盖面（coverage）封顶（cap） 1（记录通胀会让真记录一起被无视）
- 现行 / 已否决 / 已过时三种状态不可分 → 覆盖面（coverage）封顶（cap） 1
- 没有任何归档规则（过时记录只能留在原地，与现行记录混在一起）→ 覆盖面（coverage）封顶（cap） 2
- 同一件事反复反转，却没有任何一处给出当前结论与沿革 → 覆盖面（coverage）封顶（cap） 2
- 取代时没有先吸收旧记录的独有内容（没有取代前的完整性检查）→ 约束力（enforcement）封顶（cap） 2

**常见伪证（false evidence）**：数量。**一段"为什么不"的记忆，只在它仍能阻止一个可信的错误时才有价值。** 记录数不是指标。

**走形症状（failure symptoms）**：两个方向都会坏——没有备选的修补硬写记录（机械建档，很快没人再读），以及有真实取舍的变更不写（知识随人走）。

**例证（exemplar）**（可选核对）：DSH 的决策记录（decision record）强制四节（问题 / 决定 / 备选 / 后果），验证与遗留是可选节；备选必须真实存在过、不得编造；生命周期由目录承载（`proposed` / `implemented` / `rejected` / 归档目录），归档件保留 `Status: implemented` 并加一行 `Archived:`，归档后不再是当前权威。

#### KN4 分类学 · Repository taxonomy

**填的缺口**：IG2 系统由什么组成

**一句话（summary）**：任何一个"这东西该放哪、谁维护它、能不能手改"的问题，都有命名的 owner 或机器门禁（gate）。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 列顶层目录，为每个写一句"它拥有什么" | 写得出来吗？有两个目录职责重叠吗 |
| PB2 | 对每个顶层区域，指出它的规则 owner | 有没有一个文件说清这个区域的规矩 |
| PB3 | 找生成物（generated artifact；catalog、类型桩、快照、投影站点） | 能不能手改；有没有 freshness 检查；有没有人真的手改过（`git log` 看这些路径） |
| PB4 | 找测试期望输出的存放规则 | 是"跟被证明的对象住一起"还是"全堆在一个大目录" |
| PB5 | 找第三方/vendored 代码 | 有没有本地修改日志；上游版本钉在哪 |

**覆盖面（coverage）**：0 没有分类概念 / 1 有一些约定但不成文 / 2 每个区域有 owner、有"能不能手改"的说明 / 3 且按内容维护形态分类（手写 / 生成 / 录制 / 投影），每类有机器边界

**约束力（enforcement）**：0 靠口传 / 1 写在 prose 里 / 2 有生成物（generated artifact） freshness 门禁（gate）或结构检查 / 3 且有"手改生成物（generated artifact）被拒绝"的直接拦截

**封顶规则（cap rules）**
- 两个顶层目录的职责说不清边界 → 覆盖面（coverage）封顶（cap） 1
- 存在生成物（generated artifact）被手改而没有任何检查发现 → 覆盖面（coverage）封顶（cap） 2、约束力（enforcement）封顶（cap） 1
- 测试期望输出没有存放规则（各人放各处）→ 覆盖面（coverage）封顶（cap） 2
- 有顶层区域指不出规则 owner → 覆盖面（coverage）封顶（cap） 1
- 存在生成物（generated artifact）却没有任何 freshness 门禁（gate）或结构检查 → 约束力（enforcement）封顶（cap） 1

**常见伪证（false evidence）**："我们的目录结构很清晰" —— 清晰是给作者的。检验法是让一个外部 agent 判断"新增一个 X 该放哪"，看它会不会猜错。

**走形症状（failure symptoms）**：大型仓库最常见的漂移（drift）不是代码错误，是**东西放错了地方**——同一事实的第二份手写清单、被手改的生成物（generated artifact）、期望输出堆错目录。

**例证（exemplar）**（可选核对）：DSH 的根入口按顶层区域列出每个区域拥有什么；文档分层表每行同时写"放什么"和"不放什么"两列；生成类内容由源码再生成并有 freshness 门禁（gate），手改生成物（generated artifact）被拒绝。

### 变更路径 · CP 组

#### CP1 意图入口 · Work intake

**填的缺口**：IG7 交付怎样算完整

**一句话（summary）**：一个任务从"有人说要做点什么"变成"一份写得清验收条件的可开工描述"的路径。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找最近 5 个工作项的原始描述 | 能不能从中读出"外部可观察结果 + 如何观察" |
| PB2 | 找一个描述最差的工作项，看它后来怎么开工的 | 靠提问补齐 / 靠猜 / 靠口头约定；"验收条件缺失"的工作项有没有被系统明确拦下 |
| PB3 | 看工作项与提交的关联 | 提交或 PR 能不能回溯到它服务的意图 |
| PB4 | 看小改动走什么路径 | 是否所有事都必须走完整仪式（过度流程 = 会被绕过） |
| PB5 | 看"不做"的决定记在哪 | 被否的需求会不会被反复重提 |

**覆盖面（coverage）**：0 没有入口，任务靠口头分派 / 1 有工作项入口（模板或自由格式），但写不出可观察的验收条件 / 2 每项有可观察的验收条件，且与提交可关联 / 3 且区分大小改动，小改动有轻量路径

**约束力（enforcement）**：0 靠口传 / 1 有模板，但缺字段也能提交 / 2 有检查（缺少关联会红） / 3 且"验收条件缺失"会被明确拦下

**封顶规则（cap rules）**
- 最近 5 个工作项里有任何一项写不出"如何观察" → 覆盖面（coverage）封顶（cap） 1
- 所有改动都必须走完整仪式，没有轻量路径 → 覆盖面（coverage）封顶（cap） 2（流程会被绕过，绕过就全失效）
- 提交无法回溯到意图 → 覆盖面（coverage）封顶（cap） 1
- "验收条件缺失"的工作项不会被拦下 → 约束力（enforcement）封顶（cap） 2

**常见伪证（false evidence）**："我们有 issue 模板" —— 模板存在不等于被使用，更不等于验收条件是可观察的。

**走形症状（failure symptoms）**：两个方向——意图完全不落盘（做完没人知道为什么做），以及所有改动都被同一个重仪式压住（小的绕过去，大的靠人情）。

#### CP2 正确路径 · Paved road

**填的缺口**：IG4 改动落在哪里

**一句话（summary）**：仓库为常见变更提供首选入口、生产范本和升级条件，让"做对"成为阻力最小的路径。

*适用性（applicability）：仓库存在代码或配置变更路径时适用；纯文档站（没有代码或配置变更路径）标 N/A。*

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找一张"目标 → 机制"的归属表（ownership table） | 有没有；右列是不是**能直接执行的动作**（改哪个文件、调哪个注册点） |
| PB2 | 拿一个真实需求，只看这张表 | 能不能答出"改哪里"，不翻代码 |
| PB3 | 找一个"本可用配置解决、却改了核心"的例子 | 有没有升级条件在拦 |
| PB4 | 找常见任务的操作范本（cookbook / 示例） | 有没有；是不是可复制可运行的 |
| PB5 | 看有没有人自己发明过新接法 | `git log` 找旁路式实现；有没有检查拦它 |

**覆盖面（coverage）**：0 没有 / 1 有架构文档但只说"找相关模块" / 2 有归属表（ownership table） + 范本 + 升级条件 / 3 且按参与半径分层（配置 → 扩展点 → 完整能力 → 核心），每层有升级判据

**约束力（enforcement）**：0 靠口传 / 1 写在文档里，没有检查 / 2 有检查（绕过入口会被结构检查发现） / 3 且有"必须走入口"的强制机制（例如只允许通过注册 API 接入）

**封顶规则（cap rules）**
- 归属表（ownership table）右列是"参考架构文档"这类二级指引 → 覆盖面（coverage）封顶（cap） 1
- 属于常见变更类型却没有任何范本 → 覆盖面（coverage）封顶（cap） 1
- 存在"能配置却改了核心"的近期实例且无人拦下 → 约束力（enforcement）封顶（cap） 1
- 归属表（ownership table）没有升级条件（什么情况该从配置升级到改核心没有判据）→ 覆盖面（coverage）封顶（cap） 1

**常见伪证（false evidence）**："我们有架构文档" —— 架构文档解释系统**是什么**，不回答**我该改哪里**。这是两件事。

**走形症状（failure symptoms）**：归属表（ownership table）变成审批流程（申请→批准→实施），偏离了"降低判断成本"的本意；或者参与分层变成等级制（"高级的改核心"）。

#### CP3 流程固化 · Procedural memory

**填的缺口**：IG5 这类任务按什么流程做

**一句话（summary）**：反复出现、需要上下文判断的任务流程，被固化成带触发条件（trigger）、步骤、停止条件和验证方式的短文档。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找出同一类任务第三次出现时发生了什么 | 是固化成了流程，还是每次现场发明 |
| PB2 | 打开一份流程文档 | 触发条件（trigger）写清楚了吗；每一步有可执行命令或可打开的文件吗；判断标准是规则还是形容词 |
| PB3 | 看它有没有越界 | 是否把可机械判断的部分也写成了 prose（那部分应该在检查里） |
| PB4 | 看它有没有自我声明边界 | 是否说明"这是指导，不是清单" |
| PB5 | 看发现机制 | 模型/人能不能在**不读完**的情况下判断该不该读它（有没有摘要层） |
| PB6 | 挑一条会变的做法（提交 / 评审 / 发布 / 测试要求） | 现在该照哪一份？旧版本还在不在、有没有被当成现行的？这份文档什么时候复核 |

**覆盖面（coverage）**：0 没有 / 1 有一些 wiki 页但没人用 / 2 有按任务组织的流程文档，带触发条件（trigger）与步骤 / 3 且有摘要层（只看标题+适用条件决定读不读）与维护触发条件（trigger）

**约束力（enforcement）**：0 靠口传 / 1 流程只是建议，没人核对 / 2 流程里指到的命令真实存在、可跑 / 3 且可机械化的部分已经下沉到检查，流程本身只管判断

**封顶规则（cap rules）**
- 流程文档里出现"做好验证"这类没有可执行内容的句子 → 覆盖面（coverage）封顶（cap） 1
- 流程文档写成"必须依次执行 N 步"且没有判断标准 → 覆盖面（coverage）封顶（cap） 2（只写步骤：环境一变就卡死在错的步骤上）
- 没有摘要层，只能整篇读 → 覆盖面（coverage）封顶（cap） 2
- 流程文档没有维护触发条件（trigger；做法变了文档不跟着变）→ 覆盖面（coverage）封顶（cap） 2
- 同一套做法有多份并存（旧版未撤回也未标为历史），读者分不清该照哪一份 → 覆盖面（coverage）封顶（cap） 1
- 流程文档没有写触发条件（trigger；不知道什么情况该读它）→ 覆盖面（coverage）封顶（cap） 1
- 流程文档里指到的命令不存在或跑不通 → 约束力（enforcement）封顶（cap） 1
- 可机械判断的部分仍留在流程 prose 里、没有下沉到检查 → 约束力（enforcement）封顶（cap） 2

**常见伪证（false evidence）**："我们有详细的文档" —— 详细到把判断收走，环境一变就卡在错的步骤上；详细到只剩原则，执行者还得自己猜步骤。

**走形症状（failure symptoms）**：只写原则（"推送前做好本地验证"——执行者还得自己猜步骤）与只写步骤（把判断固化成固定序列）。正确形态是**步骤 + 每步的判断标准**，判断留给执行者。

#### CP4 执行与授权链 · Execution and authorization

**填的缺口**：IG1 必须遵守什么（安全与权限铁律）

**一句话（summary）**：一个自动化动作从发起到落定，走的是同一条管线；策略判在动作之前，结果只有一条出口。

*适用性（applicability）：仓库里存在**需要授权的自动化动作**时适用（CI 机器人、发布与部署脚本、代码生成器、任何让 agent 直接改仓库或动用凭据的流程）。**只跑测试、不产生可授权动作的流水线不触发本维**；没有任何这类动作时标 N/A。评的是仓库自己的自动化；如果产品本身是 agent 运行时，产品里的工具执行由 [11](./11-evaluate-runtime-harness.md) 的 RT9 评。*

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找"谁允许这个动作发生"的判定点 | 有几处？加一条新规则要改几个文件？ |
| PB2 | 看动作有没有在执行前被记录 | 失败的调用在不在记录里 |
| PB3 | 看结果怎么回到发起者（人、CI 的下一步、agent） | 有没有统一归一化；会不会出现"部分成功""未知状态" |
| PB4 | 找权限边界与"看得见"的边界 | 这两者是不是被混为一谈 |
| PB5 | 看危险动作（发布、部署、改受保护分支、动用凭据）有没有独立的授权步骤 | 还是靠"agent 或脚本不会那么做" |

**覆盖面（coverage）**：0 没有 / 1 检查散在每个工具/脚本自己身上 / 2 有统一的执行前判定层 + 单一结果出口 / 3 且有独立授权步骤与审计记录

**约束力（enforcement）**：0 靠自觉 / 1 写在 prose 里 / 2 权限判定在代码里强制 / 3 且越权必然失败并有记录

**封顶规则（cap rules）**
- 加一条策略规则需要改多个文件（策略散在各处）→ 覆盖面（coverage）封顶（cap） 1、约束力（enforcement）封顶（cap） 1
- 存在"部分成功""未知状态"被直接交回发起者 → 覆盖面（coverage）封顶（cap） 1、约束力（enforcement）封顶（cap） 1
- 把"可查询/可试验"当成"已授权" → 约束力（enforcement）封顶（cap） 1
- 危险动作没有独立的授权步骤（靠"agent 或脚本不会那么做"）→ 覆盖面（coverage）封顶（cap） 2
- 动作没有执行前的审计记录（失败的调用查不到）→ 覆盖面（coverage）封顶（cap） 2

**常见伪证（false evidence）**："我们的工具自己会检查权限" —— 那是策略散在 N 处，改一次要动 N 个文件，而且总有一个忘了改。

**走形症状（failure symptoms）**：每个脚本或工作流各自判权限（绕过统一判定层）；把"部分成功"的发布或部署当作成功交给下一步。

**例证（exemplar）**（可选核对）：DSH 的 20 个 GitHub Actions 工作流都在顶层声明 `permissions`（默认只读 `contents: read`，需要写权限的工作流逐项列出，例如 `pull-requests: write`）；发布到 npm 的只有一个 job，它跑在 `npm-publish` 环境里，必需的审批人与允许的标签配在环境上，注释写明这是整个发布序列里唯一能写 registry 的 job。

### 证据与交付 · EV 组

#### EV1 反馈分层 · Feedback layers

**填的缺口**：IG6 怎么算做对

**一句话（summary）**：不同类型的问题由不同层的检查负责，且每一层只拥有它能观察到的性质。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 列出仓库所有的检查，按"它最早能在什么时候发现问题"排序 | 编译/加载期、局部行为、组装行为、运行时关系、语义判断，各有没有 |
| PB2 | 对每一层，找它**不能**证明什么 | 仓库里有没有说清层与层的边界 |
| PB3 | 看本地反馈延迟 | 改一行到拿到相关结论要多久；要等全套吗 |
| PB4 | 看本地与远端的分工 | hooks 跑什么、CI 跑什么；hooks 是不是把 CI 的全套检查搬到了本地 |
| PB5 | 看错误信息的质量 | 失败时说得出「失败对象 + 违反规则 + 修正入口」吗 |

**覆盖面（coverage）**：0 只有"跑得起来" / 1 有测试但不足四层 / 2 至少四层齐备且各有分工说明 / 3 且每层有明确的"不能单独证明"清单

**约束力（enforcement）**：0 靠自觉 / 1 有检查但可在本地跳过且常被跳过 / 2 检查在流水线里强制 / 3 且本地按改动范围选检查（不全跑）同时远端跑穷举

**封顶规则（cap rules）**
- 绿色的一层被当作其它层也绿（例如用覆盖率证明产品可用）→ 覆盖面（coverage）封顶（cap） 2
- 本地反馈需要等全套跑完 → 约束力（enforcement）封顶（cap） 2
- 失败信息只说"失败"，说不出违反哪条规则、去哪修 → 约束力（enforcement）封顶（cap） 2
- 检查层不足四层（编译/加载期、局部行为、组装行为、运行时关系、语义判断这五类里，有具名检查的不到四类）→ 覆盖面（coverage）封顶（cap） 1

**常见伪证（false evidence）**："我们 CI 全绿" —— 全绿只覆盖检查碰巧碰到的地方，与"声称的行为都有证据"是两件事。

**走形症状（failure symptoms）**：层与层互相冒充——覆盖率绿了就当产品工作，快照绿了就当接口合理，评审去手工重复机器已经精确拒绝的格式问题。

**例证（exemplar）**（可选核对）：DSH 的测试分层文档逐层写明它**不能单独证明**什么（例如"覆盖率只证明行被执行，不证明功能可用"）；本地按改动面选最小证据，CI 拥有穷举覆盖与平台矩阵；Git 钩子明文不跑测试、快照、构建这类随改动面变化的检查。

#### EV2 负例控制 · Negative control

**填的缺口**：IG6 怎么算做对

**一句话（summary）**：每一个检查都被证明过**会失败**。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 随机挑 3 个现有检查 | 说得出它最近一次为红是什么回归吗；那次验证有没有留下记录（文件 / 注释 / CI 记录），记录里有没有"还原后变绿"这一步，还是只靠人口头记得 |
| PB2 | 挑一个检查，故意制造它该抓的违规 | 看它红不红，然后还原 |
| PB3 | 看仓库有没有"新检查必须验证"的成文要求 | 有要求 vs 有实践 |
| PB4 | 看端到端验证是"验证世界"还是"验证自述" | 测试是重新读文件/跑命令/看状态，还是相信执行者的声称 |
| PB5 | 看有没有"永远为绿"的检查 | 长期未变更、从未失败过的检查 |

**覆盖面（coverage）**：0 没有这个概念 / 1 有人偶尔做 / 2 有明确要求（新检查必须做一次负例控制 negative control）/ 3 且留了记录，可追溯每次检查的验证

**约束力（enforcement）**：0 靠自觉 / 1 写在 prose 里 / 2 有流程要求且被抽查 / 3 且"没有负例控制（negative control）的检查"会被明确拒绝合入

**封顶规则（cap rules）**
- 抽检的 3 个检查里，没有一个说得出最近一次为红的原因 → 本维约束力（enforcement）封顶（cap） 1
- 存在长期未失败过的检查且无人核查 → 约束力（enforcement）封顶（cap） 1
- 负例控制（negative control）只做了"引入违规看它红"，没有验证"还原后变绿" → 约束力（enforcement）封顶（cap） 2
- 没有"新检查必须做一次负例控制（negative control）"的成文要求 → 覆盖面（coverage）封顶（cap） 1
- 负例控制（negative control）没有留下可追溯的记录 → 覆盖面（coverage）封顶（cap） 2

**常见伪证（false evidence）**："我们的检查很全" —— 检查全绿但没人信，是这类系统最贵的走形（degradation）。

**走形症状（failure symptoms）**：绿灯数目成了 KPI；负例控制（negative control）没人做过；检查逐渐变成仪式，然后有人开始绕过它。

**这一维为什么单列**：它是整份评分卡（scorecard）里**唯一一个检验"其它维度是不是真的"的维度**。EV1 问"有没有检查"，EV2 问"检查算不算数"。一个 EL2 的检查和一个 EL3 的检查，在通过率上完全一样，在保护效果上差别是全部。

#### EV3 闭环完整性 · Delivery completeness

**填的缺口**：IG7 交付怎样算完整

**一句话（summary）**：实现、当前文档、回归证据在**同一次交付**里一起走，缺口如实标注。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 拿最近 5 笔变更，看每一笔带了什么；其中最小的那笔是什么性质 | 代码 / 文档 / 测试 / 决策记录（decision record），各带了几笔；机械性改动是走轻量路径还是也必须走完整仪式 |
| PB2 | 找"代码合并了、文档还没跟上"的情况 | `git log` 看文档滞后代码多久 |
| PB3 | 看交付说明与证据是否一一对应 | 声称跑过的检查，CI 里真的有吗 |
| PB4 | 看缺口怎么处理 | 没有证据的声称是"如实标注为缺口"还是"用绿灯盖过去" |
| PB5 | 看回滚的粒度 | 出错时是整个切片（slice）原样退回，还是打补丁式热修 |

**覆盖面（coverage）**：0 代码合并即完成 / 1 有时带文档和测试 / 2 常见变更都同批交付实现+文档+证据 / 3 且区分大小改动（机械性改动有轻量豁免），例外有明确理由

**约束力（enforcement）**：0 靠自觉 / 1 写在 prose 里 / 2 有检查（缺文档/缺测试会红） / 3 且"声称与证据不符"会被明确拦下

**封顶规则（cap rules）**
- 最近 5 笔变更里出现"先合并后补文档/补测试" → 覆盖面（coverage）封顶（cap） 1
- 交付说明里出现无法对应的验证声称 → 约束力（enforcement）封顶（cap） 1
- 没有轻量豁免路径（所有改动一律全套）→ 覆盖面（coverage）封顶（cap） 2
- 交付例外（缺文档/缺测试/缺证据）没有写明理由 → 覆盖面（coverage）封顶（cap） 2

**常见伪证（false evidence）**："我们要求每个 PR 带测试" —— 要求是一回事，最近 5 笔里带了几笔是另一回事。**这一维只能用切片（slice）查，不能用文档查。**

**走形症状（failure symptoms）**：闭环断在两处——"实现 + 文档 + 证据同批交付"退化成"先合并后补"，"缺口如实标注"退化成只报通过、不报缺口。

**自测法**：拿最近一笔变更问——README 或文档声称的行为里，有几条**没有**任何测试钉住？说不出，就是缺口没被管理。

#### EV4 评审与批准 · Review and approval

**填的缺口**：IG6 IG7

*适用性（applicability）：见 [01 §4 粗判（coarse check）一览](./01-evaluate-development-harness-coarse.md#4--十七维粗判coarse-check) 的 EV4 行（单人项目标 N/A 并写理由）。*

**一句话（summary）**：谁在什么条件下判断"这笔变更可以进"，以及这个判断为什么可信。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 看最近 10 笔变更的批准过程 | 谁批准的？有实质评论还是只点了通过 |
| PB2 | 找批准的成文条件 | 有没有明确条件，还是"有人 approve 就行" |
| PB3 | 看评审意见的质量 | 有没有指出过真实问题；还是清一色"LGTM" |
| PB4 | 看评审与机器的分工 | 评审有没有在手工重复机器已经精确拒绝的格式问题 |
| PB5 | 看谁能批准、需要几个人 | 条件是否与改动风险挂钩 |

**覆盖面（coverage）**：0 没有评审（直接推主干）/ 1 有评审但无成文条件 / 2 有成文条件且与风险挂钩 / 3 且评审范围（该看什么、不该重复什么）有明确规定

**约束力（enforcement）**：0 靠自觉 / 1 靠人际约定 / 2 平台强制（不能自批/需要 N 人） / 3 且条件（加权、路径归属（ownership））被机器计算并强制执行

**封顶规则（cap rules）**
- 最近 10 笔里，评审评论全部是"LGTM"之类的空话 → 覆盖面（coverage）封顶（cap） 1
- 评审在重复机器已经精确拒绝的格式问题 → 覆盖面（coverage）封顶（cap） 2
- 批准条件与改动风险无关（改核心和改错别字走同一套）→ 覆盖面（coverage）封顶（cap） 1
- 有评审但没有成文的批准条件（"有人 approve 就行"）→ 覆盖面（coverage）封顶（cap） 1
- 批准不靠平台强制（可自批、人数不限）→ 约束力（enforcement）封顶（cap） 1

**常见伪证（false evidence）**："我们有严格的双人评审" —— 数一数最近 10 笔的评论条数和内容，比任何制度描述都准。

**走形症状（failure symptoms）**：评审只点通过（有流程无判断），或者只挑格式（人力被消耗在机器已经管住的事上）。

### 状态与上下文 · ST 组

#### ST1 静与动 · Static and dynamic

**填的缺口**：IG2 系统由什么组成

**一句话（summary）**：把仓库里会变的东西（规则、配置、记录、生成物（generated artifact））按"变得有多快 / 谁能改 / 丢了多疼"分成层，并且**每层只被上一层或显式操作修改**。

*适用性（applicability）：评的是**仓库自己的开发状态**——开发与 CI 配置、生成物（generated artifact）、录制的期望输出、决策与变更记录，以及开发过程里得出的结论落在哪。被开发的产品自己的运行时状态（产品的数据库、缓存、会话）不在本维；如果产品本身是 agent 运行时，那部分由 [11](./11-evaluate-runtime-harness.md) 的 RT2 评。几乎没有配置与生成物（generated artifact）的小仓库标 N/A。*

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 列出仓库里所有"会变的东西"，为每一个归类 | 规则（跨版本稳定，走评审）/ 配置（开发、CI、部署时定）/ 记录（只追加或冻结：提交历史、决策记录（decision record）、录制的期望输出）/ 派生（derived；生成物（generated artifact）、索引、构建产物，可重算） |
| PB2 | 对每个"记录"，问"它丢了大不大" | 丢了不心疼、能重算的，它是派生（derived），不是记录 |
| PB3 | 找同一份配置或数据有没有两个**可写**来源 | 例如本地 `.env.example`、编排文件、CI workflow 各写一份默认值；有 → 两处存真，早晚分叉 |
| PB4 | 删掉派生（derived；生成物（generated artifact）、缓存、构建目录）后从源头重建 | 能不能得到同样的结果；一次 CI 的输入（工具版本、依赖锁）能不能复现 |
| PB5 | 看开发过程中产生的持久结论去哪了 | 一次任务、一次排障、一次 agent 会话得出的结论，有没有回写到规则或记录层（文档、决策记录（decision record）、检查） |

**覆盖面（coverage）**：0 没有分层概念 / 1 部分东西能说清属于哪层 / 2 四层齐备且各有明确的承载者与修改权限 / 3 且有"派生（derived）必须能从源头重建"的不变量（invariant）

**约束力（enforcement）**：0 靠自觉 / 1 写在 prose 里 / 2 派生（derived）物由源头生成（不能手改）/ 3 且有检查钉住可重建性（rebuildability；例如重新生成后 diff 为空、清空后重建一致）

**封顶规则（cap rules）**
- 存在同一事实的两个可写来源 → 覆盖面（coverage）封顶（cap） 1、约束力（enforcement）封顶（cap） 1
- 删掉派生（derived）后重建不出同样的结果（它实际被当成了记录）→ 覆盖面（coverage）封顶（cap） 2、约束力（enforcement）封顶（cap） 1
- 开发过程中产生的持久结论没有任何回写路径 → 覆盖面（coverage）封顶（cap） 2
- 有"会变的东西"归不到四层里的任何一层（承载者不明）→ 覆盖面（coverage）封顶（cap） 1

**常见伪证（false evidence）**："我们的配置都在仓库里" —— 在仓库里不等于**只有一个家**。三处各写一份默认值，全都在仓库里。

**走形症状（failure symptoms）**：把派生（derived）当记录存（生成物（generated artifact）被手改，成了第二真相）；绕过源头直接改派生（derived；在 CI 里临时打补丁、手改锁文件）；不回写（同一个问题下一次任务重新发明一遍）。

#### ST2 披露与隔离 · Progressive disclosure and isolation

**填的缺口**：IG2 IG5

**一句话（summary）**：仓库交给参与者（尤其是 coding agent）的知识按需披露：常驻部分有预算，其余先给摘要、命中才读全文；委派出去的子任务只带它需要的那部分说明。

*适用性（applicability）：评的是**仓库供给的上下文**——常驻入口、按目录生效的规则、流程文档、委派模板。agent 工具自己怎么压缩上下文、怎么隔离子代理，不是仓库能控制的，不在本维；如果产品本身是 agent 运行时，产品的上下文组装由 [11](./11-evaluate-runtime-harness.md) 的 RT7 评。面向 agent 的常驻规则（always-loaded rules）很少、也不在增长的小仓库标 N/A。*

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 数常驻内容的体积（根入口 + 每次会话都会被读到的规则文件） | 有没有预算上限；超了会发生什么（门禁（gate）会红吗） |
| PB2 | 看流程文档/规则怎么被发现 | 是全部常驻，还是先给摘要（标题 + 适用条件）、命中才读全文 |
| PB3 | 看重复内容 | 同一段规则会不会出现在两个常驻文件里（多个宿主的入口是否指向同一份） |
| PB4 | 看按范围生效的规则 | 只对某个子树成立的规则，是放在子树里、进入子树才读到，还是全部堆在根入口 |
| PB5 | 看委派/子任务的说明 | 仓库给出的委派模板或流程，是要求把全部背景转交，还是只给任务需要的部分 |

**覆盖面（coverage）**：0 所有规则一份常驻，没有预算概念 / 1 有"文档要写短"的纪律但没有预算 / 2 常驻有预算 + 流程文档有摘要层、按需读全文 / 3 且按范围分层（子树规则只在子树生效），委派说明只带所需部分

**约束力（enforcement）**：0 靠自觉 / 1 写在 prose 里（有预算说明，没有检查）/ 2 预算有门禁（gate；超了会红，并指出超在哪个文件）/ 3 且摘要层的结构（每份流程都写了适用条件）有检查强制

**封顶规则（cap rules）**
- 常驻内容没有上限 → 覆盖面（coverage）封顶（cap） 1
- 有预算但超出时没有任何东西报告（只能靠人发现）→ 约束力（enforcement）封顶（cap） 1
- 规则/流程只能全文常驻（没有摘要层）→ 覆盖面（coverage）封顶（cap） 1
- 同一段规则在多个常驻文件里各写一份 → 覆盖面（coverage）封顶（cap） 2
- 只对子树成立的规则堆在根入口里 → 覆盖面（coverage）封顶（cap） 2

**常见伪证（false evidence）**："我们的文档写得很短" —— 写短只解决供给，不解决"这一次该读哪一份"。那要靠摘要层与按范围分层。

**走形症状（failure symptoms）**：只做一层就当完成（只把文档写短，或只加摘要）；或者有预算但超出时没人知道，读者以为该读到的都读到了。

#### ST3 运行时查询 · Inspectability

**填的缺口**：IG2 系统由什么组成

**一句话（summary）**：能用一条命令问出"这台机器/这个进程实际生效的是什么"，而不是读源码猜。

*适用性（applicability）：评的是**开发环境与工具链**的实际生效值——构建、lint、测试配置叠加后的结果，工作区的包与注册项清单，被开发的程序在本地或测试环境跑起来时的状态。存在多层配置叠加、或声明面大到需要用命令查询时适用；单层配置的小仓库标 N/A。如果产品本身是 agent 运行时，产品的组合与启动由 [11](./11-evaluate-runtime-harness.md) 的 RT1 评。*

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 问"最终生效的配置是什么" | 有没有一条命令能答；还是要读源码/读多个叠加层自己拼 |
| PB2 | 问"仓库声明了哪些接口/注册项" | 有没有生成的清单；还是手工维护（会漂） |
| PB3 | 问"当前进程里实际有什么" | 有没有只读查询；还是只能打断点 |
| PB4 | 看静态清单会不会过期 | 有没有 freshness 检查 |
| PB5 | 看查询结果与实际生效的是不是一回事 | "声明了什么" vs "实际跑着什么"，混了吗；改一处配置后重新查询，看结果是否跟着变、与实际行为是否一致 |

**覆盖面（coverage）**：0 全靠读源码 / 1 只有一条 dump 命令 / 2 有 dump + 生成的声明面清单 / 3 且有只读的活运行时查询

**约束力（enforcement）**：0 靠自觉 / 1 写在 prose 里（说了怎么查，没有东西保证查询结果准确）/ 2 生成清单有 freshness 门禁（gate） / 3 且完整性有守卫（新增的东西不可能静默无文档）

**封顶规则（cap rules）**
- 没有任何一条命令能回答"实际生效的是什么" → 覆盖面（coverage）封顶（cap） 0
- 手工维护的接口清单且无 freshness 检查 → 覆盖面（coverage）封顶（cap） 1、约束力（enforcement）封顶（cap） 1
- 查询结果与实际生效的不一致（查询命令与真正启动各算一套）→ 约束力（enforcement）封顶（cap） 1
- 没有只读的活运行时查询（只能打断点或读静态清单）→ 覆盖面（coverage）封顶（cap） 2

**常见伪证（false evidence）**："源码就是文档" —— 源码说的是**可能是什么**，回答不了**现在是什么**。多层配置叠加之后尤其如此。

**走形症状（failure symptoms）**：用"源码就是文档"跳过这一维；或者接口清单手工维护、还把它当权威（清单必然漂）；或者查询命令与真正启动各算一套，查到的不是实际生效的。

### 维护与发布 · MT 组

#### MT1 防漂移 · Drift prevention

**填的缺口**：全部（元维度）

**一句话（summary）**：外置的知识会漂，所以给它配机器检查、配基线、配复核触发条件（trigger）。

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 数一数有多少份外置知识（文档、清单、索引、快照、决策记录（decision record）） | 每份谁维护？漂了谁发现 |
| PB2 | 找结构检查脚本 | 有没有；检查什么（编码、链接、锚点（anchor）、预算、配对、术语）；它有没有被证明会失败（最近一次为红是什么回归） |
| PB3 | 看基线怎么钉 | 文档有没有写"结论以哪个版本为准"；有没有"以当前 checkout 为准"这类会悄悄滑走的表述 |
| PB4 | 看数字类事实 | 预算、上限、个数——这类最容易漂的，有没有标注出处 |
| PB5 | 看上游更新时的复核路径 | 有没有明确"上游哪些变化要触发重审" |

**覆盖面（coverage）**：0 没有 / 1 有零散的检查 / 2 有结构性检查脚本 + 明确的复核触发条件（trigger） / 3 且有基线钉定、预算表、归档策略，形成一套维护制度

**约束力（enforcement）**：0 靠自觉 / 1 脚本存在但要人记得跑 / 2 检查接进了提交流程 / 3 且检查自己被负例控制（negative control）过

**封顶规则（cap rules）**
- 存在"手工维护的第二份清单"且无 freshness 检查 → 覆盖面（coverage）封顶（cap） 1
- 文档使用"以当前版本为准"这类相对表述 → 覆盖面（coverage）封顶（cap） 2
- 结构检查脚本从未被证明会失败 → 约束力（enforcement）封顶（cap） 2
- 没有明确"上游哪些变化要触发重审"的复核触发条件（trigger） → 覆盖面（coverage）封顶（cap） 1
- 预算、上限、个数这类数字事实没有标注出处 → 覆盖面（coverage）封顶（cap） 2

**常见伪证（false evidence）**："我们的文档更新很及时" —— 及时靠人，防漂移（drift prevention）靠机器。这两者不能互相替代。

**走形症状（failure symptoms）**：检查脚本写了一次再没跑过；规则改了引用没跟着改（漏一处漂一处）；文档用"以当前版本为准"这类相对表述，让基线悄悄滑走。

**这一维为什么是元维度**：它不管任何具体知识，管的是**前面十六维能不能长期不失效**。前面做得再好，没有 MT1，六个月后会回到原点。

**例证（exemplar）**（可选核对）：DSH 的文档有逐文件字数上限并由门禁（gate）执行；生成的目录与源码有 diff 就红；决策记录（decision record）有冻结归档纪律（归档后不再是当前权威）；历史引用一律用发布标签而不是裸 commit 哈希，并由门禁（gate）执行。

#### MT2 发布与版本纪律 · Release and versioning

**填的缺口**：IG7 交付怎样算完整

**一句话（summary）**：东西怎么出去、兼容承诺是什么、坏版本怎么退、老用户的数据怎么办。

*适用性（applicability）：仓库向外部发布产物（包、镜像、服务、数据格式）时适用。不发布任何东西的仓库标 N/A。评的是仓库发布物的兼容承诺；如果产品本身是 agent 运行时，产品持久数据的格式世代由 [11](./11-evaluate-runtime-harness.md) 的 RT3 评。*

**探针（probe）**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找一次真实发布 | 从"决定发"到"发出去"有几个步骤，有没有成文序列 |
| PB2 | 找兼容承诺 | 哪些接口承诺稳定、哪些明确不稳定；有没有写清楚 |
| PB3 | 看不可逆的产物（数据格式、已发布记录） | 变更时是就地改还是新增后继代 |
| PB4 | 看坏版本怎么退 | 有回退路径吗；回退会不会破坏已发布的数据 |
| PB5 | 看版本号与变更的关系 | 破坏性变更有没有被版本号或迁移说明标出 |

**覆盖面（coverage）**：0 想发就发 / 1 有步骤但不成文 / 2 有成文发布序列 + 兼容承诺分级 / 3 且有不可逆产物的迁移纪律与回退路径

**约束力（enforcement）**：0 靠自觉 / 1 写在 prose 里 / 2 有检查（发布前置条件、格式版本号会红） / 3 且"移动/覆盖已提交世代"这类操作被直接拒绝

**封顶规则（cap rules）**
- 破坏性变更没有版本号或迁移说明 → 覆盖面（coverage）封顶（cap） 2
- 已发布的数据/格式会被就地覆盖 → 覆盖面（coverage）封顶（cap） 2、约束力（enforcement）封顶（cap） 1
- 稳定与不稳定的边界没有写明 → 覆盖面（coverage）封顶（cap） 1
- 发布没有成文序列（每次现场拼步骤）→ 覆盖面（coverage）封顶（cap） 1
- 坏版本没有回退路径 → 覆盖面（coverage）封顶（cap） 2

**常见伪证（false evidence）**："我们遵循语义化版本" —— 版本号规则不告诉任何人**哪些接口真的承诺稳定**。那要单独写。

**走形症状（failure symptoms）**：把仪式当纪律（标签间距、RC 之间的提交数、发布 PR 的文件数），这些不防止任何具体事故；或者破坏性变更就地覆盖已发布的数据。

## 5 · 细粒度（fine-grained）示例：把 EV2 从粗判档（coarse grade）钉成定档（final grade）

> **构造的示意**，承接 [01 §8](./01-evaluate-development-harness-coarse.md#8--短例) 的后端服务。快诊（quick check）的 EV2 抽检只问了一个检查（`TestPaymentRetry`），粗判（coarse check）为覆盖面（coverage） 1 / 约束力（enforcement） 0；切片（slice）另外发现 `TestOrderTimeoutConfig` 没钉住配置读取路径。这一轮要动 EV2，于是按第 1 节的四步定档（final grade）：

| 步 | 做了什么 | 看到什么 | 结论 |
|---|---|---|---|
| 1 走探针（probe） | PB1 抽 3 个检查（`TestPaymentRetry`、`TestOrderTimeoutConfig`、CI 里的 `golangci-lint`）问最近一次为红；PB2 对 `TestOrderTimeoutConfig` 引入违规；PB3 找成文要求；PB5 找"永远为绿"的检查 | 3 个都答不出；`TestOrderTimeoutConfig` 引入违规后仍绿；没有成文要求，一位成员说自己偶尔这么做、没留记录；`TestLegacyExport` 两年没改过也没红过 | — |
| 2 按锚点（anchor）定档（final grade） | 覆盖面（coverage）：有人偶尔做 | 是 | 覆盖面（coverage） **1** |
| | 约束力（enforcement）：没有成文要求，也没有抽查 | 靠自觉 | 约束力（enforcement） **0** |
| 3 命中封顶（cap） | "抽检的 3 个检查里，没有一个说得出最近一次为红的原因" → 约束力（enforcement） 1；"存在长期未失败过的检查且无人核查" → 约束力（enforcement） 1；"没有成文要求" → 覆盖面（coverage） 1 | — | 上限都不低于第 2 步，档位不变 |
| 4 出证据 | 三个检查的文件路径、`TestOrderTimeoutConfig` 那次引入违规的 diff、`TestLegacyExport` 的提交历史 | 指得出 | 扣分成立 |

**结果**：`EV2` 定档（final grade） 覆盖面（coverage） 1 / 约束力（enforcement） 0（红），与粗判档（coarse grade）一致。细粒度（fine-grained）多出来的是扣分依据：三个检查都答不出、`TestOrderTimeoutConfig` 引入违规仍绿、`TestLegacyExport` 两年没红过——施工时要逐条消掉的正是这些。切片走查（slice walkthrough）记录（第二层）的完整示例在 [01 §8](./01-evaluate-development-harness-coarse.md#8--短例)。
