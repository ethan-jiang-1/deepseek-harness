**这份文档是什么。** 开发 Harness 评估的**细粒度**一半：对粗粒度（[01 粗粒度](./01-evaluate-development-harness-coarse.md)）里判为红、或这一轮决定要动的维度，用探针逐条钉死档位，用封顶规则压掉虚高的分。

**什么时候用。** 先跑 01：出评分卡（表 1）与缺口清单（表 2）。**只在要动的维度上翻到本文对应的小节**——全量细粒度不是必须的。粗粒度的定义、两轴档位表、成熟度档、适用性裁剪、产出模板与评估者验收全在 01，本文不重复。

**为什么分两份。** 粗粒度定下来之后基本不动；细粒度会**持续增补**（新探针、新封顶）。分开之后，加一条封顶只改本文，不会碰到稳定的粗粒度。

**编号约定。** 维度用两字母前缀（`KN`/`CP`/`EV`/`ST`/`MT`），探针用 `PB`，封顶规则见本文附录 A；完整对照见 [README 的标识符约定](./README.md#标识符约定token)。

**本文引用 01 的定义**：术语（`EL0`–`EL3`、`IG1`–`IG7`）、第一 / 第二 / 第三层、两轴档位与成熟度档 `MG0`–`MG3`——见 [01](./01-evaluate-development-harness-coarse.md) 的 §2 / §3 / §4。

## 1 · 细粒度怎么用

对每个决定要动的维度，走四步：

1. **走探针。** 用该维的探针（`PB1` 起，最多到 `PB6`）实际做一遍（不是读文档推断），记下"我做了什么、看到了什么"。
2. **按锚点定档。** 用该维自己的覆盖面/约束力锚点定档（档位含义见本卡的锚点；[01 §4](./01-evaluate-development-harness-coarse.md#4--十七维粗判) 只是总述）。
3. **命中封顶就压档。** 封顶规则是**上限**：命中哪条，对应轴的上限就被压低，不看其它证据。
4. **出证据。** 每一个扣分都要能指到具体文件、提交或命令；说不出证据的扣分不算数（见 [01 §7](./01-evaluate-development-harness-coarse.md#7--评估者自己的验收)）。

**探针与判据的分工。** 探针用来收集证据，**改变档位的只有锚点与封顶**。观察到的现象若不在该维的锚点或封顶里（例如 PB5 的补充观察），记进案例列即可，不要据此定档。

**每一次命中封顶，都要说得出是哪个探针或第三层的哪个动作观察到的**；说不出来就把它当方法缺陷记下来，不要照记分。

## 2 · 两轴与封顶语义

两轴的档位定义、成熟度档与计数口径在 [01 §4](./01-evaluate-development-harness-coarse.md#4--十七维粗判)，这里只补两件细粒度才需要的事：

- **每维以自己的锚点为准。** 01 里那两张两轴表是所有维度的概括；同一档在不同维度上的判据不同，冲突时以该维的锚点行为准。
- **封顶是上限，可能比锚点推导出的更严。** 每条规则给出的都是上限：它可能比阶梯推导出的更严（这是有意的惩罚），但不会让一个已经违反某档定义的仓库拿到那一档——"命中却仍按更高档记"永远不成立。封顶规则集中列出**比阶梯更严**的惩罚；没有列出的情形，直接按锚点阶梯定档。

## 3 · 第三层：反证

### 第三层 · 反证

第三层检验的是**前面两层自己的可信度**。四个动作：

1. **抽检一个检查**：随便挑一个现有的检查，说得出它最近一次为红是因为什么回归吗？说不出，按 EL2 记；这维的约束力按第 4 节的封顶规则处理（EV2 那条会把它压得更低）。
2. **抽检一条规则**：随便挑一条写在文档里的规则，找一条最近违反过它的提交。找得到 → 规则在裸奔（EL1）。
3. **抽检一个链接**：从根入口文件随机点 5 个链接。打不开的记进第 4 张表。
4. **抽检一次"应该失败"**：故意制造一个小违规（加一个错别字进被检查的文件、破坏一个链接），跑检查，看它红不红，然后还原。**不允许跳过这一步**——它是你判断"这个仓库的检查是真的吗"的唯一手段。

### 三层怎么合起来用

```
（第一层 = 静态清点、第二层 = 垂直切片，定义见 [01 §3](./01-evaluate-development-harness-coarse.md#3--评估分三层)。）

第一层 → 结构在哪缺（哪一维低）
第二层 → 实际怎么跑（缺口造成什么后果）
第三层 → 已有的机制可信吗（低分是"没有"还是"有但假的"）
```

第一层的缺口清单和第二层的走查记录会合流成一张**施工顺序表**（这张表由[20 从缺口到计划](./20-from-gaps-to-plan.md)的[排序原则](./20-from-gaps-to-plan.md#1--排序原则)与[循环](./20-from-gaps-to-plan.md#7--一轮打磨的循环与停止条件)产出，本文不提供模板）：每一个"靠猜"和"没证据"都能归到十七维里的某一维，**哪一维的案例最多最痛，就先去那份文档里找那一维的处置卡**。

## 4 · 十七维细粒度卡

> 每张卡给出：一句话定义（**定义以本文为准**，01 §4 一览只是概述）、填的缺口、探针、两轴锚点、封顶规则、常见伪证、走形症状，以及可选的例证。**改动维度定义或档位时改 01；只加探针或封顶时改这里。**

### 知识归位 · KN 组

#### KN1 入口链 · Entry chain

**填的缺口**：IG1 必须遵守什么 / IG2 系统由什么组成

**一句话**：新会话开始时被稳定读到的那份最小规则集，以及它指向其余知识的路由。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | `ls -a` 根目录与主要子树，找出所有面向 agent 的入口文件（`AGENTS.md` / `CLAUDE.md` / `.cursorrules` / `CONTRIBUTING.md` / `.github/copilot-instructions.md`） | 有几个？分别服务谁？有没有重复 |
| PB2 | 若同一目录同时存在两个入口文件名：`ls -la` | 是不是符号链接。不是 → 两份事实，迟早分叉 |
| PB3 | 数根入口文件的行数与词数 | 是不是"大而全总览"。含教程、历史故事、完整流程 → 超预算；有没有成文的字数预算与维护触发条件，以及执行它的字数上限门禁（它红过吗） |
| PB4 | 从根入口里抽 5 条规则，逐条找它的详细 home | 每条能不能点到唯一一个更详细的位置 |
| PB5 | 数列子树入口文件的数量与理由 | 是不是"为放而放"。绝大多数目录只该有 README |

**覆盖面**：0 没有入口 / 1 有但混着教程与历史 / 2 短入口 + 布局 + 命令，其余链接出去 / 3 且有明确的字数预算与维护触发条件

**约束力**：0 靠口传 / 1 写在 prose 里 / 2 有链接检查（断链会红）/ 3 且有字数上限门禁

**封顶规则**
- 同一目录存在两个**非符号链接**的入口文件 → 覆盖面封顶 1（已经有两份事实了）
- 根入口文件包含教程或历史叙述 → 覆盖面封顶 1
- 根入口里的链接有打不开的 → 约束力封顶 1（路由断了，等于没有）
- 根入口没有指向更详细 home 的链接（一堵墙）→ 覆盖面封顶 1
- 根入口超出行/词预算（大而全总览，即使不含教程与历史）→ 覆盖面封顶 1
- 根入口没有成文的字数预算或维护触发条件 → 覆盖面封顶 2
- 根入口没有字数上限门禁 → 约束力封顶 2

**常见伪证**："我们有 `AGENTS.md`" —— 有文件不等于有路由。文件里如果没有指出去的链接，它不是入口链，是一堵墙。

**走形症状**：把根入口写成一份完整手册；或者到处放子树入口，让每个目录都要重新学一套。

**例证**（可选核对）：DSH 的根 `AGENTS.md` 只放常驻规则、布局与命令，每条规则 1–3 行并立刻给出链接；`CLAUDE.md` 是 `AGENTS.md` 的符号链接，四个目录各一处；根文件有字数上限（≤1,950 词），由 `verify-doc-budgets` 执行。

#### KN2 归属 · One home per fact

**填的缺口**：IG1 IG2 IG3

**一句话**：每类事实住在**负责它的那一层**，其它地方只放链接、不复制。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 随便挑 5 条规则，不靠作者带路找它的唯一 home | 不靠作者带路能不能指出来；home 里有没有写清"不该从这里取得什么"（禁放什么） |
| PB2 | 对每条规则，全局搜它的关键句 | 是不是在第二个地方又写了一遍 |
| PB3 | 找一个"改了 A 必须同时改 B"的例子，并看派生内容 | 这种耦合是否存在；有没有机制保证两边同步；派生内容有没有 freshness 门禁（源头变了、派生没跟上会红吗） |
| PB4 | 检查当前事实与决策理由是否分家 | 现状文档里有没有夹着大段"为什么当初…"；决策记录里有没有被当成当前接口说明 |
| PB5 | 找负知识：有没有记录"我们为什么不走某条路" | 被否决的方案，新参与者还会不会再提一遍 |
| PB6 | 找同一概念的不同叫法 | 同一个东西有没有两个名字、两个近义词被当成两件事？词表能不能指出每个词的唯一含义 |

**覆盖面**：0 没有归属概念 / 1 部分事实有家 / 2 每类事实有明确 owner 且写了"不该从这里取得什么"，术语有唯一含义（同一概念一个名字） / 3 且有维护触发条件与同步门禁

**约束力**：0 靠口传 / 1 写在 prose 里 / 2 有链接/一致性检查（复制件不一致会红）/ 3 且有生成物 freshness 门禁（源头变了派生没跟上就红）

**封顶规则**
- 任何一条规则指不出唯一 home → 覆盖面封顶 1
- 存在同一事实的两份**可写**拷贝（非生成物） → 覆盖面封顶 1
- 有事实类别没写出"不该从这里取得什么" → 覆盖面封顶 1
- 同一概念有两个并行叫法，或一个词被用来指两件事 → 覆盖面封顶 1
- 找不到任何负知识记录（被否的方案、已知限制）→ 覆盖面封顶 2
- 存在"改了 A 必须同时改 B"的耦合却没有同步机制 → 覆盖面封顶 2、约束力封顶 1
- 派生内容没有 freshness 门禁（源头变了派生不跟着变也不会红）→ 约束力封顶 2

**常见伪证**："我们的文档很全" —— 全不等于有家。两份都全，就是两个家。

**走形症状**：owner 表写了，正文却在每一处全文复制。补救方向是**把 home 补全**，不是允许复制。

**例证**（可选核对）：DSH 的文档分层表每行同时写"放什么"和"禁放什么"，例如常驻规则的 home 明确标注"不含详细教程、历史故事"；决策理由单独进 `.agents/notes/`，README 只写 now。

#### KN3 决策记录 · Decision records

**填的缺口**：IG3 为什么这样设计

**一句话**：存"为什么"而不是"是什么"、存取舍而不是实现，并且能跟着决定一起演进的知识载体。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找 3 个"当初有明显别的选择"的地方，看有没有记录 | 记了 / 没记 / 记了但只有结论没有备选；再数最近 10 条记录里有几条对应机械性改动（无真实备选） |
| PB2 | 打开一条记录读一遍，并看一次反转 | 能不能回答"为什么这样决定、什么方案输了、后果是什么"；反转时旧记录的独有内容（理由、备选、后果、验证缺口）有没有先被吸收进新记录 |
| PB3 | 状态怎么区分；过时记录最后被放到哪 | 现行 / 已否决 / 已过时三种状态是否一眼可分；有没有成文的归档规则与归档位置（还是过时记录留在原地、无处可去） |
| PB4 | 有没有"过时的理由冒充现行" | 被取代的记录是否还挂在权威位置 |
| PB5 | 被否决的方案还会不会被重提 | 问一个不了解历史的人（或新开一个 agent 会话）会不会想到那条路 |
| PB6 | 挑一件改过几轮的事，只读记录 | 能不能只读一处就说清它现在是什么、中间反转了几次、每次为什么；还是要翻散落的提交与文档才拼得出来 |

**覆盖面**：0 没有 / 1 零散存在，没有判据 / 2 有明确判据（存在真实备选与持久取舍才写）与状态区分 / 3 且有取代纪律与归档规则

**约束力**：0 靠口传 / 1 只靠自觉 / 2 有模板/结构检查 / 3 且有取代前的完整性检查（旧记录独有内容必须先被吸收）

**封顶规则**
- 记录里没有"备选与为什么不行" → 覆盖面封顶 1（那不是决策记录，是变更说明）
- 存在被取代的记录仍被当作现行权威引用 → 覆盖面封顶 1
- 为机械性改动批量建档（最近 10 条记录里过半没有真实备选）→ 覆盖面封顶 1（记录通胀会让真记录一起被无视）
- 现行 / 已否决 / 已过时三种状态不可分 → 覆盖面封顶 1
- 没有任何归档规则（过时记录仍留在权威位置之外无处可去）→ 覆盖面封顶 2
- 同一件事反复反转，却没有任何一处给出当前结论与沿革 → 覆盖面封顶 2
- 取代时没有先吸收旧记录的独有内容（没有取代前的完整性检查）→ 约束力封顶 2

**常见伪证**：数量。**一段"为什么不"的记忆，只在它仍能阻止一个可信的错误时才有价值。** 记录数不是指标。

**走形症状**：两个方向都会坏——没有备选的修补硬写记录（机械建档，很快没人再读），以及有真实取舍的变更不写（知识随人走）。

**例证**（可选核对）：DSH 的决策记录强制四节（问题 / 决定 / 备选 / 后果），验证与遗留是可选节；备选必须真实存在过、不得编造；生命周期由目录承载（`proposed` / `implemented` / `rejected` / 归档目录），归档件保留 `Status: implemented` 并加一行 `Archived:`，归档后不再是当前权威。

#### KN4 分类学 · Repository taxonomy

**填的缺口**：IG2 系统由什么组成

**一句话**：任何一个"这东西该放哪、谁维护它、能不能手改"的问题，都有命名的 owner 或机器门禁。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 列顶层目录，为每个写一句"它拥有什么" | 写得出来吗？有两个目录职责重叠吗 |
| PB2 | 对每个顶层区域，指出它的规则 owner | 有没有一个文件说清这个区域的规矩 |
| PB3 | 找生成物（catalog、类型桩、快照、投影站点） | 能不能手改；有没有 freshness 检查；有没有人真的手改过（`git log` 看这些路径） |
| PB4 | 找测试期望输出的存放规则 | 是"跟被证明的对象住一起"还是"全堆在一个大目录" |
| PB5 | 找第三方/vendored 代码 | 有没有本地修改日志；上游版本钉在哪 |

**覆盖面**：0 没有分类概念 / 1 有一些约定但不成文 / 2 每个区域有 owner、有"能不能手改"的说明 / 3 且按内容维护形态分类（手写 / 生成 / 录制 / 投影），每类有机器边界

**约束力**：0 靠口传 / 1 写在 prose 里 / 2 有生成物 freshness 门禁或结构检查 / 3 且有"手改生成物被拒绝"的直接拦截

**封顶规则**
- 两个顶层目录的职责说不清边界 → 覆盖面封顶 1
- 存在生成物被手改而没有任何检查发现 → 覆盖面封顶 2、约束力封顶 1
- 测试期望输出没有存放规则（各人放各处）→ 覆盖面封顶 2
- 有顶层区域指不出规则 owner → 覆盖面封顶 1
- 存在生成物却没有任何 freshness 门禁或结构检查 → 约束力封顶 1

**常见伪证**："我们的目录结构很清晰" —— 清晰是给作者的。检验法是让一个外部 agent 判断"新增一个 X 该放哪"，看它会不会猜错。

**走形症状**：大型仓库最常见的漂移不是代码错误，是**东西放错了地方**——同一事实的第二份手写清单、被手改的生成物、期望输出堆错目录。

**例证**（可选核对）：DSH 的根入口按顶层区域列出每个区域拥有什么；文档分层表每行同时写"放什么"和"不放什么"两列；生成类内容由源码再生成并有 freshness 门禁，手改生成物被拒绝。

---

### 变更路径 · CP 组

#### CP1 意图入口 · Work intake

**填的缺口**：IG7 交付怎样算完整

**一句话**：一个任务从"有人说要做点什么"变成"一份写得清验收条件的可开工描述"的路径。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找最近 5 个工作项的原始描述 | 能不能从中读出"外部可观察结果 + 如何观察" |
| PB2 | 找一个描述最差的工作项，看它后来怎么开工的 | 靠提问补齐 / 靠猜 / 靠口头约定；"验收条件缺失"的工作项有没有被系统明确拦下 |
| PB3 | 看工作项与提交的关联 | 提交或 PR 能不能回溯到它服务的意图 |
| PB4 | 看小改动走什么路径 | 是否所有事都必须走完整仪式（过度流程 = 会被绕过） |
| PB5 | 看"不做"的决定记在哪 | 被否的需求会不会被反复重提 |

**覆盖面**：0 没有入口，任务靠口头分派 / 1 有模板但没人按它写 / 2 每项有可观察的验收条件，且与提交可关联 / 3 且区分大小改动，小改动有轻量路径

**约束力**：0 靠口传 / 1 模板只是模板 / 2 有检查（缺少关联会红） / 3 且"验收条件缺失"会被明确拦下

**封顶规则**
- 最近 5 个工作项里有任何一项写不出"如何观察" → 覆盖面封顶 1
- 所有改动都必须走完整仪式，没有轻量路径 → 覆盖面封顶 2（流程会被绕过，绕过就全失效）
- 提交无法回溯到意图 → 覆盖面封顶 1
- "验收条件缺失"的工作项不会被拦下 → 约束力封顶 2

**常见伪证**："我们有 issue 模板" —— 模板存在不等于被使用，更不等于验收条件是可观察的。

**走形症状**：两个方向——意图完全不落盘（做完没人知道为什么做），以及所有改动都被同一个重仪式压住（小的绕过去，大的靠人情）。

---

#### CP2 正确路径 · Paved road

**填的缺口**：IG4 改动落在哪里

**一句话**：仓库为常见变更提供首选入口、生产范本和升级条件，让"做对"成为阻力最小的路径。

*适用性：仓库存在代码或配置变更路径时适用；纯文档站（没有代码变更路径）标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找一张"目标 → 机制"的归属表 | 有没有；右列是不是**能直接执行的动作**（改哪个文件、调哪个注册点） |
| PB2 | 拿一个真实需求，只看这张表 | 能不能答出"改哪里"，不翻代码 |
| PB3 | 找一个"本可用配置解决、却改了核心"的例子 | 有没有升级条件在拦 |
| PB4 | 找常见任务的操作范本（cookbook / 示例） | 有没有；是不是可复制可运行的 |
| PB5 | 看有没有人自己发明过新接法 | `git log` 找旁路式实现；有没有检查拦它 |

**覆盖面**：0 没有 / 1 有架构文档但只说"找相关模块" / 2 有归属表 + 范本 + 升级条件 / 3 且按参与半径分层（配置 → 扩展点 → 完整能力 → 核心），每层有升级判据

**约束力**：0 靠口传 / 1 文档只是文档 / 2 有检查（绕过入口会被结构检查发现） / 3 且有"必须走入口"的强制机制（例如只允许通过注册 API 接入）

**封顶规则**
- 归属表右列是"参考架构文档"这类二级指引 → 覆盖面封顶 1
- 属于常见变更类型却没有任何范本 → 覆盖面封顶 1
- 存在"能配置却改了核心"的近期实例且无人拦下 → 约束力封顶 1
- 归属表没有升级条件（什么情况该从配置升级到改核心没有判据）→ 覆盖面封顶 1

**常见伪证**："我们有架构文档" —— 架构文档解释系统**是什么**，不回答**我该改哪里**。这是两件事。

**走形症状**：归属表变成审批流程（申请→批准→实施），偏离了"降低判断成本"的本意；或者参与分层变成等级制（"高级的改核心"）。

---

#### CP3 流程固化 · Procedural memory

**填的缺口**：IG5 这类任务按什么流程做

**一句话**：反复出现、需要上下文判断的任务流程，被固化成带触发条件、步骤、停止条件和验证方式的短文档。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找出同一类任务第三次出现时发生了什么 | 是固化成了流程，还是每次现场发明 |
| PB2 | 打开一份流程文档 | 触发条件写清楚了吗；每一步有可执行命令或可打开的文件吗；判断标准是规则还是形容词 |
| PB3 | 看它有没有越界 | 是否把可机械判断的部分也写成了 prose（那部分应该在检查里） |
| PB4 | 看它有没有自我声明边界 | 是否说明"这是指导，不是清单" |
| PB5 | 看发现机制 | 模型/人能不能在**不读完**的情况下判断该不该读它（有没有摘要层） |
| PB6 | 挑一条会变的做法（提交 / 评审 / 发布 / 测试要求） | 现在该照哪一份？旧版本还在不在、有没有被当成现行的？这份文档什么时候复核 |

**覆盖面**：0 没有 / 1 有一些 wiki 页但没人用 / 2 有按任务组织的流程文档，带触发条件与步骤 / 3 且有摘要层（只看标题+适用条件决定读不读）与维护触发条件

**约束力**：0 靠口传 / 1 流程只是建议且无人遵守 / 2 且流程里指到的命令真实存在、可跑 / 3 且可机械化的部分已经下沉到检查，流程本身只管判断

**封顶规则**
- 流程文档里出现"做好验证"这类没有可执行内容的句子 → 覆盖面封顶 1
- 流程文档写成"必须依次执行 N 步"且没有判断标准 → 覆盖面封顶 2（清单病：环境一变就卡死在错的步骤上）
- 没有摘要层，只能整篇读 → 覆盖面封顶 2
- 流程文档没有维护触发条件（做法变了文档不跟着变）→ 覆盖面封顶 2
- 同一套做法有多份并存（旧版未撤回也未标为历史），读者分不清该照哪一份 → 覆盖面封顶 1
- 流程文档没有写触发条件（不知道什么情况该读它）→ 覆盖面封顶 1
- 流程文档里指到的命令不存在或跑不通 → 约束力封顶 1
- 可机械判断的部分仍留在流程 prose 里、没有下沉到检查 → 约束力封顶 2

**常见伪证**："我们有详细的文档" —— 详细到把判断收走，就是清单病；详细到全是散文，就等于没写。

**走形症状**：散文病（"推送前做好本地验证"——执行者还得自己猜步骤）与清单病（把判断固化成仪式）。正确形态是**步骤 + 每步的判断标准**，判断留给执行者。

---

#### CP4 执行与授权链 · Execution and authorization

**填的缺口**：IG1 必须遵守什么（安全与权限铁律）

**一句话**：一个自动化动作从发起到落定，走的是同一条管线；策略判在动作之前，结果只有一条出口。

*适用性：仓库里存在**需要授权的自动化动作**时适用（CI 机器人、代码生成器、任何让 agent 直接改仓库的流程）。**只跑测试、不产生可授权动作的流水线不触发本维**；没有任何这类动作时标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找"谁允许这个动作发生"的判定点 | 有几处？加一条新规则要改几个文件？ |
| PB2 | 看动作有没有在执行前被记录 | 失败的调用在不在记录里 |
| PB3 | 看结果怎么回到模型/人 | 有没有统一归一化；会不会出现"部分成功""未知状态" |
| PB4 | 找权限边界与"看得见"的边界 | 这两者是不是被混为一谈 |
| PB5 | 看危险动作有没有独立的授权步骤 | 还是靠"模型不会那么做" |

**覆盖面**：0 没有 / 1 检查散在每个工具/脚本自己身上 / 2 有统一的执行前判定层 + 单一结果出口 / 3 且有独立授权步骤与审计记录

**约束力**：0 靠自觉 / 1 写在 prose 里 / 2 权限判定在代码里强制 / 3 且越权必然失败并有记录

**封顶规则**
- 加一条策略规则需要改多个文件（策略散在各处）→ 覆盖面封顶 1、约束力封顶 1
- 存在"部分成功""未知状态"被直接喂给模型或人 → 覆盖面封顶 1、约束力封顶 1
- 把"可查询/可试验"当成"已授权" → 约束力封顶 1
- 危险动作没有独立的授权步骤（靠"模型不会那么做"）→ 覆盖面封顶 2
- 动作没有执行前的审计记录（失败的调用查不到）→ 覆盖面封顶 2

**常见伪证**："我们的工具自己会检查权限" —— 那是策略散在 N 处，改一次要动 N 个文件，而且总有一个忘了改。

**走形症状**：在工具体内部做权限检查（绕过统一判定层）；把未归一化的中间态直接塞回上下文。

**例证**（可选核对）：DSH 的工具执行管线把策略全部放在工具体之外（`pre-execute` 判定权限、审批走独立服务、结果在注册表外层归一化，异常一律变成 `isError`），并且多处明确标注边界——例如核心作用域原语写明"不是沙箱或权限边界"、包加载检查写明"不是防范恶意包代码的沙箱"。

---

### 证据与交付 · EV 组

#### EV1 反馈分层 · Feedback layers

**填的缺口**：IG6 怎么算做对

**一句话**：不同类型的问题由不同层的检查负责，且每一层只拥有它能观察到的性质。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 列出仓库所有的检查，按"它最早能在什么时候发现问题"排序 | 编译/加载期、局部行为、组装行为、运行时关系、语义判断，各有没有 |
| PB2 | 对每一层，找它**不能**证明什么 | 仓库里有没有说清层与层的边界 |
| PB3 | 看本地反馈延迟 | 改一行到拿到相关结论要多久；要等全套吗 |
| PB4 | 看本地与远端的分工 | hooks 跑什么、CI 跑什么；hooks 是不是"小号 CI" |
| PB5 | 看错误信息的质量 | 失败时说得出「失败对象 + 违反规则 + 修正入口」吗 |

**覆盖面**：0 只有"跑得起来" / 1 有测试但只有一层 / 2 至少四层齐备且各有分工说明 / 3 且每层有明确的"不能单独证明"清单

**约束力**：0 靠自觉 / 1 有检查但可在本地跳过且常被跳过 / 2 检查在流水线里强制 / 3 且本地按改动范围选检查（不全跑）同时远端跑穷举

**封顶规则**
- 绿色的一层被当作其它层也绿（例如用覆盖率证明产品可用）→ 覆盖面封顶 2
- 本地反馈需要等全套跑完 → 约束力封顶 2
- 失败信息只说"失败"，说不出违反哪条规则、去哪修 → 约束力封顶 2
- 检查层不足四层（编译/加载期、局部行为、组装行为、运行时关系、语义判断有缺）→ 覆盖面封顶 1

**常见伪证**："我们 CI 全绿" —— 全绿只覆盖检查碰巧碰到的地方，与"声称的行为都有证据"是两件事。

**走形症状**：层与层互相冒充——覆盖率绿了就当产品工作，快照绿了就当接口合理，评审去手工重复机器已经精确拒绝的格式问题。

**例证**（可选核对）：DSH 的测试分层文档逐层写明它**不能单独证明**什么（例如"覆盖率只证明行被执行，不证明功能可用"）；本地按改动面选最小证据，CI 拥有穷举覆盖与平台矩阵；Git 钩子明文不跑测试、快照、构建这类随改动面变化的检查。

---

#### EV2 负例控制 · Negative control

**填的缺口**：IG6 怎么算做对

**一句话**：每一个检查都被证明过**会失败**。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 随机挑 3 个现有检查 | 说得出它最近一次为红是什么回归吗；那次验证有没有留下记录（文件 / 注释 / CI 记录），还是只靠人口头记得 |
| PB2 | 挑一个检查，故意制造它该抓的违规 | 看它红不红，然后还原 |
| PB3 | 看仓库有没有"新检查必须验证"的成文要求 | 有要求 vs 有实践 |
| PB4 | 看端到端验证是"验证世界"还是"验证自述" | 测试是重新读文件/跑命令/看状态，还是相信执行者的声称 |
| PB5 | 看有没有"永远为绿"的检查 | 长期未变更、从未失败过的检查 |

**覆盖面**：0 没有这个概念 / 1 有人偶尔做 / 2 有明确要求（新检查必须做一次负例控制）/ 3 且留了记录，可追溯每次检查的验证

**约束力**：0 靠自觉 / 1 写在 prose 里 / 2 有流程要求且被抽查 / 3 且"没有负例控制的检查"会被明确拒绝合入

**封顶规则**
- 抽检的 3 个检查里，没有一个说得出最近一次为红的原因 → 本维约束力封顶 1
- 存在长期未失败过的检查且无人核查 → 约束力封顶 1
- 负例控制只做了"引入违规看它红"，没有验证"还原后变绿" → 约束力封顶 2
- 没有"新检查必须做一次负例控制"的成文要求 → 覆盖面封顶 1
- 负例控制没有留下可追溯的记录 → 覆盖面封顶 2

**常见伪证**："我们的检查很全" —— 检查全绿但没人信，是这类系统最贵的走形。

**走形症状**：绿灯数目成了 KPI；负例控制没人做过；检查逐渐变成仪式，然后有人开始绕过它。

**这一维为什么单列**：它是整份评分卡里**唯一一个检验"其它维度是不是真的"的维度**。EV1 问"有没有检查"，EV2 问"检查算不算数"。一个 EL2 的检查和一个 EL3 的检查，在通过率上完全一样，在保护效果上差别是全部。

---

#### EV3 闭环完整性 · Delivery completeness

**填的缺口**：IG7 交付怎样算完整

**一句话**：实现、当前文档、回归证据在**同一次交付**里一起走，缺口如实标注。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 拿最近 5 笔变更，看每一笔带了什么；其中最小的那笔是什么性质 | 代码 / 文档 / 测试 / 决策记录，各带了几笔；机械性改动是走轻量路径还是也必须走完整仪式 |
| PB2 | 找"代码合并了、文档还没跟上"的情况 | `git log` 看文档滞后代码多久 |
| PB3 | 看交付说明与证据是否一一对应 | 声称跑过的检查，CI 里真的有吗 |
| PB4 | 看缺口怎么处理 | 没有证据的声称是"如实标注为缺口"还是"用绿灯盖过去" |
| PB5 | 看回滚的粒度 | 出错时是整个切片原样退回，还是打补丁式热修 |

**覆盖面**：0 代码合并即完成 / 1 有时带文档和测试 / 2 常见变更都同批交付实现+文档+证据 / 3 且区分大小改动（机械性改动有轻量豁免），例外有明确理由

**约束力**：0 靠自觉 / 1 写在 prose 里 / 2 有检查（缺文档/缺测试会红） / 3 且"声称与证据不符"会被明确拦下

**封顶规则**
- 最近 5 笔变更里出现"先合并后补文档/补测试" → 覆盖面封顶 1
- 交付说明里出现无法对应的验证声称 → 约束力封顶 1
- 没有轻量豁免路径（所有改动一律全套）→ 覆盖面封顶 2
- 交付例外（缺文档/缺测试/缺证据）没有写明理由 → 覆盖面封顶 2

**常见伪证**："我们要求每个 PR 带测试" —— 要求是一回事，最近 5 笔里带了几笔是另一回事。**这一维只能用切片查，不能用文档查。**

**走形症状**：闭环断在两处——"实现 + 文档 + 证据同批交付"退化成"先合并后补"，"缺口如实标注"退化成"绿灯崇拜"。

**自测法**：拿最近一笔变更问——README 或文档声称的行为里，有几条**没有**任何测试钉住？说不出，就是缺口没被管理。

---

#### EV4 评审与批准 · Review and approval

**填的缺口**：IG6 IG7

**一句话**：谁在什么条件下判断"这笔变更可以进"，以及这个判断为什么可信。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 看最近 10 笔变更的批准过程 | 谁批准的？有实质评论还是只点了通过 |
| PB2 | 找批准的成文条件 | 有没有明确条件，还是"有人 approve 就行" |
| PB3 | 看评审意见的质量 | 有没有指出过真实问题；还是清一色"LGTM" |
| PB4 | 看评审与机器的分工 | 评审有没有在手工重复机器已经精确拒绝的问题 |
| PB5 | 看谁能批准、需要几个人 | 条件是否与改动风险挂钩 |

**覆盖面**：0 没有评审（直接推主干）/ 1 有评审但无成文条件 / 2 有成文条件且与风险挂钩 / 3 且评审范围（该看什么、不该重复什么）有明确规定

**约束力**：0 靠自觉 / 1 靠人际约定 / 2 平台强制（不能自批/需要 N 人） / 3 且条件（加权、路径归属）被机器计算并强制执行

**封顶规则**
- 最近 10 笔里，评审评论全部是"LGTM"之类的空话 → 覆盖面封顶 1
- 评审在重复机器已经精确拒绝的格式问题 → 覆盖面封顶 2
- 批准条件与改动风险无关（改核心和改错别字走同一套）→ 覆盖面封顶 1
- 有评审但没有成文的批准条件（"有人 approve 就行"）→ 覆盖面封顶 1
- 批准不靠平台强制（可自批、人数不限）→ 约束力封顶 1

**常见伪证**："我们有严格的双人评审" —— 数一数最近 10 笔的评论条数和内容，比任何制度描述都准。

**走形症状**：评审变成橡皮图章（有流程无判断），或者评审变成格式警察（人力被消耗在机器已经管住的事上）。

### 状态与上下文 · ST 组

#### ST1 静与动 · Static and dynamic

**填的缺口**：IG2 系统由什么组成

**一句话**：把仓库里的事实按"变得有多快 / 谁能改 / 丢了多疼"分成层，并且**每层只被上一层或显式操作修改**。

*适用性：只要仓库里跑着会跨轮存活的东西（agent 会话、长任务、缓存、派生索引），这一维就适用。**没有 agent 会话、只有缓存或派生索引时**，把高檔判据里的"模型可见面"替换为"事实源→派生的可重建性"来评（覆盖面 3 = 派生全部来自源头；约束力 3 = 有检查钉住这一点），不必强行套 agent 语义。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 列出仓库里所有"会变的事实"，为每一个归类 | 规则（跨版本不变）/ 配置（部署时定）/ 事实源（只追加）/ 派生（每轮重算） |
| PB2 | 对每个事实源，问"它丢了大不大" | 丢了不心疼的，它是派生，不是事实源 |
| PB3 | 找同一个数据有没有两个**可写**来源 | 有 → 两处存真，早晚分叉 |
| PB4 | 试着重放 | 重开进程/新会话，能不能还原"当时到底发生了什么" |
| PB5 | 看动态里产生的持久决定去哪了 | 会话里的结论有没有升级回静态层（文档/记录） |

**覆盖面**：0 没有分层概念 / 1 部分数据能说清属于哪层 / 2 四层齐备且各有明确的承载者与修改权限 / 3 且有"模型看到的内容必须可重建"这类不变量

**约束力**：0 靠自觉 / 1 写在 prose 里 / 2 派生物由源头生成（不能手改）/ 3 且有运行时检查断言"可见即可重建"

**封顶规则**
- 存在同一事实的两个可写来源 → 覆盖面封顶 1、约束力封顶 1
- 能进入模型请求的内容无法从记录重建 → 覆盖面封顶 2、约束力封顶 1
- 会话里产生的持久决定没有任何回写路径 → 覆盖面封顶 2
- 有"会变的事实"归不到四层里的任何一层（承载者不明）→ 覆盖面封顶 1

**常见伪证**："我们有数据库，状态当然是持久的" —— 持久不等于**可重建**。能存下来，和能回答"当时它看到了什么"，是两件事。

**走形症状**：把派生当事实源存（缓存成了第二真相）；动态层走私（上下文组装、工具结果绕过记录直接进模型）；不回写（同一个问题下一轮重新发明一遍）。

#### ST2 披露与隔离 · Progressive disclosure and isolation

**填的缺口**：IG2 IG5

**一句话**：知识按需加载，而不是一次全塞；超出预算时有回收手段；子任务拿到的是它需要的那部分，不是全部。

*适用性：有内容被注入模型请求、且注入量随规则或文档增长时适用；没有上下文预算压力的小仓库标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 看常驻注入的内容有多大 | 有没有预算上限；超了会发生什么 |
| PB2 | 看流程文档/规则怎么被发现 | 是全文注入，还是先给摘要、命中才加载全文 |
| PB3 | 看重复内容有没有去重 | 同一份内容会不会被注入两次 |
| PB4 | 看长任务超预算时怎么办 | 有回收/压缩吗；压缩时会不会把一个动作的调用和结果拆散 |
| PB5 | 看子任务/子代理的输入面 | 是继承全部上下文，还是只给需要的那部分 |

**覆盖面**：0 全量注入，没有预算概念 / 1 有"文档要写短"的纪律但运行时无约束 / 2 有按需加载 + 注入预算 / 3 且有回收与隔离（超预算压缩、子任务不带父上下文）

**约束力**：0 靠自觉 / 1 只靠写作纪律 / 2 有硬预算（超了会被截断并告知）/ 3 且回收过程本身有约束（不拆散调用与结果、压缩后可重建）

**封顶规则**
- 常驻内容没有上限 → 覆盖面封顶 1
- 有预算但超预算时静默丢弃 → 约束力封顶 1（必须能看到"丢了什么"）
- 压缩会拆散一个动作的调用与结果 → 约束力封顶 2
- 规则/流程只能全文注入（没有先摘要、命中才加载全文）→ 覆盖面封顶 1
- 子任务/子代理继承父的全部上下文（没有隔离）→ 覆盖面封顶 2

**常见伪证**："我们的文档写得很短" —— 写短只解决供给，不解决"这一轮该加载哪一份"。那是运行时的事。

**走形症状**：只做一层就当完成（只把文档写短，或只加压缩）；或者有预算但超限时静默丢弃，使用者以为该加载的都加载了。

#### ST3 运行时查询 · Inspectability

**填的缺口**：IG2 系统由什么组成

**一句话**：能用一条命令问出"这台机器/这个进程实际生效的是什么"，而不是读源码猜。

*适用性：存在多层配置叠加、或声明面大到需要用命令查询时适用；单层配置的小仓库标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 问"最终生效的配置是什么" | 有没有一条命令能答；还是要读源码/读多个叠加层自己拼 |
| PB2 | 问"仓库声明了哪些接口/注册项" | 有没有生成的清单；还是手工维护（会漂） |
| PB3 | 问"当前进程里实际有什么" | 有没有只读查询；还是只能打断点 |
| PB4 | 看静态清单会不会过期 | 有没有 freshness 检查 |
| PB5 | 看这几者的区别有没有说清、有没有被混用 | "声明了什么" vs "实际跑着什么"，混了吗；文档有没有说清"可查询 ≠ 有授权 ≠ 可回滚"；再找一处只读查询与一处权限判定，看只读是否被当作放行 |

**覆盖面**：0 全靠读源码 / 1 只有一条 dump 命令 / 2 有 dump + 生成的声明面清单 / 3 且有只读的活运行时查询

**约束力**：0 靠自觉 / 1 命令存在但没人知道 / 2 生成清单有 freshness 门禁 / 3 且完整性有守卫（新增的东西不可能静默无文档）

**封顶规则**
- 没有任何一条命令能回答"实际生效的是什么" → 覆盖面封顶 1
- 手工维护的接口清单且无 freshness 检查 → 覆盖面封顶 1、约束力封顶 1
- 把"可查询"当成"有授权"或"可回滚" → 约束力封顶 1
- 没有只读的活运行时查询（只能打断点或读静态清单）→ 覆盖面封顶 2

**常见伪证**："源码就是文档" —— 源码说的是**可能是什么**，回答不了**现在是什么**。多层配置叠加之后尤其如此。

**走形症状**：用"源码就是文档"跳过这一维；或者接口清单手工维护、还把它当权威（清单必然漂）；或者把"可查询"当成"有授权/可回滚"。

### 维护与发布 · MT 组

#### MT1 防漂移 · Drift prevention

**填的缺口**：全部（元维度）

**一句话**：外置的知识会漂，所以给它配机器检查、配基线、配复核触发条件。

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 数一数有多少份外置知识（文档、清单、索引、快照、决策记录） | 每份谁维护？漂了谁发现 |
| PB2 | 找结构检查脚本 | 有没有；检查什么（编码、链接、锚点、预算、配对、术语）；它有没有被证明会失败（最近一次为红是什么回归） |
| PB3 | 看基线怎么钉 | 文档有没有写"结论以哪个版本为准"；有没有"以当前 checkout 为准"这类会悄悄滑走的表述 |
| PB4 | 看数字类事实 | 预算、上限、个数——这类最容易漂的，有没有标注出处 |
| PB5 | 看上游更新时的复核路径 | 有没有明确"上游哪些变化要触发重审" |

**覆盖面**：0 没有 / 1 有零散的检查 / 2 有结构性检查脚本 + 明确的复核触发条件 / 3 且有基线钉定、预算表、归档策略，形成一套维护制度

**约束力**：0 靠自觉 / 1 脚本存在但要人记得跑 / 2 检查接进了提交流程 / 3 且检查自己被负例控制过

**封顶规则**
- 存在"手工维护的第二份清单"且无 freshness 检查 → 覆盖面封顶 1
- 文档使用"以当前版本为准"这类相对表述 → 覆盖面封顶 2
- 结构检查脚本从未被证明会失败 → 约束力封顶 1
- 没有明确"上游哪些变化要触发重审"的复核触发条件 → 覆盖面封顶 1
- 预算、上限、个数这类数字事实没有标注出处 → 覆盖面封顶 2

**常见伪证**："我们的文档更新很及时" —— 及时靠人，防漂移靠机器。这两者不能互相替代。

**走形症状**：检查脚本写了一次再没跑过；规则改了引用没跟着改（漏一处漂一处）；文档用"以当前版本为准"这类相对表述，让基线悄悄滑走。

**这一维为什么是元维度**：它不管任何具体知识，管的是**前面十六维能不能长期不失效**。前面做得再好，没有 MT1，六个月后会回到原点。

**例证**（可选核对）：DSH 的文档有逐文件字数上限并由门禁执行；生成的目录与源码有 diff 就红；决策记录有冻结归档纪律（归档后不再是当前权威）；历史引用一律用发布标签而不是裸 commit 哈希，并由门禁执行。

#### MT2 发布与版本纪律 · Release and versioning

**填的缺口**：IG7 交付怎样算完整

**一句话**：东西怎么出去、兼容承诺是什么、坏版本怎么退、老用户的数据怎么办。

*适用性：仓库向外部发布产物（包、镜像、服务、数据格式）时适用。不发布任何东西的仓库标 N/A。*

**探针**

| # | 做什么 | 看什么 |
|---|---|---|
| PB1 | 找一次真实发布 | 从"决定发"到"发出去"有几个步骤，有没有成文序列 |
| PB2 | 找兼容承诺 | 哪些接口承诺稳定、哪些明确不稳定；有没有写清楚 |
| PB3 | 看不可逆的产物（数据格式、已发布记录） | 变更时是就地改还是新增后继代 |
| PB4 | 看坏版本怎么退 | 有回退路径吗；回退会不会破坏已发布的数据 |
| PB5 | 看版本号与变更的关系 | 破坏性变更有没有被版本号或迁移说明标出 |

**覆盖面**：0 想发就发 / 1 有步骤但不成文 / 2 有成文发布序列 + 兼容承诺分级 / 3 且有不可逆产物的迁移纪律与回退路径

**约束力**：0 靠自觉 / 1 写在 prose 里 / 2 有检查（发布前置条件、格式版本号会红） / 3 且"移动/覆盖已提交世代"这类操作被直接拒绝

**封顶规则**
- 破坏性变更没有版本号或迁移说明 → 覆盖面封顶 2
- 已发布的数据/格式会被就地覆盖 → 覆盖面封顶 2、约束力封顶 1
- 稳定与不稳定的边界没有写明 → 覆盖面封顶 1
- 发布没有成文序列（每次现场拼步骤）→ 覆盖面封顶 1
- 坏版本没有回退路径 → 覆盖面封顶 2

**常见伪证**："我们遵循语义化版本" —— 版本号规则不告诉任何人**哪些接口真的承诺稳定**。那要单独写。

**走形症状**：把仪式当纪律（标签间距、RC 之间的提交数、发布 PR 的文件数），这些不防止任何具体事故；或者破坏性变更就地覆盖已发布的数据。

粗粒度在这家仓库上把 `EV2` 标成"待定档"（命中信号：抽检的检查说不出最近一次为红的原因）。细粒度按四步把它钉死：

## 附录 A · 封顶规则速查

封顶规则用于对抗"哪哪都给了高分"的评估通胀。任一条命中，对应轴的上限被压低，**不看其它证据**。

**上限的含义。** 每条规则给出的都是**上限**：它可能比锚点阶梯推导出的更严（这是有意的惩罚），但不会让一个已经违反某档定义的仓库拿到那一档——"命中却仍按更高档记"永远不成立。 封顶规则集中列出**比阶梯更严**的惩罚；没有列出的情形，直接按本维锚点阶梯定档。

| 维 | 触发条件 | 封顶 |
|---|---|---|
| KN1 | 同一目录有两个非符号链接的入口文件 | 覆盖面 1 |
| KN1 | 根入口含教程或历史叙述 | 覆盖面 1 |
| KN1 | 根入口有打不开的链接 | 约束力 1 |
| KN1 | 根入口没有指向更详细 home 的链接（一堵墙） | 覆盖面 1 |
| KN1 | 根入口超出行/词预算 | 覆盖面 1 |
| KN1 | 根入口没有成文的字数预算或维护触发条件 | 覆盖面 2 |
| KN1 | 根入口没有字数上限门禁 | 约束力 2 |
| KN2 | 任何一条规则指不出唯一 home | 覆盖面 1 |
| KN2 | 同一事实有两份可写拷贝 | 覆盖面 1 |
| KN2 | 有事实类别没写出"不该从这里取得什么" | 覆盖面 1 |
| KN2 | 同一概念有两个并行叫法，或一个词指两件事 | 覆盖面 1 |
| KN2 | 找不到任何负知识记录（被否的方案、已知限制） | 覆盖面 2 |
| KN2 | 有"改了 A 必须同时改 B"的耦合却没有同步机制 | 覆盖面 2、约束力 1 |
| KN2 | 派生内容没有 freshness 门禁 | 约束力 2 |
| KN3 | 记录里没有"备选与为什么不行" | 覆盖面 1 |
| KN3 | 被取代的记录仍被当现行权威引用 | 覆盖面 1 |
| KN3 | 为机械性改动批量建档（最近 10 条里过半无真实备选） | 覆盖面 1 |
| KN3 | 现行 / 已否决 / 已过时三种状态不可分 | 覆盖面 1 |
| KN3 | 没有任何归档规则 | 覆盖面 2 |
| KN3 | 反复反转却没有一处给出当前结论与沿革 | 覆盖面 2 |
| KN3 | 取代时没有先吸收旧记录的独有内容 | 约束力 2 |
| KN4 | 两个顶层目录职责边界说不清 | 覆盖面 1 |
| KN4 | 生成物被手改而无检查发现 | 覆盖面 2、约束力 1 |
| KN4 | 测试期望输出没有存放规则 | 覆盖面 2 |
| KN4 | 有顶层区域指不出规则 owner | 覆盖面 1 |
| KN4 | 存在生成物却没有任何 freshness 门禁或结构检查 | 约束力 1 |
| CP1 | 最近 5 个工作项有一项写不出"如何观察" | 覆盖面 1 |
