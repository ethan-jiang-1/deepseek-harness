# 缺了维度怎么办：从缺口到计划

**这份文档是什么。** 评估告诉你"哪一维红了"，这份文档告诉你"**接下来做什么、按什么次序做、做的时候别把什么当成什么**"。

它处理的是一个具体的思考动作：**手上有一堆缺口，资源有限，先动哪一个，动成什么样算数。** 它不重复评估方法——评估在 [开发 Harness 粗粒度](./01-evaluate-development-harness-coarse.md) 与 [运行时 Harness 粗粒度](./11-evaluate-runtime-harness.md)，本文只做处置。

**可以单独使用。** 没做过评估也能用：跳到[第 2 节](#2--症状--缺口--维度总对照表)（开发 Harness）或[第 4 节](#4--运行时维度症状与处置卡)（运行时 Harness），用症状对号入座，找到维度，再翻到对应的处置卡。做过评估的话，从[第 1 节](#1--排序原则)开始，它讲怎么拿评分卡排顺序。

**编号约定。** 维度沿用 01/02 的两字母前缀（`KN`/`CP`/`EV`/`ST`/`MT`/`RT`），缺口用 `IG`（见 [README 的标识符约定](./README.md#标识符约定token)）。

**术语自包含，一处例外。** 开发 Harness 的维度名与缺口编号（IG1–IG7）在第 2 节的对照表里全部展开；**运行时那一半（第 4 节）例外**——它依赖 [运行时 Harness 粗粒度](./11-evaluate-runtime-harness.md) 的三个适用性问题（AQ1–AQ3）与五个活体实验（LX1–LX5，定义在 11 第 2 节），本文不重复定义，用第 4 节前请先做那三个判定。

## 1 · 排序原则

### 原则一：痛点优先，不按列表顺序

评分卡上哪一维的**案例最多、后果最贵**，就先做哪一维。通用优先级只是没做评估时的默认值。

判断"最痛"的方法：缺口清单里每一条都写了"谁在什么时候会踩到"。把"已经在踩"的排到"迟早会踩"前面。

### 原则二：先做前置维

有五个维度是**前置的**（分属知识归位与证据与交付两组）——它们不做，其余维度做了也白做：

| 前置 | 为什么是前置 |
|---|---|
| **KN1 入口链 + KN2 归属** | 路由不存在，你后面写的所有知识都到不了读者手里 |
| **EV1 反馈分层 + EV2 负例控制** | 没有可信反馈，你无法验证任何一项改动的效果。改进本身变成盲改 |
| **EV3 闭环完整性** | 交付不闭合，前面所有投入都会在下一次"先合并后补文档"里漏掉 |

前置维的特征：**它们的失败会让其它维度的收益归零**，而不是"它们比较重要"。

**MT1 防漂移不单独排期，伴随做。** 每外置一份知识（入口、归属表、清单、流程），就在同一次改动里给它配上结构检查和负例控制（见 [MT1 卡](#mt1-防漂移--处置卡)）。其余十一维归[原则三](#原则三有压力再借)。

### 原则三：有压力再借

以下维度**不要提前做**。它们的收益只有在对应压力真实出现时才成立，提前做会变成纯维护成本：

| 维度 | 触发条件（压力真的出现了才做） |
|---|---|
| KN3 决策记录 | 一个已被否决的方案，被第二次重新提出 |
| KN4 分类学 | 出现同一事实的第二份手写清单；或生成物被手改而无人发现 |
| CP3 流程固化 | 同一类任务第三次出现时还在现场发明流程 |
| CP4 执行与授权链 | 仓库里开始有自动化代理直接改动内容，且威胁模型清晰了 |
| ST1 静与动 | 出现同一份配置或数据两处可写；或删掉派生后重建不出同样的结果 |
| ST2 披露与隔离 | 常驻规则开始膨胀；或 agent 频繁漏读、读错流程 |
| ST3 运行时查询 | 手工维护的接口清单已经维护不动；或存在多层配置叠加 |
| MT2 发布与版本纪律 | 开始对外发布产物，且出过一次"发错了/忘 bump 了"的事故 |
| CP1 意图入口 | 出现"做完才发现理解错了"的返工 |
| CP2 正确路径 | 有人在错误的地方插代码、或自己发明一套新接法；或真实需求进来没人答得出"改哪里" |
| EV4 评审与批准 | 出现"评审只是点通过"或"评审全在挑格式" |

**在压力出现之前建这些机制，是在为一个不存在的问题付维护费。** 这是把成熟样板照搬到小项目上最常见的浪费。

### 原则四：按"成本档"而不是"重要性"排同一批

同一个优先级里，先做便宜的：

| 成本档 | 特征 | 典型 |
|---|---|---|
| **零架构依赖** | 只是一份文件、一个符号链接、一条命令 | 入口链、归属表、决策记录目录 |
| **一个脚本** | 一个 `exit non-zero` 的命令 + 一次负例控制 | 反馈分层、负例控制、防漂移、披露与隔离的预算门禁 |
| **一个流程** | 需要改协作习惯，但不需要改代码结构 | 闭环完整性、评审与批准、意图入口 |
| **一个架构** | 需要动代码结构或引入新层 | 执行与授权链、静与动的单一可写来源、发布与版本纪律 |

前两档几乎零架构依赖，是大多数项目真正的第一桶金。第四档永远排最后。

**运行时维度的对应排序**（前置三维、有压力再借、最便宜的三刀）见[第 4.1 节](#41-运行时维度的排序原则)。原则一到六对两类维度同样成立。

### 原则五：一轮只动一到三维

一轮改动同时碰五维，做完了没人说得清是哪一项起了作用。**一轮一到三维，做完回评估复测，再决定下一轮。**

### 原则六：同时评两份时，名字相近的维度各评各的对象

一个仓库本身是 agent 产品时，[01](./01-evaluate-development-harness-coarse.md) 与 [11](./11-evaluate-runtime-harness.md) 都要评。有四对维度名字相近、判据同源，但**评的是两个不同的系统**：开发侧评仓库交给参与者（含 coding agent）的机制，运行时侧评产品里的 agent 运行时。

| 开发侧（评仓库） | 运行时侧（评产品） | 两边各自看什么 |
|---|---|---|
| CP4 执行与授权链 | RT9 工具执行与授权 | 仓库的 CI 机器人、发布脚本、改仓库的 agent 流程 vs 产品里模型发起的工具调用 |
| ST1 静与动 | RT2 会话事实源 | 仓库的配置、记录、生成物 vs 产品的会话记录 |
| ST2 披露与隔离 | RT7 模型可见面组装 | 仓库供给 coding agent 的常驻规则与流程摘要 vs 产品每一步组装给模型的请求 |
| ST3 运行时查询 | RT1 组合与启动 | 开发工具链与本地环境的实际生效值 vs 产品运行时的组合结果 |

**规则：两侧各自计分、各自排期，不去重，也不互相借证据**——用产品有会话记录来给开发侧 ST1 加分，或用仓库有 CI 授权来给 RT9 加分，都是拿一个系统的证据评另一个系统。判据可以互相借鉴：一侧已经做对的做法，常常是另一侧处置卡的现成范本。

## 2 · 症状 → 缺口 → 维度总对照表

### 缺口编号（评估里的 IG1–IG7）

| 缺口 | 它缺的那句话 |
|---|---|
| **IG1 必须遵守什么** | 这里有哪些铁律？哪些事绝对不能做？ |
| **IG2 系统由什么组成** | 这个仓库有哪些部分，谁依赖谁，东西放哪？ |
| **IG3 为什么这样设计** | 当初为什么选这条路？什么方案被否了？ |
| **IG4 改动落在哪里** | 这个需求应该改哪个机制？ |
| **IG5 这类任务按什么流程做** | 这类任务该按什么步骤？什么时候停？ |
| **IG6 怎么算做对** | 什么证据能证明我没做错？ |
| **IG7 交付怎样算完整** | 实现、文档、证据要一起交吗？缺口如实说吗？ |

**从症状出发**：左边找最像你的一句，右边拿到维度，再去第 3 节翻处置卡。

| 常驻规则越塞越多，agent 每次要读完一大堆才开工，还常漏读流程 | IG2 IG5 | ST2 披露与隔离 | [ST2](#st2-披露与隔离--处置卡) |

| 发布靠手动记步骤；发布后才发现兼容性炸了 | IG7 | MT2 发布与版本纪律 | [MT2](#mt2-发布与版本纪律--处置卡) |

### 反向读法：从维度找症状

评估给出的是一张十七行的表。表上每一维低于 2 档时，它对应的**典型后果**是：

- **知识归位组低** → 读者抓不住主线，读到过期的理由当现行，东西越放越乱
- **变更路径组低** → 改动落在错误位置，流程每次重新发明，能配置的事改了核心
- **证据与交付组低** → 交付不可验证，"全绿"与"没人信"同时存在
- **状态与上下文组低** → 配置两处存真，常驻规则淹没读者，只能读源码猜实际生效的是什么
- **维护与发布组低** → 前十六维的成果在半年内失效

## 3 · 十七张处置卡（开发 Harness）

每张卡八栏：**什么时候才值得做 / 最小形态 / 做法 / 验收红线 / 一次负例控制 / 成本 / 它不买什么 / 学走形的样子**（KN3 另加一栏"不必照搬的"）。

"验收红线"是**做完必须能通过**的检查；"学走形的样子"是**做错了会长成什么样**——两者都要看，因为这类工作最常见的失败不是没做，是做成一个看起来像的东西。

---

### KN1 入口链 · 处置卡

**什么时候才值得做。** 任何时候。前置维里最先做的一张——它零架构依赖，半小时见效。

**最小形态。** 一份短的根入口文件（常驻规则 + 仓库布局 + 命令表），其余全部链接出去；如果宿主认多个文件名，用符号链接指向同一份。

**做法。**
1. 写常驻规则，每条 1–3 行，后面立刻跟一个指向详细 home 的链接。
2. 写仓库布局：每个顶层区域一句话，说明它拥有什么。
3. 写命令表：装、跑、测、构建，各一条。
4. 多个入口文件名用符号链接统一（例如 `ln -s AGENTS.md CLAUDE.md`），编辑真实文件。
5. 只在**真正有子树专属常驻规则**的少数目录放子树入口，其余目录只留 README。
6. 给根文件定一个字数上限，写进检查。

**验收红线。**
- 任何一条规则能在 10 秒内指出唯一 home；
- 根文件里没有教程、没有历史故事、没有该链接出去的细节；
- 从根文件出发的链接都能打开；
- 多宿主场景下是符号链接，不是副本。

**一次负例控制。** 故意把根文件里的一个链接改错，跑检查，看它红，然后还原。**不红说明你没有链接检查，先补这个。**

**成本。** 一次性半天；之后每加一条常驻规则都要问"它该不该在这里"。

**它不买什么。** 入口链不减少系统的复杂度。它只保证读者能**找到**复杂度在哪，不保证复杂度本身变小。

**学走形的样子。** 把根文件写成完整手册（几百行，什么都有）；或者反过来，到处放子树入口，让每个目录都要重新学一套。

---

### KN2 归属 · 处置卡

**什么时候才值得做。** 任何时候，与 KN1 同批。发现"同一事实第二个家"的当天就该做。

**最小形态。** 一张"事实 → home"对照表，每行同时写清**放什么**和**禁放什么**；然后按表把复制出来的正文删掉，改成链接。

**做法。**
1. 列出你的事实类型：常驻规则 / 当前组成 / 术语与位置 / 为什么这样选 / 某类任务怎么做 / 怎么验证。
2. 为每类指定唯一 home，并写一行"不从这里取得什么"。
3. 把散在别处的复制正文删掉，只留链接。
4. 把"当前事实"和"决策理由"分家：现状文档只写 now，理由单独进决策记录。
5. 记一条**负知识**：某个方案为什么不走、某个能力有哪些已知限制。
6. 给事实表加**维护触发条件与同步门禁**；派生内容加 **freshness 检查**（源头变了、派生没跟上就红）——这两条是覆盖面 3 与约束力 3 的判据。
7. 把**术语收进词表**：一个概念一个名字；近义词要么合并、要么明确区分，不许两个名字指同一件事。

**验收红线。**
- 任意一条规则 10 秒内指得出唯一 home；
- **删掉链接以外的复制正文，信息不丢**（丢了说明 home 没写全——该补 home，不是允许复制）;
- 现状文档里没有以"为什么当初…"开头的历史段落（这类内容只出现在决策记录里）；
- 至少有一条负知识，且新参与者读到它之后不会再提那个被否的方案；
- 同一个概念只有一个名字（词表能指出每个词的唯一含义）。

**一次负例控制。** 挑一个有两份拷贝的事实，只改其中一份，看有没有任何检查或流程发现。发现不了，就在归属表里标注这个耦合点，并把它列进 EV2 的待办。

**成本。** 一次性 1–2 天；之后每次新增一类事实都要问"它的家在哪"。

**它不买什么。** 归属让复杂系统**可查询**，不让它变简单。包、事件、生命周期仍然复杂。

**学走形的样子。** 归属表写了，正文却在每一处全文复制——表成了摆设，事实仍是多份。补救方向永远是**把 home 补全**，不是允许复制。

### KN3 决策记录 · 处置卡

**什么时候才值得做。** 一个已被否决的方案被第二次重新提出时。在那之前，用"当前事实 + 代码注释"通常够。

**最小形态。** 一个记录目录 + 一份五节模板 + 一条判据。

**做法。**
1. 定判据：**存在真实备选方案与持久取舍才写**。改动小不是豁免理由——没有取舍才是。
2. 用五节模板：`问题`（让没参与讨论的人看懂）/ `决定`（写成已交付的事实，不是提案语气）/ `备选`（被否决的方案 + 为什么不行）/ `后果`（接受的代价）/ `验证`（什么证据钉住覆盖的行为）。
3. 用目录或字段承载状态：待评审 / 已落地 / 已否决 / 已归档，让人一眼分得清。
4. 定取代纪律：反转时**新增**记录 + 交叉链接，不原地改写；完全取代前必须把旧记录的独有内容（理由、备选、后果、验证缺口）全部吸收。**否则删掉的不是文档，是别人踩过的坑。**
5. 归档按"未来决策价值"判断，不按字数或年龄；归档后冻结，**不再是当前权威**，引用它必须注明是历史。
6. 同一件事多次反转时，在**最新**那条记录里维护一节**沿革**：A → B → C 各一行、每次为什么；当前结论只出现在一处。

**验收红线。**
- 读一条记录能回答"为什么这样决定、什么方案输了、后果是什么"；
- 备选是真实存在过的（**编造落选方案会让记录失去全部可信度**）；
- 验证指到真实检查；没有就如实写"暂无"，不凑数；
- 存档里没有仍被当作现行权威引用的记录；
- 挑一件改过多轮的事：只读这一处就能说清它现在是什么、改过几次、每次为什么。

**一次负例控制。** 找一条已被取代的决定，问一个不了解历史的人（或新开一个无上下文的会话）会怎么选。如果他选了被否决的那条，说明记录没起作用。

**成本。** 每条记录半小时到两小时；成本在**读**上——记录通胀会让真记录一起被无视。

**它不买什么。** 记录不保证决定是对的，只保证下一个参与者不会在同一块石头上绊第二次。

**学走形的样子。** 两个方向都会坏：没有备选的机械修补硬写记录（很快没人再读），以及有真实取舍的变更不写（知识随人走）。

**不必照搬的。** 双语三件套（同一文档的中文、英文与配对记录三件；除非项目真的双语平等）、六类以上的分类目录（两三类通常够用）、格式门禁（先有纪律，量大到手工管不住再上机器）。

### KN4 分类学 · 处置卡

**什么时候才值得做。** 出现同一事实的第二份手写清单；或者生成物被人手改而没有任何检查发现；或者"这个文件该放哪"被问第三次。

**最小形态。** 一张顶层区域表（区域 / 拥有什么 / 规则 owner），加一张"内容的维护形态"表（手写 / 生成 / 录制 / 派生的投影），每类写清"能不能手改"。

**做法。**
1. 列顶层区域，每个写一句"它拥有什么"，再指定它的规则 owner。
2. 给内容分类维护形态，并为每一类定机器边界：手写的走评审、生成的由源码再生成（手改被拒绝）、录制的封存后不可改、投影的可丢弃重建。
3. 给测试期望输出定存放规则：**证据住在被它证明的对象旁边**，集中目录只收真正同类的东西。
4. 给 vendored / 第三方代码定所有权与本地修改日志（每一次偏离上游都要记）。
5. 边界说不清的两个区域，立刻合并或重新划界。

**验收红线。**
- 每个"放哪 / 谁维护 / 能不能手改"的问题都有命名的 owner 或门禁；
- 存在生成物的 freshness 检查（源头变了派生没跟上就红）;
- 拿一个新增项问外部的人或 agent"该放哪"，不会猜错。

**一次负例控制。** 手改一个生成物，跑检查，看它红不红，然后还原。不红的话，这个生成物现在是第二份事实源。

**成本。** 划界一次性 1–2 天；之后每次新增区域都要同时更新表和它的 README。

**它不买什么。** 分类不会减少文件数量。它让"放哪"从判断变成查表。

**学走形的样子。** 建了一堆空目录和一层没人维护的中间层；或者分类过细，以至于每个文件都要先读一遍规则才知道放哪。

### CP1 意图入口 · 处置卡

**什么时候才值得做。** 出现"做完才发现理解错了"的返工；或者提交无法回溯到它服务的意图。

**最小形态。** 一个工作项模板，第一段强制写两行：**外部可观察结果 + 如何观察**。加一条轻量路径给明显的小改动。

**做法。**
1. 在工作项里强制两行：结果是什么、怎么观察。
2. 让小改动有轻量路径——**要求所有改动走完整仪式，结果是小的绕过去，绕过就全失效**。
3. 建立工作项与提交的关联（提交或 PR 能回溯到它服务的意图）。
4. 给"不做"的决定一个家（被否的需求不再被反复重提）。
5. 定期看小改动的实际路径：它们真的走了轻量路径吗？

**验收红线。**
- 最近 5 个工作项都写得出现两行"外部结果 + 如何观察"；
- 提交能回溯到意图；
- 存在一条被真实使用的轻量路径；
- 每个被否的需求都有一条可检索的记录（含否决理由）；是否重提由下一轮复测回看。

**一次负例控制。** 拿一个最近的小改动，装作不知道它做了什么，只看它关联的工作项描述——猜得出来吗？猜不出，说明描述里只有"要做什么"，没有"怎么算做完"。

**成本。** 每项几分钟；成本在纪律上，不在工具上。

**它不买什么。** 意图写清楚了，也不会自动变成正确的实现。它只把"理解错了"从交付后提前到开工前。

**学走形的样子。** 模板存在但没人按它写；或者反过来，所有改动都被同一个重仪式压住，小的开始走私下渠道。

### CP2 正确路径 · 处置卡

**什么时候才值得做。** 有人在错误的地方插代码，或自己发明了一套新的接法；或者一个真实需求进来，没人答得出"改哪里"。

**最小形态。** 一张两列的"目标 → 机制"表。**右列必须是新参与者能直接执行的动作**（改哪个文件、调哪个注册点、配哪段配置），不能是"参考架构文档"这类二级指引。再加 2–3 个最常见任务的操作范本。

**做法。**
1. 写归属表：左边是"我想做的一件事"，右边是"具体动作"。
2. 按参与半径分层，并给每层写升级条件：改配置 → 用扩展点 → 做一个完整能力 → 动核心。**每一层的升级条件必须可核对**（"现有扩展点表达不了"是一个条件，"感觉比较复杂"不是）。
3. 升级路径上补一条横切检查：**这次改动有没有新增"外部可见"的事实？** 有的话，它必须同步进记录。这一条是横切义务，不是升级理由。
4. 给最常见的 2–3 类任务写操作范本：短入口 + 可复制的例子 + 升级条件 + 对应检查。
5. 拿一个真实需求做自测。

**验收红线。**
- 只看归属表能答出"改哪里"，不用翻代码；
- 每个范本里的"跑对应检查"指向真实存在的命令；
- 存在"本可用配置解决却改了核心"的拦截机制；
- **没有特权核心**：新行为挂到已声明的入口上，而不是往主流程里插分支。

**一次负例控制。** 拿最近一次"绕过入口"的改动，看现在的规则或检查会不会拦住它。拦不住，说明归属表和检查脱节了。

**成本。** 一次性 2–3 天写第一版；之后每加一个扩展点就要加一行。

**它不买什么。** 正确路径让"做对"变省力，不保证"做对"一定发生。语义判断仍需评审（见 EV4）。

**学走形的样子。** 归属表变成审批流程（申请→批准→实施），偏离了"降低判断成本"的本意；或者参与分层变成等级制，让人以为"改核心"更高级。

### CP3 流程固化 · 处置卡

**什么时候才值得做。** 同一类任务第三次出现，且每次做法都不一样。

**最小形态。** 一个"任务 → 流程文档"的目录；每份文档带触发条件、步骤、停止条件、验证方式；只给摘要层（标题 + 适用条件），命中才读全文。

**做法。**
1. 只固化**反复出现且需要上下文判断**的任务。可机械判断的那部分下沉到检查（EV1），不要写进流程文档。
2. 每份文档的适用条件写进标题/摘要，用 `Use when …` 这种句式把时机说全。
3. 正文每一步给**可执行命令或可打开的文件**，并写明这一步的边界。
4. 判断标准写成规则，不写成形容词。"选合适的检查"不是标准；"每个行为变更都需要一个会为这次回归而失败的最小检查"是标准。
5. 文末声明：**这是指导，不是完整清单**。
6. 文档里写进一条纪律：**命中任务时先读全文，不要从摘要猜流程**。
7. 给每份流程文档一个复核触发条件：**它引用的命令或接口变了，就重跑一次"让没做过的人照着走"**。
8. **做法变更时就地替换正文**，并留一行"替代了哪一版、为什么"；旧版撤下或明确标为历史——不要让两份做法并存。

**验收红线。**
- 抽取一份文档，每一步都能照着做（有命令或文件）；
- 没有"做好验证"这类没有可执行内容的句子；
- 判断标准是规则不是形容词；
- 可机械化的部分确实在检查里，不在文档里；
- 有摘要层，不必读完就能判断该不该读；
- 挑一条会变的做法：只读一处就知道现在照哪一份，旧版本已撤下或标为历史。

**一次负例控制。** 把一份流程文档给一个没做过这类任务的人（或新会话），让他照着做一遍。卡在哪一步，那一步就写得不够具体。

**成本。** 每份 1–2 小时；维护成本在于它引用的命令会变——引用而不是复制，能显著降低这项成本。

**它不买什么。** 流程文档**不是强制执行**。高风险且可机械判断的规则，仍然必须下沉到检查里。

**学走形的样子。**
- **散文病**：写成"推送前做好本地验证"，执行者还得自己猜步骤——等于没写。
- **清单病**：写成"必须依次执行 12 步"，把判断收走了——环境一变就卡死在错的步骤上。

正确形态是**步骤 + 每步的判断标准**：流程提供稳定入口，判断留给执行者。

### CP4 执行与授权链 · 处置卡

**什么时候才值得做。** 仓库里开始有自动化代理直接改动内容，且威胁模型清晰了。**在那之前不要建。**

*评的是仓库自己的自动化；产品里的工具执行见 [RT9](#rt9-工具执行与授权--处置卡)，两者各自处置（见[原则六](#原则六同时评两份时名字相近的维度各评各的对象)）。*

**最小形态。** 三件事，各一个：动作先记录再执行；统一的执行前检查；结果的单一出口。

**做法。**
1. **先记录再执行**：任何动作先追加到任务日志（哪怕只是一个 JSONL 文件），失败的调用也在场。
2. **统一的执行前检查**：权限/白名单在动作发起前判一次，拒绝走统一出口。**不要在每个工具自己身上做检查**——那是策略散在 N 处，改一次动 N 个文件。
3. **结果的单一出口**：所有结果经同一处归一化（异常变成明确的错误标记）再进入下一步，**不要让"部分成功""未知状态"出现在下游**。

**验收红线。**
- 拿日志能回答"昨天那条命令发了什么、结果是什么"；
- **加一条新权限规则只改一个文件**；
- 下游看不到未归一化的中间态。

**一次负例控制。** 加一条新权限规则，数一数改了几个文件。**答案应该是"一个"。** 如果改了多个，说明策略还有散落的地方。

**成本。** 第 1、3 条一天内可做；第 2 条取决于现有结构。**审计记录与单一结果出口现在就做；审批环节在威胁模型清晰时必须补上**（它是覆盖面 3 的判据）。单调守卫、文件变更意图门这些，等复杂度真到了再加。

**它不买什么。** 执行链管的是"动作怎么走"，不管"该不该做这个动作"。**"能查询/能试验"不等于"已授权"，也不等于"外部副作用可回滚"。**

**学走形的样子。**
- 在工具内部自己做权限检查（绕过统一判定层）；
- 把未归一化的中间态直接塞给下游；
- 把"给了一个查询工具"当成"给了一个沙箱"。

### EV1 反馈分层 · 处置卡

**什么时候才值得做。** 任何时候，与知识归位组同批。它是"能不能验证后续所有改进"的前提。

**最小形态。** 一张表：每一层检查能证明什么、**不能单独证明什么**。再加一条纪律：本地按改动范围选检查，远端跑穷举。

**做法。**
1. 按"最早能在什么时候发现问题"列出所有检查：编译/加载期、局部行为、组装行为、运行时关系、语义判断。
2. 为每一层写清"**不能单独证明**"什么。这一列比"能证明"更重要——它防止层与层互相冒充。
3. 定本地与远端的分工：本地跑和当前改动相关的、延迟低的；远端跑穷举。
4. 检查错误信息的格式：**失败对象 + 违反规则 + 修正入口**，三者缺一不可。
5. **不要往本地快反馈层里塞随改动面变化的重检查**——它会让这一层变慢，然后被绕过。

**验收红线。**
- 至少四层各有具名的检查；
- 每层有明确的"不能单独证明"说明；
- 本地改一行到拿到相关结论在分钟级以内；
- 失败信息说得出违反哪条规则、去哪修。

**一次负例控制。** 制造一个只在一个层能被发现的回归，跑一遍，确认**正确的那一层**抓住了它，其它层保持绿。如果所有层都红了，说明分层没有实际意义。

**成本。** 一次性 1–2 天梳理；每一层都要长期维护。

**它不买什么。** 全绿只覆盖检查碰巧碰到的地方。**"CI 全绿"与"声称的行为都有证据"是两件事**——后者要 EV3 来管。

**学走形的样子。** 覆盖率绿了就当产品能工作；快照绿了就当接口设计合理；评审去手工重复机器已经精确拒绝的格式问题。

### EV2 负例控制 · 处置卡

**什么时候才值得做。** 在你**第一次**把一条规则接成检查的同时。不是之后，是同时。

**最小形态。** 三件事：挑最容易被违反的三条规则，各配一个非零退出的命令；给这三个检查各做一次负例控制；本地只跑覆盖当前改动的这三个，远端跑全套。

**做法。**
1. 从常驻规则里挑 3 条最容易违反的，各写一个 `exit non-zero` 的命令，聚合成一个脚本。
2. 对每个检查做一次负例控制：**引入对应的违规 → 跑检查 → 看它红 → 还原 → 再跑一次确认它变绿**（只验红不验绿，按 02 的封顶规则约束力只能到 2）。
3. 把"新检查必须做负例控制"写进成文规则：没有它，检查不算数。
4. 端到端验证要**验证世界，而不是验证自述**：重新读文件、跑命令、看持久状态，不要相信执行者声称完成了。
5. 定期抽查：随机挑一个检查，问"它最近一次为红是什么回归"。

**验收红线。**
- 每个检查都能说出它最近一次为红的具体回归；
- 新增检查时留下了负例控制的记录；
- 存在"永远为绿"的检查的话，它们被明确标注或删除。

**一次负例控制。** 这一步本身就是这张卡的全部内容。挑一个检查，做一次，记录下来。

**成本。** 每个检查额外 10–30 分钟；之后每次新增检查都要付同样的钱。

**它不买什么。** 负例控制只能证明"这个检查会失败"，不能证明"它失败的原因是对的"，也不能证明"该发现的问题它都发现了"。它排除的是**假检查**，不是**漏检查**。

**学走形的样子。** 最贵的一种：**检查全绿但没人信**。绿灯数目成了 KPI，负例控制没人做过，检查逐渐变成仪式，然后开始被绕过。

### EV3 闭环完整性 · 处置卡

**什么时候才值得做。** 与 KN1/KN2 同批（前置维）——不要等"代码合并了、文档没跟上"出现才做；症状出现只是最晚期限。

**最小形态。** 一条规则 + 一个豁免条款：实现、当前文档、回归证据在同一次交付里一起走；机械性或局部改动明确豁免，且豁免要有理由。

**做法。**
1. 定交付物清单：源码、当前文档（README/现状文档）、回归证据（会为这次回归失败的检查）、以及**在存在持久取舍时**的决策记录。
2. **明确豁免**：机械性改动、局部呈现调整这类不需要决策记录；**改动小不是豁免理由，没有取舍才是**。
3. 要求交付说明与实际证据一一对应：**只报告实际跑过的检查**，未跑的报告为未跑。
4. 缺口如实标注，不用绿灯盖过去。
5. 出错时**整个切片原样退回**——代码、测试、文档、记录一起退，不打补丁式热修。

**验收红线。**
- 最近 5 笔变更里没有"先合并后补文档/补测试"的实例（与 02 的 EV3 封顶规则同一判据）；
- 交付说明里没有无法对应的验证声称；
- 存在被真实使用的轻量豁免路径；
- 回滚粒度是整个切片，不是零散修补。

**一次负例控制。** 拿最近一笔变更问："文档里声称的行为，有几条**没有**任何检查钉住？"说不出，就是缺口没被管理。

**成本。** 每笔变更多花 10–30%；对双语文档、生成目录都齐全的项目，小改动的仪式成本会明显上升——**这正是需要豁免路径的原因**。

**它不买什么。** 闭环保证交付物齐全，不保证交付物正确。正确性靠 EV1 的分层与 EV4 的语义评审。

**学走形的样子。** 闭环断在两处——"同批交付"退化成"先合并后补"，"缺口如实标注"退化成"绿灯崇拜"。

### EV4 评审与批准 · 处置卡

**什么时候才值得做。** 出现"评审只是点通过"或者"评审全在挑格式"。

**最小形态。** 一份写清的批准条件（谁、几个人、什么情况下可以放行），加上一条分工纪律：**评审不重复机器已经精确拒绝的问题**。

**做法。**
1. 写清批准条件，并让它**与改动风险挂钩**：改核心和改错别字不该走同一套。
2. 让门槛**在结构上不可能由作者一个人满足**：作者对自己的贡献计数有上限，凑不满放行线。这比"要求两人评审"这种靠自觉的写法硬。
3. 评审前先撤销既有的通过状态（**先置为待定，再做可能改变结论的动作**），避免"用旧绿灯给新代码放行"。
4. 让阻塞性意见的优先级高于分数——分数够了但有未解决的阻塞意见，仍然停。
5. 明确评审**该看什么、不该重复什么**：机器已经精确拒绝的格式问题不占评审注意力。
6. 每一层证据都公开声明"我不能证明什么"。**把"人类评审过"当作"语义正确"的证明，是最常见的越权使用。**

**验收红线。**
- 最近 10 笔的评审评论有实质内容，不是清一色"LGTM"；
- 批准条件与风险相关；
- 作者一个人无法凑满放行线；
- 评审没有在重复机器已经管住的格式问题。

**一次负例控制。** 数一数最近 10 笔变更的评审评论条数与内容。**比任何制度描述都准。**

**成本。** 每次评审 15–60 分钟；成本随改动风险上升是合理的，随改动大小无差别上升则不合理。

**它不买什么。** 加权批准不等于正确性；有评审不等于意图被理解。它降低的是"没被任何人看过就进主干"的概率。

**学走形的样子。** 橡皮图章（有流程无判断），或格式警察（人力消耗在机器已经管住的事上）。

### ST1 静与动 · 处置卡

**什么时候才值得做。** 出现同一份配置或数据两处可写；或删掉派生后重建不出同样的结果。发现"两处可写"的当天就该做。

*评的是仓库自己的配置、记录与生成物；产品的会话记录见 [RT2](#rt2-会话事实源--处置卡)，两者各自处置（见[原则六](#原则六同时评两份时名字相近的维度各评各的对象)）。*

**最小形态。** 一张四层表，每层写清：变化速度 / 承载者 / 谁能改 / **丢失代价**。

| 层 | 变化速度 | 谁能改 | 丢失代价 |
|---|---|---|---|
| 规则 | 跨版本稳定 | 只走评审，合并才生效 | 高——漂移即读者读错 |
| 配置 | 开发、CI、部署时定 | 显式变更操作 | 中——可从文档恢复 |
| 记录 | 只追加或冻结 | 追加新条目，不改不删已有的 | 极高——丢了就说不清当时为什么 |
| 派生 | 随源头重算 | 由源头生成，不手改 | 低——丢了能重建 |

**做法。**
1. 把仓库里所有"会变的东西"归类到四层。归类问一句：**"它丢了大不大？"** 丢了不心疼、能重算的，它是派生。
2. 消灭两处存真：任何配置或数据只有一个可写来源，其余从它派生或链接过去。
3. 让派生可重建：清空生成物与构建目录后，从源头重建出同样的结果；CI 的输入（工具版本、依赖锁）钉在仓库里。
4. 加一条检查钉住可重建性：重新生成后 diff 为空，否则红。
5. 给开发过程中产生的持久结论一条回写路径：一次任务或排障得出的结论 → 合并后写进决策记录、文档或检查；临时改的配置 → 落进配置源。

**验收红线。**
- 每个会变的东西说得出属于哪层、丢失代价多大；
- **删掉派生层，重建后结果一致**（删了就重建不出来的，它其实被当成了记录）；
- 同一份配置只有一个可写来源；
- 配置改错**有校验、有报错，不会静默带病运行**；
- 规则层只经评审合并才生效。

**一次负例控制。** 手改一个生成物，跑可重建性检查，看它红不红，然后还原。不红，说明这个生成物现在是第二份事实。

**成本。** 归类一次性 1–2 天；消灭两处存真往往要改本地、CI 与部署的配置加载方式，可能是一项真实工程。

**它不买什么。** 分层不减少状态总量，只让"谁是权威"不再需要争论。

**学走形的样子。**
- 把派生当记录存（生成物被手改，成了第二真相）；
- 绕过源头直接改派生（在 CI 里临时打补丁、手改锁文件）；
- 不回写——**下一次任务读不到上一次的结论，同一件事重新发明一遍**。

### ST2 披露与隔离 · 处置卡

**什么时候才值得做。** 常驻规则开始膨胀时；agent 频繁漏读或读错流程时；团队开始抱怨"规则文档越塞越多"时。**在那之前不要碰。**

*评的是仓库供给 coding agent 的上下文；产品每一步组装给模型的请求见 [RT7](#rt7-模型可见面组装--处置卡)，两者各自处置（见[原则六](#原则六同时评两份时名字相近的维度各评各的对象)）。*

**最小形态。** 按压力逐项加，每项独立见效：给常驻内容设上限 → 流程文档只给摘要、命中才读全文 → 子树规则放进子树 → 委派说明只带所需部分。

**做法。**
1. 给常驻内容（根入口 + 每次会话都会读到的规则）设一个字数上限，接进检查；超了要红，并指出超在哪个文件。
2. 同一段规则只写一份；多个宿主的入口文件名用符号链接指向同一份。
3. 流程文档/规则先给摘要（标题 + 适用条件），命中才读全文。摘要里明确写：**不要从摘要推断流程**。
4. 只对某个子树成立的规则，放进那个子树的入口，不堆在根入口。
5. 委派模板只要求转交任务需要的部分（目标、范围、验收），不要求转交全部背景。这是最便宜的一刀。

**验收红线。**
- 常驻内容有硬上限，且超限时检查会红；
- 同一段规则不会出现在两个常驻文件里；
- 有摘要层，不必读完就能判断该不该读；
- 子树专属规则不在根入口；
- 委派说明里是任务描述，不是全部历史。

**一次负例控制。** 往常驻文件里加一段内容使它超出上限，跑检查，看它红不红，然后还原。

**成本。** 按压力逐项加，每项独立见效：预算与去重是一次性整理，摘要层要逐份改流程文档的开头，分层要把规则挪进子树并更新链接。

**它不买什么。** 两个常见误读要收窄：**披露收窄的是读者的输入面，不是权限**——agent 读不到一条规则，不等于它不能做那件事；**写短、分层都不保证读者读对**——关键规则仍要下沉到检查。

**学走形的样子。** 只做一层（例如只把文档写短，或只加摘要）就当完成了。**披露是一条从常驻预算到按需加载、再到委派收窄的管线，只做一层都不完整。**

### ST3 运行时查询 · 处置卡

**什么时候才值得做。** 有人开始读源码猜"现在实际生效的是什么"；手工维护的接口清单已经维护不动；或存在多层配置叠加。**可以无限期停在第一档。**

*评的是开发工具链与本地环境；产品运行时的组合见 [RT1](#rt1-组合与启动--处置卡)，两者各自处置（见[原则六](#原则六同时评两份时名字相近的维度各评各的对象)）。*

**最小形态。** 一条命令，dump 出最终生效的配置。

**做法。**
1. **第一档（几乎零成本）**：给一条命令回答"这台机器/这个进程实际生效的是什么"——配置 dump、环境输出、等效的 `make show-config`。
2. **第二档（清单大到手工维护不动时）**：生成接口/注册项清单，并配一个 freshness 检查——源码变了清单没跟上就红。让完整性有守卫：新增的东西不可能静默无文档。
3. **第三档（多层组合、动态装卸的真出现了才做）**：只读的活运行时查询。
4. 在文档里**说清三者的区别**：配置会加载什么 / 源码声明了什么 / 当前进程实际有什么。**混为一谈会让查询结果被误用。**

**验收红线。**
- 能用命令回答"实际生效的是什么"，不靠读源码；
- 生成清单有 freshness 检查；
- 三者的边界在文档里写明。

**一次负例控制。** 改一处配置但不改生成清单，跑检查，看它红不红。不红的话，这个清单会漂。

**成本。** 第一档 1–2 小时；第二档视接口规模；第三档通常不必做。

**它不买什么。** **可查询不等于可修改，也不等于有授权。** 给了一个查询工具，不等于给了一个沙箱——外部副作用仍然不可回滚，除非另有机制。

**学走形的样子。** 把"源码就是文档"当成理由跳过这一维；或者反过来，接口清单手工维护还当作权威。

### MT1 防漂移 · 处置卡

**什么时候才值得做。** 在你**第一次**外置知识的同时。它是元维度——不管具体知识，管前面所有维度能不能长期不失效。

**最小形态。** 一个结构检查脚本 + 一段"基线与复核方式"说明。

**做法。**
1. 给规则/知识目录配一个轻量检查脚本：编码、结尾换行、相对链接、锚点。每次编辑后跑一次。
2. 给检查本身做负例控制：故意改坏一个链接，看它红，然后还原。
3. **钉基线**：文档写明"结论以某个版本为准"。上游更新后只复核被引用的文件是否变化，不全文重写。
4. 改事实只改它的 home，并修所有指向它的引用——漏一处就漂一处。
5. 数字类事实（预算、上限、个数）标注"以某个文件为准"——**数字是最容易漂的**。
6. 不许出现"以当前版本为准"这类会让基线悄悄滑走的表述。
7. 给归档内容定冻结纪律：封存后不再编辑，也不再作为当前权威引用。

**验收红线。**
- 检查脚本对当前树全绿；
- 故意引入一个坏链接 → 脚本变红 → 还原；
- 文档里没有相对化的基线表述；
- 每个手工维护的清单都有 freshness 检查，或者已改成生成。

**一次负例控制。** 见第 2 条——**这条卡的全部价值就在于它被执行过一次**。

**成本。** 脚本一次性半天；之后每次编辑多跑一条命令。

**它不买什么。** 检查只能发现**结构**问题。内容是否还准确、数字是否还对，需要"上游变了就复核被引用文件"这条纪律，不能靠脚本。

**学走形的样子。** 检查脚本写了一次再也没跑过；或者规则改了，引用没跟着改——**漏一处就漂一处**。

---

### MT2 发布与版本纪律 · 处置卡

**什么时候才值得做。** 开始对外发布产物，且出过一次"发错了"或"忘了 bump 版本"的事故。不发布任何东西的仓库不做。

**最小形态。** 一段成文发布序列 + 一份兼容承诺（哪些接口稳定、哪些明确不稳定）+ 一条不可逆产物的处理规则。

**做法。**
1. 写成文发布序列：谁在什么条件下做什么。**版本号由人写进仓库、由人打标签**——标签指向一个被评审过的树，不是一个流水线的产物。
2. 写清兼容承诺：哪些接口承诺稳定、哪些明确不稳定。**版本号规则不说明这件事，必须单独写。**
3. 不可逆的产物（数据格式、已发布记录）**只能新增后继代，不得就地覆盖或移动已提交的世代**。
4. 把"忘了 bump 版本"变成一个**硬失败**：发布时比对已发布内容，内容变了但版本没动 → 直接失败。
5. 让重试幂等：同样的内容重复发布应当跳过而不是报错，内容不同才失败。
6. **彩排与发布分开**：彩排持续跑、无需凭据；发布是显式触发的、需要授权的、**不能出现在常规检查里**。
7. **留回退路径**：坏版本怎么退、退回去读不读得懂已发布的数据，各写一条；回退不得破坏已发布世代。

**验收红线。**
- 每条规则至少满足以下之一：防止发布未经评审的内容 / 让重试安全 / 让漏 bump 硬失败 / 让使用者能确定地定位到一个渠道；
- 破坏性变更被版本号或迁移说明标出；
- 已发布的数据/格式不会被就地覆盖；
- 稳定与不稳定的边界写明；
- 坏版本有可执行的回退路径，且回退不破坏已发布的数据。

**一次负例控制。** 制造一次"内容改了但版本没动"，看发布流程会不会失败。不失败，这条规则就是装饰。

**成本。** 首次搭 1–3 天；之后每次发布多几步。

**它不买什么。** 发布纪律不保证版本内容正确。它保证的是"发出去的是被评审过的那棵树"和"发错了能退"。

**学走形的样子。** 把仪式当纪律——标签间距、RC 之间的提交数、发布 PR 的文件数，这些都不防止任何具体事故。**判据是"它防止了哪一种具体事故"，不是"它看起来多严格"。**

## 4 · 运行时维度：症状与处置卡

> 这一节服务 [运行时 Harness 粗粒度](./11-evaluate-runtime-harness.md) 的缺口。**先做适用性判定**——AQ1 答"否"时本节不适用；AQ2、AQ3 的答案只决定形态与裁剪（见 11 §0）。维度定义在 11、探针与封顶在 [12](./12-evaluate-runtime-harness-fine.md)，本节只做处置。适用性问题（AQ1–AQ3）与五个活体实验（LX1–LX5）也在那份文档里定义。

### 4.1 运行时维度的排序原则

**前置三维（不做它，其余做了也无法验证）：**

| 前置 | 为什么是前置 |
|---|---|
| **RT2 会话事实源** | 它是"系统报告什么"与"实际发生什么"之间的唯一桥梁。没有它，你无法诊断任何其它维度的问题 |
| **RT7 模型可见面组装** | 它是 RT2 在请求侧的另一半。模型看到什么不进记录，RT2 就只能重建一半 |
| **RT9 工具执行与授权** | 它决定系统报告的"结果"能不能被相信。异常被吞成空结果时，后面所有判断都建立在错的前提上 |

**有压力再借：**

| 维度 | 触发条件 |
|---|---|
| RT3 格式世代与兼容 | 持久数据要跨版本长期存活（用户不会每次升级都丢历史）|
| RT4 循环与终结边界 | 出现"它到底是做完了还是卡住了"的争论；或取消后动作仍在后台继续 |
| RT5 能力 seam | 第二个真实实现出现（不是"我们知道将来可能会有"）|
| RT6 扩展点 | 有第二个人要往上面加东西 |
| RT10 可执行治理 | 出现写在文档里、可以机械判断却没人遵守的规则 |
| RT8 入口与协议投影 | 第二个入口出现 |
| RT11 客户端组装纪律 | 有 GUI 客户端 |
| RT1 组合与启动 | 配置开始由多个人改；或出现过"以为开着实际没装"|

**最便宜的三刀（几乎零成本，收益立刻）：**

1. **坏配置大声失败**（RT1）：把"引用了不存在的组件"从警告改成错误。
2. **结果单一出口**（RT9）：把所有"异常吞成空值"的地方改成明确的错误结果。
3. **终结原因封闭化**（RT4）：把自由字符串换成封闭集合，并加上"被取消"与"已完成"的区分。

### 4.2 症状 → 维度

| 你看到的症状 | 维度 | 先去哪张卡 |
|---|---|---|
| 以为某个能力开着，实际因为配置写错没装上 | RT1 组合与启动 | [RT1](#rt1-组合与启动--处置卡) |
| 模型行为异常，但事后说不清它当时看到了什么 | RT2 会话事实源 | [RT2](#rt2-会话事实源--处置卡) |
| 升级后读不了旧数据；报错一律说"文件损坏" | RT3 格式世代与兼容 | [RT3](#rt3-格式世代与兼容--处置卡) |
| 分不清"它做完了"和"它暂时没动作了"；取消之后动作还在跑 | RT4 循环与终结边界 | [RT4](#rt4-循环与终结边界--处置卡) |
| 换一个模型/沙箱/存储要改一片代码 | RT5 能力 seam | [RT5](#rt5-能力-seam--处置卡) |
| 加一个新能力要动核心；说不清拦截点拦不住什么 | RT6 扩展点与拦截 | [RT6](#rt6-扩展点与拦截--处置卡) |

### 4.3 十一张处置卡

每张卡六栏：**什么时候才值得做 / 最小形态 / 做法 / 验收红线 / 一次负例控制 / 它不买什么**（RT11 另有一行适用性声明）。比开发卡少"成本"与"学走形的样子"两栏：运行时机制的成本随形态差别太大，排期按 4.1 的触发条件判断；走形的样子写在 12 各卡的"走形症状"行。探针、两轴锚点与封顶规则在 [运行时 Harness 细粒度](./12-evaluate-runtime-harness-fine.md)。

#### RT1 组合与启动 · 处置卡

**什么时候才值得做。** 配置开始由多个人改，或者出现过"以为开着实际没装"。

*开发侧的 [ST3 运行时查询](#st3-运行时查询--处置卡) 评的是开发工具链，与本卡各自处置（见[原则六](#原则六同时评两份时名字相近的维度各评各的对象)）。*

**最小形态。** 一条"dump 出最终生效配置"的命令，且它和真正启动用的是**同一套叠加算法**；加上"引用不存在的组件必须失败"。

**做法。**
1. 找出现有的叠加层与固定顺序，把"同 id 是覆盖整份还是深合并"写成成文规则。
2. 让 dump 命令与启动路径共用同一套叠加算法——两套代码的 dump 会撒谎。
3. 引用不存在的组件必须启动失败并指出缺什么；"文件在场但读不了"按失败处理，不当成"没有这个文件"。
4. 给叠加规则与坏配置各加一个会为回归而失败的测试。

**验收红线。**
- 能用一条命令答出"这台机器实际生效的是什么"；
- dump 的输出与真实启动一致（同一份代码算出来的），且这一点**有测试钉住**；
- 引用了不存在的组件 → 启动失败并指出缺什么；
- "文件在场但读不了" → 失败，而不是当作"没有这个文件"。

**一次负例控制。** 把一个组件的键名改错，启动。**必须失败。** 如果只是少了一个能力，这一维没做完。

**它不买什么。** 配置算得出来，不代表配置容易理解。叠加层数越多，理解成本越高——够用就停。

---

#### RT2 会话事实源 · 处置卡

**什么时候才值得做。** 任何时候。运行时前置三维之一，与 RT7、RT9 同批最先做。

*开发侧的 [ST1 静与动](#st1-静与动--处置卡) 评的是仓库自己的配置与记录，与本卡各自处置（见[原则六](#原则六同时评两份时名字相近的维度各评各的对象)）。*

**最小形态。** 一条只追加的记录，把**进入模型请求的一切**都记进去——消息、system prompt、可见工具清单、动态上下文。

**做法。**
1. 确认记录是**只追加**的：不修改、不删除已写下的条目。
2. 把"模型这一步实际看到的请求"变成可从记录重建的对象——不只是对话消息，还有提示词与工具清单。
3. 让界面/统计/检索从记录**派生**，不各自另存一份。
4. 上下文超预算时，压缩只在**投影层遮蔽**，不从记录里删除。
5. 加一条不变量：新的模型可见输入必须留下记录，违反时失败。

**验收红线。**
- 做 LX1 回放：能重建第 N 步的完整请求；
- 删掉所有派生层，功能照常（只是慢）；
- 压缩后仍能回放完整历史；
- 读到未知事件时**拒绝重建**，而不是跳过；
- 记录重建的**断言会在违反时失败**，并指出是哪一步。

**一次负例控制。** 加一个动态注入的上下文片段，不改记录逻辑。跑 LX1 回放——**重建不出来就说明有走私路径**。

**它不买什么。** 记录完备不减少记录体积。**每多一个模型可见输入，就多一笔账**——这是显式成本，不是免费的可观测性。

#### RT3 格式世代与兼容 · 处置卡

**什么时候才值得做。** 持久数据要跨版本长期存活时。一次性脚本不做。

**最小形态。** 一个版本号（**唯一权威**），加三条明确路径：能读 → 正常读；版本更旧 → 迁移；版本更新 → **拒绝并提示升级**。

**做法。**
1. 定一个唯一权威的版本常量。包的版本号、文件名、发布记录都不是权威。
2. 明确触发条件：只有**结构变化**才升版本；加一个新的事件类型不算（那是"未知事件"要处理的事）。
3. 区分三类错误，提示不同：**版本过新**（升级即可，什么都没坏）、**物理损坏**（内容真的读不了）、**没有可用迁移**。
4. 迁移**只写新世代，不改写、不移动、不删除**已有的。
5. 未知事件：同版本内按标记决定跳过还是拒绝；**跨版本边一律拒绝**。
6. 迁移链单独成规格（不在读路径里即席判断），每条迁移边有前置校验——这是覆盖面 3 的要求。

**验收红线。**
- 用更新版本写的数据喂给当前版本 → 被拒绝，提示"版本过新，请升级"，**不是"数据损坏"**；
- 迁移后原始世代原样还在；
- 版本号只有一个来源。

**一次负例控制。** 手工把一份数据的版本号改成一个更新的值，读它。看提示是"升级"还是"损坏"。

**它不买什么。** 版本纪律不保证迁移的正确性——它保证的是**迁移不会悄悄改写历史**，以及**读不懂时说出来**。

---

#### RT4 循环与终结边界 · 处置卡

**什么时候才值得做。** 出现"它到底是做完了还是卡住了"的争论时。

**最小形态。** 分层的终结概念 + **封闭的终结原因集合** + "被取消"与"已完成"的明确区分。

**做法。**
1. 定义分层：一次请求、一个输入被处理完、一段连续活动、一个长期目标——各自怎么判定结束。
2. 把终结原因做成封闭集合，不允许自由字符串。
3. 取消必须真的让动作停，并留下记录。
4. 进程重启后，正在进行的活动**不自动继续危险动作**；需要人工确认的，明确要求确认。
5. "空闲"与"完成"必须是两个不同的状态。
6. 给恢复路径写一条测试：重启后不自动重放危险动作——这是约束力 3 的判据。

**验收红线。**
- 终结原因是封闭集合；
- 做 LX5：取消后动作在声明的超时预算内真的停（预算可指认，不是"合理时间"；没有声明预算时，按"取消后动作是否仍在后台继续"判定）；
- 重启后行为可预测，不自动重放危险动作，且恢复路径**有测试钉住**；
- 拒绝一个输入时，也留下"这次尝试"的痕迹。

**一次负例控制。** 取消一个正在跑的长动作，看它在**该系统自己声明的超时预算内**是否真的停止（不是"合理时间"），并检查记录里有没有这次取消。

**它不买什么。** 边界清楚不保证任务完成。它保证的是**"没完成"能被看见**，而不是伪装成完成或伪装成错误。

---

#### RT5 能力 seam · 处置卡

**什么时候才值得做。** **第二个真实实现出现时。** 在那之前，一个私有函数就够了。

**最小形态。** 一项能力的三件套：定义（能力接口）+ 实现 + 使用方；使用方只依赖定义。

**做法。**
1. 挑**真的会换**的那一项能力开始，不要一次全建。
2. 写定义时**对着所有当前使用方**——不要为某一个使用方的方便把它的专有名词写进定义。
3. 使用方改成只依赖定义。
4. 让第二个实现真的跑通，使用方一行不改。
5. 明确列出**故意不做成可替换点**的地方及理由（这比多做几个 seam 更有价值）。

**验收红线。**
- 做 LX2：换实现时消费者代码零改动；
- 至少一项能力有两个**真实**实现（不是测试替身）；
- 定义里没有某个使用方的专有名词；
- 有一份"故意不可替换"的清单；
- **有测试证明**"换实现后真实组合仍通过"。

**一次负例控制。** 数一数某个"可替换点"有几个使用方、几个实现。**1 个使用方 + 1 个实现 = 它还是私有函数。**

**它不买什么。** seam 不减少代码量。它把"换实现"的成本从"改一片"降到"改一处"，代价是多一层间接。

---

#### RT6 扩展点与拦截 · 处置卡

**什么时候才值得做。** 有第二个人要往上面加东西时；或者出现"为了加功能改了核心"的实例时。

**最小形态。** 一张"新行为 → 挂哪里"的表，右列是**可以直接执行的动作**；拦截点按权限分类，并写明各自拦不住什么。

**做法。**
1. 列出现有的扩展点，每个写清"能做什么、不能做什么"。
2. 把拦截点分成三类并明确区分：**只观察** / **可改写** / **可短路**。混在一起会让扩展作者误用。
3. 每个拦截点写明**拦不住什么**——这比"能做什么"更重要。
4. 统一注册的生命周期：谁注册谁负责撤销，走同一条清理路径。
5. 定升级条件：什么时候必须从扩展点升级到核心改动。
6. 让**绕过扩展点的结构检查**（或"只允许通过注册 API 接入"）成为唯一入口——这是约束力 3 的判据。

**验收红线。**
- 做 LX3：加一个常见能力不改核心；
- 归属表右列是可执行动作，不是"参考某文档"；
- 每个拦截点有"拦不住什么"的说明；
- 策略改动只动一个文件。

**一次负例控制。** 拿一次"绕过扩展点"的历史改动，看现在的规则或检查拦不拦得住。

**它不买什么。** 扩展点让新能力加得快，不保证加得对。语义正确性仍需评审。

---

#### RT7 模型可见面组装 · 处置卡

**什么时候才值得做。** 任何时候，与 RT2 同批。它与 RT2 是同一件事的两半。

*开发侧的 [ST2 披露与隔离](#st2-披露与隔离--处置卡) 评的是仓库供给 coding agent 的上下文，与本卡各自处置（见[原则六](#原则六同时评两份时名字相近的维度各评各的对象)）。*

**最小形态。** 每一步**显式组装**模型看到的东西（工具清单、提示词、内容块），并把组装结果写进记录。

**做法。**
1. 可见工具清单每步显式算出来，不依赖加载顺序。
2. 排序稳定：越稳定的内容越靠前；每台机器/每个用户不同的内容放最后。
3. 组装结果写进记录（这是 RT2 的一部分，但归属在这一维）。
4. 把"看得见"和"被允许"分成两套判定——**可见性影响的是选择空间，不是授权**。
5. 非文本内容（文件、图片）的进出规则写清楚，并保证进来的东西和不进来的东西规则对称。

**验收红线。**
- 做 LX1：能重建第 N 步的可见工具清单与提示词；
- 同一个部署两次启动得到相同的请求前缀；
- 可见集合与授权判定是两套独立机制；
- 子任务能看到的是子集，且这个收窄留下了记录；
- **有断言**证明"进入模型请求的内容都进了记录"，且违反时指出是哪一步。

**一次负例控制。** 加一个动态注入的上下文片段，跑 LX1。重建不出来，说明这条路径没走记录。

**它不买什么。** 组装可控不代表提示词有效——那是提示词工程的事，与机制无关。

---

#### RT8 入口与协议投影 · 处置卡

**什么时候才值得做。** 第二个入口出现时。**只有一个入口时不要提前抽象。**

**最小形态。** 所有入口通过同一套运行时接口驱动；每个协议入口有一份"故意不保证"清单。

**做法。**
1. 让新入口复用现有运行时语义，**不自己实现循环**。
2. 明确每个入口的输出通道归属：哪个 stdout 是给人看的，哪个是协议帧。**结论决定能不能装日志。**
3. 协议入口的就绪信号**晚于**所有异步初始化完成。
4. 每个协议面写一份"故意不保证什么"的清单。
5. 事件订阅不过滤"是不是我创建的"（除非有明确理由）。

**验收红线。**
- 新入口加进来时不改运行时；
- 协议帧不被日志污染；
- 每个协议面有能力清单与否决清单，且"故意不保证"清单**被测试钉住**（不只是写在文档里）；
- 就绪信号之后，依赖的异步初始化都已完成。

**一次负例控制。** 往协议入口的 stdout 打一行日志，看协议还正常吗。

**它不买什么。** 入口统一不减少协议本身的复杂度。**不保证什么的清单**比保证什么的清单更有用。

---

#### RT9 工具执行与授权 · 处置卡

**什么时候才值得做。** 任何时候。危险动作进入系统之前就该有。

*开发侧的 [CP4 执行与授权链](#cp4-执行与授权链--处置卡) 评的是仓库自己的自动化，与本卡各自处置（见[原则六](#原则六同时评两份时名字相近的维度各评各的对象)）。*

**最小形态。** 三件事：动作**先记录再执行**；统一的执行前判定；结果**单一出口**（异常归一化成明确错误）。

**做法。**
1. 动作发起时先写记录，失败的调用也在场。
2. 参数在进入判定环节**之前**就冻结；判定环节不得改写参数。
3. 判定走统一出口，不在每个工具内部各写一份。
4. **判不了时拒绝**（fail-closed）：没有审批者 → 拒绝；审计写不进去 → **拒签**，而不是返回一笔没记录的决策。
5. 结果经同一处归一化：超时、取消、内部异常，都变成**一个明确的形态**交给模型。**不要让"部分成功""未知状态"流下去。**
6. 明确两条边界：**可见性不是授权**；**取消不撤销已经发生的外部效果**。

**验收红线。**
- 做 LX5：取消真的停；失败是明确错误而不是空结果；两者都留下记录；
- 加一条权限规则只改一个文件；
- 没有审批者时默认拒绝；
- 审计写入失败时拒绝签发决策。

**一次负例控制。** 让一个工具内部抛异常，看模型收到的是什么。**收到"空结果"或"部分成功"就不及格。**

**它不买什么。** 管线统一不保证动作是对的，只保证**它被一致地记录、判定和报告**。

---

#### RT10 可执行治理 · 处置卡

**什么时候才值得做。** 第一条"写在文档里但没人遵守"的规则出现时。

**最小形态。** 一个检查的**统一注册处**；加一条规则 = 加一个会失败的检查，而不是加一段文档。

**做法。**
1. 把所有机械可判断的规则接成检查，注册到一个聚合点。
2. **不变量只在"两个独立观察可能分歧"时才写。** 检查"某个东西存在"不是不变量。
3. 给检查做负例控制：引入一个该被抓住的回归 → 看它红 → 还原。
4. 区分**结构检查**（读代码形状）与**策略检查**（读一个部署可变的决定）——两者维护方式不同。
5. 如果有成熟度数字（可替换率、覆盖率），让它**可复算**，并把复算的坑列出来。

**验收红线。**
- 随便挑一个检查，说得出它最近一次为红是什么回归；
- 加规则的正确形状是"加一个检查"；
- 不变量检查的是关系，不是存在性；
- 若有成熟度数字，它能自动重算（没有成熟度数字时这条不适用）。

**一次负例控制。** 引入一个该被抓住的回归，跑检查，看红，还原。**没红过的检查不算检查。**

**它不买什么。** 检查只能证明它碰巧碰到的地方。**"全绿"与"没问题"是两件事。**

---

#### RT11 客户端组装纪律 · 处置卡

**仅当有 GUI 客户端时。没有 GUI 标 N/A。**

**什么时候才值得做。** 界面上出现"同一个数字两处不一样"时；或者改一个数据要在界面里同步好几处时。

**最小形态。** 一条规则：界面状态从权威事实**派生**，不另存一份业务数据。

**做法。**
1. 找到界面上自己攒业务状态的地方，改成从权威事实派生。
2. 统一订阅机制，组件里不写各自的订阅逻辑。
3. 模块之间不互相引用具体实现，只共享声明的接口。
4. 界面产生的新模型可见输入，同样要留下记录。
5. 遇到不认识的数据形态时**回落到通用形态**，不崩。

**验收红线。**
- 界面上的数字能追到权威来源；
- 删掉界面层的缓存，功能照常（只是慢）；
- 模块越界引用会被检查发现；
- 绕过界面层直接攒业务状态会被检查拦住。

**一次负例控制。** 在后台直接改一次权威数据，看界面会不会自动跟上。跟不上、或者要靠手动刷新，说明界面自持了一份。

**它不买什么。** 界面纪律不改善用户体验，只保证**界面说的是同一个事实**。

## 5 · 形态重解释：同一维在不同仓库里长什么样

## 6 · 边界与反模式

### 四条不能混淆的边界

照搬成熟样板最容易翻车的地方，是把"相似"当成"等同"。四条边界：

**1. 可读 ≠ 简单。**
归属、清单、统一术语让复杂系统**可查询**，但包、事件和生命周期仍然复杂。把知识组织好，不会让系统本身变小。

**2. 流程文档 ≠ 强制执行。**
流程文档是指导；可机械判断的规则仍需类型、脚本、不变量；语义问题仍需评审。**用流程文档替代检查，等于把一条会失败的规则降级成一条会被人略过的建议。**

**3. 清理 ≠ 事务回滚。**
撤销注册、释放资源这类清理动作，撤销的是它自己拥有的东西，**不会自动补偿已经发生的外部写入**。"卸载了就干净了"只在你拥有的范围内成立。

**4. 可查询 ≠ 安全沙箱。**
查询工具能看见运行状态，不代表它有修改权限，更不代表被它观察的东西受保护。**授权边界与可见性是两件事，必须分别设计。**

### 外置知识的维护成本

外置知识不是免费的。每引入一样，问一句"**谁维护它、漂了谁发现**"。

| 成本风险 | 对策 |
|---|---|
| 索引/清单过期 | 生成 + freshness 检查：与源码有 diff 就红 |
| 常驻层膨胀 | 给常驻文件设字数/字节上限；超限时先把内容挪到它该在的 home，再精简措辞，两者都不够才提高上限 |
| 过时的理由冒充现行 | 决策记录带状态与冻结归档；归档后不再是当前权威 |
| 假门禁 | 新检查必须做负例控制（见 EV2） |
| 多语言/多版本漂移 | 配对与哈希校验，改一侧必须重录另一侧 |
| 记录通胀 | 只记有真实取舍的；"防错而不是数量"是唯一判据 |

### 最常见的过度投入

**在还不存在相应压力时，提前造一整套分层架构。**

具体表现：只有一个主流程、少量固定依赖、单一入口的项目，却先建了完整的插件系统、生成目录体系、不变量检查框架。维护成本吃掉了可读性收益，而且**没人用得上**。

判据：**这一维的触发条件出现了吗？**（见[原则三](#原则三有压力再借)）没出现就记进待办，不建。

> 一个成熟样板之所以长成那样，是因为它承受过对应的压力。**照搬它的形状，而不照搬它承受过的压力，是这类工作最常见的失败。**

### 三个"不要照搬"

- **分层架构与完整扩展点体系**：那是组合压力的产物。没有多个可替换实现由稳定接口消费的需求，就不要建。
- **重型协作制度**（复杂的批准公式、多级标签体系、双语三件套）：它们有特定的协作规模和合规前提。
- **生成目录 + 不变量检查的全套基础设施**：先有纪律，量大了再上机器。

## 7 · 一轮打磨的循环与停止条件

### 循环

1. 拿评估的缺口清单，按第 1 节的原则排出这一轮的 1–3 维（两份评分卡各自排，见原则六）。
2. 翻对应的处置卡：开发维在 §3，运行时维在 §4.3。
3. 逐条过"验收红线"。
4. 做一次该卡的"负例控制"。
5. 回 [开发 Harness 粗粒度](./01-evaluate-development-harness-coarse.md) 或 [运行时 Harness 粗粒度](./11-evaluate-runtime-harness.md) 复测这几维（施工过的维度按 02 / 12 定档）。
6. 看切片走查记录与 [01 §6 的表 4](./01-evaluate-development-harness-coarse.md#6--四张产出表空白模板)（三张清单）里"靠猜"和"没证据"的条目比上一轮少了吗（运行时侧看另一条线：实验记录里"靠我手动兜住"的分界有没有变短）。
7. 少 → 进下一轮；没少 → 这一轮做的方式有问题，回去看"学走形的样子"。

### 每轮复测看三件事

1. 哪几维从低档升上去了？
2. 垂直切片复测里，"靠猜"和"没证据"的条数变少了吗？
3. 有没有新引入的维护负担（新脚本、新清单、新流程），它们有 owner 吗？

运行时侧把第 2 条换成：五个活体实验复跑一遍，对应被评维度的那几个还通过吗。

### 停止条件

**收工线** = 达标线 + 下面的附加条件。达标线（01 §4 与 11 §3）回答"这套机制能不能用"，收工线回答"这一轮打磨能不能停"：

- **开发 Harness**：先满足达标线（至少 MG2，且你最痛的三维达到 **约束力 3**；某维的卡片若刻意停在较低档，卡里必须写明上限与理由）。另加：裁剪后的每一维至少 **覆盖面 2**（有且成体系）；切片复测里没有"完全找不到 owner"和"声称的行为零证据"这类硬伤。
- **运行时 Harness**：先满足达标线（至少 **MG2**：事实源、模型可见面、工具执行与授权三维约束力 ≥ 2）。另加：五个活体实验都跑过，被评维度对应的实验通过（MG2 的三维对应 LX1 与 LX5），被裁掉的维度对应的实验按 N/A 记录。**单机实验档例外**：RT9 属 N/A，这一档不追求 MG2，收工线留到决定继续做之后再算（见 11 第 4 节）。

**最终标志很朴素：**

> **新来一个 agent（或人），不靠任何人带路，能把一笔普通变更从意图走到归位，并且每一步说得出证据在哪。**

达到这个标志就可以停。**继续加机制不是进步**——每多一条规则、一个检查、一份清单，未来的每一笔变更都要多付一点合规成本。成熟样板的纪律里最反直觉的一条是：**机制本身也是要维护的代码。**

## 8 · 短例

> 承接 [开发 Harness 粗粒度](./01-evaluate-development-harness-coarse.md) 第 8 节的构造示例。**这是演示，不是对任何真实仓库的评估。**

### 输入：缺口清单

那家三年、6 万行、15 人的后端服务，快诊给出五个缺口，外加 EV2 抽检与切片共同发现的一个（EV2）：

| # | 维 | 症状 | 严重度 |
|---|---|---|---|
| 1 | ST1 静与动 | OpenAPI 规范与生成的客户端两处可写；生成命令无记录 | 高 |
| 2 | KN2 归属 | 超时配置在代码与 README 各一份 | 高 |
| 3 | EV3 闭环完整性 | 12 篇文档里 7 篇接口描述已过期 | 高 |
| 4 | CP2 正确路径 | 没有"目标→机制"表；新接口绕过 task queue | 中 |
| 5 | KN1 入口链 | 400 行 README 无路由；无 agent 入口 | 中 |
| 6 | EV2 负例控制 | 抽检的检查说不出最近一次为红；切片发现 `TestOrderTimeoutConfig` 实际没钉住配置读取路径 | 中 |

### 第一步 · 排序

**过一遍原则一（痛点优先）**：六条里，"已经在踩"的是 #2（上周已经发生过一次）和 #1（规范与客户端不一致时无人知道哪边对，下次重新生成就会抹掉手改）。#3 是"迟早会踩"。#4、#5 是"经常踩但不致命"。

**过一遍原则二（前置维）**：清单里没有 KN1/KN2 的前置问题吗？——有的，#5 和 #2 都属于知识归位组。**KN1/KN2 是前置（知识归位组的后两维不是）**：如果读者找不到文档，把文档内容改对也没用。

**过一遍原则三（有压力再借）**：ST1 的触发条件（同一份东西两处可写；删掉派生后重建不出）已经出现（见 [ST1 卡](#st1-静与动--处置卡)）。CP2 的触发条件（有人绕过入口）也已经出现。没有触发条件的是：#3 里"文档过期"本身不算独立压力，它是 KN2 的后果。

**重新排：**

| 轮次 | 维度 | 理由 |
|---|---|---|
| 第 1 轮 | **KN1 入口链 + KN2 归属** | 前置维，成本最低（半天），且 #2、#3、#5 三个缺口都是它们的下游 |
| 第 2 轮 | **EV2 负例控制** | 前置维，且切片已经发现一个假测试（`TestOrderTimeoutConfig`）；不解决它，后面所有"验证"都不可信 |
| 第 3 轮 | **ST1 静与动** | 已触发的真实风险；要先把 `gen/client/` 里的三处手改挪回规范或生成器模板，再加"重新生成后 diff 为空"的检查，依赖第 2 轮的负例控制纪律 |
| 第 3 轮 | **EV3 闭环完整性**（与 ST1 同轮） | 前置维，但必须接在 KN2 之后——否则没有可挂靠的"文档与代码同步"规则；不要无限期待办 |
| 待办 | CP2 正确路径 | 触发条件已出现，排在第 4 轮 |

**注意第 2 轮为什么提前了。** 按严重度它不比 ST1 高，但它是**前置维**——团队现在的验证手段不可信（切片证明了），而后面每一轮的改动都要靠验证来判断有没有做对。**先修尺子，再量东西。**

### 第二步 · 第 1 轮怎么做（KN1 + KN2）

按 [KN1 处置卡](#kn1-入口链--处置卡) 与 [KN2 处置卡](#kn2-归属--处置卡)：

1. 把 400 行 README 拆开：常驻规则（缩到 30 行内）、布局（顶层目录各一句）、命令表（装/跑/测/构建）留下；架构说明、编码规范、部署步骤各自成文，从根文件链接出去。
2. 建"事实 → home"表，第一版只覆盖最容易漂的五类：配置项、公开接口、部署步骤、错误码、环境变量。
3. 按表把 `README.md` 里的"关键参数"一节删掉，改成指向 `config/` 的链接。
4. 给根文件定 300 行上限，再加一个根入口链接检查；两者都写成 Makefile 的检查目标，接进 CI。
5. 多个入口文件名（如果团队同时用不同的 agent 宿主）用符号链接统一。

**验收红线自查**：任意一条规则 10 秒内指得出唯一 home？——5 类里 5 类可以。删掉链接以外的复制正文，信息不丢？——"关键参数"那节删掉后，参数含义在 `config/` 里有注释，成立。

**负例控制**：把根文件里一个链接改错，跑链接检查，看它红，还原。

### 第三步 · 第 2 轮怎么做（EV2）

按 [EV2 处置卡](#ev2-负例控制--处置卡)：

1. 挑三条最容易被违反的规则，各配一个 `exit non-zero` 命令：
   - 超时配置必须只从 `config/` 读取（切片发现的反例）；
   - 新接口不得绕过 task queue（CP2 的反例）；
   - 根入口文件不超过 300 行。
2. 逐个做负例控制：引入对应违规 → 看红 → 还原。**过期的 `TestOrderTimeoutConfig` 这一轮被重写成真的会红的版本**。
3. 把"新检查必须做负例控制"写进贡献指南，并在下一轮评审里抽查一次。

**验收红线自查**：三个检查都能说出最近一次为红的原因吗？——能，因为刚刚亲手制造过。

### 第四步 · 复测

回到评估，重跑 KN1、KN2、EV2 三维 + 一次切片：

| 维 | 改造前 | 改造后 |
|---|---|---|
| KN1 入口链 | 覆盖面 1 / 约束力 1 | 覆盖面 2 / 约束力 2 |
| KN2 归属 | 覆盖面 1 / 约束力 1 | 覆盖面 2 / 约束力 1 |
| EV2 负例控制 | 覆盖面 1 / 约束力 0 | 覆盖面 2 / 约束力 1 |

**缺口清单变化**：六条减到四条（#2、#5 消除；#6 缩小为"老检查未经负例控制核查"；#3 部分缓解，因为接口文档现在有了 freshness 之外的归属路径；#1、#4 未动）。改造前一列是定档：KN1、KN2 的粗判档复核后不变，EV2 用 [02 §5](./02-evaluate-development-harness-fine.md#5--细粒度示例把-ev2-从粗判档钉成定档) 的结果。

**为什么 KN1 的约束力只到 2**：链接检查做过负例控制，但 300 行上限门禁还没被证明会失败——[02 的 KN1 卡](./02-evaluate-development-harness-fine.md#kn1-入口链--entry-chain)的约束力 3 要求字数上限门禁，且按 02 §2 的通用条件它得先被证明会失败。

**为什么 EV2 的约束力停在 1**：新检查都做过负例控制，贡献指南也写了要求并抽查过一次（锚点给 2）；但 `TestLegacyExport` 这类两年没红过的老检查还没人核查，命中"存在长期未失败过的检查且无人核查"，封顶压在 1。下一轮把老检查逐个过一遍。

**为什么 KN2 的约束力还停在 1**：归属表立起来了，但"两份拷贝不一致"目前靠人记得改，还没有检查兜住。这一条留到下一轮——**它正好和 EV3 闭环完整性是同一件事的两面**。

### 这个短例想说明的

- **严重度不是唯一的排序依据**；前置维（KN1、KN2、EV1、EV2、EV3）要提前。
- **修尺子先于量东西**：验证手段不可信时，先修验证。
- **一轮不要贪多**：第 1 轮只动了 KN1 + KN2，因为 KN2 的约束力升级依赖于"有没有检查"，而那属于第 2 轮。
- **收敛的标志是缺口清单变短**，不是评分卡变好看。

## 附录 · 一页速查

### 排序口诀

```
开发 Harness：
  前置先做：入口、归属、反馈、负例、闭环
  伴随做：防漂移（每外置一份知识就配检查）
  有压力再做：决策记录、分类、意图入口、正确路径、流程、执行链、评审、静与动、披露、查询、发布

运行时 Harness（先做适用性判定）：
  前置先做：会话事实源、模型可见面、工具执行与授权
  有压力再做：格式世代、终结边界、能力 seam、扩展点、治理、入口投影、客户端纪律、组合与启动
  最便宜的三刀：坏配置大声失败、结果单一出口、终结原因封闭化

通用：一轮一到三维，先便宜的，做完复测
  两套都评时：CP4/ST1/ST2/ST3 与 RT9/RT2/RT7/RT1 名字相近但对象不同，各评各的
```

### 运行时维度的负例控制一句话

| 维 | 负例控制 |
|---|---|
| RT1 组合与启动 | 改错一个组件键名，看启动失不失败 |
| RT2 会话事实源 | 加一个动态注入的上下文，看回放能不能重建 |
| RT3 格式世代 | 把数据的版本号改新，看提示是"升级"还是"损坏" |
| RT4 循环与终结 | 取消一个长动作，看它是否真停、是否留记录 |
| RT5 能力 seam | 数使用方与实现数：1+1 就还是私有函数 |
| RT6 扩展点 | 拿一次绕过扩展点的改动，看检查拦不拦 |
| RT7 模型可见面 | 同上 RT2；再加一次"两次启动前缀是否相同" |
| RT8 入口与协议 | 往协议 stdout 打一行日志，看协议坏不坏 |
| RT9 执行与授权 | 让工具内部抛异常，看模型收到的是错误还是空结果 |
| RT10 治理 | 引入一个该被抓住的回归，看检查红不红 |
| RT11 客户端 | 后台直接改权威数据，看界面跟不跟得上 |

### 每张卡的负例控制一句话（开发 Harness）

| 维 | 负例控制 |
|---|---|
| KN1 入口链 | 改错一个链接，看检查红不红 |
| KN2 归属 | 只改两份拷贝中的一份，看有没有人发现 |
| KN3 决策记录 | 让不知情的人选，看他会不会选到被否决的那条 |
| KN4 分类学 | 手改一个生成物，看检查红不红 |
| CP1 意图入口 | 只看工作项描述，猜它做了什么 |
| CP2 正确路径 | 拿一次"绕过入口"的改动，看规则拦不拦 |
| CP3 流程固化 | 让没做过的人照着文档走一遍 |
| CP4 执行与授权链 | 加一条权限规则，数改了几个文件（应该是 1） |
| EV1 反馈分层 | 制造只能被一层发现的回归，看是不是只有那层红 |
| EV2 负例控制 | 本身即是：引入违规→看红→还原→确认变绿 |
| EV3 闭环完整性 | 问"文档声称的行为有几条没被检查钉住" |
| EV4 评审与批准 | 数最近 10 笔的评审评论条数与内容 |
| ST1 静与动 | 删掉一个派生缓存重跑，看功能坏不坏 |
| ST2 披露与隔离 | 删掉预算机制，测每轮体积前后差 |
| ST3 运行时查询 | 改配置不改清单，看检查红不红 |
| MT1 防漂移 | 改坏一个链接，看脚本红不红 |
| MT2 发布与版本 | 内容改了但版本没动，看发布失不失败 |

### 收工线

```
开发 Harness：
  达标线：MG2，且最痛的三维 = 约束力 3
  另加：十七维（裁剪后）全部 ≥ 覆盖面 2
  另加：切片复测无「找不到 owner」「声称零证据」
  标志：新人/新 agent 不靠带路能走完一笔变更，每步说得出证据在哪

运行时 Harness：
  达标线：MG2（可重建）：事实源、模型可见面、工具执行与授权 ≥ 约束力 2
  另加：五个活体实验都跑过；被评维度对应的实验通过（MG2 的三维对应 LX1、LX5）
  标志：出问题时能只靠记录说清「它当时看到了什么、做了什么、结果是什么」
```

**两类都适用的最终判据。** 一个系统"像回事"的标志不是它有多少机制，而是——**当一个陌生人（人或 agent）接手时，他能不能不靠任何人口头补充，走完一次完整的工作，并在每一步说得出证据在哪。**
