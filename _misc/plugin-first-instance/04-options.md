# 04 · 选项矩阵：先选架构，再选时机

大多数讨论把"启动时怎么安排"当成第一个问题，其实它排在第二。**第一个问题是谁拥有项目目录**：是插件的数据面，还是 DSH 的 workspace。这一个选择决定了后面所有选项是否相关。

## 第一层：三种架构

| | **I · 插件中介写**（现状） | **II · workspace 化** | **III · 混合** |
|---|---|---|---|
| 项目目录是什么 | 插件账本里的记录 | DSH workspace | workspace 是入口，插件另存账本 |
| 谁写项目文件 | 插件的 `node:fs`（经工具） | 模型工具 + 插件 | 两边都有 |
| 会话 cwd | 与项目无关 | 必须等于项目目录 | 等于项目目录 |
| 需要 `projectsRoot` | 只作为落盘位置 | 作为扫描与注册的根 | 两者都要 |
| 沙箱 | 不相关 | 决定一切（见 [03](./03-sandbox-roots.md)） | 模型只能写当前项目 |
| 模型能力 | 只有插件工具 | 通用 `read/write/bash` | 通用 + 插件工具 |
| 用户看到 | 产品自己的界面 | DSH 侧栏的工作区/会话 | 两者都有 |
| 典型代价 | 每个动作都要有工具 | 沙箱/工作区语义要对齐 | 两套真相要同步 |

`deck-studio` 现在走的是 **I**：`dataRoot` 存账本与 deck 工作目录，`projectsRoot` 只管新项目落盘，`session-bindings.json` 把会话绑到 deck，模型只调 `deck_*` 工具。

**一个容易说错的点**：workspace 本身不产生可写性。它只给会话 cwd 和沙箱根；模型能不能 `read`/`write`/`bash`，取决于 preset 挂了哪些工具。`deck-studio` 的 preset 只有 `persona` + `deck-studio-tools`（没有 `tool-fs`/`tool-bash`），所以即使把 deck 目录登记成 workspace，模型的行为也不会变——变的只是侧栏多一行和一个沙箱根。

**I → II 的迁移成本主要在语义，不在代码**：一旦项目成为 workspace，就要回答"删了工作区算不算删项目"、"用户手动加的工作区算不算项目"、"模型是不是能绕过插件工具改文件"。这些问题在架构 I 里根本不存在。

## 第二层：架构 I 的子选项

| 维度 | 选项 | 说明 |
|---|---|---|
| 落盘位置 | `dataRoot`（默认 `$DSH_HOME/deckline`）或 `projectsRoot`（用户目录） | 前者隐藏、随 home；后者可见、可携带，但插件要小心不要覆盖用户文件 |
| 编排时机 | 启动时建目录 / 首次使用时懒建 / 手动 | 建议懒建：没有第一个 deck 就不写盘 |
| 会话关联 | `session-bindings.json`（现状） | 与 cwd 无关，最稳；换 workspace 不影响绑定 |
| 目录里放东西 | 通常什么都不放 | 除非要跨机器携带 |
| 数据面 | 共享 home 即可 | 项目内容不在 home 的风险由 `projectsRoot` 解决 |

架构 I 的"启动编排"其实很轻：**只需要准备账本**（schema 版本、素材库、预设风格），不需要碰 workspace。

## 第三层：架构 II 的子选项

一旦项目 = workspace，五个维度全部生效：

### 根从哪来

| 代号 | 来源 | 插件何时知道 | 代价 |
|---|---|---|---|
| D1 | 安装时写进 profile patch | 启动前 | 换目录要改 YAML |
| D2 | 启动参数 / env / `--patch` | 启动前 | 要维护启动器 |
| D3 | 首启由用户选 | 选完之后 | 要客户端 UI + Host 端点 |
| D4 | 从已登记 workspace 反推 | 事后 | 分不清"我的项目"和别人的 |
| D5 | `process.cwd()` | 启动前 | 只在 CLI 有意义 |

### 编排时机

| 代号 | 时机 | 能做 | 不能做 |
|---|---|---|---|
| T1 | 启动 `apply` | 扫根、注册、写脚手架 | 反应不了用户刚选的目录；与首用默认工作区竞态 |
| T2 | `agent/created` / `session/created` | 按会话 cwd 采纳、写脚手架；`agent/created` 是 serial 可阻断 | 只在已有会话时触发；不能改 cwd |
| T3 | 客户端选目录后调自家 Remote | 立刻采纳、写脚手架、提示 | 要客户端插件 |
| T4 | 显式命令 / 设置页 | 全量重建、修复 | 要用户主动 |

Host 侧没有 `workspace/created` 事件；唯一增量来源是 `workspaceController.follow()`，它是客户端流，不该当插件事件总线用。

### 目录身份载体

| 代号 | 载体 | 自描述 | 跨 home | 污染目录 |
|---|---|---|---|---|
| I1 | 只靠 registry | 否 | 否 | 否 |
| I2 | 插件 domain（`w_<sha256>`） | 半 | 否 | 否 |
| I3 | 目录内 marker | 是 | 是 | 是 |
| I4 | I1 + I2（+ 需要的 I3） | 看组合 | 看 I3 | 看 I3 |

### 数据面

| 代号 | 做法 | 隔离 | 代价 |
|---|---|---|---|
| S1 | 共享 `$DSH_HOME` | 无 | 零 |
| S2 | 同 home、重定向数据根 | 中 | 没文档把它当模式；两 profile 共根会互踩 |
| S3 | 独立 `$DSH_HOME` | 高 | 凭据/模型配置全要重来 |

### 产品形态

| 代号 | 形态 | 先例 |
|---|---|---|
| P1 | 只发 bundle + profile 说明 | 第三方主流 |
| P2 | 自带壳（`loadProfileDirectory` + `runProfile`） | Desktop |

## 四套组合

| 组合 | 架构 | 内容 | 工作量 | 适合 |
|---|---|---|---|---|
| **A 账本优先** | I | `dataRoot` + 懒建 + session 绑定，不碰 workspace | 现状 | 对话式产品、写操作全走工具 |
| **B 尊重用户** | II | D3 + T3 + I4 + S1/P1：用户选根，客户端调 `adopt(root)` | 1–2 天 | 用户目录不可预测 |
| **C 目录树权威** | II | D1 + T1 + 墓碑 + 稳定排序 | 1 天 + 语义设计 | 根完全属于产品 |
| **D 真实例** | II | B/C + S2 或 S3 + P2 | 一周+ | 对外分发、要数据隔离 |

**迁移路径建议**：先 A 稳定产品形态，再按需加 B（不改账本），最后才考虑 C（自动扫描）与 D（隔离）。不要从 C 起步——墓碑语义和首用竞态会一起找上来。

## 需要拍板的五个决策

1. **项目目录是否要成为 DSH workspace？**（架构 I vs II）
2. 如果 II：**根从哪来**，D1 写死还是 D3 让用户选？
3. 如果 II：**扫描的权威**是目录树（自动、会复活删除）还是登记表（尊重删除、要刷新）？
4. **目录里放不放东西**：`AGENTS.md` / marker / 零写入？
5. **数据面**：共享 home、重定向根，还是独立 home？

## 一条判断捷径

> 如果模型不需要对项目目录用 `read`/`write`/`bash`，就不要把项目变成 workspace。
> 如果模型需要，就必须让会话 cwd 落在项目里，并且接受"一个会话只能管一个项目"。

前者是产品选择，后者是沙箱决定的物理事实。

## 对当前 `deckline` 的推荐

现状是 **A**，而且它成立：账本在 `dataRoot`，会话绑定不依赖 cwd，写操作全走 `deck_*` 工具。建议：

1. **保持 A 作为真相**，不要为了"在侧栏看见 deck"就把账本迁到 workspace registry。
2. **只把 `projectsRoot` 指到用户目录**，让项目内容可见、可备份；账本留在 home。
3. 如果确实需要"侧栏里按项目开会话"，再加 **B**：用户选过的目录，客户端调 `adopt`，插件在账本里记一条并可选地注册 workspace。两套真相用"账本为主、workspace 为入口"的规则约束。
4. **不要先做 C**（启动扫描）。它会立刻撞上"删了又复活"和首用默认工作区的竞态，而这两件事在 A/B 下都不存在。

启动时"目录不存在怎么办"的状态机见 [07](./07-startup-resolution.md)：先解析（configured / adopted / default / unresolved），再登记；`unresolved` 时用 home 下的占位目录挡住 DSH 首用默认，等客户端弹窗。
