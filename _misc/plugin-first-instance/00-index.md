# 插件即产品：DSH 实例的目录、数据与启动编排

**状态**：调研稿，**未改动 FAQ 26**，也未改任何代码。用于先把 `projectsRoot` 一类问题想清楚，再决定 FAQ 怎么重写、沙箱那一章先写什么。

**起因**：一个 DSH 实例可以由一个插件决定用途（例：`deckline` profile + `dsh-plugin-deck-studio` + `projectsRoot`）。这类实例不是"某个插件装在别人的 DSH 里"，而是**插件就是产品**，它影响安装、启动、workspace 安排和数据归属。现有 FAQ 26 从"插件数据放哪"出发，回答不了这个场景。

## 用户真正卡住的三个问题

1. **用户肯定知道自己的目录在哪，但 DSH 启动时不知道。** 那么"用户选了目录"这件事，最后被记在哪里？
2. **选完之后，要不要在用户的工作目录里留点什么？要不要在 profile 里留点什么？** 现在完全不清楚。
3. 写插件时，**"数据目录"到底指哪个目录**——是 `DSH web` 里的 workspace，还是插件自己的状态目录，还是两个都要？

## 一页结论

0. **先选架构，再选时机。** 项目目录是"插件的私有数据面"（架构 I，模型只调插件工具）还是"DSH workspace"（架构 II，模型可直接写）？前者不需要 workspace、不受沙箱影响；后者必须让会话 cwd 落在项目里。`deckline` 现在走 I。
1. **DSH 默认两边都不留。** 用户选目录后，DSH 不在目录里写任何东西，也不在 profile 里写任何东西；知识全落在 `$DSH_HOME`（`storages/workspace.json` + `sessions/`）+ 浏览器 `localStorage`。目录本身是"哑目录"。
2. **`projectsRoot` 是五个角色叠在一个名字上**：发现根、注册根、会话根、沙箱根、插件数据根。DSH 原生只认第 3 个（会话 cwd），而**沙箱只认这一个**。
3. **沙箱每个会话只有一个可写根**（`SessionHeader.cwd`），没有额外可写根；`cd` 不放宽；放宽只能靠一次性审批。所以"让模型用通用文件工具写 `projectsRoot`"等价于"让会话建在 `projectsRoot` 下面"。
4. **目录没有自描述锚点**：同一个目录在两台机器上是两个互不相关的工作区（新 uuid）。跨 home/跨机器携带项目身份，只能靠目录内 marker 或插件自己的记录键。
5. **启动编排没有门**：Loader 的行并发启动，没有"编排完成 → 再开监听"的保证；而客户端首连在空 registry 时会自动建 `<Documents>/deepseek-harness/default-workspace`。
6. **启动时没有用户可问**：目录解析只能在 Host 侧落到确定状态（configured / adopted / default / unresolved），弹窗发生在客户端连上之后；启动时先登记一个占位工作区，才能挡住 DSH 自己的 `<Documents>` 默认工作区。
7. **现实样本已经存在**：`~/.dsh/profiles/deckline` + `~/.dsh/deckline`（`dataRoot`）证明架构 I 可行——账本、会话绑定、deck 工作目录都在 home，模型只调 `deck_*` 工具，`projectsRoot` 只负责新项目落盘。
