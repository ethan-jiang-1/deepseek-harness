# 什么时候用哪个原语：官方选择决策语义全景

源码核验入口：`packages/workflow/tool-workflow/src/index.ts`、`packages/subagent/tool-subagent/src/index.ts`、`packages/goal/tool-goal/src/index.ts`、`packages/workflow/tool-ralph/src/index.ts`、`packages/todo/tool-todo/src/index.ts`、`packages/jobs/tool-jobs/src/index.ts`、`packages/schedule/schedule/src/tools.ts`、`packages/interaction/tool-ask-user/src/index.ts`、`packages/plan/plan-mode/src/index.ts`、`packages/experimental/tool-agent-team/src/index.ts`、`packages/bundle/base/cordis.patch.yml`。

本页回答：DSH 对「什么时候用哪个编排原语」给了什么**明文语义**？原语之间怎么互相路由？哪里没说清？全部结论取自模型可见文本与部署组合，逐字引用附出处。阶梯全景与各原语的机制见 [`00-map.md`](./00-map.md)；workflow 的内部机制见 [`01-workflow-模型编写的JS编排脚本与子代理扇出机制.md`](./01-workflow-模型编写的JS编排脚本与子代理扇出机制.md)。

## 为什么是这个形状：设计考量

DSH 面对的编排问题是「谁来决定这个任务用哪种原语」。另一种显然的答案是**中心调度器**——一个读任务的引擎把工作分派到原语上（外部叙事想象的正是这个）。DSH 的答案相反：**路由知识分布在原语自身**——每个工具的描述文本和 prompt 节携带自己的使用边界，模型读了边界自己选。这个形状的考量：①策略**随工具插件走**（master convention，`packages/workflow/tool-workflow/src/index.ts:321`-`322`）——换掉工具，它的策略跟着走，不会留下指向不存在工具的孤儿规则；②同包双实例（`subagent` 与 `subagent_fork`）**各带各的 wording**——路由语义与具体工具形态绑定，而不是一份全局文档漂在上面；③它是**自描述且组合敏感的**——preset 层 disable 一个工具行，它的路由语义同时从模型视野消失，不需要任何中心配置同步。代价也真实：路由是单向的、有九处空白（见矛盾与空白节）——分布式的知识没有全局视野。这个取舍与 [`09`](./09-对照外部叙事-Captain与Kahn调度与rollback与KV看板的逐条源码真相.md) 的结论互为表里：**没有中心引擎不是缺失，是把决策权交给模型 + 把知识放进原语的设计选择**。

## 语义住在哪：两个通道 + 一个约定

官方选择语义编码在两类**模型可见文本**里：

| 通道 | 注册处 | 例子 |
|------|--------|------|
| 工具 description / 参数 description | `ctx.tools.register`（各 tool-* 包） | `create_goal` 的 "Use it when the direct human request is a long-running objective" |
| 工具自带的 systemPrompt section | `ctx.systemPrompt.section`（各 tool-* 包） | `tool:workflow` 节的 "ONLY when the user explicitly asks" |

约定（master convention）写在工作流工具的源码注释里：

> "Usage policy ships with the tool (the master convention: tool guidance lives in tool plugins as prompt sections, not in the deployment persona)."

—— `packages/workflow/tool-workflow/src/index.ts:321`-`322`

即：**使用策略随工具插件走，不放进部署 persona**。换掉工具插件，它的策略文本一起走；同包双实例（如 `subagent` 与 `subagent_fork`）各自携带自己的 wording。包 README 的 "Use this package" / "When to choose it" 节是同一语义的部署者视角转述，可作旁证但不进模型上下文。

## 逐原语边界句

### todo_write（最轻：上下文内计划留痕）

> "Record and update a task list to plan multi-step work and show progress; **skip it for trivial single-step tasks**. Add one todo per concrete step before you start."

—— `packages/todo/tool-todo/src/index.ts:45`-`47`

可写接口：`{"todos": [{"content": "修 ref-sweep 越界", "status": "in_progress"}, {"content": "复跑校验", "status": "pending"}]}`——`todos` 是**全量替换**（"The COMPLETE task list, replacing any previous list"，`:142`），status 枚举 `pending/in_progress/completed`。

plan 模式内与 `exit_plan_mode` 互斥（base bundle 的 plan-mode 部署 guidance）：

> "Do not use todo_write to track this planning phase: it tracks implementation after an approved plan, while the plan itself belongs in exit_plan_mode."

—— `packages/bundle/base/cordis.patch.yml:330`

### subagent / subagent_fork（有界委派）

同一插件 `@deepseek-ai/dsh-tool-subagent` 按 provider 生成两套 wording（`providerWording(inheritsParentContext)`，`packages/subagent/tool-subagent/src/index.ts:240`-`276`）。

`subagent`（spawn，fresh）：

> "Delegate a self-contained task to a subagent (a separate agent that works in its own context) to offload focused, independent work — research, a scoped implementation, an analysis — so it does not consume this conversation's context. The subagent returns its result, not its intermediate steps."

—— `packages/subagent/tool-subagent/src/index.ts:267`-`271`；prompt 参数："The complete, self-contained task for the subagent. It does not share this conversation's context, so include everything it needs."（`:272`-`274`）

`subagent_fork`（fork，继承已完成轮次）：

> "Delegate a task to a subagent that inherits this conversation: a child agent seeded with all completed turns so far (it does not see the current in-flight turn). **Use this when the subtask builds on this conversation's context — a follow-up analysis, a review, a continuation — without consuming this conversation's context for the work itself.** You receive its result, not its intermediate steps."

—— `packages/subagent/tool-subagent/src/index.ts:255`-`260`；prompt 参数："It already sees this conversation's completed turns, so build on them freely and state only what is new."（`:261`-`263`）

背景模式句随 `backgroundMode` 配置二选一：continuable——"It runs in the background by default and returns a subagent id you can continue with `send_message`; you are notified when the run settles."；one-shot——"This call waits for the result by default."（`:381`-`388`）。shipped base 组合是 subagent=continuable、fork=one-shot（`packages/bundle/base/cordis.patch.yml:370`-`388`）。README 的选择句："**Choose it when a subtask continues this conversation; choose spawn when the child must stand alone.**"（`packages/subagent/subagent-fork-in-process/README.md:12`）。

### workflow（规模扇出，需用户显式要求）

工具 description：

> "Run a JavaScript workflow script that orchestrates subagents at scale. **Use this for work that fans out across many independent pieces — an audit over many files, a migration, multi-angle research, adversarial verification of findings — where you write the orchestration as a script instead of delegating turn by turn.**"

—— `packages/workflow/tool-workflow/src/index.ts:158`

prompt section（`tool:workflow`）：

> "Use the ${toolName} tool **ONLY when the user explicitly asks for a workflow or for large multi-agent orchestration**: you write a JavaScript script … that fans work out across many subagents with phases and structured results. **For one or two delegations, prefer plain subagent calls.**"

—— `packages/workflow/tool-workflow/src/index.ts:323`-`327`

### ralph（fresh-agent 循环，需人类显式要求，默认关闭）

> "Run a foreground fresh-agent Ralph loop toward one immutable objective. **Use only when the direct human explicitly asks for Ralph or fresh-agent iteration.** Each round opens a new child with no parent conversation or prior child session; the shared workspace is long-term memory, and only a bounded structured report crosses rounds. The call returns when a worker reports completion or a concrete blocker, or at the round limit. **Ordinary long-running same-session work belongs to goal tools.**"

—— `packages/workflow/tool-ralph/src/index.ts:177`-`182`

prompt section 补充路由："Use same-session goal tools for ordinary long-running objectives, and plain subagents or workflows for bounded delegation and fan-out."（`:405`-`409`）。base bundle 默认 `disabled: true`，注释自述理由："completion is a worker self-report, not an independent evaluation"（`packages/bundle/base/cordis.patch.yml:440`-`449`）。

### goal（跨轮次长目标的默认档）

> "Create a persisted goal that keeps this session working across automatic continuation rounds. **Use it when the direct human request is a long-running objective, even if the user did not say "goal"; not for single-turn work.**"

—— `packages/goal/tool-goal/src/index.ts:51`-`54`

共享 guidance 节（`tool:goal`）给出推断、续臂与 blocked 阈值语义："create_goal may infer goal intent from a direct human request in any language. After session resume or fork, an active goal is disarmed: when a human asks to continue or resume in any wording or language, use update_goal action resume to rearm it. Mark complete only when the objective is actually achieved. Mark blocked only after the same blocking condition persists for at least ${blockedAfter} consecutive goal rounds…"（`:115`-`123`）。`update_goal` 的 action 参数描述区分权限：edit/pause/resume 需直接人类请求，complete/blocked 也允许在 goal 自动续轮中发生（`:244`-`245`）。goal 状态机与 Round Driver 深挖见 [`../agent-loop/01-goal-lifecycle.md`](../agent-loop/01-goal-lifecycle.md)。

### jobs（后台平面：跟踪与收尾纪律）

四个工具的 description 只定义操作（`job_output`/`job_list`/`job_kill`，`packages/jobs/tool-jobs/src/index.ts:312`、`:353`、`:373`）；选择语义在 prompt section（`tool:jobs`）：

> "Track every background job id you start. You are notified in-session when a job finishes — **do not busy-poll or sleep on one; keep working on independent steps and do not duplicate a running job's work.** Before giving a final answer, collect every still-relevant job with job_output (**set wait: true only when you are genuinely blocked on it**), and job_kill jobs that stopped mattering."

—— `packages/jobs/tool-jobs/src/index.ts:250`-`254`

### schedule（时间平面：wall-clock 提醒）

`schedule_create` 的 description 定义时序语义（"Supply exactly one timing parameter: after_seconds, at, every_seconds, daily, weekly, or cron. … After downtime, a recurring reminder delivers only its latest missed occurrence."，`packages/schedule/schedule/src/tools.ts:169`-`173`）。组 README 给出形态边界："Due reminders arrive as ordinary follow-up messages in the original conversation, **not email, SMS, or push notifications**."（`packages/schedule/README.md:12`）。shipped 组合不含 schedule，需启用 experimental optional bundle（`packages/schedule/schedule/README.md:26`）。

### ask_user_question（人机路由）

> "Ask the user a concise question **when you need confirmation, a choice, or missing information before proceeding**."

—— `packages/interaction/tool-ask-user/src/index.ts:31`

可写接口：`{"questions": [{"id": "scope", "question": "先修哪个范围？", "header": "选择", "options": [{"label": "本专题 (Recommended)", "description": "……"}]}]}`——推荐项放第一并加 "(Recommended)"（`:56`-`58`）；`id` 在回答里回显（`:50`）。

部署侧路由（base bundle plan-mode guidance）："Use ask_user_question only for user-owned choices or material ambiguity that inspection cannot answer. Do not ask the user where code lives or how current behavior works when you can find out."（`packages/bundle/base/cordis.patch.yml:332`）。README："A timeout is never approval."（`packages/interaction/tool-ask-user/README.md:44`）。

### plan mode / exit_plan_mode（审批门）

> "**Use only in plan mode.** Present your plan for the user's review and, on approval, leave plan mode. The user may approve (carry out the plan from your next step) or keep planning — their feedback comes back in the tool result; revise and present again."

—— `packages/plan/plan-mode/src/index.ts:84`-`87`

可写接口：`{"plan": "# 修复计划\n## 步骤\n1. …"}`——`plan` 必须是 `#` 标题开头的 markdown（`:282`），且按部署 guidance 必须是该回复**唯一且最后**的工具调用（`packages/bundle/base/cordis.patch.yml:336`）。

README 的选择句："Choose plan mode when the agent should explore and design before executing and you want to approve the plan first. **It does not restrict the agent: every tool stays callable, so use sandbox mode and approval prompts when you need enforced limits. Skip it when the agent should act on your requests immediately, without a planning phase.**"（`packages/plan/plan-mode/README.md:30`-`32`）。

### agent-teams（显式 opt-in 顶配，experimental）

共享策略节（`team:policy`）：

> "Agent Teams is available in this session, but **create teammates only when the user explicitly asks to use Agent Teams or teammates**. … The Lead must wait for required teammates before giving the final answer."

—— `packages/experimental/tool-agent-team/src/index.ts:31`-`37`

组合层的互斥替代："The `subagent` and `subagent_fork` tools and overlapping global child controls are disabled. Workflow retains the base profile's `spawn` provider."（`packages/experimental/agent-team-profile/README.md:49`）。机制深挖见 [`../experimental/02-agent-teams.md`](../experimental/02-agent-teams.md)。

## 官方升级阶梯（从轻到重的排序证据）

1. **todo_write**（最轻）："skip it for trivial single-step tasks"——多步但不扇出。
2. **subagent**（一两次委派的默认档）："For one or two delegations, prefer plain subagent calls."——官方把 subagent 定为 workflow 之下的默认。
3. **workflow**（规模扇出）："fans out across many independent pieces… instead of delegating turn by turn"——从逐轮委派升级为脚本编排，且需用户显式要求。
4. **ralph**（长程 fresh-agent 循环）：仅人类显式要求，且被官方从 goal 中分出（"Ordinary long-running same-session work belongs to goal tools"）。
5. **goal**（跨轮次长目标的默认档）：不需要用户说出 "goal"，从请求语义推断。
6. **jobs / schedule**（正交平面）：jobs 是执行平面（"without blocking its own turn"，`packages/jobs/README.md:12`），schedule 是时间平面（wall-clock 提醒），不与阶梯竞争而是叠加。
7. **agent-teams**（显式 opt-in 顶配）："create teammates only when the user explicitly asks to use Agent Teams or teammates"。

## 矛盾与空白（官方未说清的部分）

1. **主语不一致**：tool-workflow 的 README 与 prompt section 说 "the **user** explicitly asks"，引擎包 `packages/workflow/workflow/README.md:28` 写 "the **model** explicitly asks for workflow-style orchestration"——引擎包疑似笔误；prompt section 是权威模型可见文本。ralph 用 "the direct human"，workflow 用 "the user"，粒度也不同。
2. **目录渲染 vs 实际组合**：`docs/tool-catalog.md:2040` 渲染的 subagent description 带 one-shot 默认句 "This call waits for the result by default."，但 base 组合实际以 continuable 挂载，模型看到的是背景默认句（目录自注实例可变，`docs/tool-catalog.md:2068`）。
3. **fresh ↔ fork 无模型级路由**：选择语义只在两个工具各自的 description 与 README 里，没有针对二者的 prompt section 或部署 guidance——工具描述独自承担全部路由。
4. **goal 侧无反向路由**：goal 的描述/README 从不提 ralph、workflow、subagent 或 schedule；路由是单向的（ralph→goal、workflow→subagent），goal 语境下没有官方降级/升级指引。
5. **goal ↔ schedule 无互斥说明**：两者都跨时间推进（objective 续跑 vs wall-clock 提醒），互不提及，无选择 guidance。
6. **「何时转后台」无统一规则**：jobs 的 prompt section 只讲跟踪与收尾纪律；`run_in_background: true` 的决策散落在各 producer 的参数描述里。
7. **ralph 的 explicit-ask 仅是 prompt 约束**：无机械执行；且 shipped 组合里该工具默认 disabled，模型根本看不到。
8. **fork 无并发提示**：continuable 的并发 prompt section（"Start independent delegations together in one assistant message"，`packages/subagent/tool-subagent/src/index.ts:594`-`604`）只随 continuable 实例注册；base 的 fork 是 one-shot，fork 侧无对应提示——非对称。
9. **ask_user_question 的 timed/blocking 二选一**：随部署 mode 切换（`packages/interaction/tool-ask-user/src/index.ts:31` vs `src/timed.ts:27`-`30`），何时该开 timed 无模型级 guidance。
