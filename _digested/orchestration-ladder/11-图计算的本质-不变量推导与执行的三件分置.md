# 图计算的本质：不变量、推导与执行的三件分置

源码核验入口：`packages/experimental/agent-team/src/task-graph.ts`（图校验）、`packages/experimental/agent-team/src/task-view.ts`（就绪推导）、`packages/experimental/agent-team/src/task-board.ts:242` 与 `projection.ts:280`（两个校验调用点）、`packages/experimental/tool-agent-team/src/index.ts`（POLICY 与 ready 过滤）、`packages/workflow/tool-workflow/src/index.ts`（脚本合同）。

编排的骨子里确实是**图计算问题**——但 DSH 对它的回答不是「造一个图引擎」，而是把图计算**拆成三件分置的事**：引擎只做能机械保证的前两件，第三件交给对话与模型。本页逐行核验这个分置在源码里的形态，并回答：编排里真实的图有哪些？引擎对图做了什么、拒绝做什么？为什么这个分界画在这里？

## 三个真实的图

| 图 | 形态 | 归谁 | 本专题落点 |
|----|------|------|-----------|
| **归属树** | in-process 子代理可用 `parentSession` header、活体 ancestry 与 owned-children 表示不同查询域；默认 `maxDepth=1` 允许 fan-out，但 continuable 默认共享活体容量为 8，workflow 与 jobs 另有并发/总量/owner 限制 | **in-process 子代理运行时**维护的权限、通知与结算骨架；外部 provider 不都拥有同一 host Agent/session 结构 | [`03`](./03-subagent与subagent-fork-有界委派的隔离继承与continuable控制面.md)、[`08`](./08-组合模式-归属链深度预算通知通道与收尾纪律.md) |
| **任务 DAG** | teams 任务板的 `blocked_by`——唯一的显式 DAG，但它是**协调数据**不是执行引擎 | 引擎守不变量；语义归团队 | 本页逐行核验 |
| **脚本控制流** | workflow 的编排图不是数据结构——是一段 JS：`for`/`await`/`Promise.all` 就是扇出与汇聚，`agent()` 是图的叶子 | 代码所有（图灵完备） | [`01`](./01-workflow-模型编写的JS编排脚本与子代理扇出机制.md) |

外部叙事把这些关系捏成了一个「Kahn 拓扑调度引擎」；当前源码把任务图、脚本控制流与归属/生命周期关系分别实现。对外部叙事的逐条核对见 [`09`](./09-对照外部叙事-Captain与Kahn调度与rollback与KV看板的逐条源码真相.md)。

## 任务 DAG 的引擎侧：写时校验 + 读时推导

**写时校验（不变量，确定性）**：每次任务创建或变更，`assertTaskGraphCandidate` 对**替换候选快照后的全图**做完整性校验（`packages/experimental/agent-team/src/task-graph.ts:26`-`69`），拒绝三类违规（`TeamTaskGraphViolation`，`:6`）：

- `missing`：blocker 不存在或已删除（"blocker task … is missing or deleted"，`:46`）；
- `duplicate`：同一 blocker 重复列出（"repeats blocker"，`:41`）；
- `cycle`：**自引用**（"cannot block itself"，`:38`）或**依赖环**——后者用经典 DFS 三色标记检测：`visiting`/`visited` 两个 Set，访问中再遇即环（":54`-`65`）。这不是 Kahn 算法（Kahn 是反复摘入度零节点来线性化），是环检测——校验的目的是**拒绝非法图**，不是排出执行序。

校验有**两个调用点**：任务板命令事务内（`packages/experimental/agent-team/src/task-board.ts:242`，提交前）与事件折叠时（`projection.ts:280`）——**重放也重验**。折叠器捕获异常并将 terminal `failure` 保存在 projection（`projection.ts:225`-`:237`），不会把异常直接抛给事件驱动；后续 `journal.state()` 看到该 failure 后拒绝权威操作（`journal.ts:29`-`:33`）。因此 durable 的保证是非法日志不能继续成为可操作的合法状态，而不是日志重放永远不会产生失败。

**读时推导（纯函数）**：就绪不是一个存储的状态，是每次读取时推导的（`packages/experimental/agent-team/src/task-view.ts:24`-`26`）：

```ts
export function taskReady(state: TeamState, task: TeamTaskSnapshot): boolean {
  return task.blockedBy.every(id => state.tasks.find(...)?.status === 'completed')
}
```

这就是「入度为零」条件的**逐任务版本**——一个任务 ready 当且仅当它的全部 blocker 已 completed。推导结果进入任务视图的 `ready` 字段（且仅当 `status === 'pending'`，`:59`）、`team_task_list` 的 `ready` 过滤参数（`packages/experimental/tool-agent-team/src/index.ts:323`），以及任务状态转换的准入检查：`claim` 拒绝未 ready 的任务（`task-board.ts:129`-`:136`），`reassign` 给任务指定新 owner 时也拒绝未 ready 的任务（`:172`-`:186`）。因此 ready 不是存储状态，也不只是展示字段；它是一个被多个消费者复用的确定性派生条件。就绪推导的本体不住在这些调用点，而在 `taskReady`——一处 3 行的纯函数。同文件还推导 **advisory 写域重叠警告**（`scopesOverlap` 前缀包含关系，`:14`；`in_progress` 任务的写域与本任务重叠即告警，`:46`）——写域提示仍然不是锁。

## 执行分置：引擎拒绝做拓扑调度

关键句在 POLICY 里："**Task readiness never starts an owner.**"（`packages/experimental/tool-agent-team/src/index.ts:37`）——就绪不会自动启动 owner。派发仍由 Lead 或队友通过 `send_message` 按上下文决定「现在该叫谁」；任务板只在 `claim`/带 owner 的 `reassign` 等状态转换处把 ready 作为准入条件。引擎对图的职责因此分成三类：**校验它合法、推导它是否就绪、在受控状态转换中拒绝未就绪任务，但不替你调度 owner**。

对照 Kahn：Kahn 算法把 DAG 线性化为执行序，前提是存在一个中心 executor 按序取节点、派工、在节点完成时给后继减入度。外部叙事想象的正是一个这样的引擎（就绪队列、汇聚解冻、入度减一）。DSH 的分界线画在：**线性化与派发需要判断「接下来什么更值得做、失败了要不要重试、要不要改图」——那是概率判断，不是机械保证**。确定性归引擎（不变量 + 推导），概率性归模型（决策 + 重规划）。

## 为什么分界画在这里：重规划是常态

外部叙事自己的状态机里有一个 `REPLANNING` 态（Captain 动态手术改图）——这个态的存在本身就是证据：**静态 DAG 表达不了真实工作的图**。真实任务的依赖是做出来的过程中才被发现的（审计到一半才知道哪两个文件耦合）；一个写死的 DAG schema 要么假装图已知（然后频繁重规划），要么长出逃逸舱——而逃逸舱就是模型。DSH 让模型成为默认而非例外：

- **teams**：图（任务板）随时可改——`team_task_update` 换 `blocked_by` 即改图，改完立刻全图重校验（写时校验的设计动机正在于此：图是活的，每次改动都要保不变量）；
- **workflow**：编排图干脆用**图灵完备代码**表达——循环里可以根据中间结果构造下一批节点，改图是原生能力，不需要 DSL 逃逸舱（取舍记录见 `.agents/notes/implemented/feature/2026-07-05-dynamic-workflows.md`——脚本而不是对话持有循环、分支与中间结果）；
- **goal/ralph**：连图都不预设——objective 驱动的轮次里每轮重新决定做什么（同会话持久目标 vs fresh 迭代的两策略分裂见 [`04`](./04-ralph-fresh-agent循环的轮间传递与固定脚本机制.md)）。

## 归属树的机械细节：一棵树的三种表示

归属树不是一个数据结构，是**三种并存表示**，各自为一种查询模式优化（`packages/subagent/subagent/src/continuation-activation.ts:70`-`95` 的 Activation 字段声明）：

| 表示 | 存在哪 | 回答什么查询 | 为什么是这种形态 |
|------|--------|-------------|----------------|
| **durable 边**：`parentSession`（SessionId） | child 的 session header（`child-agent.ts:149`；`packages/core/session/src/types.ts:107`） | 向上**一跳**（持久） | lineage trace 递归向上（`session-query/src/tracing.ts:135`-`150`）、冷恢复授权（header.parentSession 必须匹配 sender）、settle notice 在 handle 死后仍要找到 durable direct parent |
| **活体成员**：`ancestry: WeakSet<Agent>` | 每个 Activation（`:85`-`89`） | "这个 caller 在我的**活体**祖先链里吗"（interrupt 授权） | Weak 成员判定保 host-scope 身份，中间祖先退出 registry 也不滞留其 runtime；**不可枚举**——所以 durable parent 要单独存（`:71`-`77` 的注释明说 WeakSet 答不了"我的父是谁"） |
| **向下集合**：`ownedChildren: Set<SessionId>` | 每个 Activation（`:91`-`95`） | 我还欠谁的命（生命周期闭包） | 一个 Session 至多一个活 Activation，所以 Session id 即可定位活 child，无需再持 runtime 引用；**非空阻塞父结算** |

另有两套**只读遍历**不加载任何 Agent：`listChildren`/`listDescendants` 走 catalog 投影（`docs/subsystems/subagent.md:271`-`281`）；session-query 的 lineage trace 递归 header 向上。initiator 判据（goal authority 的 runtime-root 检查）的运行时身份机制见 [`../agent-loop/04-agent-runtime-identity.md`](../agent-loop/04-agent-runtime-identity.md)。**为什么三种而不是一种**：三种查询的时效域不同（跨进程持久回溯 / 进程内活体授权 / 生命周期闭包）——单一结构要么丢持久性（WeakSet）、要么滞留 runtime（强引用 Set 当边表）。

## workflow 的取舍记录：模型文本是数据，直到穿过受限边界

dynamic-workflows note 的 Alternatives 节（`.agents/notes/implemented/feature/2026-07-05-dynamic-workflows.md`）没有正面辩论"JS 还是 DAG DSL"——语言问题被 Problem 陈述与 Claude Code 先例定了（脚本持有循环、分支与中间结果；DSL 的失败模式已在上面"重规划常态"论证）。它真正逐条记录的是**怎么托管与校验这段模型写的代码**，每一条都是同一原则的实例——**模型写的文本是数据，直到它穿过一个受限边界**：

- **宿主载体**：进程内 `node:vm` 被拒（首段同步切片会阻塞 `start()` 的 caller；越过首个 await 的同步自旋在进程内**不可杀**；`dispose()` 只能在宿主 loop 上抛弃不安分的脚本）→ `isolated-vm` 被拒（独立 JS 引擎带来原生依赖）→ **PTC 进程**中选：保留 vm 语境的脚本 API，同时宿主不阻塞、终止受管（这就是 [`01`](./01-workflow-模型编写的JS编排脚本与子代理扇出机制.md) 进程模型的出处）；
- **meta 位置**：CC 的 `export const meta = {...}`（内嵌脚本头）被拒——取 meta 需要在**宿主上求值模型写的文本**，连空的限时 vm context 也界定不了 script-controlled getters → meta 成为**纯 JSON 参数**，扫描器、求值、宿主自旋漏洞一并消失；
- **schema 处理**：schema 是 **wire data**——穿过 vm realm 边界、逐字落进 forced tool 的 parameters；活 schema 对象（zod/schemastery）放不进这个位置，运行时消费原始 JSON Schema 又需第三方转换器 → 手写约 70 行的子集校验器；ajv 亦被拒（它校验**全量** JSON Schema，而子集闸门才是要点——每个被接受的关键字都必须是 harness 实际执行的；且它经 `new Function` 编译、会成 dsh-tools 首个运行时依赖）；
- **结构化输出**：provider JSON mode 被拒（保证合法 JSON，不保证 schema 合规）→ **capture tool**：校验失败保留轮内重试。

## Kahn 与 DFS 的形式化对比

| | Kahn 线性化（外部叙事想象的引擎） | DSH 的实际形态 |
|---|---|---|
| 输入 | DAG | 任务图（写时已验无环） |
| 算法 | 反复摘取入度零节点 → **拓扑序** | DFS 三色环检测（`task-graph.ts:54`-`65`）——只判**合法性**，不产序 |
| 就绪语义 | 入度零 = 可调度（驱动取节点派工） | `taskReady` = 阻塞者全完成（`task-view.ts:24`-`26`）——用于**视图/过滤与 claim/reassign 准入** |
| 派发 | 引擎按序取节点 | `send_message`（对话决定） |
| 改图 | 序作废，算法重跑 | 每次写入后**全图重校验**（图是活的，改图是常规操作） |
| 全局视野 | 有（拓扑序即进度视图） | 任务板可返回全量任务投影（`task-board.ts:90`-`95`），但**没有由该视图驱动的中心调度器**；`ready` 是逐任务派发前的状态与准入信号 |

本质差异一句话：**Kahn 假设存在一个消费拓扑序的中心 executor；DSH 拆掉了这个假设**——校验（写时）、推导与准入（读时及状态转换）、派发（对话）三件分置之后，"线性化"这一步没有存在的理由。DSH 的真实代价不是没有任务全景，而是没有由任务全景自动推进 owner 的中心调度器；Lead 仍可读取全量任务并自行决定派发。这个分界与 [`../harness-idea/01-role-and-substrate.md`](../harness-idea/01-role-and-substrate.md) 的职责论述互为表里：**当前实现把可机械验证的图不变量、派发前准入和生命周期操作交给 harness，把需要任务语义判断的派发与重规划交给 Lead 或模型**。这描述当前 teams 任务板的职责分界，不是对所有编排算法或所有代码/语言关系的普遍定理。

## Agent 是原子：全部原语的统一重述

把三件分置再往下压一层，可以得到一个受限的统一模型：**in-process 模型工作的基本单位是 Agent**——一个 session、inbox 与驱动模型 turn 的 loop（loop 本身也是插件，`docs/architecture.md`；Agent 接口与 inbox 契约见 [`../agent-loop/00-map.md`](../agent-loop/00-map.md)）。这不是所有 runtime 工作的统一原子：外部 provider、PTC 脚本、普通进程 job、schedule 与 plan review 有各自的执行者和生命周期。对 in-process Agent 路径，可以把原语描述为「构造上下文 × 决定让哪个 Agent 何时跑 × 结果怎么回来」：

| 原语 | 构造什么上下文 | 哪个 Agent | 何时跑 | 结果怎么回 |
|------|--------------|-----------|--------|-----------|
| subagent spawn | prompt + fresh session + preset 重组 + 委派权限（[`03`](./03-subagent与subagent-fork-有界委派的隔离继承与continuable控制面.md)） | 新 child | 立即/后台 | 工具结果 / settle notice |
| subagent fork | 上述 + 种子=父已完成轮次（KV 前缀可复用） | 新 child（带历史） | 同上 | 同上 |
| workflow | PTC 脚本按控制流和中间结果构造 prompt+schema；可用 FIFO slot、`parallel` 与 `pipeline` 组织并发（[`01`](./01-workflow-模型编写的JS编排脚本与子代理扇出机制.md)） | 一批 child 或无 child 的脚本 | 脚本控制流与运行时容量约束共同决定 | 脚本内消化，只回最终值 |
| ralph | 六段 prompt + workspace 为唯一记忆（[`04`](./04-ralph-fresh-agent循环的轮间传递与固定脚本机制.md)） | 每轮**全新** child | 上一轮结束 | 五字段有界报告 |
| goal | `<goal_round>` 注入 + durable session（[`05`](./05-goal-驾驶座用法-objective写法轮预算与终结纪律.md)） | 当前 Session 的 live Agent incarnation；恢复会创建新的 runtime identity | idle + armed，且通过轮次准入检查 | wrapup 收尾消息 |
| teams | 任务板 + 邮箱 + POLICY 注入（[`07`](./07-agent-teams-驾驶座用法-启用代价Lead工作流与协作纪律.md)） | 具名队友（spawn/fork） | 对话唤醒（就绪不派发） | relay 消息 + 任务状态 |
| schedule | 到期提醒消息（[`06`](./06-jobs与schedule-后台作业平台与定时跟进的时间平面.md)） | Host scheduler；到期后向目标 Session 投递 | wall-clock | inbox accepted 的 follow-up 消息，不等于模型已完成处理 |

需要单独区分：**bash/pwsh/terminal 后台 job 是非 Agent 进程工作**（无模型 loop）；**schedule 由 Host 时间驱动**；**todo 是短期列表投影，plan 还包含人类 review 与后续 step 变更**。jobs 是通用执行观察与控制容器，不是某一种工作的执行者。

这个视角说明了当前实现的一种职责分配：运行时负责建立上下文、执行权限与容量准入、投递消息、取消和资源回收；Agent 在 turn 内作任务语义判断，Lead 或模型决定何时派发 teams 任务。workflow 的控制流仍可根据不确定的子代理结果动态分支，代码表达结构不等于结果可复算。当前 teams 没有自动消费 ready 队列的调度器；这项观察不应推广为所有编排算法都必须由模型决定。

### 能力包络与代码-语言光谱

再往里压两层。**Agent 的能力包络 = 智力（模型：推理与决定）× 体力（工具集：bash/fs/browser……）× 许可（权限/沙箱/深度预算）**——loop 是确定性的交替驱动器（模型请求 → 工具执行 → 再请求，直到 turn 抽干），且 loop 与工具都是插件：连「体力」的清单都是可组合的。**关系的结构有两个层面：骨架是传统程序**（CAS、环检测、inbox FIFO、通知通道、深度预算——确定性代码），**流经骨架的是语言**（prompt、消息、报告、任务描述——给模型读的）：铜线是代码，电流是语言。

从实现观察出发，可以用一个**描述性**的代码与语言维度比较这些原语；它不是确定性与概率性的等价分类，也不意味着代码越多就越可复算：

| 原语 | 关系语义的代码占比 | 语言占比 |
|------|------------------|---------|
| workflow | 结构控制由 JS 脚本表达（扇出/汇聚/分支），运行时提供 FIFO slot 与容量约束 | 叶子 prompt、子代理结果与脚本输入仍由模型和外部环境影响 |
| ralph | 节拍与校验是代码（固定脚本 + 报告 schema） | 轮间内容是语言（五字段报告） |
| goal | 节拍是代码（round driver 注入） | 每轮做什么全是语言 |
| teams | 只有不变量是代码（CAS/环检测/邮箱） | **协调几乎全是语言**（对话 + 任务板） |

这个维度只用于定位职责：workflow 把结构控制写进脚本，teams 把更多派发与协调决定留给 Lead 和队友；两者都同时包含代码准入、容量、持久化和消息协议，也都受模型结果与外部环境影响。当前源码支持的结论是“teams 不自动消费 ready 队列”，不是“没有任何中心视图或所有调度都必须语言化”。
