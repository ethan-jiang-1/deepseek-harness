# 文件块与内容块投影

源码核验入口：`packages/llm/llm/src/types.ts` 的 `FileBlock`、`packages/llm/llm/src/content.ts` 的投影函数、`packages/llm/llm/src/index.ts` 的 dispatch 边界、`packages/attachment/attachment/src/types.ts` 的 `FileAttachmentRef`。

本篇写「内容块种类」与「模型输入模态」的区别，以及文件块与图像在请求装配里的**不对称**投影。

## 两种东西

`FileBlock` 是内容块的一种，`type: 'file'`，载荷是一个 `FileAttachmentRef`（`packages/llm/llm/src/types.ts:84-90`）。`FileAttachmentRef` 是内容寻址的耐久引用：`attachmentId` 是逐字节存储内容的 sha256，另有清洗过的显示名与精确字节数；它**不是**文件系统路径，也不是 bearer URL（`packages/attachment/attachment/src/types.ts:35-45`）。本地 provider 把逐字节副本存在 attachment store 里，并用 `fileHostPath` 暴露宿主路径（`packages/attachment/attachment-local/src/index.ts:241`）。

**文件从不原生发给任何 provider。** `projectFilesToText`（`packages/llm/llm/src/content.ts:196`）在每次 dispatch 前**无条件**把 file block 替换成确定性 handle 文本，包括嵌套在 tool-result 里的内容。dispatch 边界的调用在 `packages/llm/llm/src/index.ts:1040-1056`，注释写明「Files are never dispatched natively: every route receives handle text」。

## handle 文本的两条分支

`fileHandleText(ref, readonlyPath)`（`packages/llm/llm/src/content.ts:154`）生成同一份确定性文本：文件名、字节数、`sha256:` 前 8 位，以及读取指引「按需用文件工具读这个只读副本；改之前先复制到可写位置；委派文件工作要把这个保存路径写进 delegation prompt，只有共享同一执行环境的子代理能读」。

路径无法解析时换成显式的 no-path 文本：说明当前执行环境访问不到可读路径，要求模型**报告该限制、不要声称读过**。路径解析走 `LlmRuntime.fileReadPath`（`packages/llm/llm/src/index.ts:990`）→ `ctx.attachments.fileHostPath` + `ctx.fs.processPathFromHostPath` 的结构化面；引用本身损坏时降级成 no-path handle，而不是让同一份日志之后的每个请求都失败。

`LlmRuntime.fileRequestText`（`packages/llm/llm/src/index.ts:676`）对外暴露同一文本，供 UI 与 token 记账使用（`dsh-token-meter` 用它估算文件 handle 的 token，`packages/llm/token-meter/src/index.ts:151,200-204`）。

## 与图像投影的不对称

**文件是无条件的，图像是条件式的**——这是新旧对比里最容易写反的一处：

- 文件：任何 route 都只收到 handle 文本，没有原生 file 内容。
- 图像：只有 `inputModalities` **不含** `image` 时才调用 `projectImagesForTextModel`（`packages/llm/llm/src/index.ts:1048-1052`；函数在 `packages/llm/llm/src/content.ts:302`），多模态 route 收到的是 durable attachment 引用，由序列化器解析成 provider 的图像载荷。

两者共用的递归遍历分别是 `contentHasFile`（`packages/llm/llm/src/content.ts:138`）与 `contentHasImage`（同文件 `:126`），所以嵌套 tool-result 内容的处理一致。

## 模态与内容块不是一回事

`MODALITY_GATE` 仍只有 `text` 与 `image` 两项（`packages/llm/llm-pi-ai/src/catalog.ts:47-53`），`MODALITIES` 就是这两个 key。所以「OpenRouter 的 video 输入无法在 DSH 声明」这类结论仍成立；同时 `file` 是**内容块种类**，不是模型输入模态——它不进入 `inputModalities`，也不改变任何 route 的模态门。

图像预算与 Files API 语义未变：`maxRequestFilesBytes` 默认 128 MiB、`maxInlineRequestImageBytes` 默认 20 MiB、`maxImagesPerRequest` 默认 600（配置字段 `packages/llm/llm-deepseek/src/index.ts:152-156`，常量 `packages/llm/llm-deepseek/src/request-pricing.ts:20,22` 与 `packages/llm/llm-deepseek/src/adapter.ts:151`）；超预算时 `offloadRequestImagesWithPolicy`（`packages/llm/llm/src/content.ts:354`）按最旧优先、按整数量子替换成占位文本，是请求期瞬态变换，不写回 durable log。图像编码阶梯仍由 `packages/attachment/attachment-local/src/{encoding,normalization,compression-limiter,request-image}.ts` 承担。

多 vendor 场景下这条「文件只以 handle 文本出去」的事实，见 [`../../_faq_on_digested/03_model-vendors/answer.md`](../../_faq_on_digested/03_model-vendors/answer.md)。
