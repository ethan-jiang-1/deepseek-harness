# 更新与启停：变化怎么落到运行中的树

产品源码基线：`1f81c047fc48fa190a683e469daa699857e9afe8`（`dsh-v0.2.1-rc.3`）。

## 一句话

运行期改组合只有两条路，而且它们写**不同文件**、有**不同优先级后果**：改 bundle 选择写 `package.json` 的有序列表，改单行开关写 `cordis.patch.yml` 的 `disabled`。把两者混为一谈，是插件管理面最容易出错的地方。

## 行级启停：只改一个字段

`setPluginEnabled`（`packages/boot/plugin-manager/src/index.ts:492`）改的是单个 entry 行，规则三条：

1. 在 profile 的 `cordis.patch.yml` 里定位**最后一条匹配**的 override。匹配用 entry id，加上任何模块名断言。
2. 只改 `disabled` 这一个字段。
3. 如果一条 override 只剩 `id` 与 `disabled`，而 bundle 层加剩余 patch 已经给出用户想要的状态，**这条 override 会被删掉**，也不再追加。

第 3 条决定了这个文件的性质：`cordis.patch.yml` 只记录「与 bundle 层之间的偏离」。用户把一个出厂开启的行关掉，文件里出现一条 override；再打开回去，override 消失，文件回到干净状态。

比较时**排除 home 层与命令行 patch**——它们排在 profile patch 之后，优先级更高，不参与「profile 该记录什么」的判定。

## bundle 级启停：改的是顺序

bundle 开关（`setBundleEnabled`，`packages/boot/plugin-manager/src/index.ts:510`）改的是 `package.json` 里 `dsh.profile.bundles` 的**有序**列表：

- **关掉只取消选择，不删依赖。** 包还在，随时可以再打开。
- **打开是追加到末尾。** 于是它会排在已有 bundle 之后，**可能改变配置优先级**——同一个 entry id 被两层都配置时，后者的整份替换生效。
- 安装一个新 bundle 默认就是启用，同样追加到末尾。

这条「追加即降级」是 bundle 开关唯一的非直觉后果。它不出现在任何 UI 的显式提示里，只在行为上成立。

## 更新：先移除，再安装

没有「就地升级」。显式更新等于「按当前选择移除已装的包，再装目标版本」：

| 情形 | 结果 |
|------|------|
| 有 HMR，包在运行中 | 先移除已装包（插件先停），再装新的；选择保留 |
| 无 HMR，包已跑过 | 移除不允许，于是**覆盖安装**，并报告 `restart-required` |
| 移除后安装失败或取消 | 包处于未安装状态；不会自动恢复旧版本 |
| 重装成功 | 该 bundle 落到选择列表的**末尾** |

`installBundle` 里那条 HMR 特判就是这个顺序的来源：装了 `hmr` 时，同名包已存在会直接判 `already-installed`（`packages/boot/plugin-manager/src/index.ts:541` 的注释「With HMR, an installed package is removed before another version is installed, so its plugins stop first」）；没有 HMR 就没有这条限制，代价是需要重启。

## 一条串行队列

运行期的写入不并发。模块热替换与 profile 配置重载共用同一条串行队列 `runExclusive`（`packages/boot/hmr/src/index.ts:268`），文件监视统一走 `watchConfig`（`:289`，同一队列，重复路径抛错，watcher 失败只记日志不致命）。

插件管理器的写路径从这条队列过（`packages/boot/plugin-manager/src/index.ts:852`），配置编辑器也一样（`packages/boot/config-editor/src/index.ts:153`）。**包操作在队列之外**——pnpm 是长任务，把它塞进配置队列会让热更新停摆。

于是运行期有三层互不相同的同步：

| 层 | 机制 | 谁在里面 |
|----|------|----------|
| 包操作 | profile 写锁（`lockWaitMs` 默认 120000ms） | 安装、移除、pnpm |
| 配置写入 | `hmr.runExclusive` 串行队列 | 模块热替换、patch 重载、行开关、配置编辑器 |
| 树内变更 | effect 撤销与 fiber 重载 | 插件自己的注册与监听 |

## 配置重载的失败策略

`reconcileProfilePatches`（`packages/boot/app-boot/src/index.ts` 内，HMR 调用）的原则是**只对新引入的失败大声**：

- 本次刷新**新引入**的失活条目 → 抛错。
- 启动时就存在的失败 → 逐条 warning，返回给调用方，不打断进程。
- 候选失败不提交，正在服务的树继续用旧 patch 集。

成功后 `emit('app-boot/config-reload')`，事件不带 diff 也不带解析后的配置。机制细节见 [`composition-boot/03`](../composition-boot/03-user-patch-hmr.md)。

## startup-only 面的限制

headless、sdk、acp 的 `hmr` 行显式关断（[`00-map`](./00-map.md) 的分叉表）。在这些面上：

- 改配置只在下一次启动生效。
- 移除正在运行的包不被允许——它撑起了当前进程；要用 `dsh plugin` 在进程外改。
- 更新一律需要重启。

这不是缺陷，是「一次性表面」的定义：它们本来就只为跑完一件事而存在。
