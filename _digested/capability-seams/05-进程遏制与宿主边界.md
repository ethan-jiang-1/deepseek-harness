# 进程遏制与宿主边界

源码核验入口：`packages/subprocess/subprocess-local/src/`（`linux-scope.ts`、`linux-execve.ts`、`windows-job.ts`、`spawn-runner.ts`、`runner-protocol.ts`、`runner-launch.ts`、`managed-owner.ts`、`terminal.ts`、`process-inspector.ts`、`windows-inspector.ts`）、`native/system/`、`packages/util/http-proxy/src/`。

本篇说明 dsh 里三处**不可替换**的宿主边界：子进程的 OS 级所有权、本仓库自己的 native 源码层、以及进程级出站策略。它们都不是三角色 seam——没有第二个实现可换，作用域是进程或宿主——但决定了本地执行世界的安全半径。

## 为什么单列：它们不是能力 seam

一条 seam 要有 Definition / Provider / Consumer 三个角色，替换 provider 就换一套后端。以下三者都不满足：进程遏制由 `dsh-subprocess-local` 在 spawn 请求上一次性选定，没有第二条实现路径；`native/system` 是预编译二进制的来源，按平台固定；出站策略每个进程只有一个答案（`packages/util/http-proxy/README.md` 明说它是 library 而非插件，理由正是「没有第二实现可换，也没有比进程更窄的作用域」）。判断一个 `ctx.<key>` 时，这三条都是「spine 之外但不属于 seam」的样本。

## 子进程的 OS 级所有权

`dsh-subprocess-local` 是 `ctx.subprocess` 的本地 provider。它**无配置**：每个处置、上限、终端尺寸与宽限期都随 spawn 请求到达，部署可变的选择留在调用方的配置里（见 [`02-一次bash从tool到sandbox.md`](./02-一次bash从tool到sandbox.md)）。

每次 spawn **同步**校验最终 argv、cwd 与环境，在用户命令可能运行之前就选定遏制方式，并返回一个 handle，而目标身份保持私有。关键设计是**一次 spawn 只选一个 owner，同时负责发信号与静默**：

| 平台与形态 | owner |
|---|---|
| Linux 普通启动与终端会话 | 瞬态 user-systemd scope（`systemd-run --expand-environment=no`）；scope 拥有被 reparent 或 `setsid` 的后代，同时保留 node-pty 的 PID、会话首进程、控制终端与前台 `inputWaiting` |
| Windows 普通启动 | helper 持有的 kill-on-close Job（native 支持可用时） |
| macOS、不可用的 user-systemd、不可用的 Windows native | 降级的进程组 / `taskkill` / 终端会话观察，附一条 warning |

**原生路径一旦可能已经启动过命令，就绝不改走降级重放**——否则同一个命令可能被执行两次。

Linux 的启动经一条私有一次性请求：scoped bootstrap 恢复目标 cwd 与环境、解析可执行文件、清掉 fd 0–2 的 close-on-exec，再用原始 argv 进入 libc `execve()`（`linux-execve.ts` 持有该绑定）。Windows 普通启动隔离 runner 的 fd 0–2，把 fd 3 留给 IPC，目标 stdio 走 fd 4–6；runner 把 CRT 描述符解析成 OS 句柄，**挂起**创建目标、把它分配给 Job、再恢复，最后只关掉载体描述符。

`done` 在 stdio 屏障之后结算直接命令；`waitForExit()` 单独等待所选 scope / Job / 进程组 / 观察到的会话变为空。两者是不同的承诺：命令结束不等于后代全部收敛。

**逃逸是明确的边界而非被掩盖的洞**：降级 owner 只能从有根进程树与可观察会话取回精确身份，无法找回每一个逃逸后代；Windows Job 的 breakaway 进程在保证之外；目标只在 Job 分配之后才启动。native 模式改为靠 scope 成员关系**连续持有**这些后代，而不是加一个持续轮询的进程表监视器。

宿主退出时（JavaScript 可观察的退出——直接的 `process.exit()`、默认未捕获异常、默认未处理 rejection）同步收尾：要求 Linux scope 杀掉成员，杀掉 Windows runner 使其唯一的 Job 句柄关闭，降级路径用既有 PGID / `taskkill` / 捕获身份操作。它**不创建 promise 或 timer**、保留宿主退出码与诊断、且不声称静默。`SIGKILL`、致命 OOM、native 崩溃与断电需要外部 supervisor。

## native 源码层

`native/system/`（`@deepseek-ai/node-addon-system`）是本仓库 native 源码的 source of record。平台包内含**预编译**二进制，消费者安装时永不编译 native 代码。它对外只有两个入口，各自服务一个消费方：

| 入口 | 导出 | 消费方 |
|---|---|---|
| `@deepseek-ai/node-addon-system/landlock-run` | `launcherPath`、`probe`、`grantArgs` | `packages/sandbox/sandbox-local`（Landlock 策略与 Session 生命周期留在调用方，见 [`02-一次bash从tool到sandbox.md`](./02-一次bash从tool到sandbox.md)） |
| `@deepseek-ai/node-addon-system/flock` | `tryLockExclusive(fd)` | `packages/session/session-persistence-jsonl`（见 [`../session-and-loop/04-持久化seam与互斥写.md`](../session-and-loop/04-持久化seam与互斥写.md)） |

导入任一个入口都**不会加载 addon**：`landlock-run` 是可执行文件（缺失即探测为不可用），`flock` 是惰性绑定（缺失即拒绝获取）。两条路径都不编译、也不静默授予不受支持的行为。

平台覆盖：Linux x64/arm64 含静态 Landlock 可执行文件与 glibc/musl 两份 `system.node`；macOS x64/arm64 只有 `system.node`；Windows 走 Harness 既有的锁实现。Landlock 额外要求内核处于 enforcing 状态。根门禁 `pnpm run build:native-system` 只构建当前宿主的 addon，供源码测试使用。

## 出站策略

`packages/util/http-proxy/` 把一条出站 HTTP 代理策略施加到所有走 Node 内置 `fetch` 的 Harness 请求——LLM、web search、HTTP MCP 都在内。`dsh` launcher 在第一个插件加载之前就解析并安装策略，所以导出 `HTTPS_PROXY` 的用户在所有 profile 里都被代理。

策略读 `http_proxy`、`https_proxy`、`no_proxy`、`all_proxy`，小写优先、大写兜底、空值视为未设置，来源是 launcher 的快照（先导出变量，再 `$DSH_HOME/.env`）。**项目的 `.env` 不能携带这些名字**：该文件随 clone 到达，launcher 宁可拒绝启动，也不让一个仓库决定 harness 把流量发到哪里。loopback 始终直连。无法使用的代理值（SOCKS、PAC、不可解析、不支持 scheme）被报告并跳过，该 scheme 直连——变量可能是为别的工具导出的，不能因此让 agent 起不来。

**解析器只有一个**：安装的 dispatcher 是逐 origin 调用 `proxyForUrl()` 的 `Agent`，不存在第二个会漂移的解析器。`new Agent(...)` 作为 `dispatcher` 会静默绕过全局 dispatcher，所以门禁 `verify-no-bare-dispatcher` 拒绝本包之外出现它；唯一豁免的调用点是 `web-fetch-http`（它把请求钉在自己校验过的地址上，是进程级 dispatcher 无法持有的逐请求状态），用行内 `proxy-exempt:` 注释声明。

该门禁只看得见源码，看不进 SDK 内部（OTLP exporter 走 `node:http`、E2B SDK 自建 undici dispatcher，两者都是这么发现的），所以每个出站调用点还带一个 `egress.spec.ts`，驱动真实代码路径穿过假代理并断言代理确实看到了请求——遥测是唯一反例，因为确认它**没有**被代理。新增调用点就要加一个。遥测按设计直连；`code-runtime` 与 `workflow` worker 不获得任何代理配置，因为它们运行模型写的脚本。
