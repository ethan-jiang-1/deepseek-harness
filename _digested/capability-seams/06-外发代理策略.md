# 外发代理策略：一条进程级策略，不是 seam

本页记录上游同步 0006（`0.1.2-rc.1` → `0.1.5-rc.1`）新增的外发 HTTP 代理机制。核验入口：`packages/util/http-proxy/`、`apps/cli/src/profile-boot.ts`、`packages/boot/app-boot/src/index.ts`。它是「刻意不成 seam 的进程级库」这一形状的样本，与 [`04-新增seam与Remote.md`](./04-新增seam与Remote.md) 的 Remote、`00-map.md` 里的 schedule 并列。

## 结论先行：它刻意不是 seam

`packages/util/http-proxy/` 是 `util/` 组里的一个库，不是插件、不是 `ctx.<key>`、没有可替换后端：传输策略每个进程只有一条答案，没有第二种实现可换，也没有比进程更窄的作用域可以授予。上游 Agent Note 把「Make this a capability seam」列为考虑过并否决的方案（[`2026-08-27-outbound-proxy-policy.md`](../../.agents/notes/implemented/architecture/2026-08-27-outbound-proxy-policy.md)）。它导出四个函数与一个类型（`packages/util/http-proxy/src/index.ts:17`）。包内分两层：`src/policy.ts` 是纯解析与匹配，不 import 任何传输，浏览器 Worker 里也能装载；`src/install.ts` 动态 `import('undici')`，只在装全局 dispatcher 时需要 Node 传输。它带一个外部依赖 `undici`，这不违反 `util/` 的定位——该组的要求是「任何组都可以依赖 util」，而不是禁止 util 依赖外部包。

## 四个导出函数

| 函数 | 位置 | 谁需要它 |
|---|---|---|
| `installProxyFromEnvironment(env, report)` | `packages/util/http-proxy/src/install.ts:296` | launcher：解析、报告、安装一步完成，返回还原上一份 dispatcher、策略与环境的 disposer |
| `proxyRouteFor(url)` | `packages/util/http-proxy/src/install.ts:62` | 要按「这一个请求是否走代理」分叉的调用方；代理臂同时交回已经在按该策略路由的 dispatcher（类型 `:49`） |
| `proxyEnvironmentForChild()` | `packages/util/http-proxy/src/install.ts:262` | 自己拼子进程环境的 spawner；`undefined` 表示删除该名字 |
| `clearedProxyEnv()` | `packages/util/http-proxy/src/install.ts:313` | 回放型宿主：清空八个代理名，去自己的 fixture server 而不是开发机的代理 |

`ProxyRoute` 的代理臂携带 dispatcher，而不是只给一个代理 URL，是为了关掉一类缺陷：先读策略决定是否 pin、再读一次策略建传输，两次读取之间发生卸载，就会把第一次读取判为「走代理」的 URL 交给直连、未 pin 的传输。一个 route 同时决定分支与传输，两者不可能不一致。解析入口是 `resolveProxyPolicy(env)`（`packages/util/http-proxy/src/policy.ts:306`）；它只要求一个 `get(name)` 形状的 `EnvLookup`（`:16`），launcher 的环境快照结构化满足，包因此不点名任何 harness 包。

## 唯一安装点：`runProfile` 的第 0 步

安装发生在 `runProfile` 内、第一个插件挂载之前（`apps/cli/src/profile-boot.ts:287`），shutdown 时 `disposeProxy()` 还原（`:295` 起的关闭闭包）。解析来源是 launcher 的 environment snapshot，**不是** `process.env`：`$DSH_HOME/.env` 里的代理因此能生效——Node 的 `NODE_USE_ENV_PROXY` 在进程启动时采样环境，看不到之后才合并的 `.env` 层（同文件 `:283`-`:286` 的注释）。`loadLayeredEnv` 只有一个调用者，`apps/web` 也不带 bin，所以这一个点覆盖包括 `sdk-minimal` 在内的全部 profile。旧基线里的 `NODE_USE_ENV_PROXY` 曾由 `bin/dsh` 设置又被删除，只在 `apps/cli/reference/README.md` 留下一句无人消费的说明；新基线删掉那句话，机制由这里真正装上，用户文档改由 `docs/user/guide/network-proxy.md` 承载。

## `.env` 层的例外只开给 home

四个代理名 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY` 仍在 bootstrap-only 名单里（`packages/boot/app-boot/src/index.ts:93` 起），project `.env` 照旧拒收：那个文件随 `git clone` 到达，不该由仓库决定 harness 的流量去哪里。例外是 home 层：`HOME_LAYER_PROXY_NAMES` 定义（`:126`），判定 `if (isHome && proxyName) continue`（`:170`），报错信息也给出第二条出路——导出变量，或写进 `$DSH_HOME/.env`。`DSH_HOME` 本身是 bootstrap-only，没有 `.env` 能把这份豁免指向一个仓库可控的目录；同一组里的 CA 与 TLS 名字仍然处处拒收，它们改变的是「信任谁」，不是「流量去哪」。

## 策略语义

小写名优先、大写兜底；`ALL_PROXY` 同时供两个 scheme，HTTPS 最后回退到 HTTP 代理；空值视为未设置（否则空的小写名会遮蔽有值的大写名）。loopback 永远绕行——Web UI、Connection 传输和每个本地测试服务器否则都会绕回自己。无法使用的值（SOCKS、PAC、畸形、不支持的 scheme）被报告并跳过，该 scheme 直连，**不会**落到 `ALL_PROXY` 或 HTTP 代理；诊断只点名变量，绝不回显值，因为代理 URL 可能带 `user:password`。

## 覆盖到哪里

全局 dispatcher 覆盖所有走到 `globalThis.fetch` 的请求：模型请求、web search、MCP over HTTP，以及任何以后新增的普通 `fetch()` 调用点，都不需要改代码。

两个 SDK 走不到 `globalThis.fetch`，因此各有安排。E2B SDK 自己建 undici dispatcher，改为读 `route.proxy`（`packages/e2b/e2b/src/index.ts:159`，判定针对 SDK 真正会调的那个 URL）。OTLP 遥测**刻意保持直连**：它走 `node:http`，路由它要么依赖版本更高的 `proxyEnv`，要么换成不带压缩的 `fetch` 传输、与 shipped profile 的 gzip 冲突；遥测是唯一一条丢失对用户无损的通道。`packages/session/session-telemetry-otel/tests/egress.spec.ts` 因此是**反向断言**：装了策略代理，假代理仍然看不到请求——SDK 哪天改用 `fetch`，这条测试会发现。

子进程继承走 `scrubbedParentEnv()`：在清掉凭证形状名字与 `DSH_*` 之后，叠加解析后的代理名与 `NODE_USE_ENV_PROXY` 标志（`packages/subprocess/subprocess/src/index.ts:73`），MCP stdio server 与 subagent CLI 因此与父进程同样路由。若子进程拿到的某个值正是本包拒绝过的（例如留给 `curl` 的 SOCKS URL），标志被**收回**：Node 在那个标志下会在运行程序前解析 `HTTP_PROXY` / `HTTPS_PROXY` 并因非 `http(s):` scheme 直接退出，收回后子 Node 直连，而 `curl` 仍能读到原值。刻意排除的还有两类执行模型代码的 worker：workflow worker 与 code-runtime worker 都拿不到代理配置——代理 URL 可能带凭证，而它们跑的是模型写的脚本。

`web_fetch` 是本次唯一改变对外安全承诺的地方：直连跳保留地址校验与 pinning；代理跳由代理做 DNS 与选路，不再 pin（pin 一个本地解析出的地址会直连并绕过代理）。分支由 `proxyRouteFor` 一次决定（`packages/web/web-fetch-http/src/provider.ts:134`），代理跳走 `requestVia(route.dispatcher, …)`（`packages/web/web-fetch-http/src/network.ts:229`）。URL 级策略不变：只允许 `http(s)`、不内嵌凭证、长度上限、跨源重定向拒绝，每一跳都仍执行。

## 门禁与逐调用点证据

`scripts/verify-no-bare-dispatcher.ts:36` 定义注解标记 `ALLOW_MARKER = 'proxy-exempt:'`，门禁注册为根 `package.json:135`。它按 AST 检查 `packages/*/*/src` 与 `apps/*/src`：构造 undici agent，或给 `fetch` 传显式 `dispatcher`，在本包之外一律拒绝——显式 dispatcher 会盖掉全局那个，正是 `web-fetch-http` 在代理支持存在前就有的缺陷。唯一合法豁免是 `web-fetch-http` 的 pinning（`packages/web/web-fetch-http/src/network.ts:202`、`:236` 各有 `proxy-exempt:` 注解），因为「把这一请求钉在刚校验过的地址上」是进程级 dispatcher 装不下的逐请求状态。

门禁看不进第三方 SDK，所以每个外发调用点还各带一个 `egress.spec.ts`，把该点的真实代码路径打到不可解析的 `.invalid` 主机、经过一个假代理，断言代理确实看到了请求。现役 10 个：`packages/subprocess/subprocess/tests/egress.spec.ts`、`packages/mcp/mcp-client/tests/egress.spec.ts`、`packages/session/session-telemetry-otel/tests/egress.spec.ts`、`packages/e2b/e2b/tests/egress.spec.ts`、`packages/workflow/workflow-worker-thread/tests/egress.spec.ts`、`packages/web/web-search-exa/tests/egress.spec.ts`、`packages/web/web-search-perplexity/tests/egress.spec.ts`、`packages/web/web-search-deepseek/tests/egress.spec.ts`、`packages/llm/llm-deepseek/tests/egress.spec.ts`、`packages/llm/llm-pi-ai/tests/egress.spec.ts`；`web_fetch` 的双形态另由 `packages/web/web-fetch-http/tests/proxy.spec.ts` 覆盖。新增外发调用点时，这条测试要与调用点一起加。
