# 特殊初始化：只发生一次的事

产品源码基线：`1f81c047fc48fa190a683e469daa699857e9afe8`（`dsh-v0.2.1-rc.3`）。

## 一句话

启动可以重复跑，特殊初始化不能——而且启动**确实会写盘**（首次创建 profile、清掉退休 bundle、导入旧设置），所以两者的区别不在「有没有副作用」，在「副作用有没有一次性凭据」。DSH 里有一类动作**只跑一次，跑完之后必须留下凭据**：文件的首次创建、旧格式的一次性导入、版本戳的第一次写入。判据三条——只发生一次、发生后有可判定的凭据、失败时的正确处置是「保留旧状态」或「拒绝」，而不是重试。

这页把这些动作收在一起，因为它们散落在四个不同的包里，却共享同一条风险：**重入一次就可能覆盖用户数据**。

![四个一次性实例与它们的凭据](./figures/05-one-shot-instances.svg)

## 四个实例

| 实例 | 触发点 | 一次性凭据 | 失败处置 |
|------|--------|------------|----------|
| profile 首次创建 | 第一次用到某个 profile 名 | 文件已存在即不写 | 保留已有文件，不覆盖 |
| 旧 `settings.yaml` 导入 | Settings 启动、Loader 结算之后 | 先改名成 `.imported` 再写 | 被组合拒绝的段落只留在改名后的文件里 |
| 存储版本戳 | 后端首次打开数据库 | `PRAGMA user_version` | 非当前版本**拒绝打开**，不原地迁移 |
| desktop 运行树与首启设置 | 应用启动 | `desktop-runtime.json` 与文件是否存在 | 校验失败进原生恢复；缺文件才创建 |

判据的第三项最容易被忽略：**没有凭据的动作不是一次性动作**，它可以随便重跑；而既有凭据又允许重跑的动作，凭据就是假的。下面四条逐个说明凭据长什么样。

## profile 首次创建

`initProfile`（`packages/boot/app-boot/src/profile.ts:262`）写三份文件：`package.json`（`dsh.profile.bundles` + 空依赖）、`cordis.patch.yml`（内容只有模板注释加 `[]`）、hoisted 的 `pnpm-workspace.yaml`。**已有文件一律不覆盖**——这条是这个函数唯一的安全保证，也是它能被反复调用的原因。

凭据就是「文件在不在」。所以这个动作严格来说不是「只跑一次」，而是「只写一次」：重复调用安全，因为它什么都不写。

谁来触发见 [`composition/04`](../composition/04-profile-创建与保留名.md)：shipped 名自动初始化，自定义名走 `--from-default-profile` 或 `dsh plugin`。三条路径最后都落到这个函数。

## 旧 `settings.yaml` 的一次性导入

这是全仓最干净的一例「一次性」实现（`packages/settings/settings/src/index.ts:238`–`:257`）：

```text
Loader 结算完每个 entry
  → 发现 $DSH_HOME/settings.yaml
  → 先 rename 成 settings.yaml.imported
  → 再按段落写进同 id 的 entry
```

顺序是刻意反的：**先改名，再写**。这样导入中途崩溃也不会重复导入——文件已经不在原位，`settings.yaml.imported` 本身就是「已尝试过」的凭据。被运行中的组合拒绝的段落记一条 warning，只留在改名后的文件里，不会因为导入失败而回滚已成功的段落。

段落名到 entry id 有历史映射（`LEGACY_SECTION_ENTRIES`，`:201`）：`ui-developer-tools` → `ui-settings`、`ui-onboarding` → `ui-settings-general`、`shell` → 当前平台的 shell 执行器行。映射的存在本身就是「旧世界只来一次」的证据。

## 存储：没有迁移，只有接受集与拒绝

存储层常被误读成「会迁移」。实际是三层各自独立的判定：

| 层 | 凭据 | 旧值的处置 |
|----|------|------------|
| 库文件 | `PRAGMA user_version`（`packages/storage/storage-sqlite/src/schema.ts:20` 的 `STORAGE_SQLITE_SCHEMA_VERSION = 1`） | 0 才打戳；其它非当前版本**拒绝打开** |
| 域 | 域声明里的 `version` 与 `compatibleVersions`（`packages/storage/storage-domain/src/spec.ts:39`、`:56`） | 列出的旧版本被**接受**（不是迁移）；写入永远打当前版本 |
| 单条记录 | 记录文档自带的版本戳 | 不在接受集里就**丢弃**，从不迁移（`:45`） |

记录层与「迁移」的差别只在语义：接受集是声明方对「旧字段仍满足当前 schema」的担保，改动仍然只在写入侧发生。另有 `invalidRecords` 选项让坏记录走 `backup-and-skip`（`:67`），默认仍是整个 `open` 以 `invalid-record` 拒绝——默认值总是偏保守的那一侧。

一句话：**DSH 不替用户猜旧数据的意思**。能接受就接受，不能接受就拒绝或丢弃，不写转换代码。

## desktop：运行树与首启设置

desktop 的一次性动作发生在 Host 起来之前：

1. 外壳校验 `desktop-runtime.json`——它绑定壳版本、Electron 的 Node 版本、平台架构、共享包版本与最终文件清单（`apps/desktop/src/runtime-tree.ts:12`）。
2. 准备 profile：创建缺失的清单、空用户 patch 与 pnpm workspace 文件，**不修改已装包、不跑 pnpm**。
3. 首次启动创建 `desktop/settings.json`（`apps/desktop/src/settings.ts:26`），已存在就永不覆盖；未知字段保留。

第 2、3 条与 `initProfile` 是同一条纪律的三次实现：**只补缺失，不改内容**。它们的凭据都是「文件是否已存在」，而不是某个完成标记。

## 什么不算一次性

用上面三条判据筛，两个常被误算进来的动作其实不满足：

| 动作 | 为什么不是 | 它是什么 |
|------|------------|----------|
| Session 格式世代转换 | 读时流式转换，幂等，没有持久凭据，可重复执行 | 版本适应性读取，机制见 [`session-and-loop/04`](../../session-and-loop/04-格式世代与迁移.md) |
| `appReady` 就绪信号 | 不写任何东西，只表示「现在可以开始」 | 闸门，见下 |

Session 上那个 `formatStatus: 'migration-required'` 也不是「待执行的迁移任务」，而是「这条冷 Session 还没被打开过」的投影提示：分叉一条旧格式的 Session 之前必须先打开源 Session（`packages/api/session-controller/src/index.ts:446`），打开这个动作本身完成转换。它没有把任何东西标记成「已迁移」。

## `appReady`：闸门，不是初始化

`appReady` 由 launcher 经 `provideCmdline({ ready })` 提供（`packages/boot/cmdline/src/index.ts:88`），`runProfile` 在根 fiber `ACTIVE` 且 loader 在场时提交一次。HMR 拿不到它就抛 `Profile HMR requires application readiness`，不挂 watcher（`packages/boot/hmr/src/index.ts:369`–`:370`）。

它挡住的是「初始化还没完成就开始热更新」这一类竞态。desktop 与 webworker 宿主因此天然命中这条闸门。

## 反面事实：没有统一的插件迁移钩子

DSH 不提供插件级的「一次性初始化 / 数据迁移」扩展点。想跑一次性的东西，只有三条现成路子：

1. 用 `ctx.effect` 在 `apply` 里做幂等检查，自己保证幂等（凭据自己造）。
2. 依赖存储层的接受集语义——但当前后端只接受或拒绝，不做转换。
3. 走产品级的相邻迁移库那一套（只对 Session 格式开放，且是读时转换）。

这条缺口是真的，别在插件里假装有一个 `migrate()` 会被调用。
