# 分发：包怎么到达机器

产品源码基线：`1f81c047fc48fa190a683e469daa699857e9afe8`（`dsh-v0.2.1-rc.3`）。

## 一句话

包到达机器有四条 spec 通道和三个目录档位。通道决定「怎么装、失败能不能回退」，目录决定「用户在哪里看到它」。两者互相独立：按需档里的包走的是和第三方包完全相同的登记通道。

## 四条 spec 通道

`InstallSpecKind` 是 pnpm 词汇表里的四种形态（`packages/boot/plugin-manager/src/types.ts:184`）：

| 通道 | 例子 | 装了之后依赖写成什么 |
|------|------|----------------------|
| `registry` | `@example/hello-plugin`、`@example/hello-plugin@1.2.3` | 版本范围或 tag；官方按需安装用 `saveExact: true` |
| `path` | `./hello-plugin`、绝对路径 | `link:` 到该目录 |
| `tarball` | `./hello-0.1.0.tgz` | `file:` |
| `git` | `github:you/hello-plugin#<sha>` | git 地址原样记录 |

四条通道的差异集中在两点：**取的是产物还是源码**，以及**批准发生在什么时候**。registry 与 tarball 是预构建产物，装完即可用；`path` 与 `git` 取的是源码，前者依赖检出里已有的 `lib/`，后者必须在安装期跑 `prepare`（[`01-打包.md`](./01-打包.md)）。构建批准在任何通道上都可能被要，但只有 `git` 必然触发。

官方按需安装的来源由运行中的 Host 给出（`packages/boot/plugin-manager/src/official-install-target.ts`）：发布安装提供 `package@<当前 DSH 版本>`，源码 Web 与开发态 Desktop 提供 `link:<工作区包目录>`。所以同一次点击在两种部署里装到的东西不同——即使版本号相同，registry 副本与另一个检出之间也可能需要互相替换。

## 三个目录档位

| 档位 | 规模 | 交付方式 | 用户在哪看到 |
|------|------|----------|--------------|
| 官方可选档 `OPTIONAL_BUNDLES` | 12 | **随安装出货**，默认关断 | Web Plugins 页的实验插件列表，一键开关 |
| 官方按需档 `ON_DEMAND_BUNDLES` | 2 | **不随安装出货**，按需拉取 | 离线也可见的卡片，点开触发安装 |
| 市场索引 | 部署自定 | 用户的索引文件 | Plugins 页的 Discover 页签 |

可选档的两个性质容易读错：它**随装出货**、**不可移除**、**默认关断**，且没有任何 shipped 模板选中它（`packages/boot/app-boot/src/profile.ts:223`–`:236` 的十二条）。按需档正好相反：不随装出货，卡片信息来自构建期生成的目录而不是 registry 查询（`packages/boot/app-boot/src/official-bundle-packages.ts:4` 的两条），但安装动作走的是同一个 `installBundle`，没有第二条安装路径。

市场是第三种：`pluginMarket` 读并校验用户配置的索引，标注安装状态与 DSH 兼容性，但真正的安装仍然调用 `pluginManager.installBundle`。索引只是一份菜单，不是一条安装通道。

## registry 的选择与回退

registry 配置类型是 `string | null`，`null` 表示「pnpm 自己配置里那个」（`packages/boot/plugin-manager/src/types.ts:92`）。实际会问的集合由三部分组成，顺序固定（`types.ts:96`–`:99`）：

```text
配置的 registry（先）
  → fallbackRegistries（默认 ['https://registry.npmmirror.com/']）
  → pnpm 自己配置里那个（只有它指向 npm 官方或上面某个回退时才加入）
```

两条容易踩的机械规则：

- **私域 registry 不回落**。配置集之外的 registry 单独问，问不到就报错，不会顺流到公共 registry。
- **查找与安装的重试策略不同**。查找用 `pnpm view` 且禁用 pnpm 自身的重试，让一个死掉的 registry 在 `inspectTimeoutMs` 内就报出来、轮到下一个；安装保留 pnpm 自己的重试设置。

回退只对「另一个 registry 可能改变结果」的失败生效：网络不通、超时、以及「没有这个包或这个版本」。镜像同步滞后属于这一类。git 与 tarball 没有回退可言，失败点直接报 `failedAt: 'spec-host'`。

## 装之前先看清楚

`inspect` 读的是一个 spec 命中什么，不装任何东西（`packages/boot/plugin-manager/src/index.ts:408`）。registry 名字经 `pnpm view` 在 profile 目录里问，所以同一套代理与认证配置生效；绝对路径读它自己的 `package.json`；git 与 tarball 只回答形态和来源主机。

结果里的 `problem` 是封闭枚举（`types.ts:187`–`:194`）：`invalid-spec`、`already-installed`、`not-found`、`not-a-package`、`not-a-bundle`、`network`、`unknown`。其中 `not-a-bundle` 描述的是「包存在、能装，但没有 `dsh.bundle` 声明」——它会被装成普通依赖，激活不了任何行。

## git 通道的预检

git 地址在启动 pnpm 之前先做一次 `git ls-remote`（`packages/boot/plugin-manager/src/github-connection.ts`），默认 5000ms（`githubConnectionTimeoutMs`）。这个预检**只限这一步**：它关掉凭据助手与交互提示，只有网络失败与超时才中止安装；认证错误、仓库不存在等留给 pnpm，包括它自己的 HTTPS→SSH 回退。

一个可达的仓库仍然可能在下载、`prepare` 或 bundle 校验阶段失败。预检消除的是「白等一次下载」，不是「安装一定会成功」。
