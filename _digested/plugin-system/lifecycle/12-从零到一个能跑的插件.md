# 从零到一个能跑的插件：六条命令

产品源码基线：`b830ec950faba0a46dda564be3e2d854afed94f1`（`dsh-v0.2.1-rc.5`）。本篇整条链在隔离 `DSH_HOME` 上跑过，输出为实测原文。

## 一句话

从一个空目录到「一个真的能跑起来的插件行」，只需要六条命令；每一步都有**可判定的产物**，所以不必等到最后才知道对不对。这条链同时是最小验收标准：任何插件交付物都应该能在这六步里走完。

## 六步

| # | 做什么 | 命令 | 你应该看到 |
|---|---|---|---|
| 1 | 建一个**有表面的** profile | `dsh --profile demo --from-default-profile web --dump-default-config` | 输出以 `# == @deepseek-ai/dsh-base` 开头，说明 base 已叠上 |
| 2 | 写三份文件 | 见下节 | 目录里有 `package.json`、`cordis.patch.yml`、`index.js` |
| 3 | 装进 profile | `dsh plugin --profile demo add /path/to/plugin` | `+ <pkg> 0.0.1 <- …` 与 `Done` |
| 4 | 确认进了层列表 | 看 `$DSH_HOME/profiles/demo/package.json` | `dependencies` 与 `dsh.profile.bundles` 各出现一次 |
| 5 | 确认 patch 真的插进了行 | `dsh --profile demo --dump-config \| grep -A3 <row-id>` | `# == <pkg>` 层注释 + `- id: <row-id>` |
| 6 | 真启动 | `dsh --profile demo --no-open --port 0` | `dsh web: http://127.0.0.1:<port>/?token=…`，且 stderr 里没有 `did not activate` |

第 1 步为什么用 `--from-default-profile web` 而不是直接 `dsh plugin`：`dsh plugin` 对自定义名字只初始化 **base**，base 没有表面，装完也起不来一个你能看见的界面。要验证「跑起来」，profile 里必须有 `web-app`（或 headless / sdk / acp 之一）。

## 最小 bundle：三份文件

```json
{
  "name": "dsh-demo-plugin",
  "version": "0.0.1",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } },
  "engines": { "dsh": ">=0.2.0 <0.3.0" }
}
```

```yaml
- insert:
    - id: demo-row
      name: dsh-demo-plugin
      config:
        hello: world
```

```js
export const name = 'demo'
export function apply(ctx, config) {
  // 这里才是插件代码第一次运行的地方
}
```

三个字段各自负责一件事，缺一个都会在后面的步骤里暴露：

- `dsh.bundle.patch` —— 没有它，包只是普通依赖：第 4 步 bundles 列表不会有它，第 5 步 dump 里也不会有行。
- `engines.dsh` —— 没有它就没有准入约束；写错范围会在第 3 步被**拒绝安装**（见下）。
- `insert` —— 写裸 `- id: demo-row` 是 override target，第 5 步只会得到 `patch: entry "demo-row" not found`。

## 实测原文（T）

```text
$ dsh plugin --profile demo add /tmp/dsh-demo
+ dsh-demo-plugin 0.0.1 <- ../../…/tmp/dsh-demo
Done in 232ms using pnpm v11.28.5

$ dsh --profile demo --dump-config | grep -A3 demo-row
# == dsh-demo-plugin
- id: demo-row
  name: dsh-demo-plugin
  config:
    hello: world

$ dsh --profile demo --no-open --port 0
dsh web: http://127.0.0.1:54977/?token=…
（stderr 中 `did not activate` 计数为 0）
```

反面也实测过：把 `engines.dsh` 写成 `>=9.0.0` 后执行第 3 步，输出是

```text
dsh: installation rejected: Plugin dsh-bad-plugin@0.0.1 is incompatible with dsh 0.2.1-rc.5: requirements {"engines.dsh":">=9.0.0"} …
dsh: nothing was installed.
```

随后检查 profile：`dependencies` 为空、`dsh.profile.bundles` 只有 base。**拒绝发生在写依赖之前**，这是第 3 步可信的原因。

## 走完之后的三条分叉

| 你想 | 换哪一步 | 后果 |
|---|---|---|
| 发给别人装 | 第 3 步的 spec 换成 registry 名或 tarball | 本地 `link:` 只在本机有效；git 源要 `prepare` + 用户批准构建 |
| 不要 web，要一次性任务 | 第 1 步换 `--from-default-profile headless` | 启动参数变成任务文本，没有端口 |
| 给自己的 bundle 加命令行 flag | 第 5 步之后替换 `web-startup` | 必须重实现全部 web flags，漏实现会静默降级 |

## 自证配方（把这条链当成回归）

```sh
H=$(mktemp -d)
DSH_HOME=$H dsh --profile demo --from-default-profile web --dump-default-config > /dev/null
DSH_HOME=$H dsh plugin --profile demo add ./my-plugin
DSH_HOME=$H dsh --profile demo --dump-config | grep -q 'id: demo-row' && echo "row ok"
DSH_HOME=$H dsh --profile demo --no-open --port 0 2>&1 | grep -q 'did not activate' && echo "row inactive" || echo "boot ok"
```

判据：六步任何一步失败，都停在**那一步的产物**上——不靠后面的步骤猜。
