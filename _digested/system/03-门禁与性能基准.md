# 门禁聚合与性能基准树

源码核验入口：[`scripts/run-gates.ts`](../../scripts/run-gates.ts)、[`scripts/verify-*.ts`](../../scripts/)、[`benchmarks/`](../../benchmarks/)、[`vitest.bench.config.ts`](../../vitest.bench.config.ts)、[`.github/workflows/`](../../.github/workflows/)。

本页说明 dsh 把「规则」变成红灯的那层基建：一个聚合器、它的 leaf 家族，以及一条独立的性能基准路径。产品机制见本专题其它页；这里讲的是让那些机制不腐烂的执行装置。

## 一个聚合器，两种用法

`scripts/run-gates.ts` 是唯一的门禁聚合器，所有机械可检查的规则都注册成它的一个 leaf。leaf 有两种消费方式：本地按 outgoing diff 选最小的可信子集，CI 按 mode 跑完整矩阵。

CI mode 有七个：`ci-static`、`ci-primary`、`ci-coverage`、`ci-snapshot`、`ci-artifacts`、`ci-consumers`、`ci-bench`。文档侧另有 `doc-quick`（无构建）与 `doc-sync`（全部文档门禁）两个聚合入口。

## leaf 家族

按被检查的对象分族，不是按实现方式：

| 家族 | 代表 leaf | 检查什么 |
|------|-----------|----------|
| 生成的目录 | `verify-tool-catalog`、`verify-config-catalog`、`verify-persistence-catalog`、`verify-cordis-api`/`verify-cordis-inspect-catalog`、`verify-doc-graphs` | 目录与源码是否同步（freshness） |
| 包与合同 | `verify-export-jsdoc`、`verify-package-invariants`、`verify-built-package-invariants`、`verify-tsconfig-paths`、`verify-type-equiv`、`verify-runtime-closure`、`verify-package-paths` | 导出文档、`./invariant` 有无、项目引用与类型等价 |
| package README | `verify-package-readme-model-experience`、`verify-package-readme-limitations`、`verify-package-readme-summaries`、`verify-subsystem-pages` | README 的三段合同与 100 词摘要 |
| 文档 | `verify-md-links`、`verify-doc-refs`、`verify-doc-budgets`、`verify-translation-pairing`、`verify-translation-prompt`、`verify-public-repository-links`、`verify-vendored-links` | 链接、引用、字数预算、双语配对 |
| 运行时组合 | `verify-cordis-config`、`verify-application-entrypoints`、`verify-config-source-ownership`、`verify-scoped-events` | 配置能不能解析、入口分类、事件作用域声明 |
| 会话格式 | `verify-session-format-catalog`、`verify-persistence-catalog` | 迁移链与目录一致 |
| Agent Note 治理 | `verify-agent-note-classification`、`verify-agent-note-format`、`verify-archived-agent-notes` | note 的分类、格式与归档冻结 |
| 出口与审批 | `verify-no-bare-dispatcher`、`test:approval-policy` | 见下 |

`verify-no-bare-dispatcher` 与 `test:approval-policy` 是两条**策略型**门禁：前者拒绝本包之外以 `new Agent(...)` 覆盖全局 dispatcher（见 [`../capability-seams/05-进程遏制与宿主边界.md`](../capability-seams/05-进程遏制与宿主边界.md)），后者钉加权审批策略。策略门禁与结构门禁的区别是：结构门禁读代码形状，策略门禁读一个部署可变的决定。

## 性能基准树

`benchmarks/` 是顶层独立 workspace（私有 `@deepseek-ai/dsh-benchmarks`），拥有**仓库级**性能门禁——被测用户路径跨包所有权的那种。包内诊断不进来，改用 `.perf.ts` 后缀留在各自 owner 旁边。

组织方式与包树相反：**一个目录一条被测用户路径**，不镜像 `packages/`。当前五条路径：`session-open`、`conversation-fold`、`agent-continuation`、`active-stream-reconnect`、`long-session-browser`。

宿主面用例用 `*.bench.ts`，客户端面用 `*.bench.client.ts`；worker、fixture 与 support 模块不带 bench 后缀。`test:bench` 先构建 workspace 库与 `benchmarks/.dsh-build/` 的 worker，再交给 Vitest；计时的 CPU 工作在 worker 里跑**普通 Node 且不带 TypeScript loader**，所以运行时 import 必须解析到构建产物 `lib/`——这条与源码平面的 `paths` 映射是两套，不能混（见 [`../surfaces/01-启动面与session流.md`](../surfaces/01-启动面与session流.md)）。

几条硬约束：输入必须由被评审的常量合成，**禁止**用录制的 Session、用户材料、外部仓库或网络服务；进程级墙钟与内存采样在全新子进程里跑，带私有 `mkdtemp` 根；纯同步折叠每条样本造一棵新对象图，不得改进程全局状态；参考机器的期望值与 CI 的时间尺度、方差余量分开记录，时间尺度不施加到内存或无量纲比值；环境变量**不能**覆盖性能预算。

## 与「可执行反馈」的关系

门禁家族回答的是「规则有没有红灯」，基准树回答的是「性能有没有回退」。两者都是把判断从人脑搬到机器上：一条规则写进 prose 会腐烂，写成 leaf 就会在 CI 里拦住人。

因此加一条规则的正确形状是加一个 leaf 并在 `run-gates.ts` 注册，而不是加一段文档；加一条性能约束的正确形状是在 `benchmarks/` 下加一条被测用户路径，而不是加一个包内计时。判断梯度的这一层见 [`../harness-idea/03-paved-road.md`](../harness-idea/03-paved-road.md)。
