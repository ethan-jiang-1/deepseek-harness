# 05 · 已经定下的决定

这里记的是**难回退**的词义决定：改回来的成本高，或者不写下来，后来的人会问「为什么当初这么定」。每条只记四件事——当时的问题、备选、决定、代价。追加式：定过的条目不删，改主意就加一条新的，并在旧条目上标注被哪条取代。

## D1 · 词的家放在 `canon/`，而不是各页就地定义

**问题**：同一个承重词曾在多篇正文里各自定义，写法互不相同。

**备选**：（a）继续就地定义，靠人工对齐；（b）每篇开头加一张小词表；（c）建一个专门的目录，其余页面只引用。

**决定**：（c）。`canon/` 是唯一登记处，机制细节仍归各专题。

**代价**：多一次跳转；新专题作者要先查表。

**什么时候重新考虑**：当这个目录本身开始解释机制，说明它越界了。

## D2 · 「发行版」裸词为主，只在强调「整份 Harness」时加前缀

**问题**：repo 的「发行版」指 DSH 自己的分发，第三方的同类交付没有一个词。

**备选**：（a）造一个新词；（b）一律写「Harness 发行版」；（c）沿用「发行版」，只在必须区分「不是单个插件」时加限定。

**决定**：（c）。

**代价**：裸词与 repo 语义有重叠，读者要靠上下文判断。缓解方式是首次出现处给一句限定，并在词表里写清两者不混用。

**什么时候重新考虑**：当 repo 自己引入了一个专指第三方分发的词。

## D3 · 退役「五个家／四个空间」，改用 repo 机制名

**问题**：为数据落点造了两套助记词，彼此还各有一套枚举，读者无法判断哪套是真。

**备选**：（a）保留助记词，只修内部矛盾；（b）全部换成 repo 机制名（files、session log、storage domain、derived、client state）。

**决定**：（b）。助记词退役，机制名保留英文。

**代价**：正文变长，中文读者要多认几个英文词；换来的是可检索、可核对。

**什么时候重新考虑**：不重新考虑。这两个词已经写进校验器的退役名单。

## D4 · `GLOSSARY` 只收 canonical 词，自造装置另表登记

**问题**：一开始想把 DSH 词和本卷自造的分类放在同一张表里，省一次跳转。

**备选**：（a）一张表，用标记区分；（b）两张表，分文件。

**决定**：（b）。混表会让读者以为两者同级。

**代价**：查一个自造词要多跳一次。

**什么时候重新考虑**：当自造装置多到一张表放不下——那时应该拆成独立专题，而不是合并回词表。

## 怎么加一条

1. 它必须满足三条：难回退、离开上下文会让人意外、确实有权衡。缺一条就不要写在这里。
2. 用上面的四段式：问题、备选、决定、代价，另加「什么时候重新考虑」。
3. 如果它取代了旧条目，在旧条目开头加一行「被 Dn 取代」，不要删除旧文。
