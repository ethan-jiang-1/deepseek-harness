# 08 · 一步一步怎么做：把普通项目改造成「agent 不糊涂、不乱发挥」

## 这一篇怎么用

前面七篇都在讲「是什么、为什么、可迁移什么」。这一篇把它们压成一条**可执行的落地顺序**：每一步说清楚**做什么、产出什么、怎么验收（怎么证明这一步真做对了）**，并标注它对应「不糊涂」还是「不乱发挥」。

原则只有一条：**按收益/成本从高到低做，每一步都能独立验收，别跳到第 5 级架构。** 对一个普通项目，走到 Phase 4 就已经覆盖了 80% 的价值。

> 顺序本身来自 [`07-transfer-playbook.md`](./07-transfer-playbook.md) 的优先级清单，这里把它展开成动作。

---

## Phase 0 · 先给项目打分（半天）

**做什么**：用三问框架评估现状，找出自己最痛的一档。

- 规则住在哪里？（人脑 / 文档 / 可执行检查）
- 正确入口明确吗？（能不能从目标找到 owner 和范本）
- 错误何时被发现？（编译 / 测试 / CI / review / 生产）

**产出**：一张三行打分表，每行写「现状 + 最痛的一个例子」。

**验收**：能指着具体一个 bug/返工，说出它是「哪一档缺口」造成的。说不出来，说明还没诊断透，先别动手。

**对应**：这是「不糊涂 + 不乱发挥」共同的基线。

---

## Phase 1 · 立规矩的 owner（1–2 天，收益最高）

**做什么**：写一份**短**的根 `AGENTS.md`，只放三类东西：常驻规则（每条一两行）、仓库布局（每个顶层区域一句话）、命令表。其余全部 link 到各自 home，不复制。同时把 `CLAUDE.md` 用 `ln -s AGENTS.md` 指向它，并在**真正有子树专属常驻规则**的少数目录放子树 `AGENTS.md`，其余目录/包只留 README。

**产出**：根 `AGENTS.md`（目标 ≤ 几百词）+ `CLAUDE.md`（symlink）+ 一张「事实 → home」对照表 + 少量子树 `AGENTS.md`（可有可无，按需）。

**验收（关键，机械判断）**：
- 任何一条规则，能在 10 秒内指出它的唯一 home；
- 不存在同一规则在两处各写一版；
- 根文件里没有教程、没有历史故事、没有该 link 出去的细节；
- `CLAUDE.md` 是 symlink 而非副本；子树 `AGENTS.md` 只出现在「有专属常驻规则」处，没有为放而放。

**对应**：不糊涂（知识外置 + 一个事实一个 owner）。入口链的完整骨架见 [`09-agents-entry-chain.md`](./09-agents-entry-chain.md)。

---

## Phase 2 · 划清「现在」和「为什么」（1–2 天）

**做什么**：把 `docs/`（或 README）定为 **current state**，决策理由单独进 `docs/adr/` 或 `notes/`。顺手记下负知识——「为什么不走某条路」「已知限制是什么」。

**产出**：`docs/adr/`（或等价物）的目录 + 第一批 ADR/负知识条目。

**验收**：
- 读一份 ADR 能回答「为什么这样决定、什么方案输了、后果是什么」；
- `docs/` 里没有 change history（那是 git/PR 的职责）；
- 至少有一条负知识，agent 不会再反复提出已否决方案。

**对应**：不糊涂（当前事实 vs 决策理由分开 + 负知识外置）。

---

## Phase 3 · 铺正确路径（2–5 天）

**做什么**：写一张「目标 → 机制」归属表，再给最常见的 2–3 个任务各写一个 cookbook（短入口 + 范本 + 升级条件）。

**产出**：
- 一张归属表（列：目标 / 首选入口 / 何时升级）；
- 2–3 份 cookbook，每份含「先问归属 → 照范本 → 跑对应检查」。

**验收**：
- 一个新任务进来，先查归属表就能回答「该改哪里」，而不是翻代码猜；
- cookbook 里「本可用配置/扩展点表达、却要改核心」这种情况被显式拦下（升级条件写清楚了）。

**对应**：不乱发挥·改哪里（paved road + 参与阶梯）。

---

## Phase 4 · 把可机械规则接到执行（3–7 天，回报第二高）

**做什么**：挑出 Phase 1 里「可机械判断」的规则，各配一个 `exit non-zero` 的命令；写一个聚合脚本；接进 git hook（低延迟项）和 CI（穷举项）。

**产出**：一个 `scripts/check.sh`（或等价物）+ 每个规则的负例测试。

**验收（这一条是硬指标）**：
- **每个检查都做过负例控制**：引入对应回归 → 看它变红 → 还原；
- 本地能只跑「受本次改动影响」的相关检查，CI 跑全套；
- 反馈信息能指出「失败对象 + 违反规则 + 修正入口」，不是一句无上下文的「检查失败」。

**对应**：不乱发挥·早失败（可执行反馈，最高杠杆）。

---

## Phase 5 · 固化任务流程（按需，2–4 天）

**做什么**：把反复出现、需要上下文判断的任务流程写成带触发条件的短文档（等价于 Skill）：触发条件、输入、步骤、停止条件、验证、输出格式。

**产出**：一个「任务 → 流程文档」的目录 + 2–3 份流程文档。

**验收**：
- 命中任务时先读全文、不从摘要猜（文档里明确写这条纪律）；
- 每份文档末尾声明「这是 guidance，不是 checklist」，可机械部分仍然指向 gate 而不是 prose。

**对应**：不糊涂 + 不乱发挥（按需加载省上下文，收走「发明流程」的自由度）。

---

## Phase 6 · 加运行时查询（确有压力才做，可无限期推迟）

**做什么**：最低成本先给一条「dump 最终生效配置」的命令；只有确实存在多 profile/provider/动态装卸时，才考虑生成 catalog 和只读 inspect 工具。

**产出**：一条 `show-config`（或等价）命令；可选：生成索引 + freshness 检查。

**验收**：
- 能用命令回答「这台机器实际装了什么」，而不靠读源码猜；
- 若做了 catalog，有 freshness 检查防止索引与源码漂移。

**对应**：不糊涂（可检查性）。**注意**：这不是安全沙箱，别把 inspect 当授权边界。

---

## 收尾：每一步完成后回到三问

每做完一个 Phase，重跑 Phase 0 的三问打分，确认：

1. 知识外置：规则从「人脑」搬进了「可搜索/可检查」了吗？
2. 正确路径：新参与者能便宜地找到 owner 和范本了吗？
3. 反馈延迟：错误被发现的位置，从「review/生产」往「编译/测试/CI」前移了吗？

三问都变好、且没有为了形式而造假断言，这一步才算真完成。

## 最小可用集（MVP）

如果你只有一个周末，只做四件事，就已经拿到大部分收益：

1. 短 `AGENTS.md`（常驻规则 + 布局 + 命令），`CLAUDE.md` 用 symlink 指向它；
2. 决策理由进 `docs/adr/`，`docs/` 只写 now；
3. 一张「目标 → 机制」归属表；
4. 2–3 条可机械规则接成 `exit non-zero` 脚本，并各做一次负例控制。

**这四件事覆盖了「不糊涂」和「不乱发挥」的八成来源，而且不需要任何插件架构。**
