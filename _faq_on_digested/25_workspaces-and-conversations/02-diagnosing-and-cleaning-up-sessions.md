# 02 · 排查与清理实战：为什么 `~/.dsh` 会攒出未分组会话，该怎么安全处理？

弄清了“名册显式挂接 + 前端做减法”的机制后，回看自己电脑上用了几个月的 `$DSH_HOME`（默认 `~/.dsh`），就能明白为什么侧栏末尾会慢慢攒出一串 `Ungrouped` 会话，或者留着几个目录早已删掉的旧工作区。本篇先用一次真实的本机 `~/.dsh` 静态体检把账对清楚，再按不同使用角色给出**不伤会话日志**的安全处置方案。

---

## 一、真实案例拆解：31 个工作区与 58 条未分组主会话是怎么来的？

在一台日常既开 Web 界面干活、又跑 CLI 命令和本地插件测试的开发机上，只读解析 `~/.dsh/storages/workspace.json` 与 `~/.dsh/sessions/` 下所有 `.jsonl.zstd` 日志首行（`SessionHeader`），得到如下真实分布（排查脚本见 [`reference.md`](./reference.md#四本地只读体检脚本)）：

| 排查项 | 实测读数 | 数据口径与含义 |
|---|---|---|
| 已登记的 `Workspace` 数量 | `31` | `workspace.json` 中 `tables.workspaces` 的记录条数 |
| 名册登记的 `sessionIds` 总数 | `935` | 31 个工作区 `sessionIds` 并集（含早期 `bootstrap` 扫入的 `19` 条子会话，前端不渲染） |
| 磁盘上的会话目录总数 | `3,864` | `sessions/--<cwd>--/<id>/` 目录总数，分布在 `35` 个目录分区下 |
| 其中 `subagent` 子会话 | `2,890` | 日志头 `origin === 'subagent'` 或带 `parentSession`，侧栏可见性直接过滤 |
| **参与侧栏分组的主会话** | **`974`** | `3,864 − 2,890 = 974` |
| 已被工作区名册认领的主会话 | `916` | `935 − 19 = 916`，正常挂在对应的工作区节下 |
| **未被任何名册认领的主会话** | **`58`** | `974 − 916 = 58`（扣除可能存在的空白占位后，就是侧栏 `Ungrouped` 的上界） |

最能说明问题的是这 **58 条未登记主会话的目录归属**：

- **31 条正好位于 `/Users/bowhead/deepseek-harness`**——而这个仓库目录在左侧**明明建有活跃的工作区**！之所以没进组，是因为它们是在首次 `bootstrap` 完成之后，通过命令行 `dsh --profile headless`、SDK 脚本或未隔离 `DSH_HOME` 的插件测试直接传 `cwd` 创建出来的，全程没走 GUI 的 `workspaceId` 挂接门。
- **25 条位于某个临时实验目录**——只在终端里进去跑过命令，从未在 GUI 里点“添加工作区”登记过。
- **2 条位于临时建完又清掉的 `git worktree` 目录**。

这组实测数字直接印证了一条排障铁律：**看到同一项目的会话掉进 `Ungrouped`，既不是文件损坏，也不是重启一下就能“重扫目录自愈”的缓存延迟，纯粹是创建那条会话的入口没调 `attachSession`。**

## 二、常见症状速查：动手前先对号入座

遇到侧栏显示不符合预期时，先对照下表确认原因，避免用错药方（尤其是别盲目删工作区重建）：

| 你看到的现象 | 真实原因 | 正确应对动作 |
|---|---|---|
| `Ungrouped` 里零星躺着几条会话 | 偶尔用 CLI / headless 或外部脚本在默认 `~/.dsh` 下跑过任务 | 完全正常，无需修复；嫌碍眼直接点会话菜单 **归档（Archive）** 即可隐藏 |
| 跑完一轮单测或 e2e，`Ungrouped` 突然冒出几十条记录 | 测试代码直接调 `ctx.agents` / SDK 建会话，且共用了日常 `~/.dsh` | 给测试进程设置独立的临时 `DSH_HOME`，从根源上隔离 |
| 原本好端端在某工作区下的一整批会话，突然全掉进了 `Ungrouped` | 该工作区记录被从侧栏移除了（删除工作区只删名册，保留全部会话） | 不要反复删加目录（重加只会建空名册）；日常续用不受影响，确需归队需走宿主 API 补挂 |
| 工作区还在、老会话也在，但在里面新建会话或发消息报错找不到目录 | 磁盘上的项目文件夹被改名、移走或删除了（老成员遇 `ENOENT` 保留名册，但新操作校验不过） | 把原文件夹挪回原路径；若旧目录已永久废弃且会话卡在目录校验，用 SDK 切到现存目录 |
| 某条会话点不开、呈灰显状态；或点归档时弹窗提示有活动任务 | 灰显是处于“显示已归档”视图；弹窗是 `workspace/session-active` 保护正在运行的轮次/子任务/定时任务 | 灰显会话点“取消归档”即可恢复对话；归档运行中会话时按提示确认停止活动任务即可 |
| 磁盘日志目录里有几千个会话，侧栏里怎么都翻不到某一条 | 目标很可能是 `origin = subagent` 的子会话、已归档会话，或早期无 `cwd` 的冷会话 | 先在侧栏视图菜单打开“显示已归档”；若仍是子会话或无 `cwd` 冷会话，需直接查磁盘日志 |

## 三、分角色安全维护与清理指南

### 1. 日常使用者：善用“归档”与目录恢复，切勿手改 JSON 或强删日志目录

- **清理侧栏视觉噪音：直接用归档（Archive）**。当前 DSH 产品没有提供“物理永久删除单条会话”的按钮（这是为了保护历史审计链完整）。对于跑废的测试对话或留在 `Ungrouped` 里的旧记录，直接在行菜单点**归档**，它就会从默认列表中干净消失；万一以后想翻看，随时能在筛选器里切出“已归档”恢复原位。
- **清理废弃或重复的工作区节：直接在界面移除工作区**。如果某个旧项目不再维护，在工作区菜单点删除即可去掉这一节；若它名册里还有不想在 `Ungrouped` 看到的旧会话，**先归档那些会话、再移除工作区**，侧栏就会干干净净。
- **原始项目目录永久删除后，如何拯救卡住的旧会话？** 如果一个会话的当前有效目录和创建时的 `SessionHeader.cwd` 双双在磁盘上消失，提示词组装阶段会拒绝任何新的模型轮次（连纯聊天也会拦下）。此时如果不想在磁盘上重建原路径，可以通过 TypeScript SDK 的 `setWorkingDirectory`（或 Python SDK 的 `set_working_directory`、宿主 `ctx.workingDirectory.set`）把它的有效工作目录显式指派到一个现存的绝对路径上，即可继续对话。
- **两条绝对红线**：
  1. **不要在 Web / Desktop 运行期间手改 `$DSH_HOME/storages/workspace.json`**：它既没有跨进程文件锁，又受严格 Schema 与 `pendingMutation` 完整性校验保护——运行中手改极易被内存写回覆盖，改错一个字段或漏改 `workspaceIds` 顺序还会导致下次启动直接报损坏拒绝加载。
  2. **不要进 `$DSH_HOME/sessions/` 随手 `rm -rf` 单个会话文件夹**：会话摘要与检索还关联着 SQLite 投影缓存（`session_projcache` 等）以及 `workspace.json` 里的名册/置顶/归档数组，裸删底层目录会留下悬空索引。

### 2. 插件作者与测试开发者：用独立 `DSH_HOME` 彻底杜绝污染

在本地调试插件、跑集成测试或写自动化探针时，`Ungrouped` 被刷屏 99% 都是因为没做数据目录隔离。

- **标准做法：每次测试分配一次性临时 `DSH_HOME`**（详见 [FAQ 23](../23_standalone-vs-web-release-forms/answer.md)）：
  ```sh
  DSH_HOME="$(mktemp -d)" pnpm run test
  ```
  这样做一举三得：第一，测试产生的会话和工作区跑完即弃，日常 `~/.dsh` 侧栏零污染；第二，彻底避开两个 Host 进程并发写同一份无锁 `workspace.json` 的竞态风险；第三，每次测试都从真正的干净状态启动，不会因为本机 `~/.dsh` 的 `initialized` 早已是 `true` 而掩盖首次启动逻辑的 bug。（注意：独立 `DSH_HOME` 下没有日常登录凭据文件，需通过环境变量如 `DEEPSEEK_API_KEY` 或回放桩 `dsh-llm-replay` 提供模型接入。）
- **如果你的测试专门验证工作区侧栏行为**：千万别写“在 `/tmp/demo` 下调底层接口建了会话，断言它自动出现在 `/tmp/demo` 工作区里”——这个断言只在首次未初始化的空库碰巧靠 `bootstrap` 蒙混过关。正确写法是走带 `workspaceId` 的 `session.create` 正式入口，或者建完会话后显式调用 `await workspace.attachSession(sessionId)`。

### 3. 进阶维护：真想把一批未分组旧会话补挂回某个工作区怎么办？

虽然当前 GUI 界面还没有提供“把一条 `Ungrouped` 会话拖进工作区”的交互入口，但如果团队维护者确实需要编写一段宿主侧小插件或维护动作做一次性补录，请严格遵守以下安全顺序：

1. **先只读核对路径**：用 [`reference.md`](./reference.md#四本地只读体检脚本) 中的只读脚本确认目标会话的 `SessionHeader.cwd` 经 `fs.realpath` 解析后，与目标工作区的 `workspace.path` 逐字符一致（注意 macOS 下 `/var` → `/private/var` 等符号链接差异）。
2. **彻底关闭正在运行的 Web / Desktop 宿主进程**，并先备份一份 `$DSH_HOME/storages/workspace.json`。
3. **只走官方 `ctx.workspaceRegistry` API 写入，绝不手拼 JSON**：在挂载了 `@deepseek-ai/dsh-workspace`（及配套 `sessionPersistence`、`storageDomain`）的宿主上下文中，先调用 `const ws = await ctx.workspaceRegistry.create(targetPath)` 获取或创建对应工作区，再对符合路径条件的会话逐条调用 `await ws.attachSession(sessionId)`。API 内部会自动完成五步合法性校验、前插名册、清理失效候选并原子刷新持久存储。
