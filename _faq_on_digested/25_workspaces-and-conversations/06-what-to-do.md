# 06 · 看到 Ungrouped 之后：能做什么，别做什么

## 这一篇回答什么

Ungrouped 不是错误弹窗，它只是一个事实的投影。但事实分几种，处置也不同：值得修、不值得修、以及根本不该由你手动修。这一篇按“你是谁”分三份清单，最后给一条不伤数据的检查顺序。

## 先判断它属于哪一种

| 现象 | 判断 | 建议 |
|---|---|---|
| 只有偶尔几条，来自 headless / 脚本 | 正常，符合登记模型 | 不用管；或按下面“彻底隔离”处理 |
| 一大批，集中在某个目录 | 该目录没有工作区，或工作区是后加的 | 建/选一个工作区；需要的话做一次显式补登记 |
| 曾经在组里，突然整批跑到 Ungrouped | 工作区记录被删了 | 先确认不是误删；旧会话不会自动回来 |
| 会话打不开、灰显 | 那是归档，不是 Ungrouped | 切“显示已归档”或取消归档 |
| 列表里根本没有某条会话 | 可能是无 cwd 的冷会话或 subagent | 到日志目录确认，不要在 UI 里找 |

## 你是一般用户

**推荐做法：不修。**

Ungrouped 里的会话可以正常打开、继续、分叉、归档；它只是没有工作区级的“＋”、重命名和悬浮卡片。为了把它们塞进某一节而删除/重建工作区，只会让情况更乱：重加目录得到的是空工作区，旧会话仍然留在原地。

可以做的三件事：

1. **归档噪音**：会话菜单 → 归档。归档是全局集合，会保留账户名额；对 Ungrouped 会话就是“从默认视图消失”。
2. **给常用目录建工作区**：目录选择器选中该目录即可；之后从这一节新建的会话才会入组。
3. **不要手改 `workspace.json`**：它是 schema 校验 + 两写标记的持久状态；Host 运行时没有跨进程锁，手改可能被覆盖，或被启动校验直接判损坏（fail loud）。

## 你是插件 / 测试作者

问题的根源通常不是 DSH，而是**测试与会话共用了同一个 `$DSH_HOME`**。

### 做法 A：隔离数据根（推荐）

给测试一个独立的 home：

```sh
DSH_HOME="$(mktemp -d)" pnpm run test:...
```

或者用测试夹具自己的临时 home。这样：

- 不会污染日常侧栏；
- 不会与正在运行的 Web 争同一份 `workspace.json`；
- 凭据需要显式提供（home 里没有 `.credentials.yaml`，用环境变量或测试桩）。

本仓的大量 e2e 就是这么做的：临时 home + 临时工作目录，结束后整体丢弃。

### 做法 B：如果测试就是要验证侧栏行为

显式走门，而不是“建完再看”：

- 创建时带 `workspaceId`（走 `session.create` 的正式路径）；
- 或者创建后调用 `workspaceRegistry.get(id)?.attachSession(sessionId)`，让账户里真的有这条会话；
- 断言时同时检查“它出现在哪一节”和“`sessionIds` 里有没有它”。

只断言“会话创建成功”而不管归属，测试就会在别人的侧栏里留下 Ungrouped 残留。

### 做法 C：不要用“目录一样”当断言

“我在 `/tmp/x` 建了会话，而 `/tmp/x` 有工作区，所以它应该在组里”是错的。bootstrap 一生只跑一次，attach 是显式动作。这个断言在干净 home 里可能碰巧通过（首次 bootstrap），在长期使用的 home 里必然失败。

## 你想把旧会话补回某个工作区

当前产品**没有**“把会话移入工作区”的 UI 或 CLI 入口；会话菜单只有分叉、归档、置顶、复制 id。唯一的写入口是宿主 API：

```text
workspace = ctx.workspaceRegistry.get(workspaceId)
await workspace.attachSession(sessionId)
```

它仍然要过五步校验（会话存在、有 cwd、realpath、是目录、等于 `workspace.path`）；所以：

- 先确保该目录有工作区记录（没有就 `create(path)`）；
- 只补登记那些 cwd 真正等于该路径的会话；
- 一次一条，失败会明确拒绝，不会写半条。

这属于宿主侧脚本/插件的职责，不是终端用户操作。做之前先备份 `workspace.json`，并在 Host 停止时进行——它没有跨进程写保护。

## 删掉工作区之后想反悔

先接受一个事实：**重加同一目录 = 一条新记录**，旧会话不会自动回来（bootstrap 不会重跑）。可选路径：

1. 重加目录，得到空工作区；
2. 用上面的 `attachSession` 逐条把旧会话补进去（cwd 必须匹配）；
3. 或者不补，把它们留在 Ungrouped——功能上没有损失。

不要尝试“恢复旧的 uuid”：记录已经删除，Client 的删除标记也会阻止旧 id 在同一进程内复活；跨进程只能靠持久状态，而持久状态里已经没有它了。

## 一条不伤数据的检查顺序

1. **先读，不写**：打开 `$DSH_HOME/storages/workspace.json`，确认 `workspaces` 里有几条、`workspaceIds` 顺序、目标会话是否在某个 `sessionIds` 里。
2. **确认目录**：`realpath` 一下目标目录，确认与会话日志头里的 `cwd` 一致（符号链接、尾斜杠、`..` 都会影响字符串相等）。
3. **确认会话**：在 `$DSH_HOME/sessions/--<cwd>--/` 下找到它的目录；确认它不是 subagent、不是空白。
4. **停 Host 再改**：要写就只通过宿主 API 写，不要在 Host 运行时手改 JSON。
5. **改完验证**：重启 Host，看 `workspace/follow` 的 baseline 里该工作区的 `sessionIds` 是否包含目标 id；左侧对应节应出现该行。

## 为什么 DSH 不做一个“自动收编”

因为自动收编需要一个可信的“目录 → 工作区”映射，而这个映射会与三件事冲突：

- **删除的非破坏性**：删工作区不删会话，靠的就是“账户是唯一归属”；如果启动时按目录自动补收，删掉的工作区会在下次启动自动复活一半。
- **多目录同名/符号链接**：目录身份需要 realpath，自动匹配会把临时目录、worktree、符号链接混在一起。
- **显式优于隐式**：会话归属是用户可见的组织行为，静默改写账户比留下 Ungrouped 更难排查。

设计记录里还有一条相关的否决理由：启动时清理“未被引用的行”被拒绝，因为同样的形状也可能来自损坏，静默丢弃会连元数据与账户一起丢。代价就是本篇反复出现的那句话：**账户不会自愈**。接受这一点，Ungrouped 就从“故障”变成了“未登记”的正常显示。

## 边界

- 本篇不给“直接编辑 JSON 的配方”：格式可读不等于可以手改，schema 校验与两写标记都假定写入方遵守协议。
- 会话删除在当前产品中不存在；`rm -rf` 日志目录属于未支持操作，可能留下投影缓存里的陈旧行。
- 多 Host 共享同一 home 的并发写不在保证范围内；需要并行就用不同 `DSH_HOME`。
