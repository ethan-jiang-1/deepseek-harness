# FAQ 25 · Workspace 到底是不是启动时的那个文件夹？为什么会话中途能切目录，有的历史会话又会掉进 Ungrouped？

## 问题背景

打开 Web 或 Desktop 客户端，左侧边栏按 **Workspaces** 分好了一组组项目和会话，最底下有时还躺着一个 **Ungrouped（未分组）**；回到终端敲 CLI 启动时有个当前所在目录（`process.cwd()`），进入对话后模型还能调用 `working_directory` 工具切到别的文件夹干活。

把这几件事叠在一起，日常使用或调试插件时很容易碰上四个反直觉的现象：

- 换一个目录敲 `dsh web` 启动，左侧的 Workspace 列表为什么纹丝不动？
- 全新环境首次打开界面，为什么默认工作区建在系统的 `Documents` 目录下，而不是我启动命令的文件夹？
- 明明在同一个仓库目录里跑出来的会话，为什么有的挂在对应 Workspace 下面，有的（如 CLI 或插件单测跑出来的）却掉进了 `Ungrouped`？
- 不小心在侧栏删掉一个 Workspace，再把同一个文件夹重新添加回来，原来的历史会话怎么没跟着归队？

## 具体要回答什么

1. DSH 里常被统称为“工作目录 / 工作区”的四样东西——启动进程时的 `process.cwd()`、沙箱允许写入的根（`sandboxPolicy`）、会话当前轮工具执行的有效目录（`ctx.workingDirectory`）和侧栏里的 `Workspace` 登记项——各自归谁管、改哪一个会影响什么？
2. `Workspace` 在 `$DSH_HOME` 里到底存了什么？一个会话通过哪几道门才能挂进某个 `Workspace`，为什么“目录路径一样”不会自动入组？
3. 侧栏末尾的 `Ungrouped` 是谁算出来的？当会话中途切换工作目录时，为什么沙箱可写边界和左侧分组都保持不变？
4. 长期使用后 `$DSH_HOME` 里攒出一批 `Ungrouped` 会话、已删目录的旧工作区或插件测试残留时，普通用户和开发者该怎么安全排查与清理？
