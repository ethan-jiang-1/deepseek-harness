# FAQ 01 · DSH 的目录为什么这样组织，不同目的的人该从哪条路线读起？

## 背景困惑

第一次克隆下 DeepSeek Harness（DSH）仓库，很容易被眼前的目录结构绕晕：顶层摆着十几个平行目录，`packages/` 两层嵌套着三百多个细碎的子包，反倒是承载最终入口的 `apps/` 薄得惊人；想顺着一个常见功能找实现，却发现连读写文件都拆成了 `fs`、`fs-local`、`fs-sandbox`、`fs-observation-policy`、`tool-fs` 好几个包。

这套目录为什么要摆成这样？磁盘上的文件夹和真正跑起来的进程是什么关系？带着不同目的打开仓库的人，第一眼该从哪条路线读起？

## 具体要回答的四个问题

1. **顶层分区与薄入口**：`vendor/`、`packages/`、`apps/`、`native/`、`python/`、`snapshots/`、`.agents/` 各自管什么？为什么 `apps/` 里几乎不写业务逻辑？
2. **两层包结构与角色切分**：`packages/<group>/<pkg>/` 为什么要拆得这么细？只看包名和依赖关系，怎么分辨谁是接口定义、谁是后端实现、谁是模型工具或界面插件？
3. **静态目录与运行时的关系**：“磁盘上有这个包”“`package.json` 依赖了它”“这次启动真把它挂进来了”三件事为什么不能画等号？Host 树、Client 树和单会话 Agent 作用域是怎么分开的？
4. **按目标选阅读路线**：想搞懂一轮对话怎么跑通、想查某个工具怎么实现、想自己写外部插件、或者想看 Web 前后端怎么通信，分别该顺着哪几个文件往下追，改代码该落到哪里？
