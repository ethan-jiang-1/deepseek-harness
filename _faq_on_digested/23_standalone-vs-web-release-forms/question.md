# FAQ 23 · standalone APP（Desktop）与 CLI/Web 这两份发布物各做到哪一步？插件怎么装，开发期又怎么绕过正式发布？

## 问题

官网 Download 页只给 Desktop 安装包；Hacker News 上 Desktop 的发布贴里，有人夸「点开就能用」，也有人第一句就问遥测能不能关；本机 `~/.dsh` 里同时躺着一个 `dsh web`（3080）和一堆插件目录。于是问题变成一串具体的：

1. 今天 DSH 真正「能装成应用」的发布物有几个？各自打包了什么、进程跑在哪、谁执行安装？
2. Desktop 成熟到哪一步——版本怎么同步、有没有稳定通道、发布工程（签名/公证/更新/回滚）做到什么程度、已知缺口是什么？
3. 社区的实际反应是什么？把「反应」拆成能核对的数字（star / 下载 / 讨论量）和能引用的原话。
4. 插件安装的入口有几个？Desktop 与 CLI/Web 的差别在哪，「装到哪」由什么决定？
5. 在开发过程中、**不走正式发布**，有哪些把插件（或任意配置行）塞进运行中的树的办法？各自生效在哪一层、什么时候失效、有哪些坑？

## 追加问题（同日追问 Desktop）

6. Desktop 和我们通过 npm 全局安装的 dsh 能隔离吗？能不能给它一个完全独立的环境？
7. Desktop 有 Linux 版吗？
8. Desktop 有 Mac 版吗？哪些架构？
9. 所谓「数据侧共享」到底指哪些东西？`$DSH_HOME` 里都有什么，哪些按 home 共享、哪些按 profile 分开？

第 6–8 问并入 [02 篇](./02_desktop.md)（「三问」一节），第 9 问是 [06 篇](./06_desktop-lab-isolation.md) 的「数据侧到底有哪些东西」一节——它们依赖同一批事实：可执行包与用户数据的分层、发布目标清单、以及 feed 上各架构的实际版本。

## 背景

- `standalone` 在仓库里至少指三样东西（`sdk-minimal` 的独立 bundle、session 的 standalone 事件、独立安装的桌面 App），先拆词才能谈「发布形态」。
- `apps/desktop` 是 Electron 壳，`dsh --profile desktop` 被 CLI 显式拒绝——桌面不是第五个 CLI profile，所以「桌面底下怎么装插件」跟「CLI 底下怎么装插件」不是同一条路径。
- 开发期注入手段散落在 CLI reference、plugin-manager README、desktop README、`apps/web/tests/*.overlay.yml` 和教程里，没有一处集中列过。

## 回答目标

- 给出两个发布物的**当前状态判据**（可复现：`dsh --version` 看本机、`curl` 看 feed、`curl` 看固定下载链接），而不是「据说很成熟/还早」。
- 把「社区反应」落成数字 + 原话 + 社区自己承认的边界。
- 把插件安装按**执行位置**分类：装在哪台机器、哪个 profile、由谁执行 pnpm。
- 把开发期注入按**层顺序**排开，每条给出适用形态与失效条件。
- 把 `$DSH_HOME` 的数据清单列全：路径、内容、共享范围、敏感度、迁移建议。
- 明确写清未验证项（社区条目、桌面稳定通道是否存在、隔离命令未真机实跑）。

## 不在范围

- 不审计社区插件的源码安全性；只引用它们自己声明的能力与数字。
- 不评估模型质量、不比较其他 agent harness。
- 不做桌面安装包逆向或签名链验证——那需要 release 环境。
