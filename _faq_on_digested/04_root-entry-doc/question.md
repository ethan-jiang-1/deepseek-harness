# 04 · 根入口文档：这张地图怎么画出来，跑起来又怎么被消费？

一个 coding agent 第一次进入仓库，最先看到的往往不是源码，而是根目录的 `README.md`、`AGENTS.md` / `CLAUDE.md` 以及它们指向的文档树。很多仓库的根文档容易掉进两个极端：

- **写得太散**：入口是一篇面向新人的长篇导览，真正影响改代码的硬约束埋在三层链接后面，模型经常漏读；
- **塞得太满**：把教程、配置表、历史背景全堆进根 `AGENTS.md`，常驻上下文被撑爆，关键规则反而被稀释。

DeepSeek Harness（DSH）把这件事拆成静态和运行时两半来工程化解决——缺了任何一半，“渐进式披露”都只是美好的愿望：

1. **静态设计怎么画地图？** `README.md`、`AGENTS.md`、`CLAUDE.md` 各自面向谁？为什么根 `AGENTS.md` 能只放极短的常驻规则？“一个事实一个家”的文档分层、字数上限和新鲜度门禁是怎么配合防腐烂的？
2. **运行时怎么消费这张地图？** 根和子目录的 `AGENTS.md` 是靠模型自觉去读，还是运行时主动注入？不在注入链里的包 README、生成目录和 skill 正文怎么按需拉取，上下文满了又由谁回收？

> **本篇边界**：聚焦 DSH 自身的入口地图设计与运行时加载闭环；外部团队如何按需借用这套做法，详见 [FAQ 07](../07_borrowing-dsh-harness-idea/answer.md)。
