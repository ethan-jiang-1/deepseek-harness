# Question 04 · 根入口文档：这张地图怎么画出来，跑起来又怎么被消费？

## 背景

一个 coding agent 第一次进入仓库，最先接触的通常不是代码，而是根目录的 `README.md`、`AGENTS.md` / `CLAUDE.md`，以及它们链接出去的文档。很多仓库在这里出现两类失败：

- **写得太散**：入口是一篇 onboarding 长文，真正的规则埋在第三层链接里，模型读了等于没读；
- **写得太满**：入口把什么都塞进去，常驻上下文被教程、示例、历史沿革挤爆，真正的约束反被稀释。

DSH 在这一点上有明确设计。问题分两半，只答一半都不成立：

1. **静态一半**：这张地图是怎么画出来的？谁对哪类事实负责，常驻层放什么、不放什么，靠什么保证它不会悄悄坏掉？
2. **运行时一半**：地图画对了，不等于模型真的按图走。运行时是谁把入口塞进上下文、模型用什么工具读下一份、上下文超了谁来回收？

## 要回答的问题

1. 根入口有哪些文件，各自对谁负责？`README.md` 与 `AGENTS.md` 的分流是怎么做的，`CLAUDE.md` 为什么不能产生第二份事实？
2. 根 `AGENTS.md` 为什么能只放 standing orders？「一个事实一个家」的 tier taxonomy 具体规定了什么？
3. 常驻层有没有预算？超了怎么办，处理顺序是什么？
4. 地图的新鲜度靠什么保证——生成目录、链接检查、文档预算门禁分别在挡哪一类失效？
5. 运行时：入口链是模型主动读还是被注入？注入几次、什么时机、什么上限？
6. 不在注入链里的内容（package README、architecture、catalog、skill 正文）怎么被拉到？超预算怎么回收？
7. 这套做法的边界在哪，别的仓库该怎么抄、抄不了的部分是什么？

## 范围

答静态设计与运行时消费两端。**不答**：具体某个 package README 该怎么写（见 [`docs/AGENTS.md`](../../docs/AGENTS.md)）、文档 tier 的完整分类表（那是 `docs/AGENTS.md` 的 home）、以及迁移到别的仓库的完整路线（见 [FAQ 07](../07_borrowing-dsh-harness-idea/question.md)）。
