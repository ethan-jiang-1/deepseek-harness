# Question 26 · 定制工作台与发行组装：想基于 DSH 交付一套行业工作台，哪些能力底座现成、哪六块归属必须自己设计？

假设团队想在 DSH 之上封装一套面向终端用户的领域产品或内部工程工作台（例如看板协作台 Kanban Studio、代码审计工作台或团队研发助手），交付前通常会遇到三组核心问题：

1. **什么时候发一个普通插件包就够了，什么时候才真需要做“定制工作台发行”？**
   - 如果只是给现有用户增加一组专属工具、智能体预设（preset）和前端卡片，直接发一个 Bundle 跟单独维护一套定制 Profile 有什么本质差别？
   - DSH 严禁包级自建可执行入口（`Only dsh profiles launch supported Node apps`），那定制工作台受支持的启动入口、脚本封装与容器或桌面交付形态应该怎么长？
2. **启动组装与状态归属上，哪六块责任是框架不会替你兜底、必须由发行方自己拍板的？**
   - Profile 清单（`dsh.profile.bundles`）、四层 `cordis.patch.yml` 覆盖、命令行参数与单 Profile 设置（`Config.volatile()`）按什么优先级合成？为什么改一行配置有时会让 `--port` 突然失效？
   - 同一台机器上如果既有用户自己的日常 DSH，又有你的定制工作台，怎样隔离 `$DSH_HOME`、会话历史、凭据和桌面壳 `userData` 才不会互相串数据？
3. **终端用户从首次打开、选目录建会话到后续升级卸载，完整生命周期怎么闭环？**
   - Web 端一次性鉴权链接、默认工作目录初始化、后端预建会话与浏览器前端自动打开视图之间有哪些容易断链的缝隙？
   - 升级失败怎么回退，Web 与 Desktop 两端的安装指引为什么不能混写？

### 问题边界

- 本篇面向**基于 DSH 组装定制工作台、预置团队环境或独立行业产品的发行维护者**。
- 如果你只是开发单个工具、随包技能或智能体预设供用户在现有环境中安装，请直接阅读姊妹篇 [FAQ 24 · 插件发布与数据边界](../24_plugin-publishing-and-data/answer.md)。
- 官方 CLI、Web 与 Desktop 三种运行形态本身的边界见 [FAQ 23](../23_standalone-vs-web-release-forms/answer.md)；工作区与会话的底层关系见 [FAQ 25](../25_workspaces-and-conversations/answer.md)。
