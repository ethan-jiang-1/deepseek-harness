# 02 · 怎样验证一个 Preset：从声明到真实交付

## 先确定要证明的性质

本篇给出适用于角色助手、审查助手、研究助手等 preset 的验证路径。company-pack 是其中一个实证案例，DSH 原生实现与测试提供机制依据；案例自己的角色名、目录、脚本和发布步骤不构成通用标准。项目专属分析集中在[案例研究](./research-company.md)。

验证开始前，写清目标使用者、任务、允许能力、所需资料、交付结果和失败处理。例如“审查助手读取指定资料，指出缺证据项，不修改原件，并返回可追溯意见”。这比“有审查 persona、装了几个工具”更接近产品承诺，也才能决定需要观察什么。

以下路径不是每次修改都从头跑完的清单。首次交付建立基线，后续按[改动影响](./04-long-term-development.md#四按影响选证据不只按扩展名分类)选择证据；关键是每项承诺有适合的观察点。

## 一、声明是否进入了实际交付？

先核对 bundle 的 patch 清单、preset 定义、插件依赖及随包资源，防止“源码里有，安装后没有”。静态解析可以检查条目结构、身份、已覆盖的重复 ID 和已知必填字段；运行时仍要执行各插件的 Config 校验。DSH 的[声明插件](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/preset/agent-preset/src/index.ts#L16-L29)只先检查外层，子插件由自己的校验器负责。

表达式、相对路径与条件禁用也属于真实配置。测试把 `!!js` 当字符串解析，只证明形状；从源码位置能找到资源，不证明安装后仍能找到。发布验证应使用实际包产物与目标 profile，检查必要资源、依赖和加载结果。具体安装流程由各项目拥有，不要求复制 company-pack 的启动器。

**通过条件应明确为“这份交付声明完整且可解析”，不能直接写成“角色已经可用”。** 轻量字段检查可以快速预警，但检查范围、支持语法及不识别情况需要可见；若解析器失效，应报错或明确未覆盖，不能少查几行后仍宣布全部通过。

## 二、实际组合能否激活，失败能否被定位？

通过真实应用入口加载目标 profile，再读取 preset 诊断、创建具体会话，检查所需实例与服务是否可用。当前 DSH 提前激活 preset 子树，后续读取和绑定还会重新审计等待 Host 服务的行；不是所有检查都推迟到首次任务。[激活审计](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/preset/agent-preset-registry/src/mount.ts#L134-L158)和[注册表](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/preset/agent-preset-registry/src/index.ts#L81-L145)说明了这一过程。

仅检查启动命令返回、名册有条目或没有 broken 都不够。禁用行可能有意不激活，兼容策略也可能禁用能力；某个必需服务缺失时，测试应把具体行与依赖报出来。对产品必需能力应另有正向断言，避免“没有报告失败”掩盖“根本没启用”。

company-pack 的真入口冒烟逐个创建角色与支持档会话，是这类验证的实际例子；它另外检查并发身份不串。可迁移的是走最终入口并观察绑定结果，不是“所有 preset 都必须通过 Web RPC 测试”。CLI、SDK 等产品应走自己交付给用户的入口。[案例判据](./research-company.md#3-real-mounting-adds-evidence-that-static-parsing-cannot-supply)。

## 三、这个 Agent 实际获得了什么能力与方法？

这里的 Agent 是执行任务的活跃对象；同一进程可以有多个不同组合的 Agent。应按目标会话或 Agent 查询工具与技能，不能用 Host 全局列表替代。DSH 的[作用域测试](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/preset/agent-preset-registry/tests/registry.spec.ts#L17-L35)明确验证不同 preset 的工具、提示词分别可见。

| 对象 | 建议观察 | 典型假绿 |
|---|---|---|
| 工具 | 最终名称、参数规则、可调用性及必要拒绝行为 | YAML 有插件名，却没有进入模型工具集 |
| skill | 目录成员、实际加载正文及资源解析 | 目录在磁盘，但根目录未挂载、名称冲突或正文无效 |
| persona 与必需指引 | 实际组装的请求及对应日志 | 文件存在，但被其他 persona 或组装设置遮蔽 |
| 业务事实 | 任务实际读取的来源、内容与缺失状态 | 模板或 seed 有路径，运行中却无资料或资料已过期 |
| 子会话 | 实际 preset 与能力，而非成员显示名 | 用角色名命名了 child，却继承了另一组合 |

技能 provider 与加载工具也要接通：发现目录不等于能取正文，取到正文不等于方法已经正确使用。路径优先级和同名覆盖应按真实部署检查。原生[文件技能说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/skill/skill-filesystem/README.md#L34-L85)区分目录元数据与加载正文的生命周期。

能力约束要限定范围。某个任务未暴露通用文件写入、编辑和 shell 工具，可以支持较窄的能力声明；一项任务没有修改原件是行为证据。若要承诺任何途径都不能写入，还需盘点其他工具、服务和部署权限，并验证实际执行限制。不要把 persona 的禁止、工具缺席和操作系统拒绝叫成同一种隔离。

## 四、用真实任务观察决策与交付

机制测试可以明确要求调用某工具，检查它能否执行；自主决策测试则不能把被测选择直接给出。例如要验证研究助手能选择合适协作方式，就给研究目标、约束和验收，不直接指定工具名、成员和任务图。正确方案可以多种，具体接受范围由产品需求确定。

company-pack 的组队探针明确给出了协作路线，并主要断言团队结构出现。它说明了一种通用判据风险：**测试题给出了答案，成功条件又早于任务完成。** 这适合验证指定路径，不足以证明自主判断和最终成果。[案例输入与判据](./research-company.md#6-the-product-team-probe-does-not-establish-autonomous-team-choice)。

建议从外部观察真实结果：文件内容、计算、引用、任务状态与交接。成功条件应包括需要的完成状态，而非仅看到工具调用或中间状态；失败、超时、取消与缺证据分别报告。遇到缺资料或不适用方法时，也检查是否发生了不该有的输出或修改。详细场景设计见[第三分篇](./03-behavior-evaluation.md)。

## 五、验证质量流程和检查链本身

如果 preset 内部有产出者、验证者或自动评分者，它们也属于被测产品。分别检查职责、输入、顺序、原始裁决和修订后的再验收，不因为角色叫 verifier 就采信结论。验证者不能改稿可能降低串改风险，也可能使它不能亲自跑测试；此时它判断的是别人提供的证据，需要明确证据执行者和来源。

company-pack 的质量环分开上下文、方法与裁决，并有事后审计核对日志和裁决。可借鉴的是把“谁做了什么”留下可核对记录；审计记录一致不等于裁决正确，摘要或内容哈希也不能证明被审产物在裁决后没有改变。对变更后的产物应重新验收，或清楚报告尚未复验。[质量流程的来源与范围](./research-company.md#10-补充核对质量环的实际审计与代价)。

维护者的验证链还需回答：义务写在哪里，差异怎样选中检查，runner 是否调用，必需证据是否齐全，失败是否阻止放行。检查文件存在、被导入、被执行、有本轮通过结果是不同状态。新增或修改判据时，用隔离反例证明它能拒绝目标错误；为零对象、缺证据和跳过规定可见结果。

已有案例中有“检查只验证导入文本”和“接受者未强制完整 smoke 键集合”的范围限制。它们的泛化教训是核对最终接受条件，不依赖上游总会写全的假设；具体代码分析留在[研究页](./research-company.md#5-hook-and-ci-classification-make-obligations-executable-with-deployment-prerequisites)及[发布证据](./research-company.md#9-release-evidence-binds-tests-to-bytes-but-readiness-checks-have-a-missing-key-limit)。

## 六、怎样读一份验证报告？

报告至少应让读者找到所测输入与产物、实际执行、独立期望、观察结果及未覆盖项。源码单测、真实入口、固定模型回放和真模型任务各有用途，不能以总通过数替换证明范围。对外部部署维护的业务场景，应能关联产品版本、场景归属和结果；拿不到就记录不可核实，而不是推断成功或不存在。

例如下面是一种建议报告表达，不是本轮测试结果：“新包在隔离 profile 创建会话成功；实际工具集符合预期，方法正文可加载；固定轨迹的文件断言通过；当前模型在缺资料与完整资料两项任务完成配对验收。未测跨重启恢复与长任务压力。”这比“preset 全绿，可以放心用”更能支持发布判断。

没有某层证据时，应缩小结论或补上该层观察；是否接受剩余风险由实际产品责任人决定。[下一篇](./03-behavior-evaluation.md)具体设计行为与结果判据，[维护分篇](./04-long-term-development.md)把这些观察用于后续每次改动。
