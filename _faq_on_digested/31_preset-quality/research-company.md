# External case research: company preset quality

Reference research for the independent preset-quality FAQ. These findings describe an external implementation and distinguish its declarations, executable predicates, and evidence limits; they are not Harness requirements.

## Metadata and method

- External repository: `/Users/bowhead/ai_dsh_company`.
- External snapshot: recorded only in the [central verification register](../00-baseline.md).
- Inspection date: 2026-11-20, Asia/Shanghai.
- Method: read the root instructions, preset declarations, tests, host prompt/cultivation code, check runners, hook/CI configuration, and release predicates. Only `pwd` and `git rev-parse HEAD` were executed; no external scripts, tests, builds, probes, or generators were run, and no external files were modified. No claim below means tests pass.

This is a useful guard against accidentally treating product prompts as instructions to the researcher.

## 1. What the case calls a preset

**Observation.** A concrete role preset combines a registry declaration, persona, plugin/tool rows, and skill roots. The CFO declaration supplies its id/name/description/order and nested plugins at [the declaration:7–35](/Users/bowhead/ai_dsh_company/packages/company-pack/presets/cfo/agent.cordis.yml#L7-L35); its persona assigns finance responsibilities, evidence sources, output location, and routing to skills at [the persona:35–42](/Users/bowhead/ai_dsh_company/packages/company-pack/presets/cfo/agent.cordis.yml#L35-L42). Company facts are referenced through workspace knowledge files rather than embedded as company identity in the persona.

**Observation.** Skills have several owners: packaged role skills, deliberately shared skills, and company-level role methods. CFO disables default roots and declares these paths explicitly at [skill configuration:46–62](/Users/bowhead/ai_dsh_company/packages/company-pack/presets/cfo/agent.cordis.yml#L46-L62). The skill-loading tool is separately present at [tool declaration:115–116](/Users/bowhead/ai_dsh_company/packages/company-pack/presets/cfo/agent.cordis.yml#L115-L116). Catalog discovery and the ability to load a skill body therefore require separate composition decisions.

**Observation.** A company role name does not uniquely determine the composition of every child session. The case documents teammates inheriting the Lead composition, while named activation children use the tool row's selected preset, at [session-form matrix:33–42](/Users/bowhead/ai_dsh_company/docs/contracts/presets.md#L33-L42). That is a product-specific distinction worth retaining when explaining what a preset actually controls.

**Recommendation for the FAQ.** Use this case to show that a preset is an executable composition plus model-facing instructions and discoverable methods. Describe workspace facts and operator-owned methods separately, because changing those inputs need not change the shipped preset.

## 2. Static validation has useful coverage and identifiable holes

**Observation.** The preset structure check verifies expected presets appear in the package patch list, checks referenced preset files exist, and requires role skill files with matching name text at [preset registration checks:18–58](/Users/bowhead/ai_dsh_company/checks/gates/presets.mjs#L18-L58). This catches the concrete error “directory exists but never enters the installed bundle.” Name validation uses `includes`, so it does not itself establish valid YAML frontmatter or unique names.

**Observation.** Keyless specs parse a restricted YAML representation and assert array structure, expected preset ids, plugin arrays, and top-level plugin id uniqueness at [roster specs:67–85](/Users/bowhead/ai_dsh_company/tests/presets/presets.spec.ts#L67-L85). `!!js` values are deliberately kept as strings, not evaluated, at [YAML helper:21–24](/Users/bowhead/ai_dsh_company/tests/presets/preset-yaml.ts#L21-L24). These checks cannot establish that evaluated paths or conditional groups resolve in an installed profile.

**Observation.** The required-config check extracts required top-level fields from the pinned vendor's generated configuration catalog at [catalog parser:21–41](/Users/bowhead/ai_dsh_company/checks/gates/preset-required-config.mjs#L21-L41). It rejects missing recognized keys and enforces a minimum checked-row count at [acceptance predicates:80–93](/Users/bowhead/ai_dsh_company/checks/gates/preset-required-config.mjs#L80-L93). This is stronger than a permanently hand-maintained two-field list.

**Limit.** That check explicitly skips rows with no `config` block and iterates only company roles. Its ad hoc parser collects keys nested anywhere below the detected config indentation rather than validating exact field ownership or types at [row parser:45–85](/Users/bowhead/ai_dsh_company/checks/gates/preset-required-config.mjs#L45-L85). A matching nested key can satisfy a top-level required-name comparison. The minimum row count reduces silent parser collapse but does not remove these acceptance gaps. The dependency check also iterates only company roles for preset files, uses a single-quoted-name regex there, and separately parses bundle inserts at [dependency implementation:27–53](/Users/bowhead/ai_dsh_company/checks/gates/preset-row-deps.mjs#L27-L53); support coverage must come from other tests or mounting.

**Observation.** Many semantic regressions are guarded by text presence. For example, CEO team selection and single-artifact routing use regexes at [routing specs:248–256](/Users/bowhead/ai_dsh_company/tests/presets/presets.spec.ts#L248-L256), while shared method and document-chain assertions mostly use `toContain`/`toMatch` at [shared capability specs:534–565](/Users/bowhead/ai_dsh_company/tests/presets/presets.spec.ts#L534-L565). Such tests can preserve a known instruction but cannot show the model follows it or that the instruction remains effective under competing context.

**Recommendation for the FAQ.** Explain precisely what static checks establish: parseability of the tested representation, registration, declared capabilities, and known text invariants. Avoid translating their green result into mounted availability or behavioral quality.

## 3. Real mounting adds evidence that static parsing cannot supply

**Observation.** The real-entry preset smoke queries the roster for missing/broken rows, then creates a session for every company role and support preset and verifies returned preset identity and session id at [mount assertions:154–175](/Users/bowhead/ai_dsh_company/checks/lanes/preset.entry.mjs#L154-L175). It also creates CEO and VP-Eng concurrently and requires distinct ids with correct presets at [concurrency assertion:178–188](/Users/bowhead/ai_dsh_company/checks/lanes/preset.entry.mjs#L178-L188).

**Observation.** For presets with a local skills directory, the smoke calls session-addressed `skills/list` and rejects both unexpected and missing skill names at [catalog comparison:217–229](/Users/bowhead/ai_dsh_company/checks/lanes/preset.entry.mjs#L217-L229). Expected names include locally installed role methods, so the check accommodates operator customization instead of misclassifying every method as a leak. Shared-root expectations are inferred from declared path tokens at [expected roots:44–62](/Users/bowhead/ai_dsh_company/checks/lanes/preset.entry.mjs#L44-L62).

**Limit.** This demonstrates catalog membership when run, not loading or use of skill bodies. The set being checked depends on the presence of a local `skills` directory; the script does not test every support preset's possible catalog. Expected method names are directory names at [method enumeration:77–85](/Users/bowhead/ai_dsh_company/checks/lanes/preset.entry.mjs#L77-L85), not an independent validation of method content or application. The source explicitly distinguishes client-module closure lint from actual client loading at [client closure scope:232–243](/Users/bowhead/ai_dsh_company/checks/lanes/preset.entry.mjs#L232-L243).

**Recommendation for the FAQ.** Treat mount, catalog visibility, successful skill-body retrieval, actual skill invocation, and task outcome as separate observations. This repository supplies concrete mechanisms for the first two, but they should not be advertised as all five.

## 4. Prompt assembly and skill loading are controlled, but that is not an injection defense claim

**Observation.** The host injects the company handbook as a named system-prompt section rather than relying on workspace instruction-file discovery. It prefers a workspace override when present at [handbook source selection:34–50](/Users/bowhead/ai_dsh_company/packages/company-pack/src/host/prompt/handbook.ts#L34-L50), reads it once during registration, skips non-role presets, and registers the section at [injection implementation:71–87](/Users/bowhead/ai_dsh_company/packages/company-pack/src/host/prompt/handbook.ts#L71-L87). The byte limit emits a warning and still injects the full text; it is not a runtime truncation barrier.

**Observation.** Engine usage rules can be made mandatory context while methods remain on-demand. Workflow instructions are injected only when a workflow tool is detected or an explicit preset fallback matches at [capability predicate:41–49](/Users/bowhead/ai_dsh_company/packages/company-pack/src/host/prompt/contracts.ts#L41-L49) and [registration:63–84](/Users/bowhead/ai_dsh_company/packages/company-pack/src/host/prompt/contracts.ts#L63-L84). The static loader-pair check enumerates all preset directories and requires `dsh-tool-skill` whenever `dsh-skill-filesystem` appears at [loader pairing:298–311](/Users/bowhead/ai_dsh_company/tests/presets/presets.spec.ts#L298-L311).

**Limit.** Explicit roots reduce accidental exposure to unrelated project/user skills; they do not by themselves prove resistance to malicious documents or malicious skills. The company security scan targets packaged `content`, not the live company workspace or the preset/method roots, at [scan target:29–39](/Users/bowhead/ai_dsh_company/checks/gates/security-scan.mjs#L29-L39). Its acceptance table permits “no input” code 3 at [decision table:41–67](/Users/bowhead/ai_dsh_company/checks/gates/security-scan.mjs#L41-L67). It is not evidence of live adversarial model resistance. The inspected handbook code promotes a workspace override to a system section without content trust classification; authorized override capability should be described as such.

**Recommendation for the FAQ.** Distinguish “prompt content was intentionally injected” from “prompt injection attacks are resisted.” Test the latter with untrusted input and a concrete forbidden action if making that claim; the mechanisms inspected here do not establish it.

## 5. Hook and CI classification make obligations executable, with deployment prerequisites

**Observation.** The pre-push hook executes structural checks, type checks, lint/duplication, fast smokes, changed-file-selected entry checks, check self-tests, and the coverage ratchet at [hook commands:25–44](/Users/bowhead/ai_dsh_company/.githooks/pre-push#L25-L44). The selector obtains outgoing paths from actual push ref pairs, including new-branch commit traversal and merge handling at [range calculation:76–123](/Users/bowhead/ai_dsh_company/checks/pre-push-surfaces.mjs#L76-L123). Unclassified paths produce a nonzero result at [classification enforcement:143–151](/Users/bowhead/ai_dsh_company/checks/pre-push-surfaces.mjs#L143-L151) and [final enforcement:188–201](/Users/bowhead/ai_dsh_company/checks/pre-push-surfaces.mjs#L188-L201).

**Observation.** Changes under packaged presets select the real mounting smoke, and host entry/bundle patch changes also select it, at [surface mapping:360–384](/Users/bowhead/ai_dsh_company/tools/lib/core/asset-lanes.mjs#L360-L384). Model probes, including product-team behavior, have empty automatic-lane arrays at [manual model assets:298–320](/Users/bowhead/ai_dsh_company/tools/lib/core/asset-lanes.mjs#L298-L320). The preset mounting asset is explicitly not CI-safe because it needs installed dev-profile state at [preset registration:214–220](/Users/bowhead/ai_dsh_company/tools/lib/core/asset-lanes.mjs#L214-L220).

**Limit.** Push/PR CI only installs dependencies and runs structural verification at [CI steps:21–39](/Users/bowhead/ai_dsh_company/.github/workflows/ci.yml#L21-L39). Full macOS setup, tests, keyless CI-safe sweep, and coverage are weekly/manual at [fresh-clone trigger:11–15](/Users/bowhead/ai_dsh_company/.github/workflows/fresh-clone.yml#L11-L15) and [macOS steps:64–75](/Users/bowhead/ai_dsh_company/.github/workflows/fresh-clone.yml#L64-L75). A local hook bypass therefore has different assurance from a required per-PR behavior lane. File classification also describes selected obligations, not their sufficiency for each behavioral change.

**Observation and limit.** The system guards against orphan checks, but the wiring check only looks for import text at [wiring predicate:16–26](/Users/bowhead/ai_dsh_company/checks/gates/gate-wiring.mjs#L16-L26); it does not require a corresponding `.run(ctx)` call. The runner currently does call the preset checks at [runner:149–157](/Users/bowhead/ai_dsh_company/checks/run-gates.mjs#L149-L157). Similarly, negative-example enforcement requires incident cards and dated recipe text at [red-record predicates:45–71](/Users/bowhead/ai_dsh_company/checks/gates/guard-red-record.mjs#L45-L71), not reproduction of the alleged failing test.

**Recommendation for the FAQ.** Preserve the distinction between a documented obligation, a registered asset, a selected lane, an invoked check, and current execution evidence. This case is strong at connecting changes to checks, while its meta-checks still have exact, reviewable limits.

## 6. The product-team probe does not establish autonomous team choice

**Observation.** The real-model product-team probe's prompt explicitly commands exact teammate names, `spawn_teammate`, avoidance of named delegation, two owner tasks, and a dependency edge at [prompt:59–65](/Users/bowhead/ai_dsh_company/checks/lanes/product-team-e2e.entry.mjs#L59-L65). Its predicates poll the team projection, look for those names and owners, and stop once members/tasks/edge exist at [polling:94–110](/Users/bowhead/ai_dsh_company/checks/lanes/product-team-e2e.entry.mjs#L94-L110).

**Limit.** Those assertions support instruction compliance and projection wiring. They do not establish that the CEO independently chose team assembly from the artifact request, despite the stronger claim in the script's [header:3–14](/Users/bowhead/ai_dsh_company/checks/lanes/product-team-e2e.entry.mjs#L3-L14). They do not assert completed or substantively valid MRD/PRD files, final delivery, or `present`. The extra-member predicate rejects three known role names, not every unexpected member. The loop uses the current sampled projection, not a full history of transient actions.

**Recommendation for the FAQ.** Use this as a concrete example of why the task prompt and success predicate must be read together. To evaluate autonomous routing, supply the business request without the answer, then judge tool choices and delivered work independently.

## 7. Long-term method quality has a human-controlled evolution loop

**Observation.** Methods declare applicable product types/delivery modes and required knowledge files. The check parses declarations, validates ids against installed content directories, checks fact paths against seed targets, requires `fail-closed` text for required facts, and requires workflow routing text at [method predicates:99–157](/Users/bowhead/ai_dsh_company/checks/gates/method-contract.mjs#L99-L157). This addresses concrete misuse of an otherwise plausible method in the wrong business setting. It validates declarations and seeded paths, not whether live facts are adequate or whether a model actually refuses an unsupported task.

**Observation.** The model-facing tool offers proposals, while adoption is a separate human command registration at [proposal API:669–699](/Users/bowhead/ai_dsh_company/packages/company-pack/src/host/cultivation/cultivation.ts#L669-L699) and [command registration:780–786](/Users/bowhead/ai_dsh_company/packages/company-pack/src/host/cultivation/cultivation.ts#L780-L786). Adoption checks open status, target role, configured method root, safe slug, and non-overwrite installation, with rollback on record conflict at [adoption predicates:445–486](/Users/bowhead/ai_dsh_company/packages/company-pack/src/host/cultivation/cultivation.ts#L445-L486).

**Observation.** Post-adoption verification requires a pass/fail value, nonempty bounded evidence, adopted and non-revoked status, and the correct role, then appends timestamped verification history at [verification predicates:514–546](/Users/bowhead/ai_dsh_company/packages/company-pack/src/host/cultivation/cultivation.ts#L514-L546). Revocation refuses unreachable records and requires an explicit orphan confirmation when no local adoption record exists at [revocation predicates:348–379](/Users/bowhead/ai_dsh_company/packages/company-pack/src/host/cultivation/cultivation.ts#L348-L379).

**Limit.** Adoption checks role-session identity, not independently authenticated natural-person identity; verification accepts an evidence string rather than independently replaying a task. The cultivation document explicitly limits write isolation to `workspace-write`, excludes support presets from the adoption pipeline, and states the human-maintainer dependency at [scope:13–22](/Users/bowhead/ai_dsh_company/docs/contracts/cultivation.md#L13-L22) and [isolation limits:47–54](/Users/bowhead/ai_dsh_company/docs/contracts/cultivation.md#L47-L54). Removing a method does not erase text already loaded into session history at [effect timing:35–40](/Users/bowhead/ai_dsh_company/docs/contracts/cultivation.md#L35-L40).

**Recommendation for the FAQ.** This is evidence for controlled method evolution, recorded adoption, and observable feedback. Describe “adopted,” “verified by reported follow-up,” and “demonstrated generalization” separately; only the first two have direct mechanisms here.

## 8. Behavioral corpus migration limits what this checkout can substantiate

**Observation.** The product snapshot index says real deployment evidence moved to private archives and lists a synthetic file-tool replay, isolated empty-shell UI expectation, and entry-question answer archive at [snapshot inventory:3–18](/Users/bowhead/ai_dsh_company/snapshots/README.md#L3-L18). It explicitly labels expected workspace output as authored, not an independent oracle.

**Observation.** The injection-freshness check skips non-runnable, headless, and presence-only cases at [selection:36–46](/Users/bowhead/ai_dsh_company/checks/gates/replay-fixture-freshness.mjs#L36-L46), and reports an explicit SKIP when no applicable scenes remain at [no-object result:74–79](/Users/bowhead/ai_dsh_company/checks/gates/replay-fixture-freshness.mjs#L74-L79). The runner recognizes this expected skip at [runner skip policy:101–109](/Users/bowhead/ai_dsh_company/checks/run-gates.mjs#L101-L109). That is more honest than printing PASS over zero applicable scenes.

**Limit.** The public/product checkout cannot independently supply the migrated behavioral regression corpus. Quality-loop specs explicitly say they guard declarations and that one real-model E2E's evidence lives in a Note rather than regression at [quality-loop scope:5–7](/Users/bowhead/ai_dsh_company/tests/presets/quality-loop.spec.ts#L5-L7). The declared verifier composition removes file writes/edits and bash at [verifier predicates:110–127](/Users/bowhead/ai_dsh_company/tests/presets/quality-loop.spec.ts#L110-L127); that capability restriction is useful but does not establish independence of judgment or review quality.

**Recommendation for the FAQ.** State where behavior evidence lives and whether the current reader can reproduce it. Treat a runnable synthetic pipeline, a recorded prior outcome, and maintained company-behavior coverage as different assets.

## 9. Release evidence binds tests to bytes, but readiness checks have a missing-key limit

**Observation.** Release preparation records `not-run`, and verification aligns source/pipeline/artifact fingerprints before executing checks at [prepare and alignment:270–296](/Users/bowhead/ai_dsh_company/tools/release/release.mjs#L270-L296). The normal verification path runs structural tests, keyless tests, the exact tarball with expected hash, company entry, client loading, preset mounting, and present-catalog checks, records failures immediately, and writes results at [verification sequence:298–323](/Users/bowhead/ai_dsh_company/tools/release/release.mjs#L298-L323). Manifest fields include source/pipeline fingerprints, runtime information, artifact identity, and per-check statuses at [manifest:250–265](/Users/bowhead/ai_dsh_company/tools/release/release.mjs#L250-L265).

**Observation.** Artifact validation compares tarball, sidecar, and generated manual hashes and checks the manual against the current template at [artifact validation:171–193](/Users/bowhead/ai_dsh_company/tools/release/release.mjs#L171-L193). Runtime comparison verifies vendor HEAD, dirty status, and built CLI hash at [runtime fingerprint:105–119](/Users/bowhead/ai_dsh_company/tools/release/release.mjs#L105-L119). This ties evidence to concrete installed bytes more tightly than a free-form “tested” claim.

**Limit.** Shared readiness requires `verify` and `test` to equal `pass`, then rejects any present non-pass check, but does not require the other smoke names to exist at [readiness predicates:67–75](/Users/bowhead/ai_dsh_company/tools/lib/release/readiness.mjs#L67-L75). A manifest with just the two required pass keys can satisfy this portion of readiness; the normal producer emits more, but the consumer does not enforce the complete expected inventory. Matching a built CLI hash also does not independently attest that all runtime artifacts came from a clean build. The release document acknowledges warm-tree scope and the missing clean-clone release replay at [release scope:140–144](/Users/bowhead/ai_dsh_company/docs/contracts/release.md#L140-L144).

**Recommendation for the FAQ.** Reuse the idea of evidence tied to source, pipeline, runtime, and artifact identity. Require the reader to inspect which checks the acceptance predicate actually demands; a manifest's existence or a READY label alone does not establish an exhaustive quality claim.
