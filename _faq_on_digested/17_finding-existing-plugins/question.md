# Question 17 · 开发 DSH 插件时，怎么先找到现成的轮子而不是重写？

## 背景

开发 DSH 插件一阵子后的顿悟：**利用现成插件非常重要，但原来完全没有头绪**。`packages/` 下有 316 个包（`dsh-v0.2.0-rc.2` 实测），却在动手时想不起「这个能力是不是已经有了」；等写完才发现某个 seam、某个工具、某个配置字段早就存在。这与传统框架的「先查 API 文档」直觉相悖——DSH 的能力不在一个目录里，也不在一份文档里。

## 问题

1. 「我要一个能力 X」时，怎样**系统性地**确认 dsh 是否已经提供了它，而不是凭记忆或运气？
2. 找到之后，怎么知道它**以什么形态**给（ctx 服务？模型工具？bundle？配置字段？）以及**默认拿不拿得到**？
3. 哪些情况才真的**必须自己写**？判断依据是什么？
