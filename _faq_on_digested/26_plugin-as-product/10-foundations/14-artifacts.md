# 14 · 产物不是副本：present、changes、附件、spill

## 这一篇回答什么

这一篇是**内容家**的一个切片：四层词汇见 [10](./10-taxonomy.md)，五个家见 [11](./11-five-homes.md)，空间归属见 [15](./15-four-spaces.md)。

这些产物最终落在 workspace、附件库或临时目录。用户口中的“artifact / 产物”在 DSH 里对应什么？为什么 `present` 只记路径？附件库和 `present` 有什么区别？什么时候该用 spill？把文件写到哪里，用户才能找得到？

![产物的引用与导出](../figures/14-artifact-refs.svg)

## 先给结论

**DSH 没有通用 artifact store。** 它把“产物”拆成几种引用机制，每种服务不同的读者：

| 机制 | 记录什么 | 内容在哪 | 寿命 | 读者 |
|---|---|---|---|---|
| `present` | 文件路径 + 描述 | 原文件不动 | 一条 `deliverables/presented` 事件 | 用户 |
| `workspace/changes` | 这一轮改了哪些文件 | 工作区 + 临时快照/整文件副本 | 摘要留在 Host 内存，会话销毁即止 | 用户 review |
| 附件（attachments） | 不可变二进制的引用 + 元数据 | `$DSH_HOME/attachments/v1` | 本地后端目前**一直保留**；没有自动 GC | 模型输入 |
| spill | 大段文本 + 定位符 | 本地后端默认在 **OS 临时目录**（不在 `$DSH_HOME`） | 启动时按 `cleanupPeriodDays`（默认 30 天）清理 | 模型与工具 |
| 会话导出 | 日志 + 附件 + 子会话的 ZIP | 浏览器下载 | 用户保存的那份 | 用户备份 |

共同点：**内容留在它原本该在的地方，DSH 只记录“怎么找到它”。** 例外是附件和导出：它们确实复制字节，因为模型输入/备份需要一个不受原文件影响的不可变对象。

## `present`：把文件声明为交付物

`present` 是模型-facing 的工具，插件也可以调用同一套语义：

- 输入是 `files: [{ path, description? }]`；相对路径按会话 cwd 解析，绝对路径可以指向 cwd 之外（例如 `/tmp` 或 Downloads）；
- 只接受**可读的普通文件**；目录、最终符号链接、缺失文件、provider 拒绝的路径都会失败；
- 通过后把**绝对路径**写进 `deliverables/presented` 事件（`{ turn, callId, files }`），**不复制内容**；
- 挂载配置 `maxFiles` 的默认上限是 8（部署可配）；模型-facing 的 schema 建议“通常 1–2 个、每次最多 4 个”，4 是建议不是强制上限；
- 交付属于调用它的会话，父会话要让子会话自己 `present`；
- 需要 agent Session、workspace 和已打开的 turn；不是任意宿主上下文都能调用。

这意味着：**文件必须已经在工作区（或用户可访问的位置）**。如果你把一个报告写进 `$DSH_HOME` 的私有目录再 present，用户打开的是那个路径——能找到，但它不在项目里，也不会跟着项目走。

`present` 的另一个边界：它记录的是**路径**，不是内容。文件后来被改了，用户打开看到的是新内容；文件被删了，交付就指向不存在。会话导出 ZIP 包含声明，不包含被 present 的文件内容。

## `workspace/changes`：这一轮改了什么

它解决的是 review，不是交付：

- 每轮开始/结束对 git 工作树做快照，diff 出改动；git 覆盖不到的文件，在文件工具编辑前后做整文件捕获；
- 快照用临时 git 对象目录，整文件副本放在**会话的临时目录**（OS 临时目录下的 `dsh-workspace-changes-*`）；这些都不在 `$DSH_HOME`；
- 会话日志里只写一条 `workspace/changes { turn }`；摘要与逐文件对比留在 Host 内存，**会话销毁即止**；
- 能报告新增/删除行数、二进制、超大文件；受 `maxFiles`（默认 500）、`maxFileBytes`（默认 2 MiB）、`diffTimeoutMs`（默认 100 ms）限制；
- 会话重开后，早先轮次没有改动卡片，也没有 diff。

所以它是“这次改动的说明”，不是“改动本身”。真正的改动在文件系统里，别把它当成可回放的补丁库。

## 附件：给模型看的不可变字节

- 附件是**内容寻址、不可变**的；本地后端把对象放在 `$DSH_HOME/attachments/v1`，ID 形如 `sha256:…`，但消费者不得解析这个表示或据此拼路径；
- 图片会验证类型/尺寸并归一化；也有通用文件入口；
- 会话事件只携带附件引用与元数据，不携带 base64、临时路径或 provider URL；
- **它的职责是让模型能读到二进制**，不是让用户下载交付物；
- 本地后端目前**保留所有对象，没有自动 GC**。附件服务被刻意设计成 retention-neutral：resume/fork 的会话可能共享同一个对象，所以不能把清理绑在单个会话删除上。作者在 2026-07-22 的决策里明确写：引用感知 GC 需要单独的引用模型，按年龄删会删掉仍被引用的数据。**H/C**
- 由于 session 没有删除 API，删日志/删工作区不会触发附件回收；对象会变成孤儿。**C**

如果你要交付一张图，正确顺序是：把图写到工作区文件 → 用 `present` 声明它。把图塞进附件库再告诉用户“去看附件”，不是 DSH 的交付模型。

## spill：上下文管理的产物

- `ctx.spillStore.saveText` 把调用方给的文本**原样**持久化，返回不透明定位符、检索提示与字节数；
- `owner` 是会话；`source` 说明是哪个工具/哪个会话引用产生的；`suggestedName` 只是命名提示，不是路径；
- 本地后端默认把文件放在 OS 临时目录下的私有（0700）root，按 session 哈希分组；启动时做一次清理，删除 `cleanupPeriodDays`（默认 30）之前的文件；
- 它服务“结果太大，放进上下文不划算”的场景；保留期清理可能让旧定位符过期，它不是长期归档；
- **本地默认根在 OS 临时目录**，跨进程不可见（每个进程 `mkdtemp` 一个随机根），长跑进程不会再次 sweep；部署可以配 `root` 把它放到已知位置，但 shipped base 行没有配。**C**
- spill 的读者是模型与工具，不是用户。别把用户要的最终文件放进 spill。

## 会话导出：备份的是日志与附件，不是工作区

Web 的 `/export`（或 Session Header 的 Download session log）会把会话树——当前会话、子会话、附件——打成 ZIP 下载：

- 日志按当前世代的规范文件名；图片在 `media/`，通用文件在 `files/`；
- live session 会先 flush，保证导出的日志包含最新事件；
- **被 `present` 的工作区文件不在 ZIP 里**，ZIP 里只有声明；用户要带走报告，得自己从工作区拿；
- 导出是“会话备份”，不是“项目备份”。

## 什么时候用哪个

| 你想做的事 | 用什么 | 不要用 |
|---|---|---|
| 给用户一份报告/图片/代码 | 写工作区文件 + `present` | 写 home 私有目录、附件库 |
| 让用户看这轮改了哪些文件 | `workspace/changes`（已自动） | 自己再存一份 diff |
| 让模型读用户上传的图片 | 附件服务 | 把图片塞进提示词 base64 |
| 工具输出太大，放不进上下文 | spill | 截断后丢掉、写进 domain |
| 跨会话保留一份用户产物 | 工作区文件（项目内） | spill、附件、会话日志 |
| 备份整段会话（含图片） | `/export` ZIP | 只复制 `sessions/` 目录 |

## 四个容易被忽略的边界

1. **`present` 不是复制**：这是“引用”的代价，也是用户仍然拥有自己文件的好处。
2. **附件不是项目的**：它在 `$DSH_HOME`，按内容寻址，跨会话可共享；它不会跟着项目走，也没有“删项目就删附件”的语义。**C**
3. **`workspace/changes` 不是持久证据**：摘要只在 Host 内存里活到会话销毁；要长期保留改动记录，靠 git 或你自己的状态。
4. **spill 不是缓存服务**：它没有查询、没有索引、没有按 owner 枚举；清理是启动时的一次性 sweep，不是事务。**C**

## 一个正确的交付流程

```text
1. 在会话 cwd 下生成文件（ctx.fs.writeText / 工具）
2. 需要的话做校验、格式化、写配套说明
3. 调用 present（路径 + 描述）
4. 用户在对话末尾看到文件卡片，打开的是原文件
5. 需要 review 时，workspace/changes 已经记录了这轮改动
```

这条流程里，DSH 没有复制任何东西：文件属于用户，记录属于会话，引用把两者连起来。

## 产品型实例里怎么用

| 产品里的"产物" | 应该用 | 不要用 |
|---|---|---|
| 用户要打开/带走的文件（deck、报告、导出） | workspace 文件 + `present` | 附件库、spill |
| 产品自己的模板/素材 | 插件包只读层，或复制到 workspace | 写进 `$DSH_HOME/<plugin>` 当用户内容 |
| 会话中间的大段输出 | spill | 交付目录 |
| 备份/迁移 | 会话导出 + 用户自己的目录备份 | 依赖附件库的 GC |

产品型实例最容易犯的错：**把交付物写进附件库或 `dataRoot`**——用户找不到、换机器丢、没有 GC。交付物必须落在用户能看见的 workspace 里。

## 边界

- 本篇不展开 `present` 的 UI 渲染与 `workspace/changes` 的 git 细节；只讲数据归属与引用语义。
- 附件的清理/保留策略是后端/部署的事；本地后端目前不清理，也没有“永久归档”的承诺。
- spill 的保留期与清理策略由后端决定；不要把 locator 当长期 URL。
- 会话导出是 Web 能力；headless/SDK 组合不一定挂载它。
- 删除/保留是系统性空白：session 无删除 API、附件无 GC、插件无卸载契约；外部插件有物理删日志/改 header 的补丁（E1，参考），但那是高风险反模式（见 33）。
