# FAQ 13 · 做一个“领域专家” DSH 插件，代码仓库该怎么组织？

## 背景与困惑

想基于 DSH 开发一套面向特定业务领域的“专家套件”：它有多条信息处理流，需要把上下文、专属工具、系统提示词和技能（Skill）严格收拢在自己的边界里，不污染其他普通会话，必要时还要配专属的 Web 界面卡片或面板。

在搭代码仓库和设计日常研发流时，我们既希望**仓库内的 Coding Agent 能直接读到 DSH 的文档与源码**（不用盲猜接口或反复切目录），又希望本地插拔调试顺手、升级跟进成本低，并且不会把日常干活正在用的官方 DSH 环境搞崩。这背后其实卡着五个具体的架构与工程问题：

1. **入口与交付形态**：这个“领域专家”到底做成什么？需要新写一个可执行入口或独立 Profile，还是发一个带 `agent-preset` 的 Bundle 包？
2. **包粒度与目录演进**：第 0 天该单包起步，还是按 `Service Definition / Provider / Consumer` 拆成多包？什么时候才值得拆？
3. **DSH 源码怎么放**：独立仓库配 `vendor/dsh` 子模块、直接在 DSH 主仓 `packages/` 里长、纯 npm 外部依赖，还是多专家 Marketplace 单体仓，四种方案各自怎么取舍？
4. **日常调试与双环境隔离**：怎么把本地源码免发版挂进 Profile 快速验证？怎么做到“开发侧随便折腾，日常 `~/.dsh` 毫发无伤”？
5. **UI 分层、不可变命名与规范纪律**：前端卡片和面板走哪层扩展？哪些包名和 ID 第 0 天定错就极难反悔？仓库文档与决策记录该借用 DSH 哪几招，什么时候才需要上 OpenSpec？

## 范围说明

- **本组回答**：外部团队或独立作者组织严肃 DSH 插件/专家套件仓库的架构选型、源码接入、双环境隔离、不可变命名与日常工程闭环。
- **插件打包与数据落点**：`package.json` 校验细则与运行时数据归属见 [FAQ 24](../24_plugin-publishing-and-data/answer.md)。
- **安装路径与整包发行**：桌面端与 CLI/Web 免发版挂载细节见 [FAQ 23](../23_standalone-vs-web-release-forms/02-plugin-install-and-dev-bypass.md)；若要连宿主外壳一起打包交付定制工作台，见 [FAQ 26](../26_harness-distribution/answer.md)。
