# 07 · 该不该 check in：进，但分三类——增长靠阀门，不靠节食

## 一句话

**check in。** 三个仓（主仓 + 两个真实插件仓）全都这么做了，而且这是被设计决定的，不是偏好：**夹具进了 git，「无 key 回归」才成立**——CI 从仓里读回放输入，PR 里才能逐行审 diff，录制身份才有地方落。你担心的两件事都有实测答案：**增长是 O(触发的回归数)，不是 O(时间)**；**占用是每个场景几十 KB，不是每场景几 MB**。真正要管的是边界（什么不进）和删除判据（什么时候删），不是「要不要进」。

## 三类东西，三类待遇

| 类 | 内容 | 待遇 | 依据 |
|---|---|---|---|
| **必须进** | 回放输入与期望输出：`session.vN.jsonl`、`expected.dom.json`、`ui.expected.md`、`replay.override.json`、`world.expected.json`、场景声明（manifest / snapshot.yml） | 提交，且**与代码同 PR**（改了模型可见面却不动夹具 = 要么不可见要么不变量破了） | `snapshots/AGENTS.md:17`：「每个 resulting JSONL、prompt、schema、protocol、UI、workspace diff 都在提交前人工过目」 |
| **绝不进** | 运行时原始日志（dev home / `~/.dsh` 的 sessions）、PNG/截图等拍摄副页、临时录制、未脱敏的用户内容 | gitignore；审完即弃 | 主仓 `.gitignore:14` 的 `.sessions/`——**录制原料不进，证据才进**；assistant 把 PNG 放临时目录、「肉眼核过再提交 JSON」 |
| **按需进** | 场景本身 | 每一条都要过 [05](./05-plugin-repo-organization.md) 的触发条件；**删除判据 = README 合同里「这条轨迹防什么」不再成立** | 触发条件表 + 一场景一 README |

assistant 的 `.gitignore` 第 7 行把这条边界写成了一句注释，值得抄走：

> `# snapshots/  录制会话与预期（证据，不是产物）`

**「证据，不是产物」**——运行产物（每次跑都会再生的）进 git 是垃圾；证据（审阅过、可重放的判定基准）不进 git 就等于没有。

## 实测：到底多大

| 仓 | 场景数 | tracked 字节 | 折算 |
|---|---|---|---|
| DSH 主仓 `snapshots/` | 210 | **6.7 MB**（444 个 jsonl 共 4.1MB + schema sidecar json 1.7MB + md/yml…） | **~32 KB / 场景**；最大单文件 77KB（`tool-schemas.expected.json`） |
| `ai_dsh_deep_research/snapshots/` | 1 族 4 角色 | **~270 KB**（lead 夹具 127KB 是最大的，含完整工具 schema） | 一个四角色组装面 ≈ 0.3MB |
| `ai_dsh_assitant/snapshots/` | 2（渲染期望） | **几 KB** | 窄带 DOM 证据极小 |

主仓的增长轨迹（浅克隆窗口内，tracked 字节）：8 月末 3.3MB → 9 月末 6.7MB——**主仓最重的一个月（735 次触碰 snapshots 的提交、大量新场景）翻了一倍，绝对值也就是 3MB**。9 月之后持平。git 对这种逐行文本还有 3–5 倍的 packfile 压缩，clone 实际拉下来的更小。

**这就是为什么「占用大」是错觉**：一个插件仓哪怕建 20 个场景，也就是几百 KB——比一张截图小。

## 增长模型：为什么不会没完没了

增长有没有界，取决于增长源是什么。这条 lane 的增长源**不是时间，是触发**——[05](./05-plugin-repo-organization.md) 的触发条件表就是增长阀门。四个反增长杠杆，按效力排序：

1. **重录替代世代。** DSH 保留多代 fixture 是主仓义务（格式迁移覆盖），**插件仓不用背**：重录 = 覆盖不是累加。这是最大的一条——主仓 444 个 jsonl 里相当一部分是历史世代，你没有这份负担。
2. **窄带金标准。** 只钉确定性面：assistant 的 DOM 证据只比对面是 `visibleText`/`controls`/`consoleErrors`，PNG 不进 git；deep_research 的 `ui.expected.md` 只钉卡标题与活动行、「不钉工具结果体/时间戳/bundle 渐进面」。钉得越窄，文件越小、diff 越可读、假红越少。
3. **README 合同让删除可判。** 每个场景一句话「这条轨迹防什么」。半年审一遍：触发条件还在吗？不在就删。**没有这句话的场景才是「没完没了」的真正来源**——不是 git 的问题，是没有删除判据。
4. **`authored` 优先。** 能手写 22 行最小轨迹钉住的，就不要录 79 行带完整工具目录的。

### 什么时候才真的该担心

| 信号 | 含义 | 处置 |
|---|---|---|
| 单个夹具 > 200KB | 你在钉工具结果体 / 整页 DOM / 全量 schema 而它不该钉 | 窄带化：比对面收窄，或 schema 走独立 sidecar |
| 场景数多到数不过来 | 触发条件没被执行，或 README 合同缺失 | 逐个问「它防什么」，答不上就删 |
| 出现没有 README 的场景目录 | 半年后没人敢动它 | 补合同或删 |
| 同一场景积了多代 `session.v2/v3/v4` | 你在背主仓的世代义务 | 留最高一代，其余删（插件仓无迁移覆盖义务） |

这些是「该删 / 该窄带化」的信号，**不是「不该 check in」的信号**。

## 两个补充判断

**git history 会不会越积越大？** 会——每次重录都在历史里多一版 fixture，且 packfile 不会自己瘦。但算一下量级：插件仓一年重录 50 次 × 30KB ≈ 1.5MB 历史，完全无所谓。DSH 反而**要**这份历史（世代不可变是它的迁移覆盖设计）。你不需要。

**要不要 git LFS？** 不要。夹具全是逐行文本——git 的 diff、grep、审阅全建立在文本上；进 LFS 等于自废「每个 diff 人工过目」这条命根子，换来的空间节省在几百 KB 量级。唯一值得 LFS 的场景是你未来要提交大量 PNG 视觉证据——而正确做法是 PNG 根本不进 git。

**「不进 git」的替代方案为什么都不成立**：放本地 / 对象存储 → CI 的无 key 回放直接跑不了（keyless 的前提就是物料在仓里），PR 里看不到 diff，「人工过目」无从执行，录制身份没有锚；放独立仓 / 子模块 → 夹具必须与 `codeAnchor`（录制时的代码版本）同 commit 才能解释，拆开等于把证据和它的解释力分开。

## 这一篇要你记住的

- **check in**——「证据，不是产物」；不进 git 的证据等于不存在。
- 三类待遇：夹具与期望**必须进**（同 PR）；运行时日志与拍摄副页**绝不进**；场景本身**按触发进**。
- 增长由触发条件阀门控制，四个反增长杠杆：重录替代世代、窄带金标准、README 合同让删除可判、`authored` 优先。
- 实测：主仓 210 场景才 6.7MB（32KB/场景）；你的插件仓会是几百 KB。该担心的是「没有 README 合同的场景」和「超大的单夹具」，不是 git。
- 不要 LFS——文本 diff 是这条 lane 的命根子。
