# Question 21 · 录制会话快照（`snapshots/`）：主仓为什么离不开它，独立插件仓到底该不该用？

## 背景与困惑

翻看 DSH 主仓库时，顶层那棵庞大的 `snapshots/` 目录非常抢眼：里面存着数百个场景的 `session.jsonl` 与请求头期望文件，而且仓库开发规范明确规定——凡是涉及模型可见输入、协议交互或用户界面可见变化的改动，都必须在同一个 PR 里新增或更新无密钥录制会话快照（`pnpm run test:snapshot`）。

如果你正在主仓之外独立开发一个 DSH 工具插件、领域智能体包或带自定义界面的扩展仓，很容易在这个问题上犯嘀咕：这套重型快照看起来像是大仓库为了管住几百个内置插件才搞出来的内部制度；我的小插件仓已经写了单元测试，还有必要跟进这套机制吗？

具体拆开，就是下面四个工程决策问题：

1. **主仓为什么非要它不可？** 单测行覆盖率已经硬卡到 100%，为什么仍然替代不了录制会话回放？一份 `session.jsonl` 到底记了什么、怎么重放？
2. **外部插件仓能不能直接拿来用？** 回放机制是锁死在主仓内部脚本里，还是已经发成了公开 npm 包？最小可用配置该怎么接线？
3. **对插件作者来说，它的真实收益和硬上限在哪？** 锁定模型请求头、复现偶发模型流 bug 值不值得投入？为什么说“快照绿了不代表代码对”？
4. **插件仓该按什么顺序搭测试体系？** 什么时候优先选界面渲染期望、什么时候才上完整会话回放？目录该放顶层 `snapshots/` 还是 `tests/` 下，夹具文件该不该提交进 Git？
