# 01 · 生态证据与历史先例（2026-08-27/28 核查版）

本篇回答一个前置问题：**"插件化 agent 平台"这个赌注，有没有被验证过？** 两条证据线：历史先例（同一内核的上一轮成功）与当下生态（第三方已经在长什么）。核查日期即标题日期；仓库外链接只做生态与定位判断，不进入机制论证，未做长期可用性承诺。

## 核查方式

- 仓库内事实：vendor manifest（[`vendor/README.md`](../../vendor/README.md)）、生成目录（[`docs/capability-seams.md`](../../docs/capability-seams.md)）、各包 README，以 `_digested/` 钉的基线为准；
- 仓库外链接：逐条 HTTP 请求复核可达性；GitHub 仓库用 `api.github.com` 复核存在性；目录站数字为其自报值，本文件做了抽样与分类加总核对（见下方"目录站快照"）。

## 历史先例：Cordis 的上一轮胜仗

本仓库 vendor 进树的 Cordis 钉的是 [cordiverse/cordis](https://github.com/cordiverse/cordis) `4.0.0-rc.7`（manifest 第 17 行）。Cordis 是 [Koishi](https://koishi.chat/en-US/manual/introduction.html)——跨平台聊天机器人框架——所基于的插件内核；[腾讯云技术文章](https://cloud.tencent.com/developer/article/2728030)称 DeepSeek 相关论文的案例研究就是 Koishi，并给出数据：**四年间积累了 4,000+ 社区插件**（36Kr 英文报道见 [eu.36kr.com](https://eu.36kr.com/en/p/3938795963137411)）。

Koishi 那轮循环的完整形态：

1. **框架**：跨平台 bot 框架；
2. **市场**：`koishi-plugin-*` 命名约定 + 插件市场，一键安装卸载（如 [`koishi-plugin-dialogue`](https://www.npmjs.com/package/koishi-plugin-dialogue)、[`koishi-plugin-chat-ai`](https://www.npmjs.com/package/koishi-plugin-chat-ai)，两者均已在 npm registry 复核存在）；
3. **跨渠道适配器**：QQ / Telegram / Discord 等每个平台是一个 adapter 插件——"渠道是插件"在那一轮就是现实；
4. **长尾生态**：4,000+ 插件（论文口径，二手转述；只用作量级证据，不作精确值）。

**对本仓库的意义**：被验证的命题是"**官方写不完所有需求时，市场会自己长出来**"；未被验证的命题是"企业会为基于此的治理付费"——Koishi 的市场没有治理向量，那是 DSH 的新命题。

Koishi 的现状佐证：核心包 `koishi` 仍在 npm 发布至 v4.18.11、月下载 ~23.9k（registry.npmjs.org，2026-08-28 复核），GitHub 最后 push 2026-03（api.github.com），官方市场采用 npm 为注册表、约 3 天自动同步的"薄目录、不碰支付"模式（[官方论坛](https://forum.koishi.xyz/t/topic/12557/4)）。

"从聊天里审批 Agent 动作"已是竞争现货：NanoClaw + Vercel 发布跨 15 个聊天软件的审批对话，n8n、Temporal 有官方 human-in-the-loop 教程，Claude Code 缺权限提示推送且 issue 挂着（来源与校验见 [FAQ 09 research](./research.md)）。官方实验 A 的差异化只能在**成对 ask/decide 审计 + fail-closed + 整请求可重建**上，不在聊天窗口本身。
