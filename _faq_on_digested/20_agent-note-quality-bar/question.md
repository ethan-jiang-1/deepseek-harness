# Question 20 · 不就是写个 ADR 吗，为什么 DSH 把 Agent Note 搞得这么讲究？

第一次点开 DSH 仓库的 `.agents/notes/`，几乎所有工程师都会冒出同一个直觉困惑：**不就是写个架构决策记录（ADR）吗，为什么要把生命周期目录、六个固定分类、必填章节、双语哈希三件套和归档冻结搞得这么严苛？**

真要动手改代码或者想把这套做法搬回自己团队时，最卡人的通常是下面四个具体问题：

1. **到底什么时候不用写、什么时候必须写？** 日常修个 bug、调个界面或者改几行逻辑，难道每次都得补一篇文档凑数吗？
2. **真该写的时候怎么写才算合格？** 三个状态目录和六个领域子目录怎么选？正文哪几段不能省、提案落地时怎么改写、双语三件套怎么同步？
3. **写完合入之后怎么管？** 代码后来改名或换了默认值怎么办？几百上千篇旧记录越堆越多，什么时候该更新、什么时候归档冻结、什么时候干脆整套删掉？
4. **定这么多硬规矩到底在防什么？** 如果我想在自己的单语项目或独立插件仓里借鉴一套轻量版，哪些是绝对不能砍的灵魂，哪些只是 DSH 主仓自己的历史包袱？

### 讨论范围说明

- 本篇聚焦 Agent Note 的**准入判据、写作结构、生命周期治理与轻量化裁剪**；存放路径前缀本身是可替换的（DSH 主仓放在 `.agents/notes/`，独立插件仓通常直接放在根级 `notes/`）。
- 一笔代码变更在 Issue、`docs/`、测试与 CI 之间的完整配合流程，见姊妹篇 [FAQ 06 · 变更落位路径](../06_change-landing-path/answer.md)。
