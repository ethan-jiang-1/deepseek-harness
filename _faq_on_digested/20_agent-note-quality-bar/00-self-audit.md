# 自查：这一组 FAQ 的问题在哪里

对 `20_agent-note-quality-bar/` 九篇现稿做的对抗性复核。每条都标了**证据**、**影响**与**修法**。未标注「已确认」的，是我尚未核到原文、需要在动手时一并核实的。

## A. 事实性错误（必须修）

### A1. 「`## Risks` 在 implemented 里被禁」——错，而且门禁的报错原文被我改写了

- **现稿**：[`03`](./03-note-triplets-on-disk.md) 与 [`02`](./02-what-goes-in-the-file.md) 都写「`## Proposal`、`## Plan`、`## Migration plan`、`## Acceptance criteria` 出现在 implemented 会被门禁直接拒绝」。
- **事实**：```js
BANNED_IMPLEMENTED = /^## (?:Proposal\b|Plan\b|Migration plan\b|Acceptance criteria\b)/i
```（[`scripts/verify-agent-note-format.ts:36`](../../scripts/verify-agent-note-format.ts)）。**`## Risks` 不在禁用列表里。**
- **语料反证**：活跃 implemented 里现在有 **5 篇**照样带着 `## Risks` 且在通过门禁的状态下合并——`2026-06-15-ptc.md`、`2026-07-14-provider-routed-llm-adapters.md`、`2026-08-24-session-log-snapshot-corpus.md`、`2026-08-25-electron-desktop-packaging-and-updates.md`、`2026-09-17-windows-runtime-signature-cache.md`。
- **我犯的第二个错**：02 里我写「报错原文是…」并把 `(fold it into Decision/Consequences/Testing)` 塞进了引号。那是 `h2s.includes` 判断的**合法章节清单**，不是报错文本的一部分——我拼接了两处源码。
- **修法**：删掉任何 `## Risks` 被禁的说法；引用报错时逐字照抄；补一句「`## Risks` 不在禁用集内，活跃树里仍有 5 篇在用，README 鼓励把它折进 `## Consequences`，但门禁不管」。

### A2. 六个类型的定义被我压缩后失真

- **现稿**：[`04`](./04-why-so-many-types.md) 的表格把 `architecture` 写成「关于**交付源码**的结构性决策；包之间怎么关联」。
- **事实**：README 原文是 "A structural decision about the **shipped source** — how packages relate, what the runtime vocabulary is"。我漏掉了 **runtime vocabulary**（运行时词汇），而它正是区分 architecture 与纯目录重构的关键。
- **修法**：六个定义逐条对齐 README 的 Classification 表，不要改写。

### A3. rejected 的正文规则我写漏了，且与自己的例子矛盾

- **现稿**：[`03`](./03-note-triplets-on-disk.md) 只写「`proposed/` → `rejected/` 只在 `Status:` 加理由并冻结」。
- **事实**：README:107 明确 rejected **保留提案期的全部章节**（包括 `## Acceptance criteria`、`## Plan`），只有四样东西仍然适用：头部块、`## Problem` 开头、`## Proposal`、Alternatives 强制。
- **自相矛盾**：我在 04 里引用的那篇 rejected 例子实际含 `## Acceptance criteria` 与 `## Risks`——正文规则不讲清，读者会以为那篇违规。
- **修法**：03 补 rejected 的正文章节规则；04 引例子时点明「它保留提案期章节是合规的」。

### A4. 我把「哪些事不该写 Note」写成了几乎禁止 bug 修复

- **现稿**：[`01`](./01-should-i-write-one.md) 的三十秒自检第 2 问——「我说得出被击败的备选方案吗？说不出来，通常意味着这个决定没有取舍，只有实现步骤」，配合第 1 问，读起来像「修 bug 不要写 Note」。
- **事实**：README:45 的豁免只覆盖**机械编辑与局部 UI**；类目定义里 `bug-fix` 是正式一类（implemented 侧 63 篇），archive skill 也明确「A local bug fix… does not qualify merely because its implementation is small」。
- **我真正想说但没说清的**：不是「bug 不写」，而是**「这次改动有没有一个决定」**。若只是让代码符合既有决定，答案是「没有」，那就去修，不必写；若这次改动**改变或补充了一个决定**（哪怕行数很少），就该写。sandbox-same-mode 就是后者——171 词，但它放宽了一条既有安全保证。
- **修法**：改成**三出口**结构，把「不需要商量」这一支明确还给读者：

  | 出口 | 判据 | 动作 |
  |---|---|---|
  | ① 不用写 | 这次改动没有产生任何新决定——修的是既有决定下的缺陷、文案、机械重构 | 直接改，理由进 PR |
  | ② 更新已有 Note | 决定已存在，这次只是让事实跟上（改名、换默认值） | 改 Note 的事实，不新建 |
  | ③ 写一篇 | 出现了一个新的、未来有人会踩的取舍 | 写 |

  并明确一句：**默认是 ①；写 Note 是例外，不是流程关口。** 顺带给出比例感（2026-09-18 之后一个月内新增 Note 约 110 篇，同期非合并提交约 914 个——大多数改动并不经过这里）。

## B. 结构性问题

### B1. 两个文件挂了同一个文件名，内容已经换成另一张图——我改图时没有改文件名

- `figures/three-layers.svg` 现在画的是**三层分工**（配 07），`figures/lifecycle-and-types.svg` 画的是**状态与类型**（配 04）。名字对得上，但 `three-layers.svg` 是复制 `lifecycle-and-types.svg` 后原地重写的，第一版曾出现「文件名说三层、内容画生命周期」的错配——**这类错配只靠渲染检查发现不了**（见 D1）。当前状态正确，但过程说明我缺少「图与文件名、图与引用页」的双向核对。

### B2. 07 与 04 的图注互为镜像，读者会来回跳

- 07 的图注讲三层分工，04 的图讲生命周期。两张图都以「Agent Note…」开头，都出现在页面上半部。需要各加一句指向：04 的图注补「三者如何分工见 07」，07 的图注补「状态与类型的细节见 04」。

### B3. 页面长度与摘要粒度不匹配

`02`（146 行）、`03`（108 行）明显长于 `01`（78 行）、`06`（78 行）。02 里「最短合格成品」整段引用 + 「Alternatives 写法」+ 「禁止标题」+ 「保留与删除」是**四件事**塞进一篇——按「独立问题独立 MD」的标准，至少「保留什么可以删什么」应该独立成页或并进 05（归档与删除）。

### B4. `answer.md` 的导航表与 `question.md` 的入口表重复

两处都列了 01–07。**两份清单一定会漂移**——这正是 Note 树「不要 INDEX.md」要防的事，我在自己的 FAQ 里犯了一遍。修法：question.md 只留一句「见 answer.md 的导航表」。

## C. 一致性问题

### C1. 同一件事三种叫法

- 「保留 / 归档 / 删除」在 03、05、07 里分别写作「归档/删除判据」「留下、归档还是删除」「保留 / 归档 / 删除的判定」；
- `dsh-archive-agent-notes` 一会儿称「skill」一会儿称「工作流」；
- 「三件套」与「triplet」混用（03 标题用中文，03 正文出现 triplet，05 用「完整三件套」）。

### C2. 引用格式不统一

同一份 README 在不同页被引成 `.agents/notes/README.md 的 "When to write one"`、`README.md:107`、`[`.agents/notes/README.md`](../../.agents/notes/README.md)` 三种形态；行号有时给有时不给。建议统一为「链接 + 章节名」，只在需要防止歧义时附行号。

### C3. 数量快照散落三处且会过期

578 / 641 / 各类型计数出现在 `answer.md`、`04`、`03`。仓库每天都在长，这些数字一周后就错。修法：集中到 04 一处，其余页只引用「见 04 的实测口径」，并标明测量时间。

## D. 方法论问题

### D1. 我用「文字盒估算脚本」代替了看图，这对**内容**检查是无效的

- 脚本只能证明「没有溢出」，证明不了「画的是不是那件事」。B1 的错配就是靠读文件发现的，不是靠脚本。
- **规范修法**：`_digested/_change_log/0007` 的图方法要求「只有渲染才是证据」——渲染出 PNG 后**必须看图**。当前会话的模型不支持图像输入，所以正确做法不是「用脚本顶上」，而是**如实标注**：交付时说明「图已渲染、几何已核，但未经人眼确认」。

### D2. 我用自造的估算脚本当了自造规范的执法者

估算脚本（字符宽度启发式）是我自己写的，用它来「证明」我自己的图合规，等于自证。它的价值仅限于抓粗错（B1 的溢出确实抓到了），不能当验收依据。

### D3. 深层问题：我的结论建立在「当前工作树」，而 FAQ 自称面向「未来读者」

- `question.md` 声明的基线是工作树 `caf78ed639`，但 FAQ 的正文大量使用**现在时**（「门禁拒绝」「README 要求」）。一旦上游改规则，整组页面同时过期，而没有任何机制提醒读者。
- **修法**：每页底部统一一行「基线：`caf78ed639`（2026-10-08 测量）；上游改动后按 `_digested/_change_log/` 复核」，并把易变事实（行号、数量、报错原文）集中在少量位置。

## E. 对新人不够亲切的地方

### E1. 第一屏是英文引文

01 开头直接上英文规则原文，读者还没有任何心智模型。应先给一句中文的「这个制度想解决什么问题」。

### E2. 缺少「一个完整走一遍」的叙事

现在七页都是「横切面」（门槛、格式、目录、类型…），新人没有一条**从一次真实改动到一篇 Note** 的纵切路径。建议加 `00-walkthrough.md`：拿 `2026-09-16-sandbox-same-mode` 那一次改动，从「我改了 6 行」→「为什么这值得写」→「我填了哪四段」→「PR 里还做了什么」→「三个月后它会被归档吗」，全程用真实文件与提交号。

### E3. 术语没有落地窗口

`lifecycle`、`triplet`、`grandfather comment`、`supersession`、`seal` 都是第一次出现即使用。要么换成中文，要么在首次出现处给一句白话。

## F. 逻辑与自洽性问题

### F1. 04 里「合起来就是这张图」下面的 ASCII 流程图与相邻的 SVG 冲突

同一页出现两个状态图，表达同一件事但细节不同（ASCII 有「被否决」与「诱惑消失」分支，SVG 有篇数与类型条）。**同一页保留一个即可**，另一个删掉。

### F2. 06 的「八条照抄」与「五条可发明」有重叠

第 8 条「删除优先于归档」在「可以省略什么」里没有对应项，但第 5 条「门禁脚本本身」被列为可省——而 06 又在同一页说「没有执行者的文字约定遵从度会显著下降」。**同一页既说可省又说不能省**，需要写清取舍条件（「有 CI 才可省门禁，无 CI 时改用一条便宜脚本」）。

### F3. 「移植成功的标志」给了一个无法执行的判据

「半年后你还能靠一篇 Note 阻止一次重复讨论」——不可观测。至少补一条可查的代理指标：**有没有一篇 Note 被后来的 Note 明确 supersede 过**（有 = 语料在收敛；从来没有 = 要么门槛太松，要么根本没人读）。
