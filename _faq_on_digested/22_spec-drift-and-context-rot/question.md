# Spec 越堆越多、项目左晃右晃：上下文腐化与规格漂移，DSH 机理上防住了什么？

## 问题是怎么冒出来的

提问者的原始表述是：用它写小的东西没问题、思路也连贯，但**敏捷迭代里一个东西先开头是这样，想下去之后隔了一阵子又换了个方向，它不断在滚动**，于是「整个项目一直在左晃右晃」；同时 **specs 越堆越多**，担心「上下文可能会腐化，或者发生漂移」。想知道两件事：**机理上有没有预防手段**、**使用上该注意什么**；并且直接点名要查 **DSH 的 Note 流程是不是已经考虑过这些事**。

这三个担心可能指向三种不同的失败；本组页面先判断它们各自发生在哪一层，再分别取证：

| 说法 | 要问什么 |
|---|---|
| **上下文腐化** | 模型这一步看见的内容，是否已经和真实状况脱节（旧叙述当现行、摘要吃掉细节、堆得太满反而用不上）？ |
| **规格漂移** | 写下来的 spec / 文档 / 清单，是否已经和代码、配置、真实行为对不上？ |
| **方向反复** | 一个项目先往东、隔一阵改往西，旧的决策记录是被改写、被删除，还是被叠成第二份「过时 spec」？ |

本组页面按这三条线分别取证，再回答「这套东西搬到插件仓、搬到传统应用开发还剩多少」。

## 这组页面要回答的问题

1. **先分清烂的是哪一层**：上下文腐化、规格漂移、方向反复、存量堆积，各自的机理和可观测信号是什么？
2. **运行时（DSH 产品本身）做了什么**：compaction、goal / plan / todo 等机制分别作用于哪类腐化？它们能防住什么、防不住什么？
3. **仓库治理（DSH Note 流程）做了什么**：决策被取代时走哪条路径？谁强制做 supersession 检查？归档冻结的规则是什么？
4. **门禁与证据做了什么**：哪些漂移是机器拒绝的，哪些只能靠 review？
5. **方向反复被谁接住**：所谓「左晃右晃」，在这套流程里是有记录的常态，还是没人管的债务？
6. **使用上该注意什么**：独立插件仓能照搬哪几条；传统应用开发能迁移哪几条；哪些别抄。

## 范围与边界

核验状态见 [核验基线登记](../00-baseline.md)。
- **三类陈述分开标注**：`[原文]` 是仓库里的直接陈述（`AGENTS.md`、Note 规则、package README、官方文档）；`[源码]` 是从本基线源码或生成物核对过的机制事实；`[推断]` 是从事实推出的解释，包括「搬去传统应用开发还剩什么」。这条分级按出处纪律执行（`[框架]` 一档本组不使用：凡不依赖 DSH 的通式都标 `[推断]`）。
- **不重写已有整理**：Agent Note 的写作判据、格式、三件套与归档判据归 [FAQ 20](../20_agent-note-quality-bar/answer.md)；一次变更各面的落位归 [FAQ 06](../06_change-landing-path/answer.md)；六步闭环与「spec 感是沉淀物」归 [FAQ 11](../11_native-development-loop/answer.md)；SDD 分层归 [FAQ 06/09](../06_change-landing-path/09-six-layers-and-limits.md)。本文补的是这些篇目都没合并回答的那一问：**堆积本身**。
- **插件仓部分引用同仓语料**：独立插件仓的落地做法引 [`_dsh_plugin_agent_ready_development/`](../../_dsh_plugin_agent_ready_development/00-index.md)，不重复它的机制清单。该语料已吸纳本主题的运行时会话侧机制，独立发行版是 [`native-development-model/03-context-and-drift.md`](../../_dsh_plugin_agent_ready_development/native-development-model/03-context-and-drift.md)；两份对照同一基线，下一轮同步时一起复核。
- **git 历史是浅克隆**：`.git/shallow` 有 158 个边界提交，边界之外无法核对；本文凡引用历史案例都给出仍存在于当前工作树的文件与提交号，无法核对的早期历史明确不引。
