# Spec 越堆越多、项目左晃右晃：上下文腐化与规格漂移，DSH 机理上防住了什么？

先读 [`answer.md`](./answer.md) 的一分钟版。那一页有阅读顺序和结论；下面是这组页面要回答的问题。

## 问题是怎么冒出来的

提问者的原始表述是：用它写小的东西没问题、思路也连贯，但**敏捷迭代里一个东西先开头是这样，想下去之后隔了一阵子又换了个方向，它不断在滚动**，于是「整个项目一直在左晃右晃」；同时 **specs 越堆越多**，担心「上下文可能会腐化，或者发生漂移」。想知道两件事：**机理上有没有预防手段**、**使用上该注意什么**；并且直接点名要查 **DSH 的 Note 流程是不是已经考虑过这些事**。

这三个担心其实是三种不同的失败，混在一起就答不清楚：

| 说法 | 真正在问什么 | 出事的地方 |
|---|---|---|
| **上下文腐化** | 模型这一步看见的内容，是否已经和真实状况脱节（旧叙述当现行、摘要吃掉细节、堆得太满反而用不上） | 一次会话的**模型可见面** |
| **规格漂移** | 写下来的 spec / 文档 / 清单，是否已经和代码、配置、真实行为对不上 | 仓库里的**事实载体** |
| **方向反复** | 一个项目先往东、隔一阵改往西，旧的决策记录是被改写、被删除，还是被叠成第二份「过时 spec」 | **决策的版本化**方式 |

三种失败的解法不同：第一种靠运行时的记录面与投影，第二种靠「一个事实只有一个家」加可执行门禁，第三种靠「决定不可改写、只能被取代」的版本纪律。本组页面按这三条线分别取证，再回答「这套东西搬到插件仓、搬到传统应用开发还剩多少」。

## 这组页面要回答的问题

1. **先分清烂的是哪一层**：上下文腐化、规格漂移、方向反复、存量堆积，各自的机理和可观测信号是什么？
2. **运行时（DSH 产品本身）做了什么**：为什么 compaction 能压掉上下文却不让记录腐化？goal / plan / todo 为什么算「反漂移」机制而不是普通功能？
3. **仓库治理（DSH Note 流程）做了什么**：决策被取代时走哪条路径？谁强制做 supersession 检查？归档为什么必须冻结？
4. **门禁与证据做了什么**：哪些漂移是机器拒绝的，哪些只能靠 review？
5. **方向反复被谁接住**：所谓「左晃右晃」，在这套流程里是有记录的常态，还是没人管的债务？
6. **使用上该注意什么**：独立插件仓能照搬哪几条；传统应用开发能迁移哪几条；哪些别抄。
