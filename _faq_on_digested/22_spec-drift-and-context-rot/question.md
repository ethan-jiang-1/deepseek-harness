# FAQ 22 · 项目左晃右晃、文档越堆越多：DSH 靠什么防上下文腐化与规格漂移？

## 问题背景

用 Coding Agent 写独立小工具时，几轮对话就能闭环，上下文干净、思路也连贯。可一旦进入真实的敏捷长周期开发——一个功能先往东做，隔两周想深了又掉头往西，需求与方案不断滚动调整，同时仓库里的文档、规则和决策记录越攒越厚——开发者很容易同时撞上三种烂账：

- **对话里的上下文腐化（Context Rot）**：长会话压缩后丢了关键前提，或者模型死抱着几轮前早已作废的旧方案继续往下写；
- **仓库里的规格漂移（Spec Drift）**：改了代码忘了改文档，或者同一规则抄了两份导致前后打架；
- **架构掉头后的记录堆积**：几次方向摇摆后留下一堆没人敢改也没人敢删的旧设计稿，把搜索和模型视野全污染了。

我们想知道：**DSH 在运行时产品机制、仓库 Note 治理和自动化门禁上，到底防住了哪几类腐化与漂移？又有哪些漏洞至今机器防不住、在实战和迁移时必须靠人兜底？**

## 具体要回答什么

1. **运行时会话层**：长对话压缩（`compaction`）、目标与计划外置（`goal` / `plan` / `todo`）、技能按需加载与子智能体委派，各自怎么防止模型“记串、记漏、越跑越偏”？哪些信息压缩后依然会丢？
2. **仓库文档与决策层**：面对项目频繁“左晃右晃”和成百上千篇历史记录，DSH 的文档分层与 Agent Note 制度靠什么保证“现行口径唯一、淘汰理由不丢、存量不拖垮检索”？
3. **生成器与门禁层**：哪些账实不符会被脚本和录制快照当场拦下？又有哪些跨文档语义矛盾机器完全看不懂、只能靠人工与 Agent Review 把关？
4. **实操与外部迁移**：日常用 DSH 跑长任务、维护独立插件仓库，或者做不依赖 DSH 的传统业务项目，这套防线该怎么用、抄哪几条、别硬抄哪几条？
