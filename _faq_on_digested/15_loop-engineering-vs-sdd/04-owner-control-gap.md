# 04 · owner 复盘：已经在循环，哪些判断仍靠追问

## 结论先行

[口述和四仓记录](./research.md)中的五个困惑不是同一种缺口：下一项与在途状态关乎**工作可见性**；goal 的原意与改动关乎**授权和范围**；「怎么测、质量如何」同时关乎**交付证据与人类验收**。四仓已引入部分队列、提案与指针校验，这些是针对观察到的问题的尝试；没有长期前后对照能证明把控力「补了一半」，更不能把所有问题归入队列管理。

## 第一节 从口述到可检验的假设

| 口述中的疑问 | 已观察到的做法 | 还要核实什么 |
|---|---|---|
| 下一个 feature 是哪个、按什么次序 | 部分仓用 ROADMAP 指当前项、次序与等待状态 | 谁可以改变优先级；人能否在新会话快速确认它 |
| agent 此刻在做什么、做过几个 | 会话 todo、提案登记和反馈呈批有各自载体 | 它们有没有被实际使用，状态更新是否与工作同步 |
| 提案有没有完成或被搁置 | Note 生命周期、指针与校验脚本记录部分状态 | 决策记录和任务状态是否被误当成同一件事 |
| 某个 feature 怎么测、质量怎么样 | 提交与验证报告记录部分检查 | 检查覆盖了哪些需求，谁负责接受测试之外的结果 |
| 当前 goal 究竟是什么 | goal 能供人查看，agent 可在直接人类请求的轮次代写/编辑 | objective 是否被你批准，扩张范围时何时必须停下来询问 |

## 第二节 会话证据能说明什么

B4 路选的是 **229 个会话中偏大的 20 个**，有意覆盖长程工作而非随机代表全部工作。在这 20 个会话中，goal 创建紧跟 agent 的工具调用；采样未见 owner 用 `/goal` 亲自创建/检查，也未见 plan mode 实际进入，而 `ask_user_question` 被调用 38 次，包括计划呈批。这说明**写在四仓笔记里的 Plan Mode 审阅步骤与本次实际载体不一致**，不说明 owner 在其他会话从未用过 Plan Mode，更不能把没有进入 Plan Mode 等同于没有人审。

[goal 工具](../../packages/goal/tool-goal/README.md)要求 create/edit/pause/resume 发生在直接人类输入的顶层轮次，但 objective 可以由模型拟写；[goal-round-driver](../../packages/goal/goal-round-driver/README.md)负责获准后的自动续轮和停止上限。人说了话并不等于人逐字确认了 goal；模型报告完成和轮次上限也不等于人满意。你觉得「goal 是什么都不清楚」，很可能同时来自未使用可见入口、目标文字由 agent 代写，以及没有固定的目标变更审批点。现有日志不能把三者分出单一根因。

## 第三节 四仓的补丁意味着什么

09-25 的长程运行之后，09-26 的记录显示出现指针活性、等待人类的行标与在办/已办分组等调整；时间顺序和复盘能说明哪些错误曾被注意到、后来加了什么防护，不能证明若换用 SDD 就一定能在事前发现，或者新增门禁能永久消除人工追问。把能被机器判断的指针失效做成失败检查，是有针对性的工程措施；优先级、需求是否偏移、结果是否够好，不会仅靠这一类检查自动得到答案。

你可以把这套变化理解为从「对话中反复提醒」走向「把下一项和约束留在会话之外」。其中仍应保留明确的人类判断：哪些工作获得授权、哪些结果确实符合意图。TodoPanel、goal 和 Plan Mode 是可选载体；机制在场不等于用过，用过也不等于已经获得控制。如何以一两项工作检验改进效果，见 [05 篇](./05-control-points.md)。

**最接近的一句话：你不是缺乏循环，而是把执行循环交给 agent 后，工作选择、目标批准和结果验收有时仍藏在临场对话里；队列和门禁能外显部分状态，不能替你做这些判断。**
