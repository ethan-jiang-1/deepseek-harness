# FAQ 15 · 用 DSH 开发插件，为什么感觉接近 loop engineering，又不如 SDD 看得清进度？

## 问题

owner 用 DSH 开发多个独立插件后的体感：从主意到落地可以由一个不太细的目标/proposal 启动，agent 随反馈反复推进，感觉接近 loop engineering；但不像使用 OpenSpec 时那样随手看清各 feature 的安排、进度和验收，也不像 Spec Kit 的推荐路径那样逐步审阅产物。这套做法结果尚可，人的把控感却不足。本问题分四层，先分清 DSH 提供的能力、DSH 自身仓库的贡献制度、以及插件仓自己采用的流程：

1. DSH 的运行时、插件作者文档和自身仓库贡献制度各负责什么？它们合起来是否规定了一个统一的插件开发流程？
2. owner 的实践与公开讨论中的 loop engineering 在哪些环节相似，在哪些环节仍靠人临时提醒？社区插件仓的公开材料最多能支持什么判断？
3. SDD，特别是 OpenSpec 与 Spec Kit，和这种循环的差别在哪里？规格、计划与人工审阅能否成为循环的一部分？
4. owner 感到的「把控力不够」具体涉及取题、进度、目标、验收和判断权的哪些环节？什么可以先小规模试补，什么还必须由人负责？

## 背景

owner 口述（2026-09-26，语音转写整理，全文见 [research.md](./research.md) 的 B 路节）：原来用 OpenSpec 那种 SDD 时，哪个 feature 在队里、落地次序、怎么测过、质量如何，「通通都知道」；现在 DSH 插件开发搭框架时把控力没那么强——只能时不时提醒 agent「要计划计划」，等他说做好了才知道做了几个东西；于是反复要求「显性化到 notes 底下的 proposal 里」，但 notes 底下的东西也不知道是不是像看板一样挪来挪去；现在变成 goal 追问，连 goal 是什么都搞不清楚，就一直催着他往前跑。

与已有 FAQ 的关系：FAQ 02 用分层规格解释过 DSH 自身仓库的记录与验收；FAQ 11 描述执行者的窄证据切片闭环，并把人的指挥放在其外。本篇区分**执行循环**与**跨 feature 的取题、进度和判断**：在多 feature、长周期、独立插件 repo 里，人实际能看见什么、仍得亲自接手什么；这种体验有何外部参照，能否与 SDD 的产物组合。

## 回答目标

读完本 FAQ，应当能够：

1. 分开说明 DSH 运行时、仓内贡献纪律与外部插件作者的自主选择，不把分析框架写成官方方法名。
2. 解释 loop engineering 为什么贴近 owner 的体感，以及为什么 DSH goal 续轮不自动等于完整的工作调度与验收。
3. 区分 OpenSpec 的迭代产物和 Spec Kit 的推荐审阅路径，说明 SDD 产物如何给循环提供记忆与检查依据。
4. 依据 owner 的工作记录与社区公开仓库的有限证据，提出保留人类判断权的轻量控制点，而不是宣称已有唯一最佳流程。
