## 二、关键方法论决策与代价

1. **owner 口述不当证据用，只当现象用**：口述先转写归档（含语音转写备注 logo→loop），再逐条找文件锚点。代价：口述的情绪与强度（「体感差异其实很大」）在编码表里必然失真，复审时须回读 B 路原文。
2. **会话日志只采样每目录最大的 2–4 个（v4 优先，20/229）**：理由是大会话 ≈ 长程开发主战场，与「把控力」问题最相关；代价是小会话形态未覆盖，且「最大」偏好长马拉松——可能高估 goal 驱动的比重。
3. **社区抽样 15 仓**：awesome 榜单头部 + npm 下载头部 + topic star 头部；代价：ruflo/open-design 是蹭生态大项目，对「插件作者群体」代表性打折；model-proxy（下载第一）无公开仓库——「仓库 ≠ 开发现场」这一发现本身修正了「无痕迹 = 无过程」的读法。
4. **趋势判定以 release 史与官方文档为骨**：理由是可复核、带日期；代价：无 star/下载纵向计量，「收敛」是叙事综合而非计量结论。
5. **库内基线钉在 `46a7f68b09`（dsh-v0.1.7-rc.1）**：与 00-index 全目录基线一致。

## 三、调查中被证据推翻或修正的假设（复审最有价值的部分）

1. **goal 「搞不清楚」的归因链（三段演化）**：初始假设「机制 UI 不可见」→ 查得 `ui-goal` 组件与 `/goal` 命令真实存在（A 路）→ 修正为「机制在场未被使用」→ B4 日志显示 owner **从未亲手创建过 goal**、goal 全由 agent 代建代管、objective 被反复 edit 吸收 owner 对话更正 → 最终解释：「goal 是 agent 的工作记忆，不是 owner 的仪表」（04 §3）。教训：体感的第一解释往往错在归因层，不是现象层。
2. **「Plan Mode 呈批门①」被日志推翻**：四仓笔记都把 Plan Mode 呈批写成流程（B3），但 20 个会话 **plan mode 零进入**，唯一一次 `exit_plan_mode` 调用直接报错；实际批准载体是 `ask_user_question`（38 次）。修正：**制度文本 ≠ 行为**；把控力评估必须按运行时载体计（04 §3 末段）。教训：这也是对「读 repo 取证」这一方法本身的警告——B3 与 B4 必须都做。
3. **SDD 前提的两次松动**：FAQ 02 曾把「DSH=SDD」当前提，FAQ 11 纠正为「spec 感是闭环沉淀物」；本篇继承该纠正并推进为「切片层/管线层」两层模型。**该模型是本篇自造的分析框架，不是上游术语**——复审请优先攻击它（备选框架：「过程 vs 产物」「队列 vs 证据」；采用现框架的理由：owner 五个缺口无一落入切片层机制，且与 SDD 工具的产物清单恰好互补）。
4. **社区预期的落空**：初始预期「市场大 + spec-kit 已桥接 → 社区应有 spec-first 采用者」→ 实测 15 仓零采用 → 结论改为「桥接发生在协议层，采用未发生在行为层」（03 §4），并把这条登记为可跟踪预言。
