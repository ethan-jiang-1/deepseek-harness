## 一、问题分解与分路设计

owner 的原始口述拆成四个子问题（见 [question.md](./question.md)），每个子问题至少两路独立证据交叉：

| 路 | 回答什么 | 为什么需要它 | 执行者与理由 |
|---|---|---|---|
| A 库内基线 | 子问题 1 的制度面：DSH 官方到底规定/留白了什么 | owner 的体感首先要对上游制度文本核实，否则无法区分「错觉」与「设计」 | 本代理自查；**不重做 FAQ 02/06/11/13 的考据**——同目录研究有连续性，重做会引入分叉，只取增量（管线层留白的直接证据） |
| B owner 口述 | 全部子问题的「现象」起点 | 体感是待解释现象，不是证据；先逐字归档，再逐条落到文件/提交/日志 | 本代理编码（B2 仓库盘点自查 + 两个委派 B3/B4，按证据载体切分） |
| C 社区抽样 | 子问题 2 | 「这是趋势还是错觉」需要第三个数据点：其他实践者的行为 | 委派子代理；锚点 = owner 参照系（awesome-dsh-plugin）+ 影响力口径（npm 下载/topic star）双轨 |
| D 外部 discourse | 子问题 3 | 趋势判定需要行业坐标，且需要「反方」（SDD 阵营）的声音避免回音室 | 委派子代理；release notes/官方文档为骨（一手带日期），HN/博客叙事为肉（只作第一人称叙述） |
| B2 仓库盘点 | 体感的制度面落点（四仓控制面清单） | 口述说「缺」，仓库说「补了什么」——两边对账 | 本代理自查（ls / git log / AGENTS 头） |
| B3 流程笔记深读 | 痛点→机制的因果链与引入时间 | 控制面是建仓即有还是痛点后补，决定「把控力缺口」的性质 | 委派子代理（指定笔记 + git -S 取证） |
| B4 会话日志 | 子问题 4 的行为面 | B3 的笔记是「事后制度」，日志是「事中行为」——两者可能不一致（事实证明不一致了，见三.2） | 委派子代理；zstd JSONL 逐事件分析 |

方法论原则：**结论一律标注证据强度**（【一手】/【口述】/【推断】/【聚合】）；负结论（「未找到」）必须写明搜过什么。

## 二、关键方法论决策与代价

1. owner 口述不当作机制证据，只当现象用：先归档使用者对 loop engineering 的体感，再逐条找文件锚点。代价：口述的情绪与强度（「体感差异其实很大」）在编码表里必然失真，复审时须回读 B 路原文。
2. **会话日志只采样每目录最大的 2–4 个（v4 优先，20/229）**：理由是大会话 ≈ 长程开发主战场，与「把控力」问题最相关；代价是小会话形态未覆盖，且「最大」偏好长马拉松——可能高估 goal 驱动的比重。
3. **社区抽样 15 仓**：awesome 榜单头部 + npm 下载头部 + topic star 头部；代价：ruflo/open-design 是蹭生态大项目，对「插件作者群体」代表性打折；model-proxy（下载第一）无公开仓库——「仓库 ≠ 开发现场」这一发现本身修正了「无痕迹 = 无过程」的读法。
4. **趋势判定以 release 史与官方文档为骨**：理由是可复核、带日期；代价：无 star/下载纵向计量，「收敛」是叙事综合而非计量结论。
5. **库内基线钉在 `46a7f68b09`（dsh-v0.1.7-rc.1）**：与 00-index 全目录基线一致。

## 三、调查中被证据推翻或修正的假设（复审最有价值的部分）

1. **goal 「搞不清楚」的归因链**：初始假设「UI 不可见」→ A 路核得 `/goal` 人面存在 → B4 在特意选择的 20 个大会话里未见 owner 直接建/查 goal，创建和编辑紧跟 agent 工具调用。这个样本说明目标文字常由 agent 代拟，不能解释全部会话，更不能排除**授权范围未确认**这个独立原因；当前 [04 篇](./04-owner-control-gap.md)将它们分开。
2. **「Plan Mode 呈批门①」被日志推翻**：四仓笔记都把 Plan Mode 呈批写成流程（B3），但 20 个会话 **plan mode 零进入**，唯一一次 `exit_plan_mode` 调用直接报错；实际批准载体是 `ask_user_question`（38 次）。修正：**制度文本 ≠ 行为**；把控力评估必须按运行时载体计（04 §3 末段）。教训：这也是对「读 repo 取证」这一方法本身的警告——B3 与 B4 必须都做。
3. **SDD 前提的两次松动**：FAQ 02 曾以「DSH=SDD」组织问题，FAQ 11 把交付中产生的规格记录与上游必经流程区分开。本轮曾将「交付层/工作层」写成互补模型，但 owner 的五项困惑不全是进度问题：goal 改写牵涉授权，质量牵涉验收覆盖与人的判断。这个尺度区分仍可帮助定位状态，不能推出 SDD 与 DSH 各自只负责一层，见 [01 篇](./01-slice-vs-pipeline.md)。
4. **社区预期的落空及观察限制**：初始预期「spec-kit 已桥接 → 公开仓库会有相关产物」→ 15 仓目录未发现 `.specify/`；这只限制了**公开痕迹**，不是「行为层未采用」的证据。跟踪目录变化可描述工具产物公开度，要判断开发过程还需作者访谈。

## 七、复审回写（2026-09-26）

owner 指出：「官方流程就是 loop engineering」站不住，官方没这么说；那是体感，体感里觉得有点像 loop。顺着这句核对后改了定稿，原研究日志里被带偏的句子一并改掉：

1. **身份句撤回。** DSH 有会话级 goal 续轮，仓内没有统一的跨 feature 进度盘；根目录没有 ROADMAP 和 Note 树不建 INDEX 只说明这个仓库如何组织记录，不能推断产品禁止插件作者使用队列。把这些机制命名为「官方的 loop engineering」没有文本依据；owner 的体感本身另有公开概念参照。
2. **公开用法并非一套准入标准。** LangChain 2026-06-16 和 Osmani 2026-08-14 使用这个词；后续补核的 [Osmani 2026-06-07 原文](https://addyosmani.com/blog/loop-engineering/)尤其贴近 owner 的体感：系统接替人逐轮提示，并负责找工作、派工、检查和接续。停止条件是可靠委托的重要建议，而非「没有就不算 loop engineering」的统一定义。DSH 的 goal 负责单会话状态与续轮，插件仓可以自定跨 feature 的工作来源。
3. **#4336 的方向。** issue #4334 要的是在 DSH 里跑 `/speckit-*`，而非 DSH 官方采纳 Spec Kit。15 仓公开树未见 `.specify/`，不能据此声称作者在私有开发中没有使用 SDD。
4. **Anthropic 的 feature list 是进度规格。** 它同构的是 owner 后补的队列。原 02 篇「解法不是上游大 spec、与 DSH 最同构」与 05 篇「feature_list 本质是单次长跑的 spec」互相矛盾，现以 05 篇为准。
5. **`requireDirectHuman` 不禁止模型代写 goal。** create / edit / pause 要求当前轮有人类消息；暂停态 resume 才被拒绝。原 05 篇「模型不能自己 create」过宽，会把「goal 搞不清楚」解释成机制禁止人看，而机制实际是模型代写。

未重做的部分：15 仓树没有逐仓重克隆；20/229 会话日志没有重解压；规模律仍是未独立检验的推断。

## 八、后续概念与外推复核

1. **补入更贴近 owner 体感的定义。** Osmani 2026-06-07 [《Loop Engineering》](https://addyosmani.com/blog/loop-engineering/)直接说系统替人逐轮提示、取题、检查和接续工作。先前只引用 6 月 LangChain 与 8 月 Osmani，把「停止条件 + 外层系统」写成所有公开用法的硬门槛，属漏检和过度外推。停止条件是可靠自主工作的设计建议；DSH goal 是部分运行时能力；owner 的跨 feature 来源如何安排仍由自己决定。
2. **重新分开 SDD 的产物与人工门。** Spec Kit quickstart 建议每步审阅；OpenSpec OPSX 明说无刚性阶段门。原「OpenSpec/Spec Kit 都是每阶段审批」及「SDD 只长工作层、不长交付层」的对称叙述不成立。规格和任务可以成为循环的外部记忆及验收依据。
3. **社区和 owner 证据限缩。** 15 仓缺少公开 `.specify/` 只说明样本的公开产物，无法判定作者私下是否 spec-first 或目标开跑；20 个偏大的会话不能代表全部 229 个；四仓短期记录不证明一张队列与几道门禁已补齐控制感。现在把困惑分别定位为工作可见性、goal 的授权/范围、质量验收；建议用数项工作试行并复核，见 [04](./04-owner-control-gap.md)、[05](./05-control-points.md)。

## 最接近的一句话

**原研究骨架仍有用，但不能把目录缺席当成实践缺席，也不能用一种作者的建议为整个 loop engineering 划硬门槛。主回答现将 DSH 的执行能力、仓内交付纪律与插件仓自主安排分开，并允许 SDD 产物成为循环的一部分；其效果仍待 owner 以真实工作复核。**
