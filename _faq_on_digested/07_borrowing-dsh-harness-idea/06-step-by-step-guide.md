# 一步一步怎么做：把你的 harness 打磨到像回事

> **分水岭 · 落地总纲。** 前五篇是道——五个大概念（变更闭环、归属、决策记录、静与动、正确路径）和它们的落地实物；从本页起是术。本页拥有从道到术的接力：**先在十个维度（道五维 + 术五维）评估你手上的 harness，再按评估结果一轮一轮打磨，直到像回事。**

## 这一篇怎么用

道讲完了，本页把它变成一条**可执行的打磨路径**：每一步说清楚**做什么、产出什么、怎么验收（怎么证明这一步真做对了）**，并标注它打磨哪个维度。

原则只有一条：**先诊断、后施工，按收益/成本从高到低做，每一步都能独立验收**。评估不是走过场——评估的产出（哪一维最痛、痛在哪个具体案例）直接决定你先打磨哪一步；一轮打磨完成后回到评估复测，像回事了才算完。

> 默认次序参考 [`迁移清单`](./10-transfer-playbook.md) 的优先级，但真正决定次序的是你自己的评估结果——哪维最痛先磨哪维，不必按线性走。

## Phase 1 · 评估你的 harness：道五维 + 术五维，打分加实证（一次性，最轻，先于一切）

评估分两步——先打分（自报的静态状态），再切片（一笔真实变更的动态实证）。只打分不切片是自欺：表上写的和实际能做到的是两回事。

**第一步 · 打分。** 对整个 harness 的十个维度逐维打分——道五维管「知识是否归位」，术五维管「执行链路是否完备」。每维三档：**没有**（全靠人脑/口传）/ **有但不成体系**（零散文档或检查，没纪律）/ **像回事**（有 owner、可核对、可持续）。每维记「档位 + 一个最痛的真实案例」：

**道（概念的骨架，01–05）：**

| 维度 | 自评问题 | 打分锚点 |
|---|---|---|
| 变更闭环（01） | 一笔变更从意图到归位，走得通吗？ | 意图写得出吗？实现+文档+证据同 PR 吗？合并后新 agent 能回答三问吗？ |
| 归属（02） | 每类事实有唯一 home 吗？ | 一条规则 10 秒内指得出唯一出处吗？同一事实有第二份拷贝吗？ |
| 决策记录（03） | 「为什么」存得住、跟得上吗？ | 被否决的方案，新 agent 还会再提吗？过时的理由会冒充现行吗？ |
| 静与动（04） | 静态层和动态层分得清吗？ | 同一事实存两处吗？会话/任务历史能回放吗？临时决定回写吗？ |
| 正确路径（05） | 「改哪里」有表可查吗？ | 新任务靠猜位置还是查归属？能用配置解决的，动过核心吗？ |

**术（链路的完备，07–13）：**

| 维度 | 自评问题 | 打分锚点 |
|---|---|---|
| 入口链（07） | agent 的第一印象像回事吗？ | 有入口文件吗？多宿主是 symlink 还是多份拷贝？字数有上限吗？ |
| 执行链（08） | agent 动手有管线吗？ | 动作先记录再执行吗？有统一的执行前检查吗？结果走单一出口吗？ |
| 反馈（09） | 做错了会被抓住吗？ | 可机械规则接了 `exit non-zero` 吗？新检查做过负例控制吗？绿灯有人信吗？ |
| Skills（11） | 重复任务有标准流程吗？ | 同类任务第三次出现还在现场发明吗？流程文档带命令还是散文？ |
| 披露（13） | 上下文是预算管理还是无底线？ | 按需加载还是全量注入？超预算有回收吗？子任务隔离吗？ |

**产出**：一张十行打分表 + 每维的最痛案例。

**打分的验收**：能指着具体一个 bug/返工，说出它是哪一维的缺口造成的。说不出来，说明还没诊断透，先别动手。

> answer 的三问自检（知识外置/正确入口/反馈时机）是道五维的快速汇总视角，适合日常快诊；施工前用这张十维表，粒度才够。术的 10（迁移清单）、12（运行时查询）是收束与深化：10 归入每轮复盘的核对清单，12 的评估由「静与动」和「披露」覆盖，不单列。

**第二步 · 垂直切片。** 挑你们仓库**最近已完成的一笔真实小变更**（修复或小功能，不改核心架构），按变更闭环标准全程走查：

1. 这笔变更的用户可观察结果是什么？写得出两行「外部结果 + 如何观察」吗？
2. 从任务描述出发，能不能一路找到改动位置的 owner（不靠当时作者本人带路）？
3. 交付里有没有携带持久取舍？有的话它记在哪里？没有的话，理由说得出吗？
4. 哪项证据会在旧行为上失败？把实现回滚、保留测试，跑一次看它红不红（红灯对照）。
5. 每一步标注证据状态：能指出文件的 / 只有口头说法的 / 完全没有的。

**产出**：一张五行走查记录，外加三份清单——打不开的链接、要靠猜的 owner、没有证据支持的声称。

**切片的验收**：每一个「靠猜」和「没证据」都能归到第一步十维表的某一维——这张清单就是你的定制化施工顺序，比任何通用优先级都准。

**对应**：变更闭环的完整预演。DSH 的标准演示是[提交 5124a2a310](https://github.com/deepseek-ai/deepseek-harness/commit/5124a2a310a904d28118609c41d89f26440b946b)——[变更闭环](./01-sdlc-change-loop.md) 有它的逐环对照表。

## Phase 2 · 立入口和规矩的 owner（通常收益最高）

**做什么**：写一份**短**的根 `AGENTS.md`，只放三类东西：常驻规则（每条一到三行）、仓库布局（每个顶层区域一句话）、命令表。其余全部 link 到各自 home，不复制。同时把 `CLAUDE.md` 用 `ln -s AGENTS.md` 指向它，并在**真正有子树专属常驻规则**的少数目录放子树 `AGENTS.md`，其余目录/包只留 README。

**产出**：根 `AGENTS.md`（目标 ≤ 几百词；推荐区间见 [`入口链`](./07-agents-entry-chain.md)）+ `CLAUDE.md`（symlink）+ 一张「事实 → home」对照表 + 少量子树 `AGENTS.md`（可有可无，按需）。

**验收（机械判断）**：
- 任何一条规则，能在 10 秒内指出它的唯一 home；
- 不存在同一规则在两处各写一版；
- 根文件里没有教程、没有历史故事、没有该 link 出去的细节；
- `CLAUDE.md` 是 symlink 而非副本；子树 `AGENTS.md` 只出现在「有专属常驻规则」处，没有为放而放。

**对应**：归属维（02）+ 入口链维（07）。骨架见 [入口链](./07-agents-entry-chain.md)。

## Phase 3 · 划清「现在」和「为什么」

**做什么**：把 `docs/`（或 README）定为 **current state**，决策理由单独进 `docs/adr/` 或 `notes/`。顺手记下负知识——「为什么不走某条路」「已知限制是什么」。

**产出**：`docs/adr/`（或等价物）的目录 + 第一批 ADR/负知识条目。

**验收**：
- 读一份 ADR 能回答「为什么这样决定、什么方案输了、后果是什么」；
- `docs/` 里没有 change history（那是 git/PR 的职责）；
- 至少有一条负知识，agent 不会再反复提出已否决方案。

**对应**：归属维 + 决策记录维（02、03）。

## Phase 4 · 铺正确路径，同批把可机械规则接到执行（回报第二高）

归属表和检查是一对：表说「这类改动该走哪里」，检查保证「没走对会红」。分两批做会脱节——表立起来时没有检查， cookbook 里「跑对应检查」是空话。所以这一 Phase 同时做两件事：

**做什么**：
1. 写一张「目标 → 机制」归属表（列：目标 / 首选入口 / 何时升级）；
2. 从归属表和 Phase 1 切片清单里挑出**可机械判断**的规则，各配一个 `exit non-zero` 的命令，写一个聚合脚本，接进 git hook（低延迟项）和 CI（穷举项）；
3. 再给最常见的几类任务各写一个 cookbook（短入口 + 范本 + 升级条件 + 对应检查）。

**产出**：归属表 + `scripts/check.sh`（或等价物）+ 每个规则的负例测试 + 第一批 cookbook。

**验收**：
- 一个新任务进来，先查归属表就能回答「该改哪里」，而不是翻代码猜；
- 每个检查都做过**负例控制**（引入对应回归 → 看它变红 → 还原），否则可能是永远为绿的摆设；
- cookbook 里「本可用配置表达、却要改核心」这种情况被显式拦下，且「跑对应检查」指向真实存在的命令；
- 反馈信息能指出「失败对象 + 违反规则 + 修正入口」。

**对应**：正确路径维（05）+ 反馈维（09）+ 变更闭环维的证据环（01）。机制见 [可执行反馈](./09-executable-feedback.md)。

## Phase 5 · 给 agent 的动作立管线（执行链）

**做什么**：agent 的每个动作走同一条三段管线，不散在工具里各写一份：

1. **动作先记录再执行**——工具调用先 append 到任务/会话日志（JSONL 也行），失败调用也在场；
2. **统一的执行前检查**——权限/白名单在调用前判一次，deny 走统一出口；「工具体里自己做检查」是反模式（策略散 N 处，改一次动 N 个文件）；
3. **结果单一出口**——工具结果经同一处归一化（异常→isError）再进模型上下文，模型永远看不到「部分成功」「未知状态」。

**产出**：动作日志（append-only）+ 执行前检查层 + 结果归一化出口。

**验收**：
- 拿日志能回答「agent 昨天那条命令发了什么、结果是什么」；
- 加一条新权限规则只改**一个**文件（检查层），不是每个工具一个；
- 模型的下一个上下文里不存在未归一化的中间态。

**对应**：执行链维（08）+ 静与动维的事实源（04）。完整管线（审批、guard、fs 意图门那些）见 [执行链](./08-task-execution-chain.md)——普通项目第一天只要这三个环节。

## Phase 6 · 固化任务流程（按需）

**做什么**：把反复出现、需要上下文判断的任务流程写成带触发条件的短文档（等价于 Skill）：触发条件、输入、步骤、停止条件、验证、输出格式。

**产出**：一个「任务 → 流程文档」的目录 + 第一批流程文档（数量由重复出现的频率决定）。

**验收**：
- 命中任务时先读全文、不从摘要猜（文档里明确写这条纪律）；
- 每份文档末尾声明「这是 guidance，不是 checklist」，可机械部分指向 Phase 4 的 gate 而不是 prose。

**对应**：Skills 维（11），写法标准见 [Skills](./11-skills-as-procedural-memory.md)。

## Phase 7 · 运行时查询与披露预算（确有压力才做，可无限期推迟）

两个深化项，压力出现才碰：

1. **运行时查询**：最低成本先给一条「dump 最终生效配置」的命令（`show-config` / `make show-config` 等价）；接口清单大到手工维护不动时，加生成索引 + freshness 检查；多 profile/动态装卸的真出现了，才考虑只读 inspect。
2. **披露预算**：上下文开始爆炸时，给「入口文件加载」设预算（`maxBytes` 等价）、同内容去重、按变化抑制重复；长任务活不下来时，加压缩回收且绝不拆散 tool-call/result 配对。

**产出**：`show-config` 命令；可选：生成索引 + freshness、注入预算与回收。

**验收**：
- 能用命令回答「这台机器实际生效的是什么」，不靠读源码猜；
- 若做了 catalog/索引，有 freshness 检查防漂移；
- 若做了预算：删掉预算机制前后的每轮上下文体积可测量、可对比。

**对应**：静与动维 + 披露维（04、13）的深化，见 [运行时查询](./12-runtime-inspection.md) 与 [披露管线](./13-progressive-disclosure-pipeline.md)。**注意**：inspect 不是安全沙箱，别把它当授权边界。

## Phase 8 · 防漂移：让这套东西长期不失效（持续，从第一次交付后开始）

前面的 Phase 都是「建」，这一 Phase 是「维护」。DSH 最反直觉的一条纪律：**外置的知识会漂，所以它给外置知识配机器检查**。

**做什么**：
1. 给规则/研究目录配一个轻量 verify 脚本（严格 UTF-8、结尾换行、相对链接、锚点），每次编辑后跑一次；
2. 钉基线：文档开头写明「结论以 X commit 为准」；上游更新后**只复核被引用文件是否变化**，不全文重写；
3. 改事实只改它的 home：一条规则变了，改 owning 文件 + 所有链到它的引用——漏一处就漂一处；
4. 数字类事实（预算、上限、个数）标注「以基线的某文件为准」——数字是最容易漂的；
5. 新检查做负例控制：verify 脚本第一次上时，故意改坏一个链接看它红，再还原。

**产出**：一个 verify 脚本 + 一段「基线与复核方式」说明。

**验收**：
- verify 脚本对当前树全绿；
- 故意引入一个坏链接 → 脚本变红 → 还原；
- 文档里没有「以当前 checkout 为准」这类会把基线悄悄滑走的表述。

**对应**：反馈维的「机器检查兜底 + 负例控制」用在维护这套文档自己身上——[可执行反馈](./09-executable-feedback.md)。

## 收尾：一轮一轮打磨，直到像回事

**打磨不是一条单行道。** 每做完一轮 Phase，回到 Phase 1 的十维表重新打分，并用切片的那笔真实变更复测一次：

- 哪些维从「没有」升到了「有但不成体系」、从「不成体系」升到了「像回事」？
- 复测的走查记录里，「靠猜」和「没证据」的条目比上一轮少了吗？

**「像回事」的验收**：十维全部至少「有且成体系」，其中你项目最痛的三维达到「像回事」；垂直切片复测里没有「完全找不到 owner」「声称的行为零证据」这类硬伤。达标的标志很朴素——**新来一个 agent（或人），不靠任何人带路，能把一笔普通变更从意图走到归位，并且每一步说得出来证据在哪。** 这就是 DSH 那种 harness 的样子。

没达标就再来一轮：评估结果会告诉你下一轮先打磨哪里。

## 最小可用集（MVP）

如果只打算投入最少的功夫，只做五件事：

1. Phase 1 的十维打分 + 垂直切片——先知道自己缺什么，再动手建；
2. 短 `AGENTS.md`（常驻规则 + 布局 + 命令），`CLAUDE.md` 用 symlink 指向它；
3. 决策理由进 `docs/adr/`，`docs/` 只写 now；
4. 一张「目标 → 机制」归属表 + 第一批可机械规则接成 `exit non-zero` 脚本（同批做，负例控制各一次）；
5. agent 动作的三段管线：先记录、统一执行前检查、结果单一出口。

**这五件事不需要任何插件架构，且第 1 件事会告诉你其余四件里哪个对你最要命。** 如果还有余力，补一个 verify 脚本（Phase 8 的第 1、5 条），让这些从此有机器兜底。

本页声称的 DSH 事实，上游一手出处集中登记在 [`reference.md`](./reference.md)（本章「06 · 落地总纲」一节）——按需核对，不读不影响理解。
