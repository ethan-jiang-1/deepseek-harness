# 02 · 轻量决策记录与同提交闭环：管住“失忆”与“半成品交付”

光把静态文档地图画清楚，只能保证 Coding Agent 进门那一下不迷路；真等它动手连续改上几十个 PR，另外两个顽疾就会冒出来：

1. **跨会话失忆，反复重提死胡同方案**：代码只能表达“我们最终选了 A”，没法表达“我们试过 B 但在慢机器上会死锁，所以彻底放弃了 B”。下一轮新会话的 Agent 一看 B 写起来更短，顺手又给你改回 B。
2. **只交代码的“半成品 PR”**：人类开发常说“功能先合，文档和补测我下个 PR 补”；但在 Agent 高频迭代的仓库里，一旦代码先合、README 还写着旧行为，明天进来的另一个 Agent 就会拿旧 README 当权威合同，把刚改好的逻辑当成 bug 修回去。

DSH 管住这两件事靠的是一静一动两套机制：**严卡门槛的决策记录（Agent Note）**，加上**代码、现状文档、回归证据绑死在同一个 PR 落地的原子闭环**（主仓完整流程见 [FAQ 06](../06_change-landing-path/answer.md)）。

## 一、轻量决策记录：90% 日常改动免写，只记“代码说不清的取舍”

很多团队推行 ADR（Architecture Decision Record）最后沦为形式主义废纸堆，原因只有一个：**不分青红皂白要求“大点的改动都得写设计文档”。** Agent 最擅长凑字数写空话，一旦强制每单必写，目录三天就会被毫无信息量的八股文淹没。

抄 DSH 的 [`.agents/notes/README.md`](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/README.md)，最值钱的恰恰是它**“什么时候不写”的准入红线**：

- **唯一触发条件**：只有当这笔改动包含**代码、测试和现有文档都解释不了的持久设计取舍**（尤其是存在认真考虑过的备选方案、或者明确放弃了什么代价）时，才在同一个 PR 里新增或更新决策记录。
- **明确豁免范围**：局部修补、机械重构、单纯的界面展示与交互微调**一律豁免**；反过来，哪怕只改了十行代码，只要背后藏着关键的机制取舍（比如超时策略、并发锁边界），就不能因为 diff 小而漏写。

拿 DSH 仓库里两笔真实的提交对看，分寸感立刻就清楚了（详细走查见 [FAQ 06 分篇](../06_change-landing-path/01-before-coding.md)）：

| 真实案例 | 改了什么 | 写没写决策记录？为什么？ |
|---|---|---|
| **模型选择器显示原始 ID**<br/>（提交 [`5124a2a310`](https://github.com/deepseek-ai/deepseek-harness/commit/5124a2a310a904d28118609c41d89f26440b946b)，PR [`#5004`](https://github.com/deepseek-ai/deepseek-harness/pull/5004)） | 把下拉列表从显示模型别名改为显示原始 model ID、悬停看别名（共 7 个文件，`+15/-14`） | **不写（合规豁免）**。纯局部 UI 展示调整，没有复杂的方案博弈；改完组件、测试和 README 事实就已完整。 |
| **有界 pnpm 子进程防占锁**<br/>（提交 [`ccaa0dc11c`](https://github.com/deepseek-ai/deepseek-harness/commit/ccaa0dc11c)，[对应记录](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/archived/bug-fix/2026-09-23-bounded-pnpm-runs.md)） | 修复静默挂起的 `pnpm` 子进程长期霸占 profile 锁 | **必写**。为什么选“无输出静默超时”而非“总耗时上限”（防慢机器合法安装被误杀）？淘汰了哪 5 条备选路线？接受了什么极端误杀代价？这些全在代码之外，不记下来后人必踩坑。 |

## 二、拿来即用的最小 ADR 模板与三条防腐烂铁律

普通项目完全不必照搬 DSH 的双语三件套（英文 + 中文 + `.i18n.yaml`）或六大分类子目录。在仓库里建一个扁平的 `docs/adr/`（如 `docs/adr/0001-idle-timeout-over-wall-clock.md`），用下面这份四段式模板就够了：

```markdown
# ADR-0001 · 用输出静默超时替代总时长上限回收卡死子进程

Status: implemented

## Problem（背景与问题）
包管理子进程偶发网络挂起不退出，导致工作区锁永久阻塞后续操作；需要自动回收卡死进程，同时不能误杀低配机器或冷缓存下的正常慢速安装。

## Decision（最终决定 — 用现在时态陈述已落地事实）
子进程监控按 stdout/stderr 静默时长判定超时（默认阈值可配置），有持续输出的安装过程不受总时长截断。

## Alternatives considered（放弃的真实备选方案）
- 固定总时长上限（如 120s 强杀）：实现最简单，但在弱网首次拉取大依赖时会稳定误杀合法任务。
- 外部守护进程轮询清理：引入跨平台孤儿进程管理复杂度，收益不抵成本。

## Consequences（后果与验证）
- 接受的代价：若某个合法命令长时间既无标准输出也无错误输出，仍可能触发超时报错。
- 验证锚点：`tests/subprocess-timeout.spec.ts` 覆盖静默超时强杀与持续输出保活两条路径。
```

管好这个目录只需要守住三条规矩：

1. **备选方案只写“真刀真枪纠结过的”**：没有备选就别硬凑稻草人方案充数——凑不出真实备选，往往说明这事根本不配写 ADR。
2. **合入时一律改写成现在时态**：如果动工前写过 `Status: proposed` 草案，功能落地合入的同一个 PR 里必须把 `Status` 改为 `implemented`，并把正文里的“计划将要（will/should）”全部擦干净写成当前事实，别留半截施工单混淆视听。
3. **推翻旧决定时新增记录，绝不原地篡改**：后来决定改走别的路时，新建一篇 ADR 并在两篇之间互相标明取代关系（或把旧篇独有的背景与教训完整吸收进新篇后再归档/删旧篇）；如果某次提案评审被毙了，只要它还能防住后人重踩同一个诱人陷阱，就标成 `Status: rejected — <一句话原因>` 留着当醒目的路障。

## 三、同提交原子闭环：每次 PR 必交“三件套”与诚实缺口

有了地图和 ADR，日常每一笔改动怎么走才不会越改越散？把 DSH 的交付闭环翻译成普通团队每天能执行的规矩，就是下面四步：

1. **改前两句话定验收**：不管是写进 Issue 还是直接写在 PR 描述第一段，先用大白话说清“外部可观察行为变成什么样、怎么验证它成了”。
2. **同一个 PR 交齐“原子三件套”**：
   - **实现代码**；
   - **同步刷新后的现状文档**（受影响的模块 `README`、配置说明、导出函数注释）；
   - **在旧代码上会报红的行为测试**。
   把“先合代码，下周补文档和测试”明确列为团队反模式——对 Coding Agent 来说，顺手在一个上下文里把三样改齐只需要多花三十秒，拆到下周就成了没人收拾的烂尾楼。
3. **修改源头，自动刷新派生物**：凡是有单点事实源的东西（比如 OpenAPI 定义、数据库 schema、配置默认表），只准改源头再跑生成命令，严禁手改下游派生文件制造双份真相。
4. **老实标出没测到的缺口，拒绝“假全面测试”**：回到前面模型选择器 `5124a2a310` 的真实例子——那笔提交里，组件单测把断言从模型名称反转为原始 model ID（实测把实现回退、只留新测试会跑出 **2 红 95 绿**，证明测试真能抓回归）；但 README 同时承诺的“等宽字体样式”和“鼠标悬停显示原名”并没有写进自动化断言。DSH 的做法不是逼着为两行 CSS 硬写脆弱快照，而是在交付说明与评审里**如实指出哪部分靠测试钉死、哪部分留给人工检查**。让 Agent 养成“跑了哪条命令就报哪条、没覆盖的表面直说”的习惯，人工 Code Review 才能一把捏住重点。
