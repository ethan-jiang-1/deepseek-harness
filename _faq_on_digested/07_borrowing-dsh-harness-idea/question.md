# FAQ 07 · 另一个项目想借鉴 DSH 的 Harness 思路，让 Coding Agent 不糊涂、不乱发挥，该抄什么、别盲目照搬什么？

## 问题背景

假设你手头维护着一个自己的代码库——可能是一个 TypeScript / Python 业务应用、后端服务，或者一个独立的插件仓库，并不是 DSH 这种 300 多个包的插件化框架。你想让 Coding Agent（无论是 DSH、Claude Code、Codex 还是 Cursor）进仓库干活时少出两类洋相：

- **读糊涂了**：面对目录抓不住主线，把历史残留代码当现行接口，或者反复重新提议团队上个月刚否决掉的方案；
- **乱发挥了**：放着现成扩展口不用去硬改核心逻辑，在两个地方各存一份状态导致分叉，或者只交代码不补文档和测试。

DSH 主仓自己的开发主力就是 Coding Agent，但它同时背着多包发布、双语文档配对、双语言 SDK 同步等大仓包袱。

站在外部项目负责人的视角，我们关心一个直接能落地的工程问题：**怎么把 DSH 里真正管用的治理骨架挑出来，又不把大仓专属的重型仪式感背回自己团队？**

## 具体要回答什么

1. Agent 进项目后“读糊涂”和“乱发挥”，根源上缺的是哪几类工程信号？为什么靠换更聪明的模型救不了？
2. 区分普通中小型仓库、大型工程仓库与自研 Agent 运行时三类场景，DSH 里哪些做法**值得立刻抄**，哪些**盲目照搬反而背债**？
3. 入口地图（`AGENTS.md`）、现状文档与轻量决策记录（ADR）、同提交交付闭环、秒级可执行门禁这几块核心机制，怎么裁剪成低成本方案？
4. 面对一个已经在跑的存量仓库，按 **Day 1 → Week 1 → Month 1+** 分三步接入，每一步最小投入做什么、怎么验收效果？
