# 04 · 存量项目分步接入路线：Day 1、Week 1 到 Month 1+（含改造前后对照）

往一个已经在跑的存量仓库里引借鉴，最忌讳“停工一周搞文档大基建”——基建铺得太重，业务一忙立刻烂尾。最稳妥的打法是**先花 15 分钟拿一笔旧 PR 摸清真痛点，再按 Day 1 → Week 1 → Month 1+ 逐级加装**，每一步都做到当天投入、当天见效。

---

## 一、开工前 15 分钟：拿最近合入的一笔真实 PR 做切片体检

先别急着新建文件。打开你们仓库上周刚合并的一笔中等规模 PR（比如加了个小接口或修了个跨文件 bug），对着下面四个问题过一遍：

1. **找路成本**：假如换一个从没见过这项目的全新 Agent 会话，只看仓库根目录，它能在 3 次文件读取内找准该改哪个目录、该跑哪条测试命令吗？
2. **同步交付**：这笔 PR 改了外部行为或配置项时，对应的 README / 接口说明和会报红的测试是跟着**同一个 PR** 一起合入的吗？
3. **决策留痕**：如果当时讨论过“为什么不走另一条更省事的方案”，现在关掉聊天软件只看仓库，还能找到原因吗？
4. **拦截时机**：Review 评论里人类指出的问题，有哪些其实用 20 行脚本就能在提交前自动拦住？

哪一问卡壳，哪一问就是你们回报率最高的第一刀。

---

## 二、三阶段渐进落地路线图

### 阶段一：Day 1（投入 1–2 小时 · 零业务代码侵入，先治“进门抓瞎”）

| 动作 | 具体怎么做 | 最小验收标准 |
|---|---|---|
| **1. 立短根入口与软链接** | 新建根 `AGENTS.md`（控制在 100–200 行内），只写三块：**顶层目录一句话地图、常用构建/单测命令、5–10 条绝对红线**；执行 `ln -s AGENTS.md CLAUDE.md` | 开一个全新 Agent 会话，不喂任何路径提示，让它解释项目结构并指出某功能该跑什么测试，一次答对 |
| **2. 补一张“改动路由表”** | 在 `AGENTS.md` 或 `docs/architecture.md` 写一张 10 行以内的 `常见需求 → 具体目录/注册文件` 两列表 | 问 Agent“新增一种消息通知渠道该改哪”，它直接指向正确的注册入口而非瞎猜核心主干 |
| **3. 建 `docs/adr/` 记下第一条负知识** | 建目录放进四段式模板（见 [`02`](./02-decision-notes-and-change-loop.md)），先把团队最近踩过坑、最怕新人重提的 1–2 个被否决方案记进去 | ADR 里说清了放弃的真实备选方案与原因；同时明确宣布“普通日常小改免写 ADR” |

### 阶段二：Week 1（投入半天到一天 · 立住“同 PR 闭环 + 秒级快检查”）

| 动作 | 具体怎么做 | 最小验收标准 |
|---|---|---|
| **1. 固化同 PR 三件套规矩** | 新建或精简 `.github/pull_request_template.md`，只留三栏：**外部可观察变化 / 同步更新的现状文档 / 实际跑过的最小检查命令（及未测缺口）** | 团队形成共识：改了外部行为却没同步改 README 和测试的 PR 不予合入 |
| **2. 上线首个可执行快门禁** | 挑 2–3 条最常破的死规矩（如文档相对死链、根 `AGENTS.md` 行数超标、跨层违规 `import`），写一个 `scripts/verify-repo.mjs`（或 `.py`）接入 CI | **亲手做过红灯对照**：故意写坏一个链接或违规引用，脚本返回 `exit 1` 并打印具体修复提示，还原后变绿 |
| **3. 切开本地快钩子与慢测试** | 配 `lefthook` 或 `husky`：`pre-commit` 只跑暂存区 lint 与空白检查（严格压在 3 秒内）；在 `AGENTS.md` 写明日常只按改动目录跑单文件测试 | 本地 `git commit` 无卡顿感；改单个业务模块跑对应测试不超过 10 秒 |

### 阶段三：Month 1+（按真实痛点选配 · 没痛点坚决不加）

跑顺前两周后，只有当下面某类摩擦反复出现时，才去借对应的进阶工具：

- **同类多步任务第 3 次漏步骤**（比如数据库迁移、发版核对、新增外部网关）→ 抽一篇 `.agents/skills/<name>/SKILL.md`，写明触发时机与每步可执行命令。
- **多层环境变量与配置文件叠加总让 Agent 猜错线上值** → 给服务加一个 `--dump-config` 或 `pnpm show-config` 只读打印子命令。
- **错误码表、CLI 参数表、权限点清单频繁跟代码脱节** → 写小脚本从代码导出 Markdown，并在 `verify-repo` 里加 `--check` 新鲜度比对。
- **外部 API / 大模型集成链路经常单测全绿、拼起来报错** → 引入关键链路的录制回放测试（参考 [FAQ 21](../21_recorded-session-snapshots/answer.md)）。

## 三、改造前后直观对比：以一个典型 TypeScript 后端仓库为例

假设你维护一个订单与通知服务 `order-hub`，团队想让 Agent 帮忙开发“新增飞书告警通知渠道”。看看改造前后的真实体验差别：

```text
【改造前：靠口口相传的普通仓库】                【改造后：花一天半搭好骨架的仓库】
order-hub/                                    order-hub/
├── README.md (800行：三年前的部署教程+过期架构) ├── AGENTS.md (120行：目录路标 + 铁律 + 单包测试命令)
├── src/                                      ├── CLAUDE.md -> AGENTS.md (软链接，一份事实)
│   ├── core/order-service.ts                 ├── docs/
│   ├── legacy-notify/ (废弃未删的旧版)        │   ├── architecture.md (当前模块边界 + 改动路由表)
│   └── channels/ (现行渠道适配器)             │   └── adr/
└── tests/                                    │       └── 0001-deprecate-legacy-notify.md (负知识)
                                              ├── .agents/skills/
                                              │   └── add-channel/SKILL.md (新渠道标准接线步骤+验证命令)
                                              ├── scripts/verify-repo.mjs (查死链 + 禁引 legacy-notify)
                                              ├── .github/pull_request_template.md (三件套与命令清单)
                                              └── src/ & tests/ ...
```

同一句需求丢给 Coding Agent，两边的走势截然不同：

- **改造前**：Agent 读完 800 行过期 `README` 一头雾水，在 `src/` 里同时搜到 `legacy-notify/` 和 `channels/`；它要么在 `order-service.ts` 核心流程里硬塞一段飞书 HTTP 请求，要么照着废弃的 `legacy-notify` 抄出一套死代码，最后跑一遍耗时 4 分钟的全量测试嫌太慢干脆中断，直接甩给你一个没改文档、没测异常分支的半成品 PR。
- **改造后**：Agent 开局自动读到 120 行的 `AGENTS.md`，顺着链接翻开 `docs/architecture.md` 的路由表，10 秒确认“新增通知渠道归 `src/channels/` 并挂进注册表”，同时从 `0001` 号 ADR 知道绝不能碰 `legacy-notify`（就算误引了，`scripts/verify-repo.mjs` 也会在 1 秒内报错拦下）；接着它按需加载 `add-channel/SKILL.md`，照标准步骤补齐适配器、更新渠道 `README`、写好能在旧代码上报红的单测，花 3 秒跑完 `vitest src/channels/feishu.spec.ts`，最后在 PR 里清楚列出跑过的命令交卷。

## 四、长期维护防走形：每季度花五分钟自查四句话

1. **根 `AGENTS.md` 超重了吗？** 如果它已经涨破了 300 行、开始塞进具体业务流程和历史故事，赶紧把细节踢回子文档或 `SKILL.md`。
2. **`docs/adr/` 变成流水账垃圾桶了吗？** 如果里面躺着一堆“没有任何真实备选方案”的常规功能记录，重申豁免红线，删掉纯机械修补的废话文档。
3. **门禁脚本真能报红吗？** 抽查最近加的两条检查规则，看看它们有没有抓到过真问题，还是写成了永远退 `0` 的安慰剂。
4. **本地提交变慢了吗？** 一旦有人嫌慢开始敲 `--no-verify`，立刻把耗时检查从 `pre-commit` 挪回按需命令或远端 CI。
