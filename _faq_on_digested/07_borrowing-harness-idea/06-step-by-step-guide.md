# 一步一步怎么做：把你的 harness 打磨到像回事

> **分水岭 · 落地总纲。** 前五篇是道——五个大概念（变更闭环、归属、决策记录、静与动、正确路径）和它们的落地实物；从本页起是术。本页拥有从道到术的接力：**先评估你手上的 harness 在五个维度各是什么水平，再按评估结果一轮一轮打磨，直到像回事。**

## 这一篇怎么用

道讲完了，本页把它变成一条**可执行的打磨路径**：每一步说清楚**做什么、产出什么、怎么验收（怎么证明这一步真做对了）**。

原则只有一条：**先诊断、后施工，按收益/成本从高到低做，每一步都能独立验收**。评估不是走过场——评估的产出（哪一维最痛、痛在哪个具体案例）直接决定你先打磨哪一步；一轮打磨完成后回到评估复测，像回事了才算完。

> 顺序参考 [`迁移清单`](./10-transfer-playbook.md) 的优先级，但真正决定次序的是你自己的评估结果。

## Phase 0 · 评估你的 harness：道的五个维度（一次性，最轻，先于一切）

**做什么**：对齐道五篇的五个维度，逐维给自己项目打分。每维三档：**没有**（全靠人脑/口传）/ **有但不成体系**（零散文档或检查，没纪律）/ **像回事**（有 owner、可核对、可持续）。每维记「档位 + 一个最痛的真实案例」：

| 维度（道之篇） | 自评问题 | 打分锚点 |
|---|---|---|
| 变更闭环（01） | 一笔变更从意图到归位，走得通吗？ | 意图写得出吗？实现+文档+证据同 PR 吗？合并后新 agent 能回答三问吗？ |
| 归属（02） | 每类事实有唯一 home 吗？ | 一条规则 10 秒内指得出唯一出处吗？同一事实有第二份拷贝吗？ |
| 决策记录（03） | 「为什么」存得住、跟得上吗？ | 被否决的方案，新 agent 还会再提吗？过时的理由会冒充现行吗？ |
| 静与动（04） | 静态层和动态层分得清吗？ | 同一事实存两处吗？会话/任务历史能回放吗？临时决定回写吗？ |
| 正确路径（05） | 「改哪里」有表可查吗？ | 新任务靠猜位置还是查归属？能用配置解决的，动过核心吗？ |

**产出**：一张五行打分表 + 每维的最痛案例。

**验收**：能指着具体一个 bug/返工，说出它是哪一维的缺口造成的。说不出来，说明还没诊断透，先别动手。

> answer 的三问自检（知识外置/正确入口/反馈时机）是这五个维度的快速汇总视角，适合日常快诊；施工前用这张五维表，粒度才够。**今后术篇若确立新维度（如 Skills 写法、披露预算），追加进这张表。**

## Phase 0.5 · 拿一笔真实变更跑通垂直切片（一次性，先于一切建设）

**做什么**：评估完维度，再用一笔真实变更验证一次「用」。挑你们仓库**最近已完成的一笔真实小变更**（修复或小功能，不改核心架构），按变更闭环标准全程走查：

1. 这笔变更的用户可观察结果是什么？写得出两行「外部结果 + 如何观察」吗？
2. 从任务描述出发，能不能一路找到改动位置的 owner（不靠当时作者本人带路）？
3. 交付里有没有携带持久取舍？有的话它记在哪里？没有的话，理由说得出吗？
4. 哪项证据会在旧行为上失败？把实现回滚、保留测试，跑一次看它红不红（红灯对照）。
5. 每一步标注证据状态：能指出文件的 / 只有口头说法的 / 完全没有的。

**产出**：一张五行走查记录，外加三份清单——打不开的链接、要靠猜的 owner、没有证据支持的声称。

**验收**：每一个「靠猜」和「没证据」都能归到 Phase 0 五维表的某一维——这张清单就是你的定制化施工顺序，比任何通用优先级都准。

**对应**：变更闭环的完整预演。DSH 的标准演示是[提交 5124a2a310](https://github.com/deepseek-ai/deepseek-harness/commit/5124a2a310a904d28118609c41d89f26440b946b)——[变更闭环](./01-sdlc-change-loop.md) 有它的逐环对照表。

## Phase 1 · 立规矩的 owner（通常收益最高）

**做什么**：写一份**短**的根 `AGENTS.md`，只放三类东西：常驻规则（每条一到三行）、仓库布局（每个顶层区域一句话）、命令表。其余全部 link 到各自 home，不复制。同时把 `CLAUDE.md` 用 `ln -s AGENTS.md` 指向它，并在**真正有子树专属常驻规则**的少数目录放子树 `AGENTS.md`，其余目录/包只留 README。

**产出**：根 `AGENTS.md`（目标 ≤ 几百词）+ `CLAUDE.md`（symlink）+ 一张「事实 → home」对照表 + 少量子树 `AGENTS.md`（可有可无，按需）。

**验收（机械判断）**：
- 任何一条规则，能在 10 秒内指出它的唯一 home；
- 不存在同一规则在两处各写一版；
- 根文件里没有教程、没有历史故事、没有该 link 出去的细节；
- `CLAUDE.md` 是 symlink 而非副本；子树 `AGENTS.md` 只出现在「有专属常驻规则」处，没有为放而放。

**对应**：归属维（02）。入口链的完整骨架见 [`入口链`](./07-agents-entry-chain.md)。

## Phase 2 · 划清「现在」和「为什么」

**做什么**：把 `docs/`（或 README）定为 **current state**，决策理由单独进 `docs/adr/` 或 `notes/`。顺手记下负知识——「为什么不走某条路」「已知限制是什么」。

**产出**：`docs/adr/`（或等价物）的目录 + 第一批 ADR/负知识条目。

**验收**：
- 读一份 ADR 能回答「为什么这样决定、什么方案输了、后果是什么」；
- `docs/` 里没有 change history（那是 git/PR 的职责）；
- 至少有一条负知识，agent 不会再反复提出已否决方案。

**对应**：归属维 + 决策记录维（02、03）。

---

## Phase 3 · 铺正确路径

**做什么**：写一张「目标 → 机制」归属表，再给最常见的几类任务各写一个 cookbook（短入口 + 范本 + 升级条件）。

**产出**：
- 一张归属表（列：目标 / 首选入口 / 何时升级）；
- 第一批 cookbook（按 Phase 0.5 清单里最痛的任务定数量），每份含「先问归属 → 照范本 → 跑对应检查」。

**验收**：
- 一个新任务进来，先查归属表就能回答「该改哪里」，而不是翻代码猜；
- cookbook 里「本可用配置/扩展点表达、却要改核心」这种情况被显式拦下（升级条件写清楚了）。

**对应**：正确路径维（05）。

---

## Phase 4 · 把可机械规则接到执行（通常回报第二高）

**做什么**：挑出 Phase 1 里「可机械判断」的规则，各配一个 `exit non-zero` 的命令；写一个聚合脚本；接进 git hook（低延迟项）和 CI（穷举项）。

**产出**：一个 `scripts/check.sh`（或等价物）+ 每个规则的负例测试。

**验收（硬指标）**：
- **每个检查都做过负例控制**：引入对应回归 → 看它变红 → 还原；
- 本地能只跑「受本次改动影响」的相关检查，CI 跑全套；
- 反馈信息能指出「失败对象 + 违反规则 + 修正入口」，不是一句无上下文的「检查失败」。

**对应**：变更闭环维的证据环（01）+ [`可执行反馈`](./09-executable-feedback.md) 的机制细节。

---

## Phase 5 · 固化任务流程（按需）

**做什么**：把反复出现、需要上下文判断的任务流程写成带触发条件的短文档（等价于 Skill）：触发条件、输入、步骤、停止条件、验证、输出格式。

**产出**：一个「任务 → 流程文档」的目录 + 第一批流程文档（数量由重复出现的频率决定）。

**验收**：
- 命中任务时先读全文、不从摘要猜（文档里明确写这条纪律）；
- 每份文档末尾声明「这是 guidance，不是 checklist」，可机械部分仍然指向 gate 而不是 prose。

**对应**：术——[`Skills`](./11-skills-as-procedural-memory.md) 的写法标准。

---

## Phase 6 · 加运行时查询（确有压力才做，可无限期推迟）

**做什么**：最低成本先给一条「dump 最终生效配置」的命令；只有确实存在多 profile/provider/动态装卸时，才考虑生成 catalog 和只读 inspect 工具。

**产出**：一条 `show-config`（或等价）命令；可选：生成索引 + freshness 检查。

**验收**：
- 能用命令回答「这台机器实际装了什么」，而不靠读源码猜；
- 若做了 catalog，有 freshness 检查防止索引与源码漂移。

**对应**：术——[`运行时查询`](./12-runtime-inspection.md)。**注意**：这不是安全沙箱，别把 inspect 当授权边界。

---

## Phase 7 · 防漂移：让这套东西长期不失效（持续，从第一次交付后开始）

前面的 Phase 都是「建」，这一 Phase 是「维护」。DSH 最反直觉的一条纪律：**外置的知识会漂，所以它给外置知识配机器检查**。

**做什么**：
1. 给规则/研究目录配一个轻量 verify 脚本（严格 UTF-8、结尾换行、相对链接、锚点），每次编辑后跑一次；
2. 钉基线：文档开头写明「结论以 X commit 为准」；上游更新后**只复核被引用文件是否变化**，不全文重写；
3. 改事实只改它的 home：一条规则变了，改 owning 文件 + 所有链到它的引用——漏一处就漂一处；
4. 数字类事实（预算、上限、个数）标注「以基线的某文件为准」——数字是最容易漂的；
5. 新检查做负例控制：verify 脚本第一次上时，故意改坏一个链接看它红，再还原。

**产出**：一个 verify 脚本 + 一段「基线与复核方式」说明。

**验收**：
- verify 脚本对当前树全绿；
- 故意引入一个坏链接 → 脚本变红 → 还原；
- 文档里没有「以当前 checkout 为准」这类会把基线悄悄滑走的表述。

**对应**：[`可执行反馈`](./09-executable-feedback.md) 的「机器检查兜底 + 负例控制」先用在维护这套文档自己身上。

## 收尾：一轮一轮打磨，直到像回事

**打磨不是一条单行道。** 每做完一轮 Phase，回到 Phase 0 的五维表重新打分，并用 Phase 0.5 的那笔真实变更复测一次垂直切片：

- 哪些维从「没有」升到了「有但不成体系」、从「不成体系」升到了「像回事」？
- 复测的走查记录里，「靠猜」和「没证据」的条目比上一轮少了吗？

**「像回事」的验收**：五维全部至少「有且成体系」，其中你项目最痛的两维达到「像回事」；垂直切片复测里没有「完全找不到 owner」「声称的行为零证据」这类硬伤。达标的标志很朴素——**新来一个 agent（或人），不靠任何人带路，能把一笔普通变更从意图走到归位，并且每一步说得出来证据在哪。** 这就是 DSH 那种 harness 的样子。

没达标就再来一轮：评估结果会告诉你下一轮先打磨哪里。

## 最小可用集（MVP）

如果只打算投入最少的功夫，只做五件事：

1. 五维打分 + 拿一笔最近的真实变更跑一次垂直切片（Phase 0 + 0.5）——先知道自己缺什么，再动手建；
2. 短 `AGENTS.md`（常驻规则 + 布局 + 命令），`CLAUDE.md` 用 symlink 指向它；
3. 决策理由进 `docs/adr/`，`docs/` 只写 now；
4. 一张「目标 → 机制」归属表；
5. 第一批可机械规则（从评估里挑最痛的）接成 `exit non-zero` 脚本，并各做一次负例控制。

**这五件事不需要任何插件架构，且第 1 件事会告诉你其余四件里哪个对你最要命。** 如果还有余力，补一个 verify 脚本（Phase 7 的第 1、5 条），让这些从此有机器兜底。

本页声称的 DSH 事实，上游一手出处集中登记在 [`reference.md`](./reference.md)（本章「06 · 落地总纲」一节）——按需核对，不读不影响理解。
