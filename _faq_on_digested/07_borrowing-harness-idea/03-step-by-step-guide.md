# 03 · 一步一步怎么做：把普通项目改造成「agent 不糊涂、不乱发挥」

## 这一篇怎么用

其余各篇讲「是什么、为什么、可迁移什么」；这一篇把它们压成一条**可执行的落地顺序**：每一步说清楚**做什么、产出什么、怎么验收（怎么证明这一步真做对了）**，并标注它对应「不糊涂」还是「不乱发挥」。

原则只有一条：**按收益/成本从高到低做，每一步都能独立验收，别跳到第 5 级架构。** 对一个普通项目，做完 Phase 0–4 就覆盖了「不糊涂 + 不乱发挥」的主要来源；Phase 5–6 按需。

> 顺序本身来自 [`07-transfer-playbook.md`](./07-transfer-playbook.md) 的优先级清单，这里把它展开成动作。每个 Phase 做完后，用 Phase 0 的三问打分 + Phase 0.5 的垂直切片复测——详见文末「收尾」。

---

## Phase 0 · 先给项目打分（一次性，最轻）

**做什么**：用三问框架评估现状，找出自己最痛的一档。

- 规则住在哪里？（人脑 / 文档 / 可执行检查）
- 正确入口明确吗？（能不能从目标找到 owner 和范本）
- 错误何时被发现？（编译 / 测试 / CI / review / 生产）

**产出**：一张三行打分表，每行写「现状 + 最痛的一个例子」。

**验收**：能指着具体一个 bug/返工，说出它是「哪一档缺口」造成的。说不出来，说明还没诊断透，先别动手。

**对应**：这是「不糊涂 + 不乱发挥」共同的基线。

---

## Phase 0.5 · 拿一笔真实变更跑通垂直切片（一次性，先于一切建设）

**做什么**：在动任何「建」的动作之前，先检验一次「用」。挑你们仓库**最近已完成的一笔真实小变更**（修复或小功能，不改核心架构），按 DSH 的变更闭环标准对它做一次全程走查：

1. 这笔变更的用户可观察结果是什么？写得出两行「外部结果 + 如何观察」吗？
2. 从任务描述出发，能不能一路找到改动位置的 owner（不靠当时作者本人带路）？
3. 交付里有没有携带持久取舍？有的话它记在哪里？没有的话，理由说得出吗？
4. 哪项证据会在旧行为上失败？把实现回滚、保留测试，跑一次看它红不红（DSH 称为红灯对照）。
5. 每一步标注证据状态：能指出文件的 / 只有口头说法的 / 完全没有的。

**产出**：一张五行走查记录，外加三份清单——打不开的链接、要靠猜的 owner、没有证据支持的声称。

**验收**：每一个「靠猜」和「没证据」都对应到 Phase 1–6 的某一步——这张清单就是你的定制化施工顺序，比任何通用优先级都准。

**对应**：变更闭环（时间层）的完整预演。DSH 的标准演示见 [`_agent_ready_development/sdlc-tutorial/01-follow-a-change.md`](https://github.com/deepseek-ai/deepseek-harness/blob/46a7f68b0922371ce7144b668b90e377d8e799f4/_agent_ready_development/sdlc-tutorial/01-follow-a-change.md)（一笔 7 文件真实变更的证据地图）与 [`04-implementation-and-evidence.md`](https://github.com/deepseek-ai/deepseek-harness/blob/46a7f68b0922371ce7144b668b90e377d8e799f4/_agent_ready_development/sdlc-tutorial/04-implementation-and-evidence.md)（红灯对照实测记录）。

## Phase 1 · 立规矩的 owner（收益最高）

**做什么**：写一份**短**的根 `AGENTS.md`，只放三类东西：常驻规则（每条一到三行）、仓库布局（每个顶层区域一句话）、命令表。其余全部 link 到各自 home，不复制。同时把 `CLAUDE.md` 用 `ln -s AGENTS.md` 指向它，并在**真正有子树专属常驻规则**的少数目录放子树 `AGENTS.md`，其余目录/包只留 README。

**产出**：根 `AGENTS.md`（目标 ≤ 几百词）+ `CLAUDE.md`（symlink）+ 一张「事实 → home」对照表 + 少量子树 `AGENTS.md`（可有可无，按需）。

**验收（关键，机械判断）**：
- 任何一条规则，能在 10 秒内指出它的唯一 home；
- 不存在同一规则在两处各写一版；
- 根文件里没有教程、没有历史故事、没有该 link 出去的细节；
- `CLAUDE.md` 是 symlink 而非副本；子树 `AGENTS.md` 只出现在「有专属常驻规则」处，没有为放而放。

**对应**：不糊涂（知识外置 + 一个事实一个 owner）。入口链的完整骨架见 [`08-agents-entry-chain.md`](./08-agents-entry-chain.md)（04 的进阶深化）。

---

## Phase 2 · 划清「现在」和「为什么」

**做什么**：把 `docs/`（或 README）定为 **current state**，决策理由单独进 `docs/adr/` 或 `notes/`。顺手记下负知识——「为什么不走某条路」「已知限制是什么」。

**产出**：`docs/adr/`（或等价物）的目录 + 第一批 ADR/负知识条目。

**验收**：
- 读一份 ADR 能回答「为什么这样决定、什么方案输了、后果是什么」；
- `docs/` 里没有 change history（那是 git/PR 的职责）；
- 至少有一条负知识，agent 不会再反复提出已否决方案。

**对应**：不糊涂（当前事实 vs 决策理由分开 + 负知识外置）。

---

## Phase 3 · 铺正确路径

**做什么**：写一张「目标 → 机制」归属表，再给最常见的几类任务各写一个 cookbook（短入口 + 范本 + 升级条件）。

**产出**：
- 一张归属表（列：目标 / 首选入口 / 何时升级）；
- 第一批 cookbook（按 Phase 0.5 清单里最痛的任务定数量），每份含「先问归属 → 照范本 → 跑对应检查」。

**验收**：
- 一个新任务进来，先查归属表就能回答「该改哪里」，而不是翻代码猜；
- cookbook 里「本可用配置/扩展点表达、却要改核心」这种情况被显式拦下（升级条件写清楚了）。

**对应**：不乱发挥·改哪里（paved road + 参与阶梯）。

---

## Phase 4 · 把可机械规则接到执行（回报第二高）

**做什么**：挑出 Phase 1 里「可机械判断」的规则，各配一个 `exit non-zero` 的命令；写一个聚合脚本；接进 git hook（低延迟项）和 CI（穷举项）。

**产出**：一个 `scripts/check.sh`（或等价物）+ 每个规则的负例测试。

**验收（这一条是硬指标）**：
- **每个检查都做过负例控制**：引入对应回归 → 看它变红 → 还原；
- 本地能只跑「受本次改动影响」的相关检查，CI 跑全套；
- 反馈信息能指出「失败对象 + 违反规则 + 修正入口」，不是一句无上下文的「检查失败」。

**对应**：不乱发挥·早失败（可执行反馈，最高杠杆）。

---

## Phase 5 · 固化任务流程（按需）

**做什么**：把反复出现、需要上下文判断的任务流程写成带触发条件的短文档（等价于 Skill）：触发条件、输入、步骤、停止条件、验证、输出格式。

**产出**：一个「任务 → 流程文档」的目录 + 第一批流程文档（数量由重复出现的频率决定）。

**验收**：
- 命中任务时先读全文、不从摘要猜（文档里明确写这条纪律）；
- 每份文档末尾声明「这是 guidance，不是 checklist」，可机械部分仍然指向 gate 而不是 prose。

**对应**：不糊涂 + 不乱发挥（按需加载省上下文，收走「发明流程」的自由度）。

---

## Phase 6 · 加运行时查询（确有压力才做，可无限期推迟）

**做什么**：最低成本先给一条「dump 最终生效配置」的命令；只有确实存在多 profile/provider/动态装卸时，才考虑生成 catalog 和只读 inspect 工具。

**产出**：一条 `show-config`（或等价）命令；可选：生成索引 + freshness 检查。

**验收**：
- 能用命令回答「这台机器实际装了什么」，而不靠读源码猜；
- 若做了 catalog，有 freshness 检查防止索引与源码漂移。

**对应**：不糊涂（可检查性）。**注意**：这不是安全沙箱，别把 inspect 当授权边界。

---

## Phase 7 · 防漂移：让这套东西长期不失效（持续，从第一次交付后开始）

前六个 Phase 都是「建」，这一 Phase 是「维护」。DSH 最反直觉的一条纪律：**外置的知识会漂，所以它给外置知识配机器检查**——这正是「长期静默执行后不漂移」的答案。

**做什么**：
1. 给规则/研究目录配一个轻量 verify 脚本（严格 UTF-8、结尾换行、相对链接、锚点），每次编辑后跑一次；
2. 钉基线：文档开头写明「结论以 X commit 为准」；上游更新后**只复核被引用文件是否变化**，不全文重写；
3. 改事实只改它的 home：一条规则变了，改 owning 文件 + 所有链到它的引用——漏一处就漂一处；
4. 数字类事实（预算、上限、个数）标注「以基线的某文件为准」——数字是最容易漂的；
5. 新检查做负例控制：verify 脚本第一次上时，故意改坏一个链接看它红，再还原。

**产出**：一个 verify 脚本 + 一段「基线与复核方式」说明。

**验收**：
- verify 脚本对当前树全绿；
- 故意引入一个坏链接 → 脚本变红 → 还原；
- 文档里没有「以当前 checkout 为准」这类会把基线悄悄滑走的表述。

**对应**：这是本 FAQ 所有章节的自我适用——[`06`](./06-executable-feedback.md) 的「机器检查兜底 + 负例控制」先用在维护这套文档自己身上；上游合入后按 `_digested/_change_log/` 复核，见 [`research.md`](./research.md) 的说明。

---

## 收尾：每一步完成后回到三问

每做完一个 Phase，重跑 Phase 0 的三问打分，并用 Phase 0.5 的那笔真实变更复测一次垂直切片，确认：

1. 知识外置：规则从「人脑」搬进了「可搜索/可检查」了吗？
2. 正确路径：新参与者能便宜地找到 owner 和范本了吗？
3. 反馈延迟：错误被发现的位置，从「review/生产」往「编译/测试/CI」前移了吗？

三问都变好、且没有为了形式而造假断言，这一步才算真完成。

## 最小可用集（MVP）

如果只打算投入最少的功夫，只做五件事：

1. 拿一笔最近的真实变更跑一次垂直切片（Phase 0.5）——先知道自己缺什么，再动手建；
2. 短 `AGENTS.md`（常驻规则 + 布局 + 命令），`CLAUDE.md` 用 symlink 指向它；
3. 决策理由进 `docs/adr/`，`docs/` 只写 now；
4. 一张「目标 → 机制」归属表；
5. 第一批可机械规则（从 Phase 0.5 清单里挑最痛的）接成 `exit non-zero` 脚本，并各做一次负例控制。

**这五件事不需要任何插件架构，且第 1 件事会告诉你其余四件里哪个对你最要命。** 如果还有余力，补一个 verify 脚本（Phase 7 的第 1、5 条），让这些从此有机器兜底。
