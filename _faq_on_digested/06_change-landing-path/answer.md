# Answer 06 · 变更落位全景：中间“原子三件套”每次必交，两头载体按需启用

## 一句话结论

别把 DSH 里的各种文档和模板看成一条“每次改代码都得过九道关”的瀑布流水线。它真正的规矩非常干脆——**中间的“交付核心包”每次必交，前后的规划与决策载体按需启用**：

- **每次改行为必交的“原子三件套”（同一个提交 / PR 同步落地）**：
  1. **实现代码**（`packages/`、`apps/`、`python/` 等）
  2. **当前状态合同**（受影响的 `docs/`、包双语 `README`、类型与 JSDoc、自动刷新的生成目录）
  3. **会在旧行为上报红的行为证据**（单测、真实组装测试，涉及模型/协议/界面可见变化时同步更新录制快照）
- **编码前按需启用的上游件**：
  - **GitHub Issue**：固定“为什么要改、外部看起来该怎样”；机器策略只在**人类作者的非草稿 PR 进入 Review 后**才强制检查是否关联了 Issue。
  - **`proposed/` Agent Note**：只有体量大、需要先评审方案的未来工作才提前写。
  - **Plan Mode（`/plan`）**：会话内的可选规划模式，方案存在聊天历史里供用户点按钮拍板，不往仓库里提交计划文档。
- **交付时按需附带的下游件**：
  - **`implemented/` Agent Note**：**现行规则并不是“非平凡改动必写”**，而是**只有当这次改动包含代码、测试和现有文档都解释不了的持久设计取舍（比如为什么选 A 放弃 B）时才写**；若之前写过 `proposed/`，必须在实现 PR 里挪过来并改写成现在时态。
  - **语义 Code Review 与归档**：Review 负责把关机器查不出的设计合理性；失去未来参考价值的老 Note 后续再冻结进 `archived/`。

## 一、一张表看清：六类载体各管什么，绝不互相抄

DSH 把“一个事实只放一个地方”（one home per fact）贯彻到了变更流程的每一个环节：

| 类别 | 住在哪里 | 负责回答什么问题 | 什么时候强制 / 怎么检查 |
|---|---|---|---|
| **1. 变更意图** | `.github/ISSUE_TEMPLATE/`（Bug / Feature / Task） | 为什么要改？外部可观察行为该变成什么样？ | 人类非 Draft PR 请求或产生 Review 后，`rules.mjs` 强制要求正文关联同仓 Issue |
| **2. 设计取舍** | `.agents/notes/{proposed,implemented,rejected}/` | 为什么选这套设计？淘汰了哪些方案？承担什么代价？ | **仅在存在持久设计取舍时同 PR 新增或更新**（局部/机械/纯 UI 呈现改动豁免）；目录与章节骨架由门禁脚本校验 |
| **3. 本次施工单** | 会话内的 Plan Mode（`exit_plan_mode`） | 这一回具体改哪几个子系统、接口、边界情况和测试？ | **纯可选会话状态**；提示词软约束，须经用户批准才退出计划态 |
| **4. 当前合同** | 类型声明、JSDoc、包 `README`、`docs/`、生成目录 | **截至当前 HEAD，系统对外承诺的行为与接口是什么？** | **每次行为变更必同步更新**；由 `typecheck`、`doc-sync`、双语配对与目录新鲜度门禁强制 |
| **5. 行为证据** | 单测、真实组装测试、`snapshots/`、浏览器与真 API e2e | 代码在真实入口下真的按合同工作吗？改坏了能抓到吗？ | **每次行为变更必同步交付**；CI 跑单文件 100% 覆盖率（`test:coverage`）与全平台矩阵 |
| **6. 工程规则与合入** | `AGENTS.md`、`dsh-*` 技能、`scripts/run-gates.ts`、`.github/` | 仓库有哪些底线不能破？谁批准、哪些检查全绿才能合入？ | 9 个必过 CI Job 汇总为 `all-checks-passed`，叠加审批策略与语义 Review 后合入 |

## 二、`docs/` 在这条链上到底算什么？

很多人习惯把 `docs/` 当成“设计方案存档处”或者“发版更新日志”，但在 DSH 里，[`docs/AGENTS.md`](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/AGENTS.md) 立了铁律：**`docs/` 只写系统现在的样子（Document current state）。**

它的时态分工非常清楚：

- **以前是怎么想的、为什么没选别的路** → 去翻 `.agents/notes/`；
- **这笔改动是怎么一步步改过来的** → 去翻 Git 提交历史和 PR 页面；
- **现在调用方和用户打开仓库看到的契约是什么** → 看 `docs/`、包 `README` 和 JSDoc。

所以 `docs/` 既不是编码前写的瀑布式需求规格书，也不是编码后想起来才补的说明书，而是**跟代码和测试绑在同一个提交里同步刷新的“当前合同投影”**。因果顺序上，是高频的窄切片开发闭环（见 [FAQ 11](../11_native-development-loop/answer.md)）先跑起来，跑完每一圈顺手把当前合同擦干净，外人看起来才像一套严丝合缝的规格体系。

## 三、看清边界：从仓库事实**不能**推出哪五个结论？

把这套机制介绍给团队或往自己的插件仓库借鉴时，千万别过度脑补出下面五条假规矩：

1. **DSH 从未自称采用某套标准“SDD（规格驱动开发）”或 OpenSpec 框架**：仓库里没有任何外部规格工作流依赖，所有约束都是用自家的门禁脚本、TypeScript 类型和 Markdown 目录搭出来的。
2. **不是每笔改动都得先写提案（Proposal-first）**：已经想清楚的架构决定可以直接随实现提交写进 `implemented/`；日常局部修补和界面微调更是连 Agent Note 都不需要写。
3. **不强制教条的“先写红测试再写代码（TDD）”**：仓库要求同一个 PR 里必须带能在旧代码上报红的测试，但并不限制你在本地编码时的先后手顺序。
4. **Agent Note 不是 API 说明书**：它只管“决策理由与取舍”；查精确字段、配置项和事件签名，永远以源码类型、包 `README` 和自动生成目录为准。
5. **不是所有规矩都有自动门禁兜底**：机器能查格式、死链、类型和覆盖率，但“这笔改动该不该写 Note”“测试是不是只测了表面没测真入口”仍然靠语义 Review 把关。另外，这套载体是 **DSH 主仓自身**的治理结构，独立插件仓完全可以根据规模裁剪，也可以在外层自由搭配自己的 `ROADMAP.md` 或任务看板（迁移方法见 [FAQ 07](../07_borrowing-dsh-harness-idea/answer.md)）。
