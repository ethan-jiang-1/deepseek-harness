# FAQ 28 · 总听人说给 DSH“打个探针”，它到底是内置机制还是开发工作法？

## 问题背景

做 DSH 插件开发或排查多插件装配问题时，常听老手说“别对着源码猜了，先打个探针（probe）看一眼”，不少外部插件仓库里也建了专门的 `probes/` 目录。

可真去 DSH 主仓源码里搜 `probe`，跳出来的却是 `ctx.pluginRegistryProbe`（安装源延迟探测）、Linux 目录选择器的 `PATH` 探测、沙箱或进程存活检查——既没有叫 `probe` 的插件接口，也没有 `pnpm run probe` 命令。而且仓库里明明已经有单元测试、录制会话快照（`test:snapshot`）和真模型 `test:e2e`，为什么大家还会高频用到“探针”？

## 具体要回答的四个问题

1. **名实辨析**：“探针”是不是 DSH 官方术语或内置子系统？它和源码里那些名叫 `probe` 的自检逻辑是什么关系？
2. **实操长相**：一套真能定位问题的探针到底怎么打？具体去读哪份文件、哪条事件、哪棵界面树？
3. **成立前提与分工**：DSH 的哪三条底层设计让这套黑盒取证工作法格外顺手？它和单测、录制快照、真 API 测试怎么配合？
4. **演进与边界**：探针查清事实后，什么时候该“毕业”进 CI 门禁、什么时候用完即弃？有哪些靠探针也证明不了的事？
