# 28/04 · 背后的原理：三条不变量撑起一件「看起来不严谨」的事

> **查询手册，不是读物。理解它不需要任何前置。** 但在爬完 [00](./00-ladder.md) 之前不建议读；它回答的是「为什么这件看起来不严谨的事成立」。
>
> 本篇的三条不变量都是 DSH 的真实规则，分别写在根 [`AGENTS.md`](../../AGENTS.md)、[`docs/subsystems/session.md`](../../docs/subsystems/session.md) 与 [`docs/testing.md`](../../docs/testing.md)。把它们串起来论证探针为什么成立，是本篇的推理。

## 原理一：model-visible ⟺ logged —— 请求侧是可重建的事实

DSH 的根规则里有一条不变量：

> **Model-visible ⟺ logged**：任何到达模型请求的东西，都必须能从会话日志重建。

这条规则本来是给持久化用的（会话 resumer、fork、SDK 投影都靠它），但它顺带解决了一个别处很难解决的问题：**「模型到底收到了什么」不再需要猜**。

落到具体事件上（[`docs/subsystems/session.md`](../../docs/subsystems/session.md) 的 The request header event 一节）：

| 你想知道的事 | 它住在哪个事件 |
|---|---|
| 本次请求的 envelope（call config、adapter 默认值、**组装后的工具 schema**） | `request/header`（每次 envelope 变化追加一份快照；`foldRequestHeader` 取最新） |
| 渲染后的 system prompt | `system/message`（surface 节点 0，以及历史中后续的 system 节点） |
| 模型这一轮说了什么、调了什么 | assistant 结算事件与 tool 事件 |

注意第一行与第二行的分家：**system prompt 不进 header**，它是 surface 节点上的派生历史。这个设计的后果对探针极重要——想看「提示词改了没有」要读 `system/message`，想看「工具集合变了没有」要读 `request/header`，**两个地方，两种事件，混着读必然读出假结论**。

这也是为什么一篇探针的操作手册第一步永远是「**先把事件类型枚举一遍，再读任何字段**」：猜事件的嵌套形状，猜错的代价是白跑一轮。

## 原理二：日志可解析 ⇒ 黑盒可观测（不需要被测对象配合）

探针不要求被测对象「上报事实」。它只要求**日志文件在磁盘上、格式可解析**。

这就是 DSH 与硬件探针在结构上的同构：硬件探针不要求芯片做任何事，只要求引脚暴露信号。DSH 的等价物是 `$DSH_HOME/sessions/<project>/session-<uuid>/session.v*.jsonl.zstd`——一个普通的、带版本的、可以离线解压的文本文件。任何外部脚本都能：

1. 解压日志（`zstd -dc`）；
2. 按事件类型计数、抽取、量字节；
3. 得出「这次请求里 X 段有多大、Y 工具在不在」这类**可复核的事实**。

关键推论：**探针不需要产品为它开接口**。这也是为什么 DSH 产品树里没有探针机制，而插件仓却能把探针做得有模有样——所有需要的孔洞已经由「日志是合同」这件事打开了。

反过来，一旦日志不可解析（比如渲染后的提示词被 token 化、或被省略成引用），探针就退化成「看模型自己说了什么」。这正是主仓明确否决过的路线：给 session log 瘦身会破坏可重建性。

## 原理三：确定性来自「固定输入」，不来自「固定输出」

第三条不是一句口号，而是一条**结构**：把不确定性搬到最外层，然后钉死。

```
真实世界的不确定性：模型回复、网络、时间
        ↓ 录一次（record）
固定输入：session.vN.jsonl（模型流是固定的）
        ↓ 回放（replay）
真组合里唯一不确定的东西消失了 ⇒ 探针可以反复跑
```

`@deepseek-ai/dsh-llm-replay` 就是这条链的落点：它是一个**发布在 npm 上的普通插件**，挂在真 adapter 的位置上，用录好的脚本喂给真 agent。于是探针获得了：

- **真的装配**（提示词、工具、会话都是真的走的）；
- **假的模型**（回复固定，不需要 key，不烧配额）；
- **可复跑**（同一份夹具跑两次，除时间戳外应当一致）。

于是探针与快照共享同一份产物：**夹具既是探针的输入，也是回归的基线**。区别只在用法——探针用它读出「现在是什么」，快照用它比对「和上次差什么」。这一点是 FAQ 21 的核心结论，本篇只引用不重述。

这也解释了为什么探针能把「失败」做成可控变量：`replay.override.json` 这个 sidecar 专门表达**日志重建不出来的四类失败**（pre-2xx 抛、post-2xx 抛、挂起、注入重试）。没有它，探针永远只能探成功路径——而 agent 系统的大部分 bug 恰恰在失败路径上。

## 把三条串起来：探针从「经验」变成「方法」的那一步

| 没有这条不变量 | 探针会退化成 |
|---|---|
| model-visible ⟺ logged | 「模型说它看到了」——自报，不可复核 |
| 日志可解析、有版本 | 只能看截图或看模型措辞，无法量事实 |
| 确定性可外移到夹具 | 每次跑都不一样，「这次红 / 下次绿」无法判断是 bug 还是噪声 |

三条同时成立，探针才成为一个**方法**而不是一个**习惯**：任何一个人，拿着同一份夹具和同一份判据，应当读出同一个结论。**这是探针唯一必须守住的严格性。**

## 一条容易被忽略的推论：探针与测试共用同一个「世界」

探针不是「不严谨的测试」，而是**在同一个真实世界上取消了断言的测试**。因为世界相同，探针发现的事实可以**直接转成测试**：

1. 探针跑一次 → 读出事实；
2. 人把事实写成判据（「这段应当在、约占 N 字节、在第 K 段之前」）；
3. 判据 + 固定夹具 = 一条断言；
4. 再给它配基线 → 它变成快照 / 期望。

所以插件仓的组织纪律里有一条看似反直觉的规定：**能进基线的探针不要另立脚本**。它不是洁癖——它是在说「这条事实已经毕业了，别再让它在探针里游荡」。
