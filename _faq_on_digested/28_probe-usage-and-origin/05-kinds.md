# 28/05 · 探针有哪几类

> **查询手册，不是读物。** 从 [00 第 4 级](./00-ladder.md) 爬到「造条件」那一级时再翻。
>
> 分类是本篇的说法，不是 DSH 的术语。依据是插件仓里 `probes/` 目录的实际长相（见 08 的校准表），四个仓各自演化出了同一套分层。

## 按「它连的是什么」分四类

> 这一套切的是**它连什么**，与 [07 的四个实例](./07-worked-examples.md)（按戳到哪一层证据）和 [09 的四个接口](./09-exploratory-testing.md#三四个观测接口各自能探到什么)（按能看到什么）是**三个不同维度**，不要混为一谈：一个装配探针可以同时戳日志和请求侧。

| 类 | 连什么 | 产出 | 典型问题 |
|---|---|---|---|
| **装配探针**（session 类） | 真 `dsh` 进程 + 可选回放模型，不连浏览器 | 会话日志、请求侧的 system/tools | 提示词段落进没进请求？工具挂上没有？preset 真挂上了吗？ |
| **渲染探针**（web / cdp 类） | 真浏览器（CDP）+ 真 Web 实例 | 截图、DOM、console 错误、判决 JSON | 页面真是这个样子吗？页签都开得出来吗？首屏有没有横幅？ |
| **行为探针**（真模型） | 真浏览器或真 RPC + 真模型 | 会话日志里的行为判据 + `sessionId` | 这条规矩模型照做了吗？它会不会自己去问人？ |
| **机制探针**（域内） | 真服务 + 真文件系统 + 真并发 | 逐相位 verdict | 两个会话同时抢同一个占位会发生什么？委派深度会不会崩？ |

四类的成本阶梯很明显：装配类最便宜（秒级、无浏览器）、渲染类次之（要 Chrome）、行为类最贵（真模型、按次烧配额）、机制类最难搭（要造出竞争条件）。

**由此得出一条重要的排序：能用便宜的证，就不要用贵的证。** 插件仓的操作手册把这件事写成了「按意图选入口」的路由表：先看配置组合（`--dump-config`，零成本），再验装配（one-shot，秒级），然后才轮到浏览器与真模型。AL 探针本身也不例外——**探针也有它自己的探针**。

## 按「它跟基线的距离」分三档

这一档划分比上一档更能决定一个探针该不该存在：

| 档 | 形态 | 寿命 | 归宿 |
|---|---|---|---|
| **一次性** | 为某次 bug 猎捕或某条已归档验收行写的脚本 | 短 | 保留供复跑，不进任何门禁，不进命令清单 |
| **常驻入口** | 有别名、有人反复跑（`pnpm preflight`、`pnpm shots`） | 中 | 进命令清单，一条命令一个意图 |
| **已毕业** | 有了基线、进了门禁 | 长 | 搬进快照 / 期望目录，**不再是探针** |

插件仓把这档划分写进了目录契约：一次性探针「各自服务一个已归档验收行，保留供复跑，不进任何门禁，也不出现在命令清单里」，用到时先读文件头的「为什么存在」。这条规定挡住了探针目录最常见的死法——**脚本越堆越多，没人知道哪个还活着**。

## 按「谁来读它」分两类（最容易被忽略）

| 读的人 | 探针应当长什么样 |
|---|---|
| **人**（现场判断） | 打屏幕文本、截图、逐相位 verdict；顺序与相位清楚，能对着 bug 报告看 |
| **agent**（自动化交接） | 判据写在文件头，退出码语义严格，证据落固定目录；没有「看一眼就知道」这种隐含前提 |

第二类正在变成主流：很多探针的真实消费者不是人，而是**正在干活的 agent**。外仓的 evidence 政策直接为这类消费者定了形式——缺 Chrome、缺 `zstd`、缺 profile 一律 `BLOCKED`（exit 2），**不冒充 PASS**。理由很直接：agent 读不到「这次运气不好」，它只读得到「绿」。

于是有了那条最容易被违反的纪律：

> **探针的退出码是给机器的合同，不是给人的提示。** `0 / 1 / 2` 三档（通过 / 发现 / 环境未就绪）几乎是所有插件仓的共同形状，因为它正好对应 agent 需要的三种动作：继续、停下报告、换个环境再试。
