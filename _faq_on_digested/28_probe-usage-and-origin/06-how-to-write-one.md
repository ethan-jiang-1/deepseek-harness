# 28/06 · 怎么写一条不自欺的探针：八条判据

> **查询手册，不是读物。** 写完第一条探针、准备把它交给别人之前再逐条对。想先看别人真怎么写，从 [00 第 4 级](./00-ladder.md) 爬起。
>
> 本篇是本篇的说法，不是仓库规范。每一条都能在插件仓的真实文件头里找到对应做法（见 08 校准表）。

## 判据一：先写「为什么需要它」，再写代码

常驻探针的文件头必须回答三句：**它证明什么、不证明什么、什么时候该跑**。

- 差：`// probe for delegation`。
- 好：`// 何时跑：日期口径文案或 CEO skill 记账步改动时；真模型 ≈$0.05、排练场`，后面紧跟「为什么需要它：日期口径是文案层规矩，preset-smoke 只能证明 skill 挂上了、证明不了模型照做」。

第二句才是探针存在的理由。**没有「为什么需要它」的探针，下次没人敢删，也没人敢跑。**

## 判据二：判据要写成一句话，并且允许被推翻

判据不是「跑通就算过」，而是「什么现象算这个问题的证据」。外仓有一条探针的文件头写着「判据（2026-09-30 随日期通道翻新；旧判据『占位 = PASS』会把正确行为判红——仪表反挂）」。

这一行信息量很大：**判据本身会错，且判错的后果是「正确被判红」**。所以判据要带日期、带校准记录、带「为什么这次要这样判」。探针的仪表可靠性是它自己的一个 bug 面。

## 判据三：区分「环境未就绪」与「被测对象失败」

三档退出码不是风格问题，是**归因**问题：

| 退出码 | 含义 | agent 应该做什么 |
|---|---|---|
| `0` | 判据成立 | 继续 |
| `1` | 判据不成立（**这是发现**） | 停下，报告，按判据处置 |
| `2` | 环境未就绪（缺 Chrome / 缺 key / 缺 home / 缺 `zstd`） | 换环境重试，**不要**当作失败 |

把 2 混进 1，会让「这台机器没装 Chrome」看起来像「产品坏了」；把 2 混进 0，会让探针在什么都没测的情况下报绿——后者是最坏的一种，因为**它污染的是判断力**。

## 判据四：证据落到固定目录，一份失败不留两份成功

两条硬习惯：

- **证据目录固定**（如 `.tmp/shots/`、`runtime/harness-home/diagnosis/<probe>-<timestamp>/`），文件里有 `verdict.json`、`page.png`、`console.log`。位置固定，agent 才找得到。
- **一个输出路径只留一张图**：成功的图或失败的图，绝不两张并存。否则一个陈旧的 `*.failed.png` 会永远躺在绿跑旁边，下一次读证据的人会以为自己看到的是这次的红。

第二条来自真实事故，不是洁癖。

## 判据五：探针取证时必须消除「工具使用」这条旁路

这是 session 类探针最要紧的一条。如果模型的回答是它调了 `curate` 工具后汇报出来的数字，那你证明的是**工具**，不是**提示词**。

所以取证式探针的任务描述必须写成：「**不要调用任何工具；只用已经摆在眼前的东西回答；如果没有，就说没有。**」这时请求本身成了被测对象——模型诚实的「我没有」是一次发现，不是失败。

推论：**一次 one-shot 会话只有一个请求**。任何「下一轮就热了」的行为在这里无法验证，而这恰恰是 one-shot 探针最擅长抓的一类 bug：如果某段内容必须常驻，那就必须在**第一个请求**上证明它常驻。

## 判据六：会话按差分取，不按「最新」取

并行会话下 `ls -t` 会指到别人的对话，这是被记录过的真实事故。正确做法是：跑之前把会话目录列表快照下来，跑完再 diff，新出现的那个才是你的。

同理，定位「刚才那次探针」不要靠时间猜，要靠**判据里带上 `sessionId`**——外仓的探针判决 JSON 里直接带 `sessionId`，由上下文决定读哪一条日志。

## 判据七：探针要能证明自己会红

一条从没红过的探针，和一个什么都不做的脚本，在被观察时无法区分。所以：

- 改动判据或被测对象之后，**故意破坏一次**，看它是否按预期变红，再恢复；
- 或者用「红线先行」的次序：先让探针在改动前跑红，改动后跑绿，两段日志都留档。

这和外仓 dev-loop 的第四条判据同源：**机制面 = 实现前那个测试已写且红；行为 / UX 面 = 场景先立**。探针属于后者：先把场景立起来，再看它红不红。

## 判据八：探针和它的补丁必须镜像它替代的那一行

涉及 `--patch` 的探针（把某个 profile 行换掉）有一条极易翻车的纪律：**探针补丁要从真实补丁复制过来，只改一件事**。

反例极具教育意义：手写一个只插入 `preset-runner` 行、却没禁用 shipped `headless-runner` 行的补丁，进程会在**打印完正确答案之后**才崩在 `the launcher must provide ctx.appExit before the tree mounts`——正确答案已经出现，人很容易以为那是成功。

同族的失败形态还有两种，都属于「探针看着绿其实什么都没测」：

- 行 id 写错 → 不报错，只在 `--dump-config` 里留一行 `patch: entry "…" not found`，真实 adapter 照常接住全部请求（模型是真答的，探针以为自己在测回放）；
- 把裸脚本塞进 `file` 字段 → 报一行解析错误并使整行不 activate，真实模型照答。

三种失效的共性：**探针的失败是静默的**。所以判据一是硬要求——只有当文件头写清了「它证明什么」，读的人才能发现「它这次其实什么都没证明」。

## 一条总结句

> 探针的价值 = 它产出的事实可信度 × 判据的清晰度 × 它自己会不会撒谎。
> 三项里任意一项为 0，这条探针的产出就是 0——**而且看上去和满分没有区别**。
