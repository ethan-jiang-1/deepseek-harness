# FAQ 27 · Agent 跑到一半，workflow 还是 Agent Team？

## 问题

一个 agent 正在跑，手上有一批活：四十个文件要审、一个迁移要铺开、一个目标要做三天、两个人要在同一个 checkout 里持续改。它可以自己做，可以派一个 subagent，可以写一段 workflow 脚本扇出，可以开一个跨轮 goal，也可以把工作交给一个持续在线的 Agent Team。

这些选项在工具面板上是并列的，但它们换掉的东西可能不同：谁持循环、谁记得、崩溃之后还剩什么、装了什么就再也看不见什么。本 FAQ 不回答「DSH 有哪些编排能力」——那由工具描述、包 README 与源码回答——而是三个更窄的问题：**站在这些岔口上，判断依据是什么？每种选择的代价差在哪？选错了怎么看出来、怎么换？**

## 为什么这个问题不好答

- **同名不同物。** `agent-team`、`workflow` 的名字很容易让人按外部框架（多代理 DAG、工作流引擎）类比；它们各自实际是什么，需要回到工具描述与实现。
- **能力重叠。** `subagent`、`workflow`、`ralph` 都能「把活分出去」；`jobs` 和后台 workflow 都能异步；`goal` 和 `schedule` 都能跨轮。仅凭能力清单很难区分，需要用代价和保证来问。
- **没有一处能查全。** 官方边界句分散在多个工具描述里，且互相引用；读完单个工具，只能知道它自己的适用范围。

## 要回答的问题

要回答：

1. 模型在 workflow / subagent / goal / jobs / agent-team 之间选择时，实际面对哪些岔口？触发信号是什么？
2. 用什么判据解释这些原语为什么不能互换？代价差在哪？
3. 面对一个具体任务，怎样先判断用户是否点名、是否模型工作，再选择原语？
4. 选错的典型症状是什么？如何迁移、迁移时丢什么？
5. DSH 为什么把编排做成“原语 + 运行时判断”，而不是中心 DAG 调度器？

产品源码基线：`dsh-v0.2.1-rc.5`（上游 `b830ec95`；写作 checkout `66800f88`，产品树与 rc.5 一致）。行号以当前树为准。[`reference.md`](./reference.md) 登记每条结论的出处与核验状态。
