# 07 · 为什么不是 DAG 引擎：这套形状的取舍，以及它新在哪

## 与中心 DAG 的差异

| | 中心 DAG 调度器 | DSH |
|---|---|---|
| 输入 | 一张图 | 一段脚本、一句目标、或一块任务板 |
| 算法 | 拓扑排序、入度队列、按序派工 | 环检测、就绪推导、状态转换准入 |
| 派发 | 引擎取节点 | 模型或 Lead 决定 |
| 改图 | 图变即重算 | 图是活的，每次写入重全图校验 |

外部叙事常把 DSH 描述成「Captain 规划 + Kahn 入度调度 + Reviewer 门禁」。逐条核对见 [digest 09](../../_digested/orchestration-ladder/09-对照外部叙事-Captain与Kahn调度与rollback与KV看板的逐条源码真相.md)：真实存在的是任务板依赖图、脚本控制流和归属树，缺的是中心 executor。本篇不重复那份核对，只说这个形状为什么合理。

## 为什么

**DSH 的设计假设是：重规划是常态。** 真实任务的依赖常常是做着做着才发现的：审到一半才知道哪两个文件耦合，迁移到一半才发现有个调用点绕过了抽象层。静态 DAG 表达不了这件事，于是要么假装图已知（然后频繁重规划），要么长出逃逸舱——而逃逸舱就是模型。

DSH 的选择是不引入中心调度器：派发由模型、它写的脚本或 Lead 决定，只把**能机械保证**的部分留给引擎：图是否合法（写时校验）、任务是否就绪（读时推导）、状态转换是否允许（claim/reassign 准入）。派发和改图需要判断「接下来什么更值得做、失败了要不要重试、要不要改图」，那是概率判断，不是机械保证（[digest 11](../../_digested/orchestration-ladder/11-图计算的本质-不变量推导与执行的三件分置.md)）。

## 深度换广度

这套系统的默认值是浅的：

- subagent 工具的委派深度默认 1 层（[subagent config](../../packages/subagent/subagent/src/index.ts):196）。这是**工具策略**，不是全局不变量：workflow 引擎启动 child 时不传这个上限。
- workflow 脚本里没有嵌套的 `workflow()` 钩子（[workflow README](../../packages/workflow/workflow/README.md):128）；但 child 本身是完整 agent，如果它的 preset 里有 workflow 工具，理论上可以自己再调一层。
- Team 只有 Lead 能拉人，队友不能再拉队友。
- 换来的是：workflow 一次默认最多 1000 个 child、单次调用 4096 项。

| 路径 | 深度检查 | 说明 |
|---|---|---|
| `subagent` 工具 | 有，默认 1 层 | 工具把 `maxDepth` 传给服务 |
| `workflow` 的 `agent()` | 无 | 引擎启动 child 时不传 `maxDepth` |
| `team` 的 `spawn_teammate` | 无（Lead-only 授权） | 队友不能再拉队友；但成员仍可用 workflow |
| `ralph` | 无（走 workflow） | 固定脚本每轮起 fresh child |

所以「深度 1 层」是 `subagent` 工具的默认，不是系统的硬边界。宁可宽，不愿深——但这是默认值与配额的取向，不是结构上的禁止。深层次委托会让归属、预算、取消和验收全部变复杂；宽扇出只是数量问题，每个 child 的边界都是清晰的。

## 三条可迁移原则

1. **把循环放在能看见结果的那一层。** 谁需要根据中间结果改主意，循环就该在谁手里。脚本适合「下一步已知」，对话适合「下一步要看结果」，driver 适合「下一步每轮重估」。
2. **用最浅的承诺完成。** 能一次调用解决的，不要开跨轮目标；能一轮跑完的，不要建团队。承诺越深，可逆性越差，而收益往往只是形式上的整齐。
3. **验收方式跟原语一起选。** 完成通知、任务状态、worker 自报都不是正确性证明；选原语的同时把「怎么算完成」定下来，否则你会在 [06](./06-diagnosis-and-migration.md) 的症状表里认出自己。

## 一条反原则

**不要造中心调度器，除非你能证明重规划不会发生。** 证明不了，就把派发留在能看见上下文的那一层——这既是 DSH 的现状，也是它有意不补的那个缺口。

## 这套思路新在哪

传统编排的产物是**图**：节点、边、调度器、重试策略，都在运行前写好。DSH 的产物是**选择面**：一组原语、每个原语自带的边界句、以及一层能把它们换掉的组合机制。

三个差别：

- **路由下放。** 没有「任务类型 → 原语」的全局映射，判断由持有上下文的那一层做。
- **策略随工具。** 使用边界写在工具插件里，disable 工具即同时移除策略，不会留下指向不存在工具的规则。
- **引擎只守不变量。** 合法性、就绪、准入是确定性的事；派发和重规划留给模型。

代价也是真的：没有统一的进度视图，没有任务级回滚，没有自动升级。这三样都是这套取舍的账单，不是疏漏。

## 可证伪

如果 DSH 出现以下任一改动，本文「深度换广度」与「这套思路新在哪」两节的结论要重写：

- 出现按任务图自动派工的中心 executor；
- 原语之间出现自动升级（例如 goal 自动转 Team）；
- workflow 获得持久化与恢复（journal / resume）。

在那之前，「原语 + 运行时判断」仍然是对当前形状最准确的描述。
